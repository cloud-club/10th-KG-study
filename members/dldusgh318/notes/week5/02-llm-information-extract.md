# **W5-2. LLM 정보 추출 : 문서에서 사실을 어떻게 뽑을까?**

앞에서 내가 어떤 정보를 그래프에 저장할지 정하기 위해 닫힌 스키마를 만들었다.

클래스는 `Project`, `Technology`, `TechnologyUse`로 제한하고, 관계 역시 `PART_OF`, `USES_TECHNOLOGY`, `HAS_PURPOSE`, `HAS_STATUS`, `REPLACES`처럼 미리 정해두었다.

이제 실제로 해야 할 일은 **내가 W2에서 저장했던 문서 청크를 읽고 이 스키마에 맞는 사실을 자동으로 찾아내는 것**이다.

전체 흐름은 생각보다 단순하다.

**문서 Chunk → LLM → 스키마에 맞는 사실 추출 → 원문 근거 검증 → Entity/Edge 저장**

문제는 LLM에게 그냥 `"여기서 트리플을 추출해줘"`라고 시키면 원하는 그래프가 나오지 않는다는 것이다.

## **1. 그냥 “트리플 뽑아줘”라고 하면 뭐가 문제일까?**

예를 들어 문서에 이런 내용이 있다고 하자.

SeCause에서는 분석 요청을 비동기로 처리하기 위해 Redis 도입을 검토했다.

여기서 원하는 정보는 대략 이렇다.

| **Project** | **Technology** | **Purpose** | **Status** |
| --- | --- | --- | --- |
| SeCause | Redis | 분석 요청 비동기 처리 | proposed |

그런데 출력 형식을 자유롭게 두면 LLM은 실행할 때마다 관계 이름이나 구조를 다르게 만들 수 있다.

`USES`, `USES_TECHNOLOGY`, `CONSIDERED_TECHNOLOGY`, `RELATED_TO`처럼 비슷하지만 서로 다른 술어가 생길 수도 있고, `"검토했다"`를 실제 구현한 것으로 해석해서 `implemented`라고 만들어버릴 수도 있다.

그래서 W5에서 필요한 건 일반적인 요약이 아니라 **Closed-schema Relation Extraction**, 즉 **미리 허용한 개체와 관계 안에서만 정보를 추출하는 것**이다.

앞에서 닫힌 스키마를 먼저 만든 이유가 여기서 나온다.

## **2. 프롬프트로 부탁하는 것과 스키마로 강제하는 것은 다르다**

처음 생각할 수 있는 방법은 프롬프트에 이렇게 적는 것이다.

관계는 PART_OF, USES_TECHNOLOGY, HAS_PURPOSE, HAS_STATUS, REPLACES 중 하나만 사용하세요.

물론 이것도 도움이 된다. 하지만 LLM이 항상 지킨다는 보장은 없다.

그래서 가능하면 출력 자체를 **JSON Schema 같은 구조화된 형식으로 제한**하는 편이 낫다.

예를 들어 관계 타입을 다음처럼 `enum`으로 정의할 수 있다.

```json
"predicate": {
  "type": "string",
  "enum": [
    "PART_OF",
    "USES_TECHNOLOGY",
    "HAS_PURPOSE",
    "HAS_STATUS",
    "REPLACES"
  ]
}
```

이렇게 하면 모델에게 단순히 `"이 다섯 개 중 하나를 골라줘"`라고 부탁하는 것에서 한 단계 더 나아가, **출력 형식 자체에서 허용 가능한 값을 다섯 개로 제한**할 수 있다.

현재 Structured Outputs 계열 기능은 JSON Schema의 `enum` 등을 이용해 출력 구조와 허용 값을 제한할 수 있다. 다만 이것이 **내용까지 사실이라는 것을 보장하는 건 아니다.** 형식은 맞아도 LLM이 원문에 없는 사실을 그럴듯하게 채울 수 있다.

즉 두 문제를 분리해서 봐야 한다.

| **문제** | **해결 방법** |
| --- | --- |
| 출력 구조가 제멋대로임 | Structured Output / JSON Schema |
| 내용이 원문과 일치하지 않음 | Evidence + 후처리 검증 |

## **3. “추출할 사실이 없다”도 정상적인 답이다**

여기서 내 데이터 특성상 특히 중요한 문제가 하나 있다.

W2에서 저장한 모든 청크가 기술 사용 정보를 포함하고 있는 것은 아니다. 회의 내용이나 요구사항 설명처럼 현재 스키마로 뽑을 게 아예 없는 청크도 많다.

이때 LLM에게 추출을 강하게 요구하면 문제가 생긴다.

**“뭔가 하나는 답해야 하나 보다”라고 판단해서 없는 관계를 만들어낼 수 있기 때문이다.**

Structured Outputs 공식 가이드에서도 입력이 스키마와 맞지 않을 때 모델이 스키마를 채우려고 하면서 잘못된 값을 생성할 수 있으므로, 이런 경우 빈 값 등을 반환하도록 명시할 것을 권장한다.

그래서 출력은 처음부터 다음 상태를 허용해야 한다.

```json
{
  "triples": []
}
```

그리고 few-shot 예시에도 **추출 성공 예시뿐 아니라 추출할 것이 없는 예시를 같이 넣는다.**

예를 들어

입력: “이번 회의에서는 다음 스프린트 일정을 논의했다.”

출력: `{"triples":[]}`

이렇게 하면 **“없으면 만들지 않는다”도 올바른 행동이라는 걸 명시적으로 보여줄 수 있다.**

이걸 이번 실습에서는 일종의 **빈 배열 게이트**로 사용한다.

## **4. 트리플만 뽑으면 끝일까? → Evidence가 필요하다!**

이번 실습에서는 사실 하나를 추출할 때 **그 판단의 근거가 된 원문도 함께 저장**한다.

예를 들어:

```json
{
  "project": "SeCause",
  "technology": "Redis",
  "purpose": "분석 요청 비동기 처리",
  "status": "proposed",
  "evidence": "분석 요청을 비동기로 처리하기 위해 Redis 도입을 검토했다."
}
```

여기서 `evidence`는 LLM이 새로 요약한 문장이 아니라 **입력 청크에 실제로 존재하는 원문 구간**이어야 한다.

이게 중요한 이유는 W3 실험에서 이미 한 번 확인했다.

A01에서는 답변 내용 자체는 맞았지만 **인용한 문장이 실제 원문과 일치하지 않는 citation 실패**가 있었다. 그래프에서도 똑같은 문제가 생길 수 있다.

`SeCause → Redis`라는 관계를 잘 찾았더라도 **왜 그렇게 판단했는지 원문으로 돌아갈 수 없다면 검증 가능한 지식 그래프라고 보기 어렵다.**

그래서 이번에는 관계와 근거를 같이 움직인다.

**Triple + Evidence + Source Chunk**

이 세 가지가 한 세트다.

## **5. Evidence는 반드시 원문 그대로 가져온다**

Evidence를 저장한다고 해서 LLM에게 `"근거를 설명해주세요"`라고 하면 안 된다.

예를 들어 원문이 “분석 요청을 비동기로 처리하기 위해 Redis 도입을 검토했다.” 인데

LLM이 evidence를 “Redis를 비동기 분석 처리 목적으로 검토함.” 이라고 반환했다고 하자.

의미는 맞지만 이건 **원문 근거가 아니라 LLM이 만든 요약**이다.

그러면 나중에 정말 원문에 존재하는 문장인지 자동으로 검증하기 어렵다.

그래서 규칙을 단순하게 잡는다.

**Evidence는 입력 청크에서 그대로 복사한다. 요약하거나 바꾸지 않는다.**

그러면 추출 후 아주 단순한 검증이 가능해진다.

```python
if evidence not in chunk_text:
    reject("evidence_not_found")
```

LLM이 아무리 그럴듯한 관계를 만들어도 근거 문장이 실제 입력에 없으면 저장하지 않는다.

물론 문자열 완전 일치는 공백·정규화 문제 때문에 이후 조금 다듬을 수 있다. 하지만 v0에서는 이 정도의 단순한 검증부터 시작하는 게 오히려 결과를 해석하기 쉽다.

## **6. LLM 출력은 바로 DB에 넣지 않는다**

여기까지 오면서 중요한 원칙이 하나 생겼다.

**LLM의 출력은 정답이 아니라 후보(candidate)다.**

따라서 흐름은 **Chunk → LLM 추출 → Validation → 통과한 사실만 저장** 으로 간다.

최소한 다음 정도는 확인할 수 있다.

| **검증** | **확인할 내용** |
| --- | --- |
| Schema | 허용한 타입과 필드인가 |
| Predicate | 정의한 관계만 사용했는가 |
| Evidence | 실제 청크에 존재하는가 |
| Status | `implemented/proposed/not_implemented` 중 하나인가 |
| Required field | 필요한 값이 비어 있지 않은가 |
| Entity ID | 정규화 규칙에 맞는가 |

특히 마지막 `Entity ID`는 LLM에게 그대로 맡기지 않는 게 좋다.

예를 들어 모델이 어떤 청크에서는 `Redis`, 다른 청크에서는 `redis`, 또 다른 청크에서는 `tech_redis`라는 ID를 만들면 같은 기술이 세 노드로 갈라진다.

따라서 LLM에게는 **사람이 읽을 수 있는 개체명**을 추출하게 하고, 내부 ID는 애플리케이션에서 규칙에 따라 다시 만드는 편이 안전하다.

`Redis` → normalize → `tech-redis`

즉 **정규화도 그래프 저장 직전에 반드시 거쳐야 하는 추출 파이프라인의 일부**다.

## **7. 통과한 것만큼 탈락한 것도 저장한다**

처음에는 검증에서 떨어진 결과를 그냥 버리면 될 것 같았다.

그런데 이번 실습에서는 오히려 **왜 떨어졌는지가 중요한 실험 결과**가 된다.

예를 들어 전체 추출 결과가 이렇게 나왔다고 하자.

| **결과** | **개수** | **비율** |
| --- | --- | --- |
| 검증 통과 | 323 | 78.4% |
| evidence 원문 불일치 | 53 | 12.9% |
| 허용하지 않은 관계 | 18 | 4.4% |
| 기타 검증 실패 | 18 | 4.4% |

그러면 단순히 `"LLM으로 트리플 412개를 만들었다"`보다 훨씬 많은 걸 알 수 있다.

**어떤 종류의 오류가 얼마나 발생했는지 측정할 수 있기 때문이다.**

다만 `evidence_not_found = 환각`이라고 바로 단정하지는 않는 게 좋다. 모델이 원문을 요약해서 반환했거나 문자열 정규화 때문에 일치하지 않았을 수도 있다.

따라서 정확하게는 **“원문 evidence 검증을 통과하지 못한 추출 비율”**이라고 기록하고, 그중 실제 hallucination이 얼마나 되는지는 샘플을 눈으로 확인한다.

## **8. Few-shot은 성공 예시보다 경계 사례가 중요하다**

- **Few-shot이란?**
    
    Few-shot prompting이란 LLM에게 작업 지시만 주는 것이 아니라, 몇 개의 `입력 → 원하는 출력` 예시를 프롬프트에 함께 제공하는 방식이다. 이번 실습에서는 이를 이용해 `implemented`와 `proposed`를 어떻게 구분하는지, 그리고 추출할 사실이 없는 경우에는 빈 배열을 반환해야 한다는 판단 기준을 예시로 보여준다.
    
    ```sql
    [예시 1]
    입력: "Redis를 캐시로 실제 적용했다."
    출력:
    {
      "technology": "Redis",
      "purpose": "캐시",
      "status": "implemented"
    }
    
    [예시 2]
    입력: "Redis 도입을 검토했다."
    출력:
    {
      "technology": "Redis",
      "status": "proposed"
    }
    
    [예시 3]
    입력: "다음 회의 일정을 논의했다."
    출력:
    {
      "triples": []
    }
    ```
    

프롬프트에 예시를 넣을 때도 단순한 정답 예시만 많이 넣을 필요는 없다.

이번 스키마에서는 **헷갈리는 경계를 보여주는 게 더 중요하다.**

예를 들면:

| **문장** | **기대 결과** |
| --- | --- |
| Redis를 실제 캐시로 적용했다 | `implemented` |
| Redis 도입을 검토했다 | `proposed` |
| Redis를 사용하지 않기로 했다 | `not_implemented` 또는 규칙에 맞게 처리 |
| Redis라는 기술도 고려할 수 있다 | 추출 X |
| 다음 회의 일정을 논의했다 | `triples: []` |

특히 마지막처럼 **아무것도 추출하지 않는 예시**를 반드시 넣는다.

Structured Outputs를 사용하더라도 스키마는 형식을 제한할 뿐 의미적 오류까지 없애주지는 않는다. 공식 가이드 역시 모델이 값 자체에서는 여전히 실수할 수 있으며, 예시를 제공하거나 작업을 더 단순한 단계로 나누는 방법을 권장한다.

## **9. 그래서 이번 추출 파이프라인은 이렇게 간다**

지금까지 내용을 합치면 구조가 꽤 명확해졌다.

**Postgres Chunk → LLM → Structured Output → Evidence 검증 → Entity 정규화 → 통과/탈락 분리 → 통과 데이터만 KG 저장**

여기서 LLM에게 맡기는 범위도 생각보다 좁다.

- **LLM이 하는 일:** 문장을 읽고 `무슨 개체와 관계가 명시돼 있는지` 판단
- **코드가 하는 일:** 허용된 형식인지 확인하고, evidence를 검증하고, ID를 정규화하고, 중복을 제거하고, DB에 저장

즉 LLM을 믿고 그래프를 만드는 게 아니라, **LLM은 후보 사실을 제안하고 프로그램이 검증해서 그래프에 넣는 구조**다.

## **10. 바로 전체 문서를 돌리지는 않는다**

이제 코드까지 만들었다고 바로 W2의 전체 청크를 넣으면 안 된다.

먼저 **20~50개 정도의 청크만 뽑아서 직접 눈으로 확인**한다.

여기서 보고 싶은 건 단순하다.

- 뽑아야 할 관계를 놓치지는 않는가?
- 없는 관계를 만들어내지는 않는가?
- `implemented`와 `proposed`를 구분하는가?
- evidence가 정말 원문 그대로인가?
- 추출할 게 없는 청크에서 `[]`를 반환하는가?
- Redis 같은 동일 개체가 일관되게 잡히는가?

문제가 있다면 이 단계에서 프롬프트와 스키마를 수정하고 다시 돌린다.

전체 데이터를 먼저 처리한 뒤 기준 자체가 잘못됐다는 걸 발견하면 **이미 만든 그래프를 다시 지우고 추출해야 하기 때문**이다.

## **이번 단계에서 확인하려는 것**

결국 이번 실습의 질문은 **“LLM이 트리플을 만들 수 있는가?”**보다 조금 더 구체적이다.

**내가 정의한 닫힌 스키마 안에서, 원문 근거가 있는 사실만 안정적으로 추출할 수 있는가?**

그래서 결과도 단순 트리플 개수만 보지 않는다.

**추출 수 / 빈 배열 비율 / 검증 통과율 / evidence 불일치율 / 술어별 추출 수 / 대표 실패 사례**

정도는 남겨두는 게 좋다. 이 숫자들이 나중에 미니 온톨로지 v0가 실제 내 데이터에 맞았는지 판단하는 근거가 된다.

그리고 여기서 아직 한 가지 문제가 남는다.

지금까지는 **LLM이 사실을 어떻게 뽑을지**만 정했지, 그렇게 뽑은 사실을 다른 시스템에서도 읽을 수 있는 표준 형태로 어떻게 표현할지는 다루지 않았다.

그래서 다음에는 같은 그래프를
