# 02. 임베딩·코사인 유사도·HNSW — 의미 검색을 직접 돌려 본 기록

문자열이나 BM25 검색은 결국 같은 토큰이 있어야 출발한다. 임베딩 검색은 질문과 대화를 같은 벡터 공간에 놓고 가까운 것을 찾는다. 그래서 `마감 일정`이라는 단어가 없는 `제출일` 대화도 후보로 가져올 수 있었다. 대신 “가깝다”의 기준을 모델이 학습 데이터에서 배웠다는 점, 근사 인덱스는 일부 정답을 놓칠 수 있다는 점을 같이 봐야 한다.

## 텍스트를 벡터로 바꾸는 이유

검색용 임베딩 모델은 문장이나 문서 조각을 고정 길이 실수 벡터로 바꾼다. 질문과 관련 문서는 가깝게, 관련 없는 문서는 멀게 놓이도록 학습한다. 문서 벡터는 미리 계산해 둘 수 있고 질문만 새로 인코딩하면 되므로, 질문과 모든 문서를 한 쌍씩 함께 읽는 cross-encoder보다 1차 검색에 쓰기 쉽다. Sentence-BERT가 이 bi-encoder 방식을 검색에 실용적으로 적용한 대표적인 연구다.

“같은 모델끼리만 비교한다”는 말은 차원이 같다는 뜻보다 강하다. 모델, 전처리, 정규화 방식, query/document 지시문이 같아야 같은 공간으로 볼 수 있다. 임베딩 모델을 바꾸면 기존 문서 벡터도 다시 만들어야 한다.

이번 실습에서는 `nlpai-lab/KURE-v1`을 사용했다. 공식 저장소와 모델 카드 기준으로 BAAI의 `bge-m3`를 바탕으로 만들었고, 약 200만 개의 한국어 query-document-hard negative 데이터로 학습했다. 각 질의에는 hard negative 5개가 포함된다. 출력은 1024차원이고 라이선스는 MIT다.

API 대신 로컬 모델을 고른 가장 큰 이유는 개인 카톡 원문을 외부 서비스에 보내지 않기 위해서다. 실행 기록상 Apple Silicon의 MPS에서 이미 캐시된 모델을 불러오는 데 10.31초, 1,922개 청크를 batch 32로 인코딩하는 데 519.29초가 걸렸다. 총 529.60초, 약 8분 50초이고 처리량은 초당 3.70청크였다. 최초 모델 다운로드 시간은 이 측정에 들어 있지 않다.

## 코사인 유사도와 pgvector

두 벡터의 방향이 얼마나 비슷한지는 코사인 유사도로 계산할 수 있다.

```text
cos(a, b) = (a · b) / (|a| × |b|)
cosine distance = 1 - cos(a, b)
```

0이 아닌 실수 벡터의 코사인 유사도 범위는 -1부터 1, 코사인 거리 범위는 0부터 2다. 두 벡터를 L2 정규화해 길이를 1로 만들면 코사인 유사도는 내적과 같아진다. 현재 파이프라인은 저장 전에 임베딩을 정규화한다.

pgvector에서 자주 쓰는 연산자는 다음 정도만 기억하면 된다.

| 연산자 | 의미 | 대응 opclass |
|---|---|---|
| `<=>` | 코사인 거리 | `vector_cosine_ops` |
| `<->` | L2 거리 | `vector_l2_ops` |
| `<#>` | 음의 내적 | `vector_ip_ops` |
| `<+>` | L1 거리 | `vector_l1_ops` |

PostgreSQL의 인덱스 스캔은 오름차순 연산자를 사용하므로, 내적은 큰 값이 먼저 오도록 음수로 반환하는 `<#>`를 쓴다. 더 중요한 것은 쿼리의 거리 연산자와 인덱스 opclass를 맞추는 일이다. 이번 인덱스는 `vector_cosine_ops`이므로 `ORDER BY embedding <=> query_vector`일 때 HNSW를 사용할 수 있다.

코사인 0.59 같은 숫자에 보편적인 합격선을 붙이기는 어렵다. 모델과 데이터에 따라 점수 분포가 다르다. 실제 평가 질문에서 정답과 오답의 분포를 보고 임계값을 정해야 한다.

## HNSW는 무엇을 근사하는가

인덱스가 없으면 질문 벡터를 N개의 문서 벡터와 전부 비교한다. 결과는 정확하지만 데이터가 커지면 비교 횟수도 함께 늘어난다. HNSW는 여러 층의 근접 그래프를 만들고, 성긴 위층에서 먼 거리를 건너뛴 뒤 촘촘한 아래층에서 후보를 좁힌다. 원 논문은 이 구조가 여러 실제 데이터셋에서 높은 recall과 로그에 가까운 검색 확장성을 보인다고 설명한다. 다만 모든 데이터에서 보장되는 엄밀한 최악 시간복잡도라고 쓰는 것은 지나친 단정이다.

pgvector의 HNSW 기본값은 다음과 같다.

- `m=16`: 노드 연결 수를 결정한다. 높이면 대체로 recall과 메모리 사용량, 빌드 시간이 함께 늘어난다.
- `ef_construction=64`: 인덱스를 만들 때 검토할 후보 폭이다.
- `hnsw.ef_search=40`: 검색 때 유지할 후보 폭이다. 높이면 대체로 recall은 좋아지고 검색은 느려진다.

pgvector는 기본적으로 정확 검색을 하고, HNSW나 IVFFlat 인덱스를 추가했을 때 근사 검색을 사용한다. HNSW는 IVFFlat처럼 별도의 학습 단계가 없어 빈 테이블에도 만들 수 있지만, 공식 문서대로 데이터를 먼저 적재한 뒤 만드는 편이 빌드가 빠르다.

현재 1,922개 청크에는 사실 전체 벡터를 훑는 정확 검색도 충분히 작다. HNSW는 당장 성능 문제를 해결한다기보다, 다음 단계에서 근사 검색의 recall과 속도 교환을 확인하기 위해 넣은 셈이다. 실제 `EXPLAIN (ANALYZE, BUFFERS)`에서는 top-5 코사인 쿼리가 `chunk_embeddings_hnsw`를 선택했고 약 1.6~1.9ms에 끝났다. 이 시간은 현재 노트북과 캐시 상태에서 한 번 확인한 값이라 일반 성능 수치로 해석하면 안 된다.

인덱스가 잡을 수 있는 차원에도 제한이 있다. 현재 pgvector 공식 문서 기준 HNSW가 색인할 수 있는 `vector`는 최대 2,000차원, `halfvec`은 최대 4,000차원이다. KURE-v1의 1,024차원은 그대로 색인할 수 있다.

### 방 필터를 붙일 때 생기는 일

근사 검색에서 `WHERE room_id = ...` 같은 필터는 보통 인덱스 스캔 뒤에 적용된다. `ef_search=40`으로 뽑은 후보 중 특정 방의 청크가 적으면 `LIMIT 10`인데도 10건을 못 받을 수 있다. pgvector 0.8.0부터는 iterative scan으로 필요할 때 후보 탐색을 이어갈 수 있다.

```sql
SET LOCAL hnsw.iterative_scan = strict_order;
-- 또는 더 느슨한 거리 순서를 허용하는 relaxed_order
```

필터가 자주 쓰이면 `ef_search`만 계속 키우기보다 필터 컬럼의 일반 인덱스, 부분 HNSW 인덱스, 파티셔닝도 함께 검토해야 한다.

## 카톡에서는 청크가 더 중요했다

카톡 메시지를 한 건씩 임베딩하면 `ㅋㅋ`, `넵`, 사진 같은 검색 가치가 낮은 벡터가 지나치게 많아진다. 반대로 하루 대화를 통째로 묶으면 여러 주제가 한 벡터에 섞인다.

현재 규칙은 30분 이상 대화가 끊기면 새 세션을 만들고, 세션 안에서 최대 30건 또는 700자까지 묶으며 다음 청크에 3건을 겹치는 방식이다. 날짜·시간·참여자 헤더는 상대적인 표현을 해석하는 데 도움을 주지만, 반복되는 이름과 방 정보가 유사도를 과도하게 끌어올릴 수도 있다. 그래서 헤더를 뺀 버전과의 비교가 필요하다. 사진·이모티콘·시스템 메시지는 검색 청크에서 제외하되 원본 `messages`에는 남겼다.

## `마감 일정`에서 나온 결과

팀리더 방에서 벡터 1위는 `제출일`을 논의한 `#1653`(코사인 0.592), 2위는 `언제까지 완성`할지를 묻는 `#1695`(0.573)였다. 질문에 `마감`이나 `일정`이 없어도 의미가 가까운 표현을 가져왔다.

BM25 상위 5개와 벡터 상위 5개의 교집합은 `#1463` 하나였다. 고유명사, 숫자, 정확한 문구는 BM25가 더 안정적인 경우가 있었고, 동의어나 풀어 쓴 질문은 벡터 쪽이 유리했다. 집계나 여러 대화를 이어 봐야 하는 질문은 둘 다 제대로 답하지 못했다. 이 결과 때문에 다음 단계에서는 점수 합산이 아니라 각 검색기의 순위를 RRF로 합쳐 볼 예정이다.

## 다음에 확인할 것

- HNSW를 끈 정확 검색 결과와 근사 top-10의 겹침으로 recall을 측정한다. 비교할 때는 트랜잭션 안에서 `SET LOCAL enable_indexscan = off`를 사용한다.
- `hnsw.ef_search`를 40, 100, 200으로 바꾸고 recall과 지연 시간을 같이 기록한다.
- 청크 헤더 유무, 최대 길이, 겹침 수만 바꿔 같은 평가 질문을 다시 돌린다.
- 모델 비교를 한다면 코사인 절댓값이 아니라 동일한 정답셋의 Recall@k로 판단한다.
