# **RDF 트리플 스토어 vs** Property **그래프, 둘 다 그래프인데 뭐가 다를까?**

앞에서는 Semantic Web이 왜 웹 전체의 표준으로 자리 잡지 못했고, 이후 Knowledge Graph가 어떤 식으로 그 문제를 우회했는지 살펴봤다. 그 과정에서 계속 `RDF`, `Triple`, `Knowledge Graph`라는 말을 사용했는데, 여기서 한 가지 의문이 생겼다.

**Knowledge Graph를 만든다고 해서 반드시 RDF를 사용해야 할까?**

실제로 Neo4j 같은 그래프 데이터베이스를 찾아보면 RDF와는 조금 다른 **Property Graph(프로퍼티 그래프)**라는 모델을 사용한다. 둘 다 노드와 관계로 데이터를 표현하는데, 데이터를 바라보는 방식과 만들어진 목적이 다르다.

이번에는 두 모델의 차이를 보고, 지금 만들고 있는 그래프가 어느 쪽에 가까운지도 정리해봤다.

## **1. 시작부터 목적이 달랐다**

두 모델의 차이를 이해하기 가장 쉬운 방법은 **왜 만들어졌는지**부터 보는 것이다.

|  | **RDF** | **프로퍼티 그래프** |
| --- | --- | --- |
| 출발점 | 서로 다른 시스템의 데이터를 표현하고 연결 | 애플리케이션의 그래프 데이터를 저장하고 조회 |
| 중요하게 보는 것 | 표준, 식별, 상호운용성 | 탐색, 질의, 개발 편의 |
| 대표 질의어 | SPARQL | Cypher / GQL |
| 대표 시스템 | GraphDB, Apache Jena 등 | Neo4j 등 |

RDF는 웹에 흩어진 데이터를 서로 연결하려는 Semantic Web에서 발전했다. 그래서 **다른 시스템에서도 같은 대상을 가리킬 수 있는 IRI, 공통 데이터 모델, 표준 질의 방식**이 중요했다.

반면 프로퍼티 그래프는 소셜 네트워크처럼 **“A와 연결된 사람을 찾고, 그 사람과 연결된 다른 사람을 또 찾는다”** 같은 그래프 탐색을 애플리케이션에서 편하게 처리하는 데 초점이 있다.

그래서 RDF를 단순히 “그래프 DB의 옛날 버전”처럼 보면 안 된다. **애초에 풀려고 했던 문제가 조금 달랐다.**

## **2. 가장 눈에 띄는 차이 : 관계에도 속성을 붙일 수 있다!**

두 모델의 차이가 가장 쉽게 보이는 부분은 **Edge 자체에 정보를 붙이는 방법**이다.

예를 들어 서울에서 부산으로 이동하는 관계가 있고, 이 관계에 거리와 비용을 저장한다고 해보자.

단순히 `서울 → 연결됨 → 부산`만으로는 `거리 325km`, `비용 50,000원`이라는 정보를 어디에 붙여야 할지 애매하다.

Property 그래프에서는 이게 자연스럽다.

<aside>

**서울 ──[이동: 거리=325km, 비용=50,000원]──> 부산**

노드뿐 아니라 **관계 자체가 Property를 가질 수 있기 때문**이다.

</aside>

RDF의 기본 Triple은 다르다.

<aside>

**서울 → 연결됨 → 부산**

Subject-Predicate-Object 세 자리로 끝나기 때문에 이 Triple 자체에 거리나 비용을 바로 추가할 자리가 없다.

그래서 앞에서 배운 **reification이나 중간 노드**가 필요해진다.

**Connection → 출발지: 서울 / 도착지: 부산 / 거리: 325km / 비용: 50,000원**

</aside>

하나의 관계를 다시 하나의 대상으로 만들어 추가 정보를 붙이는 것이다.

## **3. 이 문제를 이미 우리 스키마에서 만났다**

이 차이가 특히 와닿았던 이유는 이번 주 그래프 스키마를 만들면서 똑같은 문제를 이미 겪었기 때문이다.

내가 진행한 AI 코드 보안 분석 프로젝트인 `SeCause`에서 Redis를 사용한 경험을 처음에는 이렇게 표현하려고 했다.

- **`SeCause → USES_TECHNOLOGY → Redis`**

그런데 이걸로는 **왜 사용했는지, 실제 구현한 기술인지**를 표현할 수 없었다.

그래서 결국 **“특정 프로젝트에서 특정 기술을 사용한 경험”** 자체를 `TechnologyUse`라는 중간 노드로 만들었다.

- **`TechnologyUse → 프로젝트 / Redis / 사용 목적 / 구현 상태`**

RDF에서 봤던 n항 관계와 reification 문제를 그대로 만난 것이다.

---

그런데!! Property 그래프였다면 조금 다르게 표현할 수 있다.

- **`SeCause ──[USES_TECHNOLOGY: 목적=작업 큐, 상태=implemented]──> Redis`**

굳이 `TechnologyUse`라는 별도 노드를 만들지 않고 **기술을 사용했다는 Edge 자체에 목적과 상태를 붙일 수 있다.**

물론 `TechnologyUse` 자체를 독립적인 개체로 다뤄야 한다면 프로퍼티 그래프에서도 노드로 만드는 게 더 적절할 수 있다. 여기서 핵심은 프로퍼티 그래프에서는 **관계를 단순한 연결선이 아니라 자체 속성을 가질 수 있는 대상으로 표현할 선택지가 기본적으로 제공된다**는 것이다.

## **4. 식별자를 바라보는 방식도 다르다**

앞에서 RDF를 공부할 때 IRI가 계속 등장했다.

RDF는 서로 다른 시스템에서 만들어진 데이터를 연결하는 것이 중요한 목적이었기 때문에 **전역적으로 대상을 식별할 수 있는 이름**을 중요하게 본다. 그런데 프로퍼티 그래프에서는 보통 상황이 다르다.

| **RDF** | **프로퍼티 그래프** |
| --- | --- |
| 외부에서도 대상을 식별할 수 있는 IRI 중요 | 그래프 내부에서 식별할 수 있으면 됨 |
| 다른 데이터셋과 연결을 고려 | 하나의 애플리케이션 DB가 중심 |
| 전역 식별 체계 관리 필요 | 내부 ID나 애플리케이션 키 활용 가능 |

이것도 결국 출발점의 차이와 연결된다.

- **RDF: “나중에 다른 곳의 데이터와 연결할 수도 있다.”**
- **프로퍼티 그래프: “일단 이 애플리케이션 안에서 잘 조회하면 된다.”**

현재 실습에서도 웹 전체에서 통용되는 IRI를 만드는 대신 `project:secause`, `technology:redis`처럼 **우리 그래프 내부에서 구분할 수 있는 ID를 직접 정의하는 방향(프로퍼티 방향)**에 가깝다.

## **5. SPARQL과 Cypher도 생김새가 다르다**

RDF에서는 앞에서 직접 사용해본 SPARQL로 그래프를 조회했다.

SPARQL은 **Triple Pattern을 적고 비어 있는 부분을 변수로 두는 방식**이었다.

예를 들어:

```sql
**?person → WORKS_AT → ?company
?person → ATTENDS → 홍익대학교**
```

처럼 같은 `?person` 변수를 공유하면 두 관계가 자연스럽게 연결됐다.

그러나 프로퍼티 그래프에서 많이 사용하는 Cypher는 그래프 모양을 거의 그대로 적는다.

`(사람)-[:WORKS_AT]->(회사)` 처럼 **노드와 Edge를 화살표로 그리는 형태**다.

| **SPARQL** | **Cypher** |
| --- | --- |
| Triple Pattern 중심 | Node-Edge Pattern 중심 |
| `?변수`로 패턴 연결 | `(node)-[:EDGE]->(node)` |
| RDF 생태계의 표준 질의어 | Property Graph에서 널리 쓰이는 질의어 |

둘 다 결국 **그래프에서 원하는 패턴을 찾는다**는 점에서는 비슷하다. 다만 SPARQL은 RDF/RDFS 같은 Semantic Web 생태계와 함께 사용될 수 있고, Cypher는 프로퍼티 그래프의 노드·관계·속성을 탐색하기 편한 형태로 설계되어 있다.

그리고 프로퍼티 그래프 쪽에서도 2024년 ISO 표준인 **GQL(Graph Query Language)**이 나오면서 그래프 질의 언어의 표준화가 진행되고 있다.

## **6. 열린 세계와 닫힌 세계는 모델 자체보다 사용 방식의 차이로 보기**

앞에서 RDF/OWL을 공부하면서 **Open World Assumption(열린 세계 가정)**을 봤다.

데이터에 `연호 → 다닌다 → 홍익대학교`만 있다고 해서 **“연호는 연세대학교에 다니지 않는다”**고 판단하지 않는다. 데이터에 없을 뿐 실제 사실까지 없다고 단정할 수 없기 때문이다.

반면 일반적인 애플리케이션 데이터베이스는 보통 **현재 DB에 들어 있는 데이터를 시스템이 알고 있는 전체 상태로 취급**하는 경우가 많다.

그래서 이렇게 대비된다.

- **Semantic Web/RDF·OWL 활용 → 없으면 모를 수 있음**
- **일반적인 애플리케이션/Property Graph 활용 → 현재 DB에 없으면 없는 관계로 처리하는 경우가 많음**

다만 이 부분은 조심해서 볼 필요가 있다! **RDF라는 데이터 모델 자체가 무조건 열린 세계이고 Property Graph라는 데이터 모델 자체가 무조건 닫힌 세계라고 정해지는 것은 아니다.** 

열린 세계 가정은 특히 RDF의 형식 의미론과 RDFS/OWL 추론 생태계에서 중요하게 나타나는 관점이고, Property Graph도 애플리케이션을 어떻게 설계하느냐에 따라 불완전한 데이터를 다룰 수 있다.

그래서 둘의 차이를 단순히 `RDF = OWA`, `Property Graph = CWA`로 외우기보다는 **RDF/OWL은 불완전하고 분산된 지식을 연결하는 환경에서 발전했고, Property Graph는 하나의 애플리케이션이 관리하는 그래프를 조회하는 환경에서 많이 사용된다** 정도로 이해하는 게 더 정확했다.

## **7. 그래프 DB는 관계를 따라가는 방식에서도 차이가 난다**

프로퍼티 그래프 DB가 많이 사용되는 이유 중 하나는 **관계를 여러 단계 따라가는 탐색**이다.

대표적으로 Neo4j는 연결된 노드 사이를 탐색하기 편한 저장·실행 구조를 사용한다. 흔히 **index-free adjacency**라는 개념으로 설명한다.

핵심은 시작 노드를 찾은 뒤 매번 전체 Edge 테이블을 검색하는 방식이 아니라, **현재 노드와 연결된 관계를 따라 이웃 노드로 이동하기 쉽게 저장한다는 것**이다.

반면 우리가 PostgreSQL에서 그래프 비슷한 구조를 만든다면 상황이 다르다.

예를 들어 `entities`와 `edges` 테이블이 있을 때,

**Project → TechnologyUse → Technology → …**

처럼 관계를 따라갈수록 `edges` 테이블을 계속 JOIN해야 한다. 깊이가 정해져 있지 않다면 Recursive CTE(자기 자신을 참조하여 반복적으로 데이터를 처리하는 SQL 기능) 같은 방법도 필요하다.

다만 그렇다고 **“Postgres는 3홉부터 느리다”처럼 고정된 기준이 있는 것은 아니다.** 실제 성능은 그래프 크기, 연결 밀도, 인덱스, 쿼리 형태 등에 따라 달라진다.

이번 실습에서는 그래프 자체가 작기 때문에 전용 그래프 DB의 성능상 이점보다 **기존 PostgreSQL 안에서 Vector Search와 관계 검색을 같이 실험할 수 있다는 편의성**을 우선했다.

## **8. 한 번에 비교하면**

|  | **RDF / Triple Store** | **Property Graph** |
| --- | --- | --- |
| 출발점 | 분산된 데이터의 표현·교환·연결 | 애플리케이션 그래프 저장·탐색 |
| 기본 표현 | Subject-Predicate-Object | Node-Edge-Node |
| Edge Property | 기본 Triple에는 직접 없음 | 직접 표현 가능 |
| 관계에 추가 정보 | 중간 노드, reification 등 활용 | Edge Property 활용 가능 |
| 식별 | IRI 중심 | 내부/애플리케이션 ID 사용 가능 |
| 대표 질의 | SPARQL | Cypher, GQL |
| 의미·추론 생태계 | RDFS, OWL 등이 존재 | 보통 패턴 탐색 중심 |
| 강점 | 표준화, 데이터 연결, 의미 표현 | 애플리케이션 개발, 관계 탐색, Edge Property |
| 대표적인 활용 | Wikidata, Linked Data 등 | 소셜 그래프, 추천, Fraud Detection 등 |

결국 둘 중 하나가 무조건 더 좋은 게 아니라 **어떤 문제를 풀려고 하는지가 다르다.**

여러 조직의 데이터를 표준화해서 연결하고 의미 체계까지 공유해야 한다면 RDF의 장점이 크다. 반대로 하나의 애플리케이션 안에서 노드와 관계를 빠르게 탐색하고 관계 자체에도 여러 속성을 붙여야 한다면 프로퍼티 그래프가 자연스러울 수 있다.

## **9. 그러면 우리는 어느 쪽일까?**

이번 주 내내 RDF의 용어를 많이 사용했다.

`Triple`, `Subject`, `Predicate`, `Object`라고 부르고 관계도 `PART_OF`, `USES_TECHNOLOGY` 같은 Predicate 형태로 정의했다.

그런데 실제로 만들려는 저장 구조를 보면 RDF보다는 **프로퍼티 그래프에 가까운 부분이 많다.**

| **기준** | **현재 실습** |
| --- | --- |
| Node | `entities` 테이블 |
| Node Property | `props JSONB` |
| Edge | `edges` 테이블 |
| Edge Property | `chunk_id`, `evidence`, `confidence` |
| 식별자 | 실습 내부에서 사용하는 문자열 ID |
| 관계 | 미리 정한 소수의 Predicate |
| 추론 엔진 | 없음 |
| 저장소 | PostgreSQL |

특히 중요한 건 `evidence`다.

우리는 “프로젝트가 Redis를 사용했다”라는 관계만 저장하려는 게 아니라, 그 관계를 어떤 원본 문서에서 추출했는지까지 Edge에 남기려고 한다.

즉 Edge 자체가 단순한 연결선이 아니라 **근거와 신뢰도 같은 정보를 가진 데이터**가 된다.

그래서 현재 구조를 설명할 때는 이렇게 말하는 게 가장 정확할 것 같다.

**우리는 RDF의 Triple이라는 사고방식과 용어를 참고하고 있지만, 실제 구현은 PostgreSQL 위에 간단한 프로퍼티 그래프 구조를 만든 것에 가깝다.**

## **10. 그런데 왜 그냥 Neo4j를 쓰지 않을까?**

여기까지 보면 자연스럽게 “프로퍼티 그래프라면 Neo4j를 쓰면 되는 것 아닌가?”라는 질문이 생긴다.

이번 실습에서는 PostgreSQL을 유지하는 이유가 있다.

첫째, 지난주부터 PostgreSQL + pgvector로 Vector Search를 이미 사용하고 있다. 그래프 관계도 같은 DB에 두면 **기존 Vector Search와 Graph Retrieval을 한 저장소 안에서 실험하기 쉽다.**

둘째, 이번 목표는 그래프 DB 자체의 성능을 검증하는 것이 아니라 **관계를 구조화했을 때 기존 RAG의 Retrieval Failure가 개선되는지 확인하는 것**이다.

셋째, 데이터 규모도 아직 개인 문서 수준이다. 이 단계에서 새로운 DB를 추가하면 그래프 모델 자체보다 운영과 학습 범위가 더 커질 수 있다.

대신 Trade-off는 알고 있어야 한다.

PostgreSQL에서는 여러 홉을 따라갈수록 JOIN이나 Recursive CTE가 필요해지고, 그래프가 커지고 탐색이 복잡해지면 전용 그래프 DB와 차이가 커질 수 있다.

즉 **Neo4j가 필요 없어서 Postgres를 쓰는 게 아니라, 현재 실험의 규모와 목적에서는 Postgres로 얻는 단순함이 더 크다고 판단한 것**이다.

## **11. 결국 두 모델도 서로 가까워지고 있다**

재밌는 건 두 진영이 완전히 따로 발전하는 것도 아니라는 점이다.

RDF 쪽에서도 **statement 자체에 정보를 붙이는 문제를 더 편하게 다루려는 방향**이 발전하고 있고, Property Graph 쪽에서도 GQL처럼 표준 질의 언어가 등장했다. Neo4j와 RDF 사이의 데이터를 연결하려는 도구도 존재한다.

즉 한쪽은 **Edge를 더 풍부하게 표현하는 방향**, 다른 한쪽은 **표준화와 상호운용성을 강화하는 방향**으로 서로의 장점을 일부 흡수하고 있다.

그래서 RDF와 프로퍼티 그래프를 완전히 대립하는 기술로 보기보다는 **서로 다른 문제에서 출발해 발전해온 두 그래프 모델**로 보는 편이 자연스러웠다.

## **12. 4주차를 마치면서**

이번 주는 처음에는 RDF, SPARQL, RDFS, OWL처럼 서로 다른 기술을 하나씩 배우는 느낌이었다.

그런데 끝까지 보고 나니 계속 같은 문제가 반복되고 있었다.

처음 내 프로젝트 데이터를 그래프로 표현하려고 했을 때 단순히 아래와 같이 라고 저장하려 했다.

**프로젝트 → 사용 기술 → Redis**

그런데 실제 데이터를 넣으려니 “왜 사용했지?”, “실제로 구현했나?”라는 정보가 필요했다. 그래서 `TechnologyUse`라는 중간 노드를 만들었다.

이후 RDF를 공부하면서 이게 **2항 관계와 n항 관계의 문제**라는 걸 알게 됐고, Wikidata에서는 **statement와 qualifier**, RDF에서는 **reification 같은 모델링**, 프로퍼티 그래프에서는 **Edge Property**를 이용해 비슷한 문제를 다룬다는 걸 확인했다.

즉 이론을 먼저 보고 스키마를 따라 만든 게 아니라 **실제 데이터를 표현하려고 스키마를 만들다가 그래프 모델이 오래전부터 고민해온 문제에 도착한 셈**이었다.

이번 주 내용을 한 흐름으로 다시 보면:

**RDF로 사실과 관계를 표현 → SPARQL로 관계를 조회 → RDFS/OWL로 의미와 추론을 이해 → Semantic Web에서 Knowledge Graph로 이어진 흐름 확인 → RDF와 Property Graph의 서로 다른 모델링 방식 비교**

정도로 정리할 수 있다.

그리고 다음 실습에서는 여기서 배운 모델을 그대로 따라가는 게 아니라, **현재 목적에 맞는 작은 관계 스키마를 PostgreSQL에 직접 구현하고 기존 Hybrid RAG와 비교**하게 된다.
