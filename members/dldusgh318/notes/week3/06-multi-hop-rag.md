# **06. Multi-hop — RAG는 왜 여러 관계를 따라가지 못할까?**

앞에서는 Hybrid Search로 찾은 chunk를 LLM에게 전달해 **근거 있는 답변을 생성하는 RAG**까지 살펴봤다.

```
질문
 ↓
BM25 + Vector
 ↓
RRF
 ↓
관련 chunk
 ↓
LLM
 ↓
답변 + 근거
```

그런데 검색 품질을 높이고 RAG까지 붙여도 여전히 이상하게 못 푸는 질문이 있다.

**“부산 같이 간 사람들 중 같은 회사 다니는 사람?”**

왜 못 풀까?

⇒ 결론부터 말하면 **LLM이 추론을 못해서가 아니라, 한 번의 검색으로 필요한 정보를 모두 가져오기 어렵기 때문**이다.

---

## **핵심 개념**

- **Multi-hop Question**: 하나의 정보만으로 답할 수 없고 여러 정보를 순서대로 연결해야 하는 질문
- **Bridge Entity**: 첫 번째 단계에서 찾은 답이 다음 검색의 연결고리가 되는 것
- **Oracle Context**: 정답에 필요한 chunk를 직접 넣어 LLM의 추론 문제인지 검색 문제인지 확인하는 실험
- **Agentic Search**: 검색 결과를 보고 다시 질문을 만들어 재검색하는 방식
- **근본적인 한계**: chunk에는 텍스트가 저장되어 있을 뿐 **관계 자체가 명시적으로 저장되어 있지 않다**

---

## **1. Multi-hop Question이란?**

예를 들어 다음 질문을 생각해보자.

**“부산 같이 간 사람들 중 같은 회사 다니는 사람?”**

사람이라면 자연스럽게 이렇게 푼다.

```
[Hop 1]
부산에 누구랑 갔지?
 ↓
민지 / 주영 / 지훈

[Hop 2]
각자 어디 다니지?
 ↓
민지 → X사
주영 → X사
지훈 → Y사

[Final]
같은 회사는?
 ↓
민지 / 주영
```

여기서 `민지`, `주영`, `지훈`이 **Bridge Entity**다.

중요한 점은 이 사람들의 이름이 **첫 번째 검색을 하기 전에는 검색어로 주어져 있지 않다는 것**이다.

```
원래 질문
"부산 같이 간 사람들 중 같은 회사?"

       ↓ 검색

"부산 여행"
       ↓

민지 / 주영 / 지훈 발견

       ↓ 다시 검색해야 함

"민지 회사"
"주영 회사"
"지훈 회사"
```

즉 **첫 번째 결과가 두 번째 검색어를 결정한다!**

---

## **2. 그런데 현재 RAG는 어떻게 동작할까?**

현재 구조에서는 질문을 한 번 검색한다.

```
"부산 같이 간 사람들 중 같은 회사?"

              ↓

        Hybrid Search

              ↓

부산 여행 기록
부산 맛집 기록
부산역 기록
회사 면접 기록
...
```

문제는 우리가 정말 필요한 이런 문서다.

```
"민지는 X사에 입사했다."
"주영도 X사에 다닌다."
"지훈은 Y사에 다닌다."
```

이 문서에는 **`부산`이라는 단어가 없다.**

BM25 입장에서는:

```
질문: 부산 / 같이 / 회사
문서: 민지 / X사 / 입사

→ 겹치는 핵심 term이 거의 없음
```

Vector Search에서도 여행 이야기와 입사 이야기는 의미적으로 멀 수 있다.

그리고 둘 다 못 찾았다면 RRF도 해결할 수 없다.

```
BM25  → 못 찾음 ─┐
                  ├→ RRF → 여전히 못 찾음
Vector → 못 찾음 ─┘
```

**RRF는 검색 결과를 잘 합쳐주는 기술이지, 존재하지 않는 두 번째 검색을 만들어주는 기술은 아니다.**

Open-domain multi-hop QA에서도 뒤쪽 hop의 주제가 원래 질문에 직접 드러나지 않아 supporting passage 검색 자체가 어려워지는 문제가 지적되어 왔다.

---

## **3. 진짜 검색 문제인지 어떻게 알까?**

여기서 중요한 질문이 생긴다.

**“그냥 LLM이 추론을 못한 거 아니야?”**

이를 확인할 수 있는 간단한 방법이 **Oracle Context 실험**이다.

### **A. 일반 RAG**

```
질문
 ↓
검색
 ↓
자동으로 찾은 chunk
 ↓
LLM
 ↓
❌ 답변 실패
```

### **B. Oracle Context**

정답에 필요한 문서를 내가 직접 넣어준다.

```
[1] 부산 여행 멤버
    → 민지, 주영, 지훈

[2] 민지 회사
    → X사

[3] 주영 회사
    → X사

[4] 지훈 회사
    → Y사
```

그리고 똑같은 질문을 한다.

```
질문
 ↓
정답 chunk 직접 주입
 ↓
LLM
 ↓
✅ "민지와 주영입니다."
```

이렇게 된다면 결론은 명확하다.

| **일반 RAG** | **Oracle** | **의미** |
| --- | --- | --- |
| ❌ | ✅ | **검색 문제** |
| ❌ | ❌ | **추론/생성 문제** |
| ✅ | ✅ | 기존 RAG로도 해결 가능 |

즉, **LLM이 못 푼 게 아니라, 풀 재료를 못 가져온 것이다.**

이 실험을 통해 RAG 실패의 원인을 구분할 수 있다.

---

## **4. 검색 결과를 직접 보면 더 명확하다**

예를 들어 실제 검색 결과가 다음과 같다고 하자.

```
Query
"부산 같이 간 사람들 중 같은 회사 다니는 사람?"

Top-5

1. 부산 여행 2박 3일 정산
2. 부산역 도착
3. 부산 돼지국밥
4. 회사 면접 후기
5. 같이 여행 갈 사람 모집
```

하지만 실제로 필요한 것은 다음과 같다.

```
민지 → X사 입사
주영 → X사 입사
지훈 → Y사 입사
```

첫 검색은 **부산에 같이 간 사람이 누구인지는 찾았지만**, 그 결과를 이용해서 두 번째 검색을 하지 않았다.

이게 Multi-hop에서 현재 RAG가 막히는 지점이다.

---

## **5. 그럼 다시 검색하면 되지 않을까?**

가장 먼저 떠오르는 해결책이다.

LLM에게 첫 번째 결과를 읽게 한 뒤 새로운 검색어를 만들게 하면 된다.

```
질문
 ↓
검색 ① "부산 같이 간 사람"
 ↓
민지 / 주영 / 지훈 발견
 ↓
LLM이 새로운 Query 생성
 ↓
검색 ② "민지 회사"
검색 ② "주영 회사"
검색 ② "지훈 회사"
 ↓
결과 종합
```

이런 방식을 **Agentic Search / Iterative Retrieval**이라고 볼 수 있다.

기존 RAG는 검색 → 답변 흐름이라면

Agentic 방식은 검색 → 생각 → 재검색 → 생각 → 필요하면 다시 검색 → 답변 흐름 이다.

실제로 multi-hop QA에서는 bridge entity를 이용해 후속 문서를 다시 찾는 방식이 중요한 접근법이다.

---

## **6. 하지만 재검색도 만능은 아니다…**

이론적으로는 좋아 보이지만? 새로운 문제가 생긴다.

### **첫 번째 검색이 틀리면?**

```
Hop 1에서 잘못된 사람 발견
 ↓
잘못된 이름으로 Hop 2 검색
 ↓
오류 누적
```

### **언제 검색을 멈출까?**

```
한 번 더?
두 번 더?
정보가 충분한가?
```

이 판단도 LLM에게 맡겨야 한다.

### **비용도 증가한다**

```
일반 RAG
검색 → LLM

Agentic
검색 → LLM → 검색 → LLM → ...
```

홉이 늘어날수록 검색과 LLM 호출도 늘어난다.

따라서 Agentic Search는 **일부 Multi-hop 질문을 해결할 수 있는 방법**이지만, 관계를 매번 텍스트 검색으로 다시 찾아야 한다는 점은 그대로다.

---

## **7. 이번에는 실패 자체를 기록해보자**

이번 실습에서는 단순히:

```
❌ 이 질문 못 풀었다
```

로 끝내지 않는다.

다음처럼 기록한다.

```yaml
question: "부산 같이 간 사람들 중 같은 회사 다니는 사람?"

expected:
  "민지, 주영"

retrieved:
  - 부산 여행 기록
  - 부산역 기록
  - 부산 맛집 기록

missing:
  - 민지 회사 정보
  - 주영 회사 정보

oracle_test: success

failure_type: retrieval
```

특히 중요한 것은 두 가지다.

```
oracle_test
→ 필요한 정보를 직접 줬을 때 풀었는가?

failure_type
→ 어디에서 실패했는가?
```

실패 유형은 다음 정도로 나눌 수 있다.

| **유형** | **의미** |
| --- | --- |
| `retrieval` | 필요한 chunk를 못 찾음 |
| `assembly` | 찾았지만 Context에 못 넣음 |
| `composition` | 정보가 있는데 추론 실패 |
| `no_data` | 애초에 데이터에 정보가 없음 |

이렇게 기록하면 **“RAG가 안 됐다”가 아니라 “왜 안 됐는가”를 설명할 수 있다.**

---

## **8. 실험 질문도 단계별로 만들자**

Multi-hop 질문만 던지는 것보다 **단일 홉 질문을 대조군으로 같이 넣는 것**이 중요하다.

| **난이도** | **예시** |
| --- | --- |
| 단일 홉 | 부산 언제 갔었지? |
| 2-hop | 부산 같이 간 사람들 중 같은 회사 다니는 사람? |
| 집계 | 올해 나랑 가장 자주 만난 사람? |
| 3-hop | 캡스톤 팀원들이 다니는 회사의 위치는? |
| 조건 결합 | 작년 이후 만난 사람 중 개발자는? |

단일 홉은 잘 되는데 Multi-hop부터 실패한다면:

**검색 시스템 전체가 망가진 것이 아니라, 여러 정보를 연결해야 할 때 문제가 생긴다**

는 것을 보여줄 수 있다.

특히 `가장 자주`, `몇 명`, `모두` 같은 **집계 질문**도 top-k 검색에는 어렵다.

검색 결과 5개만 가져와놓고 전체 데이터에서 누가 가장 많이 등장했는지 알 수는 없기 때문이다.

## **그래서 다음은?**

지금까지 데이터를 이런 형태로 저장했다.

```
Chunk A
"부산 여행을 민지, 주영과 함께 갔다."

Chunk B
"민지가 X사에 입사했다."

Chunk C
"주영도 X사에 입사했다."
```

사람이 보면 관계가 보인다.

하지만 시스템 입장에서는 그냥 **서로 떨어진 세 개의 텍스트 조각**이다.

그래서 매번:

```
부산 검색
 ↓
민지 발견
 ↓
민지 검색
 ↓
X사 발견
```

처럼 관계를 **검색으로 다시 추론**해야 한다.

그렇다면 애초에 관계를 저장하면 어떨까?

```
(나, 함께_여행, 민지)
(나, 함께_여행, 주영)

(민지, 소속, X사)
(주영, 소속, X사)
```

이것을 **Triple**이라고 한다.

이제 질문은:

```
나
 ↓ 함께_여행
민지 / 주영
 ↓ 소속
X사
```

처럼 **저장된 관계를 따라가는 문제**가 된다.

**청크는 문서 조각이고, Triple은 관계다.**

그래서 4주차에서는 기존 chunk를 버리는 것이 아니라, **chunk 위에 Entity와 Relation을 추출해 관계 구조를 추가**한다.

```
원본 문서
 ↓
Chunk
 ├─ BM25 / Vector → 서술적인 질문
 │
 └─ Triple / Graph → 관계를 따라가는 질문
```

즉 지금까지의 발전은 대체가 아니라 누적이다.

**grep → BM25 → Vector → Hybrid RAG → Relation/Graph**

다음에는 **텍스트 속에서 Entity와 Relation을 어떻게 뽑고, `(Subject, Predicate, Object)` 형태의 Triple로 저장할 것인지** 살펴보자.
