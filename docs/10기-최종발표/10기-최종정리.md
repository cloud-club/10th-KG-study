## 2. 1주차부터 걸어온 길: 검색 기술의 변천사

| 주차 | 주제 | 손에 남은 한 줄 |
|---|---|---|
| 1 | OT, 데이터 선정, 개인정보·동의, KG 기초 용어 | 가명화는 임베딩 **앞에서** 한다. 원문과 파생물을 분리한다. |
| 2 | **검색의 세 세대**: grep → 역색인·BM25(nori) → 임베딩·HNSW(pgvector) | 자연어 질문을 grep으로 찾으면 10개 중 10개가 실패했다. 한국어에서는 분석기가 만든 토큰이 곧 검색의 입력이다. |
| 3 | 하이브리드(RRF), Recall@k 평가, RAG 루프, 근거 인용, 멀티홉 한계, RAGAS | RRF가 항상 이기는 건 아니다. 평가셋 11개의 결과가 승·동률·패로 갈렸다. |
| 4 | 지식그래프의 배경: 시맨틱 웹, RDF·OWL·SPARQL, Wikidata, 프로퍼티 그래프, 기업 사례·Palantir | `domain`/`range`는 검증 규칙이 아니라 추론 규칙이다. 그래프에 경로가 없다고 해서 "답이 없다"는 뜻은 아니다(열린 세계 가정). |
| 5 | 닫힌 스키마, LLM 트리플 추출, 엔티티 신원해소, Postgres·Neo4j 적재, Cypher | LLM이 뽑은 트리플은 확정된 사실이 아니라 **후보**다. 형식 검사 통과율 99%와 의미 오류 3/8이 함께 나왔다. |
| 6 | **GraphRAG**: 로컬·글로벌 서치, Text2Cypher, 하이브리드 리트리버, 에이전틱 검색 | 그래프는 관계·다중 홉·집계 질문에서만 이긴다. 그것도 **맞는 경로를 골랐을 때만** 이긴다. |

흐름을 한 문장으로 줄이면 이렇다.
**"무엇을 찾을까"(1~3주차)에서 "찾은 것을 어떻게 이을까"(4~6주차)로 넘어갔다.**

## 3. 핵심 발견 (멤버 실측 기준)

1. **BM25는 지금도 강한 기준선이다.** 동의어와 표현 차이는 벡터 검색이, 고유명사와 숫자는 BM25가 잡는다. 실패하는 지점이 서로 달라서 둘을 합친다.
   → [[검색의-세-세대]]
2. **RRF는 기본값으로 쓸 만하지만 반드시 이기지는 않는다.** 모든 k에서 RRF가 최고였던 평가셋은 11개 중 하나(e0ng 10문항)뿐이다. 질문이 가장 많은 평가셋(yujeong430 40문항)에서는 졌다. 패배 패턴은 네 멤버에게서 같았다. 한쪽 검색기에서만 상위였던 정답이, 양쪽 모두에서 중간 순위였던 문서에 밀렸다.
   → [[하이브리드-검색과-RRF]]
3. **평가 수치는 "누가 정답을 정했나"와 채점 엄격도에 좌우된다.** 평가셋을 만드는 방식이 다섯 갈래로 나뉘었다. 정직하게 "모른다"고 답하면 RAGAS가 감점하는 문제도 확인했다.
   → [[RAG-평가-지표]], [[RAGAS]]
4. **"멀티홉이면 그래프"는 틀린 말이다.** 기준은 hop 수가 아니라 **한 번의 검색으로 필요한 청크를 모두 확보할 수 있는가**다. 세 멤버가 각자 다중 홉인데도 RAG로 풀린 반례를 냈다.
   → [[멀티홉-질문과-Bridge-Entity]]
5. **텍스트가 비슷하다고 관계가 정확한 건 아니다** (do-dop). 주제가 비슷하면 RAG는 다른 회사의 사실을 섞어 답한다. 이 엔티티 귀속 오류는 모델을 키워도 풀리지 않았다.
   → [[RAG-vs-그래프-질의]]
6. **6주차 GraphRAG 실측** → [[GraphRAG]], [[Text2Cypher]]
   - kdyann (인스타그램 17건·8문항): 다중 홉·추천 질문의 Recall@5가 v1(청크 검색) 0.00~0.50, v2(그래프 결합) 1.00이었다. 단순 질문은 둘 다 1.00이었다.
   - sunghyun (회사 문서): 경로를 코드로 고정한 v2는 9/9였다. 반면 **모델이 경로를 직접 고르는 에이전틱 방식에서는 그래프 도구를 줘도 4/9에서 3/9로 떨어졌다.** 틀린 경로를 골라 13개를 18개로 셌다.
   - heebindev (운영체제 노트): 설명 질문은 v1로 충분했다. 집계 질문은 Text2Cypher로 풀렸지만, 검토 대기 중인 관계까지 함께 세어졌다.
   - dldusgh318 (Notion 20청크 표본, 7문항 × 3회, PR #45 미머지): v2가 나아진 것은 X01 하나(wrong → partial)였고, 그래프를 거쳐 들어온 정답 청크는 0건이었다. 집계는 Text2Cypher가 맡았다(21회 중 17회 정답).
   - 공통 결론
     - 전체 개수를 세는 질문은 Top-k 검색으로는 답할 수 없다.
     - Text2Cypher는 "실행됐다"와 "맞았다"가 다르다.
     - 그래프 답변의 품질은 추출 품질에 달려 있다.

## 4. 우리가 만든 것

### 4-1. 현황판 (cloud-club.github.io/10th-KG-study)
- `members/`에 푸시하면 GitHub Actions가 노트·실습·커밋을 스캔해 GitHub Pages로 배포한다. 매일 09:00에도 다시 빌드한다.
- 화면 구성: **중계석**(LLM이 커밋 diff를 읽고 캐스터 말투로 중계), **주차별 읽을거리**, 노트 태그로 그린 **스터디 지식그래프**(반별), **멤버 카드**(GPT가 붙인 칭호·요약), **활동 히트맵**.
- 역할 분담: 현황판은 **"누가 어디까지 왔나"**, 위키는 **"무엇을 알게 됐나"**를 맡는다.

### 4-2. LLM 위키 (`wiki/`, 옵시디언 볼트)
- Karpathy의 *LLM Wiki* 패턴을 실제로 적용했다.
  - **소재**: `members/`. 불변이다.
  - **위키**: `wiki/`. 에이전트가 소유한다.
  - **스키마**: `CLAUDE.md`. 사람과 함께 고친다.
  - **3연산**: Ingest(정리) · Query(질의) · Lint(점검).
- 저장소에 노트를 올린 멤버 14명이 각자 정리한 노트를 **주제별로 합성**했다. 개념 페이지마다 "누가, 어떤 데이터로, 무엇을 측정했나"가 붙어 있고, 노트끼리 결론이 다른 곳은 `⚠️ Contradiction`으로 양쪽을 다 드러냈다.
- 규칙은 사람의 약속이 아니라 **하네스 훅으로 강제**했다.
  - `protect-raw.py`: 다른 멤버의 노트를 수정하지 못하게 막는다.
  - `check-bookkeeping.py`: 위키를 고치면 `index.md`·`log.md` 갱신을 강제한다.
- **매주 월요일 09:00에 GitHub Actions가 Claude Code를 무인으로 띄워 자동 ingest**하고, 결과를 PR로 올린다.
- 운영하며 배운 것 (→ [[LLM-위키의-한계와-비판]])
  - 위키가 아끼는 것은 검색 비용이 아니라 advanced RAG의 추가 LLM 호출과 생성 입력의 밀도다.
  - 원문 패턴에는 모순 감지와 provenance(출처 추적) 절차가 없다. 그래서 이 저장소의 스키마로 채웠다.

### 4-3. 공용 로컬 인프라
- `docker compose up -d` 한 번으로 PostgreSQL 17 + pgvector, Elasticsearch 9 + nori, Neo4j 5.26 + APOC가 함께 뜬다.
- 실제로 겪은 함정은 위키에 모았다.
  - pg_trgm로 한국어를 쓰려면 UTF-8 ctype이 필요하다.
  - 데이터가 적으면 플래너가 HNSW 인덱스를 타지 않는다.
  - ES 버전이 멤버마다 여섯 가지로 달랐다.
  - → [[로컬-인프라]], [[PostgreSQL과-pgvector-함정]], [[Elasticsearch-운영-함정]]

## 6. 최신 지식베이스 흐름 공부

| 주제 | 무엇을 봤나 | 위키 |
