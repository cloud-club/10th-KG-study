## 한 줄 요약

BM25와 벡터 검색을 RRF로 합쳐 LLM 답변까지 연결하고, 같은 질문으로 세 검색 방식의 Recall을 비교했다. 하이브리드가 항상 더 좋은 것은 아니었다.

## 핵심 개념

- 하이브리드 검색: 키워드 검색과 의미 검색의 결과를 함께 사용한다.
- RRF: 서로 다른 검색의 점수를 직접 더하지 않고 순위로 결합한다.
- 컨텍스트: LLM이 답변할 때 참고하도록 전달하는 청크 본문과 출처다.
- Recall@k: 정답 근거 청크 중 검색 상위 k개에 포함된 비율이다.
- 검색 평가와 답변 평가: 필요한 근거를 찾았는지와 그 근거로 정확히 답했는지를 나눠 본다.

## 상세 정리

### 1. 같은 청크에서 두 검색을 시작했다

2주차에 준비한 문서 364개에서 청크 2,685개를 만들었다. 같은 청크를 두 검색에 재사용했다.

```text
청크 원본 2,685개
    ├─ Elasticsearch + Nori → 역색인 → BM25
    └─ qwen3-embedding:0.6b → 벡터 파일 → PostgreSQL + pgvector
```

`raw_text`는 청크 본문이고, `embedding_text`는 문서 경로·섹션 경로·본문을 묶은 문자열이다. BM25는 embedding_text를 검색하고, 벡터 검색은 같은 문자열을 1,024차원 벡터로 바꿔 사용했다.

PostgreSQL에는 벡터만 넣는 것이 아니라 chunk_id와 본문·출처도 함께 보관했다. 양쪽 검색에서 같은 청크는 같은 chunk_id를 사용하므로 결과를 합칠 수 있었다.

기존 BM25 실습은 AND였지만, 하이브리드에서는 후보를 넓히기 위해 OR를 사용했다. OR/AND는 후보 조건이고 BM25는 후보의 순위를 계산하는 방식이다.

### 2. RRF는 왜 점수 대신 순위를 사용할까?

BM25의 19.4와 코사인 유사도의 0.66은 같은 척도가 아니다. 그대로 더하면 숫자 범위가 큰 쪽이 과하게 영향을 줄 수 있다.

점수를 정규화해서 결합하는 방법도 있지만, 이번에는 순위를 사용하는 RRF를 실습했다.

```text
RRF 점수 = 1 / (60 + BM25 순위) + 1 / (60 + 벡터 순위)
```

순위는 1부터 시작하고, 해당 검색의 후보 목록에 없으면 그쪽 기여는 0이다. 60은 순위 차이의 영향을 조절하는 상수다.

예를 들어 한쪽에서만 1위인 청크 A는 1/61 ≈ 0.01639이다. 양쪽에서 모두 3위인 청크 B는 2/63 ≈ 0.03175라서 B가 더 높다. 다만 두 목록에 있다는 이유만으로 언제나 더 높거나 정답이라고 단정할 수는 없다.

이번 실습에서는 각 검색의 후보 20개를 chunk_id로 합친 뒤, RRF 점수로 정렬해서 최종 Top-5를 선택했다. 후보 수 20과 답변에 사용할 Top-k 5는 역할이 다르다.

### 3. 질문 하나로 답변까지 연결했다

처음에는 검색 결과의 청크 ID를 직접 지정해 LLM에 전달했다. 이 방식은 컨텍스트 조립과 답변 생성 단계를 따로 관찰하기 위한 것이었다.

이후 검색 코드와 답변 코드를 연결해 질문만 입력하면 전체 과정이 실행되도록 했다.

```text
사용자 질문
    ├─ BM25 OR 검색 → 후보 20개
    └─ 질문 임베딩 → pgvector HNSW 검색 → 후보 20개
                    ↓
          chunk_id 기준 RRF 결합
                    ↓
             최종 Top-5 청크
                    ↓
          전체 본문·출처로 컨텍스트 조립
                    ↓
            질문 + 컨텍스트 + 답변 지침
                    ↓
              LLM 답변 + 근거 인용
```

이 흐름을 실행하는 주체는 프로그램이다. 답변용 LLM이 직접 Top-k를 결정하는 구조는 아니다. LLM에는 검색용 숫자 벡터가 아니라 원래 본문을 전달했다.

청크마다 [1], [2] 같은 번호를 붙이고, 답변에도 번호를 인용하도록 요청했다. 번호의 범위가 올바른지만 자동 검사했으며, 인용한 본문이 실제 주장을 뒷받침하는지는 직접 확인했다.

### 4. HNSW와 BM25의 조정 지점

벡터 검색에 기존 HNSW 인덱스를 사용했다. 실행 계획에서 chunks_embedding_hnsw의 실제 사용을 확인했고, 후보 20개에 ef_search=40을 사용했다. HNSW는 근사 검색이므로 정확 검색 결과와 항상 같다고 보장하지 않는다.

BM25는 이미 역색인을 이용한다. 속도와 품질을 조정하는 지점이 다르다고 이해했다.

- 속도: Top-k만 필요할 때 정확한 전체 일치 건수 계산을 생략할 수 있다. 연결 코드에는 track_total_hits=False를 적용했다.
- 품질: OR/AND, 최소 일치 조건, 검색 필드 가중치, 분석기 등을 조정할 수 있다. 필드 가중치나 분석기 변경 실습은 하지 않았다.

현재 프로그램에는 데이터 일치 검사와 실행 계획 확인도 있으므로, 전체 실행을 속도 위주로 최적화한 상태는 아니다. DB 검색 시간과 임베딩·검사·LLM 생성을 포함한 전체 시간도 구분했다.

### 5. 로컬 LLM과 OpenRouter를 사용했다

답변 모델을 선택하도록 연결했다.

| 모드 | 답변 모델 | 실행 위치 |
|---|---|---|
| local | qwen2.5:7b | 로컬 Ollama |
| openrouter | z-ai/glm-5.2 | OpenRouter API |

임베딩·BM25·HNSW·RRF는 로컬에서 실행하고, OpenRouter 모드에서는 질문과 선택된 본문·출처를 외부 API에 전달했다. 키는 환경변수로 입력했고 코드나 실행 기록에 저장하지 않았다.

로컬 답변에서 문서의 약어 CB를 Central Board라고 잘못 확장한 사례가 있었다. 의도는 Codebeamer였고, 제공된 청크에 없는 뜻을 만들어낸 답변 오류였다.

GLM 5.2 실습에서는 자료만으로 CB의 구체적인 정의를 알 수 없다고 답하는 모습을 확인했다. 다만 질문에 “CB가 뭐야?”를 추가하면서 검색 결과도 달라졌으므로 모델 자체의 우열로 해석하지 않았다. 모델만 비교하려면 질문·컨텍스트·지침을 고정해야 한다.

### 6. 정답 근거를 먼저 정하고 Recall을 계산했다

정답 근거는 특정 단어가 들어 있는 청크가 아니다. 질문에 대한 답을 실제로 뒷받침하는 본문을 읽고 정한 청크다. 단어 검색은 후보를 찾는 준비 단계일 뿐이다.

```text
Recall@k = 상위 k개에서 찾은 정답 근거 수 / 정답 근거 전체 수
```

정답 근거가 A, B 두 개이고 Top-5가 A, X, Y, Z, W라면 Recall@5는 1/2 = 0.5이다. 분모를 검색 결과 수 5로 잡는 것은 Recall이 아니다. 이때 Precision@5는 1/5 = 0.2이다.

같은 질문에서는 Recall@1 ≤ Recall@3 ≤ Recall@5이다. 범위를 넓힐수록 정답 근거가 추가될 수 있기 때문이다. 검색 방식끼리 비교할 때는 같은 k의 값을 비교한다.

정답셋에 없는 다른 유효한 근거를 찾았을 수도 있으므로, 현재 정답셋은 초기 기준이다. 누락된 유효 근거를 추가했다면 모든 검색 방식을 같은 기준으로 다시 평가해야 한다. 정답 근거가 비어 있는 질문의 Recall은 0으로 처리하지 않는다.

### 7. 실제 비교 결과

BM25 OR, HNSW(ef_search=40), 각 후보 20개를 결합한 RRF를 같은 질문으로 비교했다. 평가할 때는 LLM을 호출하지 않았다.

#### 전송·연결 해제 기능: 질문 표현을 바꿔 비교

| 질문 유형 | BM25 Recall@5 | 벡터 Recall@5 | RRF Recall@5 |
|---|---:|---:|---:|
| Unlink 기능명으로 삭제 여부 질문 | 1.00 | 1.00 | 1.00 |
| 연결만 끊고 원래 항목을 남기는 자연어 질문 | 0.00 | 1.00 | 1.00 |
| Send Items 기능명으로 전송 정보 질문 | 1.00 | 1.00 | 1.00 |
| 제목·설명을 다른 시스템으로 옮기는 자연어 질문 | 0.50 | 0.00 | 0.00 |
| 질문별 평균 | 0.625 | 0.750 | 0.750 |

연결 해제의 자연어 질문에서는 정답 청크가 BM25 11위, 벡터 2위, RRF 3위였다. 의미 검색이 도움이 됐다.

반대로 마지막 질문에서는 BM25가 정답 청크 하나를 5위에 가져왔지만 RRF에서는 9위로 내려갔다. 하이브리드가 항상 Recall을 높여주는 것은 아니었다.

#### 회의록에서 특정 IDE를 사용하는 회사 조회

원문에서 확인한 네 회사의 청크를 정답으로 고정했다. 전체 청크를 검색했으며 회의록만 필터링하지 않았다. 회사명과 원문은 공개하지 않는다.

| 방식 | Recall@1 | Recall@3 | Recall@5 | Recall@10 |
|---|---:|---:|---:|---:|
| BM25 | 0.25 | 0.50 | 0.75 | 1.00 |
| 벡터 | 0.00 | 0.25 | 0.25 | 0.50 |
| RRF | 0.25 | 0.50 | 0.50 | 0.75 |

이 질문에서는 BM25가 가장 잘 찾았다. BM25 4위였던 정답 하나가 벡터 후보 20개에 없었고, 결합 후 14위로 내려갔다.

#### CodeCenter에서 서버 모델을 가져와 선택하는 방법

정답 청크 두 개 모두 “모델 가져오기 → 원하는 모델 선택 → 저장하고 시작하기”를 설명했다.

| 방식 | Recall@1 | Recall@3 | Recall@5 |
|---|---:|---:|---:|
| BM25 | 0.50 | 1.00 | 1.00 |
| 벡터 | 0.50 | 1.00 | 1.00 |
| RRF | 0.50 | 1.00 | 1.00 |

세 방식 모두 정답을 1·2위에 배치했다. 두 청크가 비슷한 절차를 설명하므로 첫 청크 하나로 답변할 수 있어도 청크 기준 Recall@1은 0.5이다. Recall과 답변 가능 여부가 같지는 않다는 점을 확인했다.

처음 질문한 “조직 모델 등록 방법”은 선택 방법과 다른 질문이었다. 조직 등록 절차를 확정할 근거를 찾지 못해, 관련 자료를 억지로 정답으로 넣지 않고 질문 범위를 모델 선택으로 바꿨다.

### 8. 08_evaluate_recall.py까지 직접 실행한 검색 평가

05에서 검색 결과를 결합하고, 06에서 본문을 LLM에 전달하고, 07에서 질문 하나로 답변까지 연결했다. 마지막으로 08에서는 답변 모델을 호출하지 않고 검색 자체를 평가했다.

정답 문서를 검색 결과에서 고르는 것이 아니라, 원문을 읽고 질문에 답하는 청크 ID를 먼저 고정했다. 질문과 정답 ID를 CASES에 저장하고 같은 질문을 BM25·HNSW·RRF에 사용했다.

```text
질문 + 미리 정한 정답 청크 ID
             ↓
BM25 후보 20개 / HNSW 후보 20개 / RRF 결합 결과
             ↓
각 결과의 상위 1·3·5·10개 ID와 정답 ID 비교
             ↓
Recall 계산 + 정답 청크의 순위 표시
             ↓
질문별 평균과 상세 결과를 CSV·JSON에 저장
```

#### 직접 실행한 명령

아래 명령은 실습 파일과 데이터가 준비된 로컬 환경 기준이다. 이 저장소에는 회사 데이터와 로컬 실습 스크립트를 포함하지 않았으므로 저장소를 내려받는 것만으로 실행되지는 않는다.

```bash
# Q1~Q4 전송·연결 해제 질문 비교 당시
python3 08_evaluate_recall.py

# 이후 추가한 Q5: 회의록 기반 회사 조회
python3 08_evaluate_recall.py --question Q5 --ks 1 3 5 10

# 이후 추가한 Q6: 서버 모델을 가져와 선택하는 방법
python3 08_evaluate_recall.py --question Q6 --ks 1 3 5 10
```

현재는 Q5·Q6도 평가 파일에 추가되어 있으므로, 옵션 없이 실행하면 등록된 질문 전체를 평가한다. 회사명과 회의록 본문은 공개 기록에서 제외했다.

#### 세 결과에 같은 계산 적용하기

다음은 실습 로직을 이해하기 위해 정리한 핵심 부분이다. 실제 08은 질문별 정답 ID 검증, 후보 검색, 결과 저장도 수행한다.

```python
report = hybrid.retrieve(
    query,
    operator="or",
    candidates=20,
    mode="hnsw",
    ef_search=40,
    track_total_hits=False,
)

rankings = {
    **report["lists"],          # bm25, vector
    "hybrid": report["results"],
}

for method, hits in rankings.items():
    ranked_ids = [hit["chunk_id"] for hit in hits]
    for k in (1, 3, 5, 10):
        score = recall_at_k(ranked_ids, gold_ids, k)
        print(method, k, score)
```

단어가 있는지만 검사하는 로직이 아니다. 원문으로 정한 정답 ID가 실제 검색 결과의 어디에 있는지를 비교한다. 벡터를 만들기 위한 로컬 임베딩 호출은 있지만 답변용 LLM이나 OpenRouter는 호출하지 않는다.

#### 출력에서 확인한 것

- Q1~Q4: 같은 기능도 질문 표현에 따라 순위가 달랐다. RRF가 BM25의 정답 청크를 5위에서 9위로 밀어낸 실패도 있었다.
- Q5: 정답 근거 4개 중 BM25 Top-5는 3개, 벡터는 1개, RRF는 2개를 찾았다. Top-10에서는 BM25가 4개를 모두 찾았다.
- Q6: 두 정답 청크를 세 방식 모두 1·2위에 배치했다. Recall@1=0.5, Recall@3=1.0이었고 RRF의 추가 이득은 없었다.
- 순위 None은 그 방식의 수집된 후보 목록에 없다는 뜻이다. 전체 원본에 문서가 없다는 뜻은 아니다. RRF는 두 후보 목록을 합쳐 최대 40개의 고유 청크를 가질 수 있다.
- CSV는 질문·방식별 Recall 표이고, JSON에는 정답 ID, 실제 후보 순위, 제목·섹션, 설정, 질문별 평균을 저장했다.

#### 이번 실습으로 이해한 점

Recall@k의 분모는 k가 아니라 정답 근거 수다. 같은 질문에서는 k를 늘리면 Recall이 감소하지 않는다. 검색 방식을 비교할 때는 같은 k와 같은 정답셋을 사용한다.

질문 하나에 정답 근거가 한 개여도 괜찮다. 숫자를 다양하게 만들려고 정답을 늘리기보다 다양한 기능과 질문을 추가하는 것이 중요하다. 같은 내용을 담은 두 청크 중 하나만 찾으면 답변이 가능해도 청크 Recall은 0.5일 수 있다.

08까지 실행해 검색 실패 사례를 결과로 남겼다. 그러나 정답셋 전체의 완전성 검증, 회사 단위 Recall, 자동 답변 품질 평가와 다중 홉 질문 실습까지 완료한 것은 아니다.

## 예시 / 코드

Recall 계산은 정답 ID와 검색 상위 k개 ID의 교집합을 센다.

```python
def recall_at_k(ranked_ids, gold_ids, k):
    gold = set(gold_ids)
    if not gold:
        raise ValueError("정답 근거가 비어 있습니다.")
    found = set(ranked_ids[:k]) & gold
    return len(found) / len(gold)
```
