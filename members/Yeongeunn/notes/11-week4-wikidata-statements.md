# Wikidata의 식별자·진술·근거

## 1. ‘사실 한 줄’만 저장하면 무엇을 잃나

설명용 가상 문서를 생각해보자.

> 초기에 배송서비스는 A팀이 담당했다. 운영 이관 이후에는 B팀이 담당한다.

아래처럼 두 관계만 저장하면 겉으로는 충돌한다.

```text
배송서비스 ──담당 팀──▶ A팀
배송서비스 ──담당 팀──▶ B팀
```

두 팀 중 하나가 틀렸다고 바로 지우면 과거 정보를 잃는다. 필요한 것은 ‘언제의 사실인가’라는 조건이다. 또 “누가 그렇게 주장했는가”, “무슨 문서를 근거로 했는가”도 필요하다.

Wikidata는 단순 속성–값뿐 아니라 한정어·출처·순위를 포함하는 진술을 관리한다. 이 구조를 통해 값이 여러 개인 이유와 적용 맥락을 보관할 수 있다. [Statements](https://www.wikidata.org/wiki/Help:Statements)

## 2. Q와 P: 표시 이름을 식별자로 쓰지 않는다

Wikidata의 항목은 Q로 시작하는 ID, 속성은 P로 시작하는 ID로 식별한다. 예를 들어 대한민국은 Q884, 수도 속성은 P36이다. 같은 항목의 표시 이름은 언어에 따라 달라도 ID는 같다. [Wikidata SPARQL 튜토리얼](https://www.wikidata.org/wiki/Wikidata:SPARQL_tutorial)

프로젝트에 옮기면 ‘배송서비스’라는 한국어 이름과 `shipping-service`라는 코드명을 같은 ID의 별칭으로 관리할 수 있다. 하지만 이름이 비슷하다고 자동으로 같은 항목인 것은 아니다. 먼저 대상을 식별하는 기준이 필요하다.

회사 자료를 Wikidata에 공개하거나 반드시 Q번호를 부여하자는 뜻은 아니다. 여기서는 **표시 이름과 안정적인 식별자를 분리하는 설계 원리**를 배운다.

## 3. Claim과 Statement: 값에 맥락을 붙인다

Wikibase의 용어를 간단히 정리하면 claim은 주요 속성–값과 한정어를 담고, statement는 여기에 출처와 순위까지 갖춘 진술이다. 화면이나 설명 문서에서 용어가 느슨하게 사용되기도 하므로 구현할 때는 해당 데이터 모델을 확인한다. [Wikidata 용어집](https://www.wikidata.org/wiki/Wikidata:Glossary)

프로젝트용 가상 진술을 펼치면 다음과 같다.

```text
대상: 배송서비스
주요 관계: 담당 팀 → A팀
한정어: 적용 종료 시점 → 운영 이관 시점
출처: 담당 이관 회의록, 관련 청크
순위: 일반
```

단순한 엣지 하나에 무엇이 빠졌는지 드러난다. 실무에서는 이것을 관계 속성으로 저장할 수도, 진술 노드를 만들 수도 있다. 관계에 조건·출처가 많아지면 독립적인 진술 ID가 변경 이력과 검토를 관리하기에 편할 수 있다.

## 4. 한정어: 언제·어떤 조건에서 성립하는가

한정어는 주요 진술의 범위를 구체화한다. 재직 기간, 측정 시점, 적용 위치처럼 값만으로 전달되지 않는 맥락을 담는다. [Qualifiers](https://www.wikidata.org/wiki/Help:Qualifiers)

가상 프로젝트에서는 다음처럼 생각할 수 있다.

| 주요 진술 | 추가로 필요한 맥락 |
|---|---|
| 배송서비스의 담당 팀은 A팀이다 | 어느 기간의 담당인가? |
| 이 API의 제한 횟수는 10이다 | 어떤 버전·어떤 시간 단위인가? |
| 이 정책은 결제를 차단한다 | 어떤 사용자·상태에서 적용되는가? |

모든 조건을 자유로운 문자열로 붙이면 질의하기 어렵다. 기간·버전·상태 등 반복해서 쓰는 조건은 어떤 자료형과 의미로 저장할지 합의해야 한다. 여러 한정어의 결합 의미도 설계 없이 자동으로 해석되는 것은 아니다.

## 5. 출처: 진실 인증서보다 검토 가능한 근거

출처는 진술을 지지하는 자료를 가리킨다. Wikidata는 진술의 참고문헌·웹 출처 등을 구조화해 기록할 수 있다. [Sources](https://www.wikidata.org/wiki/Help:Sources)

프로젝트에서는 `문서 ID + 버전 + 청크 ID + 인용문`으로 구체화할 수 있다. 생성 모델 이름만 저장하는 것은 원문 근거를 대신하지 못한다. 모델은 진술을 만든 도구이고, 원문은 그 진술을 검사할 자료다.

출처가 있다고 항상 참인 것은 아니다. 폐기된 설계 문서이거나 인용문이 관계를 지지하지 않을 수 있다. 따라서 출처의 존재 여부와 근거의 적절성은 따로 평가한다.

## 6. 순위: 정답 확률과 구분한다

Wikidata 진술의 rank는 preferred·normal·deprecated로 구분된다. 특정 속성의 진술 중 어떤 것을 우선 사용하거나 사용을 피할지 나타낸다. 검색 결과의 1위·2위나 모델의 confidence 0.9와는 다른 개념이다. [Ranking](https://www.wikidata.org/wiki/Help:Ranking)

예전 담당 팀은 과거 시점의 정확한 정보일 수 있으므로 오래됐다는 이유만으로 deprecated라고 보면 안 된다. 현재 값을 우선 표시하고 과거 값도 보존하는 식의 사용이 가능하다. 구체적인 순위 기준은 데이터와 공동체의 규칙에 따라야 한다.

프로젝트에 그대로 복사하기보다 검토 상태와 유효 기간을 분리하는 편이 명확할 수 있다.

```text
review_status: 미검토 / 승인 / 반려
valid_from, valid_to: 사실의 적용 기간
source_version: 원문 버전
```

‘검토자가 승인함’과 ‘현재에도 유효함’은 서로 다른 상태다.

## 7. 직접 관계 조회가 맥락을 생략하는 이유

Wikidata에서 `wdt:` 경로는 직접 관계로 간단히 조회하기 좋지만, 한정어와 출처를 함께 다루려면 진술 노드를 거쳐야 한다. 직접 관계는 rank를 반영한 truthy 진술을 제공한다. preferred가 있으면 이를 사용하고, 없으면 normal을 사용하는 방식이며 deprecated는 제외된다. ‘truthy’라는 명칭이 현실의 진실을 보증하는 것은 아니다. [SPARQL 튜토리얼의 진술·순위 설명](https://www.wikidata.org/wiki/Wikidata:SPARQL_tutorial)

아래는 대한민국의 수도 진술을 노드로 조회하는 예제다. 실행 결과를 기록한 것은 아니다.

```sparql
PREFIX wd: <http://www.wikidata.org/entity/>
PREFIX p: <http://www.wikidata.org/prop/>
PREFIX ps: <http://www.wikidata.org/prop/statement/>
SELECT ?statement ?capital WHERE {
  wd:Q884 p:P36 ?statement .
  ?statement ps:P36 ?capital .
}
```

첫 패턴은 수도 ‘값’ 대신 해당 진술을 찾고, 다음 패턴은 그 진술의 값을 찾는다. 이제 진술 노드에 붙은 한정어·출처를 추가로 조회할 발판이 생긴다.

## 8. 추출 파이프라인에 적용할 질문

Wikidata 전체 구조를 구현할 필요는 없다. 다음 질문을 작은 그래프 설계에 적용하는 것부터 시작한다.

1. 같은 대상을 이름이 아닌 ID로 연결하는가?
2. 관계가 적용되는 버전·시점·조건을 잃지 않는가?
3. 원문이 바뀌어도 어떤 자료에서 뽑았는지 확인할 수 있는가?
4. 상충하는 두 진술을 하나로 덮어쓰지 않고 검토할 수 있는가?
5. 사람이 승인한 상태와 모델의 자신감, 사실의 현재 유효성을 구분하는가?

이 주제의 핵심은 ‘더 많은 관계를 추출하기’에서 **‘추출한 관계를 설명하고 검토할 수 있게 만들기’**로 관심을 넓히는 것이다. 모델을 바꾸기 전에 데이터 구조에서 해결해야 할 문제를 볼 수 있다.
