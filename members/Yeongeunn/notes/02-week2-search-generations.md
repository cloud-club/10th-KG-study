# 검색 방식과 데이터 저장 구조

> 문자열 검색은 같은 표현을, BM25는 중요한 단어의 일치를, 벡터 검색은 학습된 표현 공간에서의 가까움을 이용한다. 어느 방식도 모든 질문에서 항상 우세하지 않다.

## 같은 질문에 서로 다른 기준을 적용한다

가상 문서에 “발송 전 주문은 취소할 수 있다”가 있다고 하자. “발송 전”이라는 문자열은 쉽게 찾을 수 있지만, “아직 보내지 않은 물건을 취소하려면?”에는 표현 차이가 있다.

| 방식 | 저장·준비 | 찾는 기준 | 강점 | 놓칠 수 있는 것 |
|---|---|---|---|---|
| grep 고정 문자열 | 텍스트 파일 | 지정한 문자열의 포함 여부 | 식별자·오류 문구 확인, 작은 기준선 | 다른 표현, 관련도 순위 |
| BM25 | 토큰화와 역색인 | 질문 토큰과 문서 토큰의 일치 점수 | API 이름·전문 용어·고유명 | 동의어, 생략된 표현 |
| 벡터 | 청크와 임베딩 | 벡터 간 유사도 | 의미가 비슷한 다른 표현 | 정확한 숫자·부정·버전 차이 |

`grep`은 정규식 검색도 지원한다. 여기서 비교할 기준선은 `grep -F`에 해당하는 고정 문자열 매칭으로 명시한다. 질문 전체를 그대로 매칭하는지, 단어별 OR인지에 따라 결과가 다르므로 평가 시 규칙을 고정해야 한다.

### grep으로 찾으면 무엇이 달라질까

설명용 문서에 다음 두 문장이 있다고 하자.

```text
문서 A: 발송 전 주문은 취소할 수 있다.
문서 B: 아직 보내지 않은 상품은 철회할 수 있다.
```

`grep -F '취소'`는 A를 찾지만 B는 찾지 못한다. B도 관련 내용이지만 글자가 다르기 때문이다. 여러 파일이 일치해도 grep 자체는 질문과 관련성이 높은 순서로 정렬해주지 않는다.

```bash
# 로컬 Markdown에서 고정 문자열을 찾는 명령 예시
find data/Yeongeunn/raw/Erumpay_notion -type f -name '*.md' -exec grep -nH -F '검색어' {} +
```

BM25는 토큰 일치에 점수를 매기고, 벡터 검색은 표현이 다른 문장을 찾는 데 도움을 줄 수 있다. 다만 정확한 식별자를 찾는 상황에서는 단순 문자열 검색도 유용하다.

## 역색인과 TF-IDF, BM25

일반 목록이 “문서 → 들어 있는 단어”라면 역색인은 “단어 → 그 단어가 있는 문서”다. 질문 토큰으로 후보를 빨리 찾고, 그 후보에 점수를 매긴다.

TF는 문서에서 단어가 등장한 빈도, IDF는 많은 문서에 흔한 단어의 영향력을 줄이는 가중치다. TF-IDF는 이 둘을 조합한다. [Stanford IR 교재](https://nlp.stanford.edu/IR-book/html/htmledition/tf-idf-weighting-1.html)

BM25는 단어 빈도가 늘 때 점수가 무한히 선형 증가하지 않도록 포화시키고, 문서 길이도 보정한다. 대표적인 한 항은 다음과 같다.

```text
IDF(t) × tf(t,d) × (k1+1)
         / (tf(t,d) + k1 × (1-b+b×문서길이/평균문서길이))
```

질문 토큰별 기여를 합한다. 실제 점수는 엔진의 IDF 정의·분석기·필드·쿼리 방식에도 의존한다. Elasticsearch BM25 기본값은 `k1=1.2`, `b=0.75`이며, 현재 코드에서는 기본값을 따르고 `title`, `content`를 `multi_match`로 검색한다. 점수 20은 정답 확률 20%가 아니다. [Elasticsearch similarity](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

## 한국어에서는 토큰을 어떻게 만들지가 중요하다

- 형태소 분석: 조사·어미 등 언어 구조를 고려해 검색 토큰을 만든다. Elasticsearch의 nori를 현재 기준선으로 사용한다.
- 문자 n-gram: 연속된 n개 문자를 토큰으로 만든다. 붙여쓰기·일부 표기 변형에 도움이 될 수 있지만 토큰 수와 불필요한 일치가 늘 수 있다.

nori가 모든 띄어쓰기 오류를 고쳐주는 것은 아니다. 서비스명·영문 약어·경로처럼 도메인 고유 표현은 실제 분석 결과를 확인해야 한다. 이후 동일 질문으로 nori와 n-gram을 비교하되 지금은 비교 결과가 없다. [nori 공식 문서](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori)

### 형태소와 n-gram 예시

`배송조회`를 문자 2-gram으로 나누면 `배송`, `송조`, `조회`가 된다. `송조`처럼 사전에 없는 조각도 생긴다. 형태소 분석은 언어적인 단위를 찾는 접근이고, n-gram은 일정 길이의 문자 조각을 만드는 접근이다. Nori의 실제 결과는 사전과 복합어 처리 설정에 따라 달라지므로 분석 API로 확인한다.

Nori 내부에서 쓰는 문맥 모델의 bigram과, 검색용 문자열을 두 글자씩 자르는 bigram 토큰화도 같은 뜻은 아니다.

## 임베딩, 코사인 유사도, HNSW

임베딩 모델은 텍스트를 숫자 벡터로 변환한다. 검색에서는 문서와 질문에 호환되는 임베딩 설정을 사용한다. 모델에 따라 질문·문서 전용 접두어나 인코더가 필요할 수 있다.

`cosine(q,d) = (q·d) / (||q|| ||d||)`는 두 벡터의 방향이 얼마나 비슷한지 측정한다. 높은 유사도가 사실의 일치나 최신 버전임을 보장하지 않는다.

pgvector는 PostgreSQL에서 벡터를 저장하고 검색하게 해주는 확장이다. 청크와 질문은 임베딩 모델로 벡터화한다. 처음에는 정확 검색으로 기준선을 만들고, 데이터가 커져 지연이 문제가 되면 근사 검색을 비교한다. [pgvector](https://github.com/pgvector/pgvector)

HNSW는 가까운 벡터 사이의 연결을 계층적으로 구성해 후보를 탐색하는 근사 최근접 이웃 인덱스다. 속도·메모리·최근접 이웃 회수율 사이의 절충이 있다. 여기의 “그래프”는 서비스가 어떤 API를 호출한다는 의미 관계 그래프와 다르다. [HNSW 논문](https://arxiv.org/abs/1603.09320)

### 코사인 유사도 계산 예시

방향만 비교한다는 뜻을 보기 위해 가상 2차원 벡터를 사용한다.

```text
질문 q = [1, 0]
문서 A = [2, 0] → 코사인 유사도 1
문서 B = [0, 1] → 코사인 유사도 0
```

A는 길이가 두 배지만 방향이 같아서 유사도가 1이다. B는 질문과 직각이어서 0이다. 실제 임베딩은 더 많은 차원을 사용하며, 유사도 값은 모델이 학습한 표현의 가까움이지 정답 확률은 아니다.

### HNSW에서 계층을 두는 이유

문서 벡터를 전부 비교하면 데이터가 늘수록 계산할 대상도 늘어난다. HNSW는 상위 계층의 적은 연결로 대략적인 위치를 찾고, 아래 계층으로 내려가 주변 후보를 더 자세히 탐색한다. 큰 지도에서 구역을 찾은 다음 동네 지도를 보는 것에 비유할 수 있다.

모든 후보를 확인하지 않으므로 더 가까운 벡터를 놓칠 수 있다. 탐색 범위를 늘리면 보통 근사 정확도를 높일 수 있지만 계산량도 늘어난다. [HNSW 설명과 탐색 그림](https://www.pinecone.io/learn/series/rag/hnsw/)

## 저장 구조와 현재 구현

| 대상 | 현재 | 다음 단계 |
|---|---|---|
| 원본 파일 | 로컬 Markdown | 스냅샷 해시·export 시점 관리 |
| PG 청크 | id, page_id, title, source, start, content | content_hash, 문서 버전, 파서 버전 |
| ES | 같은 청크의 title/content를 nori+BM25로 색인 | 분석기·중복 처리 비교 |
| pgvector | 미구현 | chunk_id, embedding, 모델·차원·설정 기록 |

문서 경로 해시를 ID로 쓰는 현재 방식은 경로가 바뀌면 새 문서가 된다. 동일 내용의 복제 문서도 별개다. 임베딩 캐시를 만들 때에는 내용 해시와 모델 버전을 함께 키로 사용하되 원본별 출처는 잃지 않도록 한다.

## DDIA 3장과 연결하기

| 구조·개념 | 이해할 핵심 |
|---|---|
| 해시 인덱스 | 키로 위치를 찾는 데 적합하지만 범위 검색은 별도 고민 |
| SSTable·LSM | 정렬된 파일과 병합으로 쓰기·읽기 비용을 조정 |
| B-tree | 정렬된 키 탐색과 범위 조회에 적합 |
| 역색인 | 용어에서 문서 후보를 찾는 구조 |
| 전문 검색 | 토큰·위치·빈도 등으로 문서 후보를 찾고 순위를 계산 |
| 퍼지 검색 | 편집 거리 등으로 철자 차이가 있는 후보 탐색 |
| OLTP / OLAP | 작은 거래의 처리와 대량 분석의 접근 패턴 차이 |

PostgreSQL은 B-tree만 제공하지 않고 GIN 등 여러 인덱스를 지원한다. Elasticsearch/Lucene의 세그먼트와 병합을 LSM과 비교할 수는 있지만 모든 내부 구조가 동일하다는 뜻은 아니다. “PG 대 ES”라는 제품 대결보다 **이 쿼리가 어떤 인덱스를 이용하는가**를 묻는다. [PostgreSQL 인덱스 종류](https://www.postgresql.org/docs/current/indexes-types.html)

## 토큰과 청크: 잘게 읽는 단위와 검색에 묶어 두는 단위

**토큰은 모델의 토크나이저가 텍스트를 처리하는 단위**, **청크는 우리가 검색·전달할 문맥을 묶은 단위**다. 청크 안에 여러 토큰이 들어간다. 청크를 만든다는 것과 임베딩을 계산한다는 것도 다른 작업이다.

가상 문서가 다음 세 문장이라고 하자.

```text
① 발송 전에는 주문을 취소할 수 있다.
② 발송 후에는 취소할 수 없으며 반품 절차를 안내한다.
③ 결제 수단에 따라 환급 일정이 다르다.
```

①만 청크로 만들면 “발송 후에는?”이라는 질문에 필요한 예외가 빠진다. ①②를 함께 묶으면 취소 조건을 설명할 문맥이 생긴다. 문서 전체를 한 청크로 만들면 다른 주제까지 섞여 검색 초점이 흐려질 수 있다.

모델에 ①②를 넣을 때 내부적으로는 더 작은 토큰으로 분할한다. 이해를 위한 모형으로 `[발송][ 전][에는]…`처럼 그릴 수 있지만, **이는 실제 모델의 토큰 분할 결과가 아니다.** 한국어 음절·단어·공백 수로 토큰 수를 정확히 계산할 수 없고, 모델의 토크나이저에 따라 달라진다. [Gemini 토큰 설명](https://ai.google.dev/gemini-api/docs/tokens)

| 작업 | 결과 | 담당 |
|---|---|---|
| 청킹 | 문맥을 가진 텍스트 묶음 | 현재 Python 파서 |
| 토큰화 | 모델 입력 단위와 ID | 해당 모델의 토크나이저 |
| 임베딩 | 검색에 비교할 숫자 벡터 | 임베딩 모델 |
| DB 적재 | 텍스트·메타데이터·선택적으로 벡터 저장 | DB와 적재 코드 |

현재 코드는 토큰을 세어 자르지 않는다. 정제한 Python 문자열을 `text[start:start+1200]`으로 나누며, 다음 시작은 1,000자 뒤다.

```text
청크 1: 문자 위치 0~1199
청크 2: 문자 위치 1000~2199
겹치는 부분: 1000~1199, 최대 200자
```

마지막 청크는 더 짧을 수 있다. 1,200자는 1,200토큰이 아니며 글자 수가 같아도 모델 입력 토큰 수는 다를 수 있다. 겹침은 경계의 문맥 손실을 줄이지만 저장량·임베딩 계산량·중복 검색도 늘린다.

다음에는 제목·문단·표·코드 경계를 우선 유지하고, 임베딩 모델의 최대 입력 토큰 수 안에 들어가는지 확인한다. 생성 모델에는 **시스템 지시 + 질문 + 여러 근거 청크**가 함께 들어가므로 청크 하나의 길이만 확인해서는 부족하다.

## PostgreSQL과 Elasticsearch에 실제로 무엇이 들어갔나

**pgvector는 PostgreSQL에서 벡터를 저장하고 검색하는 확장**이다. [pgvector 공식 저장소](https://github.com/pgvector/pgvector)

다음 가상 청크를 저장한다고 생각하면 된다.

```json
{
  "id": "demo-document:0",
  "page_id": "demo-document",
  "title": "주문 취소 조건",
  "source": "demo/cancel.md",
  "start": 0,
  "content": "발송 전에는 주문을 취소할 수 있다."
}
```

| 위치 | 현재 코드가 넣는 데이터 | 활용 |
|---|---|---|
| PostgreSQL `chunks` 테이블 | 위 6개 필드를 행으로 저장 | 청크·출처 관리, 이후 다른 결과와 ID로 연결 |
| Elasticsearch 문서 | 동일 JSON 필드 | 원문을 결과로 돌려주고 제목·본문을 분석해 검색 |
| ES 내부 역색인 | 분석기가 만든 용어와 문서 연결 등 | BM25 후보 검색과 점수 계산 |
| PG 벡터 컬럼 | 현재 없음 | 이후 임베딩 저장 시 의미 검색에 사용 예정 |

Elasticsearch에 “단어만 들어 있고 원문은 PG에서 꺼낸다”는 구조가 아니다. 현재 코드는 ES의 `_source`에서 본문·출처를 읽는다. `_source`는 색인 시 제공한 JSON을 보관하는 필드다. [Elasticsearch `_source`](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field)

현재 질문 경로는 **질문 → ES → 선택한 본문 → Gemini**이며 PG를 읽지 않는다. PG는 적재·보관 경로에 있다. 같은 청크를 두 곳에 둔 이유는 스터디의 저장·검색 구조를 나누어 관찰하고, 다음 단계의 벡터·관계 데이터와 ID로 연결하기 위해서다. 실제 서비스에서 이 두 제품이 항상 필수라는 뜻은 아니다.

임베딩을 추가한다면 PG에 `chunk_id`, `embedding`, `embedding_model`, `content_hash` 등을 함께 관리할 계획이다. 숫자 배열만 저장하면 어떤 문서·모델에서 나온 값인지 잃는다. 모델을 바꾸면 차원이 같아도 기존 벡터와 직접 비교하지 않는다.
