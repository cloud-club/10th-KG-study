# 분담 ① 시맨틱 웹은 왜 실패했고, 지식 그래프는 왜 성공했나?

앞의 변천사에서는 Semantic Web에서 Google Knowledge Graph로 흐름이 바뀌었다는 사실을 봤다. 이번 분담에서는 역사를 다시 설명하기보다 **왜 그런 전환이 필요했는지**에 집중했다.

> **Semantic Web은 모두의 협력이 필요한 구조에서 발생하는 조정 문제를 해결하지 못했고, Knowledge Graph는 그 문제를 해결했다기보다 협력이 덜 필요한 범위로 좁혀 우회했다.**
> 

## 1. Semantic Web은 무엇에 실패했을까?

먼저 “Semantic Web은 실패했다”는 표현부터 나눠서 볼 필요가 있었다.

Semantic Web이 목표로 했던 **웹 전체의 공통 의미 체계, 공용 Ontology에 대한 폭넓은 합의, 웹 규모의 논리적 추론**은 일반적인 웹의 모습으로 자리 잡지 못했다. 하지만 모든 아이디어가 사라진 것은 아니다. 구조화 데이터는 schema.org와 JSON-LD 같은 형태로 활용되고 있고, 개체와 관계를 그래프로 표현하는 방식도 Wikidata와 여러 Knowledge Graph에 남아 있다.

즉 실패한 것은 Triple이나 구조화 자체라기보다 **웹 전체가 함께 참여하는 무거운 Semantic Web의 비전이 널리 정착하지 못한 것**에 가깝다.

> **“Semantic Web 전체가 죽었다기보다, 무거운 부분은 널리 정착하지 못했고 가벼운 구조화는 살아남았습니다.”**
> 

그렇다면 왜 무거운 부분은 널리 정착하지 못했을까?

## 2. 핵심 원인 — 누가 비용을 내고, 누가 이득을 얻는가?

Semantic Web이 제대로 동작하려면 누군가는 웹페이지의 내용을 기계가 이해할 수 있도록 구조화하고 이를 계속 관리해야 한다.

| **주체** | **역할** |
| --- | --- |
| 웹사이트 운영자 | 메타데이터를 작성하고 유지 |
| 검색엔진·Agent | 구조화된 데이터를 검색·통합·추론에 활용 |

내가 RDF를 열심히 작성해도 당장 내 서비스가 좋아진다는 보장은 없다. 오히려 그 데이터를 가져가는 다른 서비스가 더 큰 이득을 얻을 수도 있다.

> **“좋은 건 알겠는데, 내가 왜 먼저 해야 하지?”**
> 

모두가 참여하면 전체 웹의 가치는 커지지만, 개별 참여자가 먼저 비용을 부담할 이유는 약하다. Semantic Web에는 이런 **조정 문제(coordination problem)**가 있었다.

같은 웹 표준인 HTML과 비교하면 차이가 더 잘 보인다.

**HTML 작성 → 내 페이지가 제대로 보임 → 내가 바로 이득**

**Semantic Metadata 작성 → 외부 프로그램이 내 데이터를 이해함 → 생태계 전체가 이득**

이 차이는 곧 닭과 달걀 문제로 이어진다.

**구조화 데이터 부족 → 유용한 서비스 부족 → 데이터를 만들 이유 부족 → 다시 구조화 데이터 부족**

결국 기술 표준만 잘 만든다고 해결할 수 있는 문제가 아니었다.

## 3. 모두가 참여하더라도 합의 문제가 남는다

사람들이 모두 데이터를 제공한다고 해도 또 다른 문제가 생긴다. Cory Doctorow의 *Metacrap*에서 지적했던 것처럼 **같은 현실을 표현하는 방법은 하나가 아니기 때문**이다.

이번 실습에서도 비슷한 문제를 만났다. 프로젝트 경험을 그래프로 만들 때 사용한다, 도입했다, 활용했다를 각각 다른 관계로 둘 수도 있고 전부 `USES_TECHNOLOGY`로 합칠 수도 있었다. 실제 구현과 제안을 어떻게 구분할지도 정해야 했다.

결국 우리는 실험 범위를 통제하기 위해 소수의 관계만 사용하기로 했다. 하지만 이 관계들이 세상을 표현하는 유일한 정답이라서 선택한 것은 아니다.

한 사람의 데이터라면 내가 결정하면 끝난다. 웹 전체라면 **누구를 Person으로 볼 것인지, 어떤 관계를 별도로 구분할 것인지, 서로 다른 표현을 언제 같은 Entity로 합칠 것인지**에 여러 주체가 합의해야 한다.

즉 Semantic Web의 어려움은 데이터를 Triple로 표현할 수 있느냐보다 **누가 데이터를 만들고, 어떤 의미 체계에 합의할 것인가**에 더 가까웠다.

## 4. Knowledge Graph는 이 문제를 어떻게 우회했을까?

Knowledge Graph가 앞의 문제를 전부 기술적으로 해결한 것은 아니다. 대신 **문제의 범위를 바꿨다.**

| **Semantic Web의 문제** | **Knowledge Graph의 접근** |
| --- | --- |
| 여러 주체의 참여가 필요 | **한 조직**이 직접 구축하고 사용 |
| 데이터가 쌓이기를 기다려야 함 | 기존 데이터 소스를 **직접 수집·통합** |
| 웹 전체의 스키마 합의 | 서비스에 필요한 스키마를 내부에서 정의 |
| 데이터 품질 편차 | 출처와 정제 과정을 직접 관리 |
| 범용 의미 모델의 높은 비용 | 필요한 도메인과 활용 목적에 집중 |

Google Knowledge Graph가 대표적이다. Google은 웹 전체가 하나의 Ontology에 합의하기를 기다리지 않고 여러 데이터 소스를 통합해 자신들이 필요한 그래프를 만들고 검색에 활용했다.

**Google이 구축 비용 부담 → Google 검색 품질 개선 → Google이 직접 이득**

여러 참여자 사이에 있던 조정 문제 상당 부분을 **한 조직 내부의 설계 문제로 바꾼 것**이다.

> **Knowledge Graph는 모두의 협력이 필요한 문제를 한 조직이 통제할 수 있는 범위로 좁혀 우회했다.**
> 

대신 대가도 있다. 각 조직이 자기 스키마와 그래프를 만들면서 Semantic Web이 목표로 했던 **개방성과 상호운용성은 줄어들고, 다시 각자의 데이터 사일로가 생길 수 있다.**

아이러니하게도 Semantic Web은 사일로를 연결하려 했고, 기업 Knowledge Graph는 **사일로의 존재를 인정한 채 그 안에서 잘 동작하는 방식**을 선택한 셈이다.

## 5. schema.org는 왜 살아남았을까?

여기서 재미있는 반례가 schema.org다. 웹 전체의 협력이 어렵다면 왜 많은 웹사이트가 구조화 데이터를 제공할까?

차이는 **데이터를 만드는 쪽에도 직접적인 이득이 생겼다는 것**이다. 구조화 데이터를 제공하면 검색엔진이 상품, 리뷰, 이벤트 같은 정보를 더 정확히 이해하고 검색 결과의 풍부한 표현에 활용할 수 있다.

**구조화 데이터 작성 → 검색엔진이 이해 → 내 콘텐츠의 검색 경험에도 이점**

이 사례는 오히려 앞의 주장을 강화한다. Semantic Web의 구조화 아이디어 자체가 불가능했던 게 아니라, **참여자가 비용을 낼 이유가 생기면 구조화 데이터 생태계도 작동할 수 있다.**

## 6. 이 문제를 우리도 다시 만나게 된다

현재 개인 문서만 그래프로 만드는 단계에서는 조정 문제가 거의 없다.

**내 문서 → 내가 정한 관계 → 내 그래프**

스키마 합의 대상이 사실상 한 명이기 때문이다.

하지만 이후 여러 스터디원의 데이터를 하나의 그래프로 합치면 상황이 달라진다. 누군가는 `USES_TECHNOLOGY`, 다른 사람은 `USES`라고 부를 수 있다. `Spring`, `Spring Boot`, `SpringBoot`를 같은 Entity로 볼지도 결정해야 한다. 같은 사람이 여러 이름으로 등장하면 Entity Resolution도 필요하다.

**여러 사람의 데이터 → 공통 관계 합의 → Entity 통합 → 공통 Graph**

결국 Semantic Web이 웹 규모에서 만났던 **스키마 합의와 Entity Resolution 같은 조정 문제를 우리는 작은 스터디 규모에서 다시 만나게 된다.**

그래서 이후 커리큘럼에 공통 스키마를 합의하는 과정이 따로 있는 이유도 이해할 수 있었다.

## 결론 : 해결한 게 아니라, 우회했다

처음에는 “Semantic Web은 실패했고 Knowledge Graph가 그다음 기술이다” 정도로 생각했다.

하지만 둘은 완전히 다른 아이디어라기보다 **개체와 관계를 구조화한다는 비슷한 아이디어를 서로 다른 범위와 운영 방식으로 구현한 것**에 가까웠다.

Semantic Web은 웹 전체가 공통된 의미 체계로 연결되는 것을 목표로 했고, 그만큼 여러 참여자의 합의와 지속적인 데이터 제공이 필요했다. Knowledge Graph는 이 문제를 완전히 해결하지 않고 **도메인을 좁히고 한 조직이 데이터와 스키마를 통제하는 방식으로 우회했다.**

> **Semantic Web은 모두가 함께해야 가치가 생기는 구조의 조정 문제를 풀지 못했고, Knowledge Graph는 모두의 합의를 기다리지 않아도 되는 범위로 문제를 좁혀 실제 서비스에 적용했다.**
> 

그리고 여러 사람의 데이터를 하나로 합치는 순간 우리가 우회했던 합의의 문제가 다시 등장한다. 결국 Knowledge Graph에서는 그래프를 만드는 기술뿐 아니라 **어떤 Entity와 관계를 공통으로 사용할지 합의하는 과정 자체도 중요한 문제**다.
