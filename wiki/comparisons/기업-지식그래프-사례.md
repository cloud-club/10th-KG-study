> 웹 전체의 합의를 기다리지 않고 한 조직이 범위를 좁혀 KG를 만든 사례들. heebindev가 Google·Amazon·Apple을, Yeongeunn이 거기에 Amazon COSMO·LinkedIn·Siemens·AstraZeneca를 더해 1차 자료로 비교했다. 공통점은 "사용자가 말한 대상이 무엇이고 다른 대상과 어떤 관계가 있는지 파악하기 위해"(heebindev)이고, 공통 과제는 **식별자 정리 / 관계의 의미 합의 / 근거·품질 관리 / 변경 반영**(Yeongeunn)이다. 사례마다 "무엇을 보장하지 않는지"를 함께 적는다. Palantir는 [[Palantir-Foundry-Ontology]].

## 비교표

| 조직 | 주요 대상 | KG가 돕는 일 | 누가 |
|---|---|---|---|
| **Google** (2012, "things, not strings") | 웹의 사람·장소·사물 | 동명 대상 구분(타지마할 = 건축물·음악가·카지노·식당, Jaguar = 자동차·동물), 주요 사실 요약, 관계로 관련 정보 제시, 다음에 궁금해할 대상 연결. Wikipedia·Freebase 직접 통합 | heebindev, do-dop, dldusgh318, e0ng |
| **Amazon AutoKnow** | 상품 (수천 종류, 판매자 표현이 제각각) | 상품 분류체계·속성 자동 발견. 동일·유사 상품 구분, 판매자별 속성 정리, 검색·추천 관계 생성, 누락·이상 정보 탐지. "속성 추출·단위 정규화가 틀리면 구조화된 결과도 틀리므로 검증이 필요" | heebindev, Yeongeunn |
| **Amazon COSMO** | 검색–구매·함께 구매 데이터 | **사용 목적 관계 후보를 LLM으로 생성** → 사람 라벨링 + ML 필터링 + 재반영. "함께 구매됐다는 사실이 특정 구매 이유를 증명하지는 않으므로 모델이 생성한 관계를 곧바로 사실로 취급해서는 안 된다" | Yeongeunn |
| **LinkedIn** | 회원·채용공고·직함·스킬·회사 | 후보 생성 → 의미 구분 → 중복 제거 → 사람 검증. **사용자가 입력한 관계와 모델이 추정한 관계를 구분**, "직접 입력한 정보 역시 오류가 있을 수 있다" | Yeongeunn |
| **Siemens** | 설계 변경 → 부품 → 제품 → 제조·서비스 기록 | 변경 영향 추적. "공개된 접근과 시나리오이지 기업 전체에서 검증된 성과라는 뜻이 아니다." 전제: 부품 버전·시스템별 코드·갱신 시점 정합 | Yeongeunn |
| **AstraZeneca · Elsevier** | 암 후성유전학 표적 | 문헌 기반 맞춤 KG. "문헌의 연관성이 인과관계나 임상 효과를 보장하지 않는다" | Yeongeunn |
| **Apple** (Saga) | 가상 비서 질의의 엔티티 | 엔티티 연결, 사실 순위·검증, 관련 엔티티 탐색. **heebindev는 단정을 피했다** — "Apple이 Siri의 전체 지식 구조를 공개한 것은 아니므로 'Siri가 특정 KG 하나로 동작한다'고 단정하기 어렵다." 공개 연구에서 확인되는 것만 적음 | heebindev |
| **기업 KG 일반** | 고객·주문·배송·문의 | "배송이 지연된 주문을 한 고객은 누구인가" = 역방향 2-hop (`배송지연 ◀상태─ 주문 ◀주문함─ 고객`) | e0ng |
| **Palantir Foundry Ontology** | 조직의 운영 객체 | Object · Link · **Action**. 조회에서 실행으로 → [[Palantir-Foundry-Ontology]] | kdyann, do-dop, e0ng, dldusgh318, Yeongeunn, kungbi |

## 갈리는 지점

- **왜 기업 KG는 되고 시맨틱 웹은 안 됐나**: do-dop의 5행 대조(웹 전체↔특정 도메인, 다조직 합의↔한 조직 통제, 범용 추론↔명확한 목적, 공개 표준↔내부 ID 허용, 보편 의미↔측정 가능한 가치). dldusgh318은 유인 구조로 설명한다 — `Google이 구축 비용 부담 → Google 검색 품질 개선 → Google이 직접 이득`. 대가는 개방성·상호운용성 감소와 사일로의 재등장 → [[시맨틱-웹에서-지식그래프까지]].
- **LLM이 만든 관계는 후보다**: COSMO·LinkedIn의 "모델이 생성한 관계를 곧바로 사실로 취급하지 않는다"는 스터디 5주차 실습(kdyann·Yeongeunn·dldusgh318)이 각자 도달한 "검토 전 후보" 규율과 같은 결론이다 → [[LLM-트리플-추출]]. Google 사례의 "동명이인을 합치면 잘못된 사실도 함께 붙는다"는 [[엔티티-신원해소]].
- "KG를 사용한다는 사실만으로 모든 기업이 같은 DB나 RDF/OWL을 쓴다고 볼 수는 없다" (Yeongeunn).
- **GraphRAG 그래프는 기업 KG가 아니다** (do-dop): 문서에서 자동 생성·재생성 가능한 검색 인덱스 vs 식별자·출처·시점·품질을 지속 관리하는 지식 기반 → [[RAG-변천사]].
- 자료 신뢰: heebindev가 Apple 사례에서 비공개 영역을 추정으로 채우지 않은 태도는 이 위키의 "인용과 정직" 규칙과 같다. 반면 dldusgh318·e0ng의 기업 사례 서술은 1차 자료 URL이 없다(아래 출처는 heebindev·do-dop readings).

## 열린 질문

- 공개 자료만으로 각 기업의 저장 구조·질의 경로를 확정할 수 없다(heebindev·Yeongeunn 둘 다 명시). 스터디가 실제로 쓸 수 있는 것은 "LLM 생성 관계 = 후보"와 "이름 유사성 ≠ 동일성"이라는 두 규율이다.
