> 지식그래프·검색에 넣을 데이터를 모을 때 "이 사실은 어느 원본의 어느 시점에서 왔는가"를 되짚을 수 있게 설계하는 문제. kungbi의 수집 실습 설계와, 카카오톡 실습들이 각자 도달한 "정본과 파생물 분리" 원칙을 모은다.

## kungbi의 수집 계약 (설계, 미구현)

- 목표는 무작정 많이 모으는 게 아니라 작은 공개 데이터 하나로 **수집 → 원문 보존 → 정규화 → 관계 생성 → 근거 확인** 경로를 검증하는 것. 첫 대상은 공개 Git 저장소 1개 — commit SHA와 blob ID라는 안정적 식별자가 있고, 이력을 로컬에서 재현할 수 있고, Slack·Notion·AWS보다 개인정보·인증정보 통제가 쉽다.
- **수집 계약** 항목: source, scope, native ID, `observed_at`(수집기가 실제로 관측한 시각), redaction 규칙, `completeness`(complete / partial / denied / error).
- 저장 계층 분리: 원문 payload → 현재 commit/file 상태 → commit과 변경 이력 → 검색용 document/chunk → `commit -[CHANGED]-> file` 관계. **PostgreSQL을 canonical source로 두고 graph DB와 vector index는 언제든 다시 만들 수 있는 projection으로 취급한다.**
- provenance 경로: file relation → commit → ingestion run → source payload → 실제 diff. 성공 기준은 관계가 존재하는 것만이 아니라 **관계를 만든 근거와 관측 시점까지** 확인되는 것.
- 멱등성: payload가 같으면 같은 hash로 판별, 값이 바뀌면 현재 상태를 갱신하고 이전 관측은 이력으로 남긴다. 순서는 **Backfill → Enrichment → Incremental → Reconciliation**. 실시간 이벤트보다 정확한 backfill을 먼저 만들어야 누락·중복이 보인다.
- 검증 표 6항목: 재현성, 멱등성, 완전성(성공·부분·권한 거부·실패 구분), provenance(정규화한 사실에서 원문과 diff로 복귀), 관계 질의, 개인정보(비공개 원문·토큰·계정 식별자 미포함).
- 확장 단위: Slack = channel → thread → message → revision, Notion = data source → page → block tree → revision, GitHub = PR → review → commit → diff, AWS = account → resource → observation.
- 2026-09-12 기준 상태: 수집 대상·저장 계층·수집 순서 설계와 17장 발표 자료 완료, **Git fixture 수집·PostgreSQL 적재·증분 수집·검색/그래프 평가는 미구현.** kungbi는 "아직 실행하지 않은 환경을 완료된 구성처럼 기록하지 않는다"는 규율을 문서에 적어 두었다.

## 카카오톡 실습들이 도달한 같은 원칙

- lys0611: `messages`(원문 1건 1행)가 **정본**이고 `chunks` → `chunk_embeddings` / ES 인덱스는 언제든 다시 만들 수 있는 **파생물**. 같은 파일을 다시 넣어도 `(room_id, seq)`·`content_hash` 유니크로 중복되지 않는다. 가명화를 임베딩 **앞**에 두어 파생물을 공개할 수 있게 했다 → [[개인-데이터-가명화와-공개-범위]].
- sese2204: `kakao.rooms.source_file` 기준으로 방을 upsert하고 기존 메시지를 지운 뒤 COPY. 같은 파일 재적재 시 방 1개, 메시지 수 동일, `(room_id, seq)` 중복 0. 원본 txt에는 초 단위가 없어 같은 분 안의 순서를 `seq`로, 파싱 검증용으로 원본 줄 번호 `line_no`를 함께 저장한다.
- 이 셋은 표현이 다를 뿐 같은 원칙이다: **원문은 불변으로 한 번 저장하고, 검색용 구조는 파생물로 재생성 가능하게, 재적재는 멱등하게.** 이 위키의 세 층(`members/` 불변 소재 → `wiki/` 파생)도 같은 구조다([[LLM-위키-패턴]]).

> ⚠️ Contradiction: kungbi의 "PostgreSQL 단일 정본 + projection" 모델과 sunghyun의 "pgvector 경로와 Neo4j 경로 병렬" 모델은 정본 개념이 다르다. [[지식그래프와-온톨로지]] §저장소 아키텍처 참조.
