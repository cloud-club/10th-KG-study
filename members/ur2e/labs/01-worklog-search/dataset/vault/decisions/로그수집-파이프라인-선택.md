# 로그 수집은 Fluent Bit DaemonSet 으로

## 배경

노드 로그를 중앙으로 모으는데 사이드카 방식과 DaemonSet 방식 중에 고민했다.

## 결정

Fluent Bit DaemonSet. 사이드카는 Pod 마다 컨테이너가 하나씩 늘어나서 리소스 오버헤드와 관리 대상이 같이 늘어난다.

## 근거

- 노드당 하나면 설정 변경 지점이 한 곳이다.
- 애플리케이션 Pod 스펙을 건드리지 않아도 된다.
- 다만 애플리케이션별로 파서를 다르게 주기 어렵다. 이건 감수했다.

## 이후 변경 (2026-06)

**이 결정은 뒤집혔다.** control-plane 노드 메모리 압박 원인을 추적하다가 수집 에이전트 메모리 사용량도 원인 후보로 올라왔다 ([[INC-007-apiserver-oom-restart]]). DaemonSet 자체가 문제였다는 뜻은 아니고, 노드에 뜨는 에이전트마다 메모리 상한을 안 걸어둔 게 문제였다.

지금은 리소스 상한을 명시한 상태로 같은 방식을 유지한다. 문서 status 는 `superseded` 로 두고 상한 값은 별도 관리한다.

기록 목적으로 남겨둔다. **지운 게 아니라 왜 바뀌었는지가 필요해서 남긴 문서다.**
