# 03. RRF와 RAG 루프

## 점수 정규화

서로 다른 범위의 점수를 일정한 범위로 변환

<details>
<summary>정규화 종류</summary>

<br>

| 방법 | 방식 | 특징 |
|---|---|---|
| **Min-Max Normalization** | 최솟값→0, 최댓값→1로 변환 | 직관적이고 간단하지만 최댓값·최솟값에 민감 |
| Z-score Standardization | 평균을 0, 표준편차를 1로 변환 | 점수가 평균에서 얼마나 떨어졌는지 표현 |
| Softmax | 점수를 확률처럼 변환 | 높은 점수를 상대적으로 더 강조 |
| L2 Normalization | 전체 벡터의 크기를 1로 맞춤 | 점수들의 상대적인 크기를 유지하면서 스케일 조정 |

</details>

### 예시: BM25와 코사인 유사도

| 문서 | BM25 점수 | 코사인 유사도 |
|---|---:|---:|
| A | 20 | 0.7 |
| B | 10 | 0.9 |
| C | 5 | 0.8 |

| 문서 | BM25 정규화 | Vector 정규화 | 합산 |
|---|---:|---:|---:|
| A | 1.00 | 0.00 | 1.00 |
| B | 0.33 | 1.00 | 1.33 |
| C | 0.00 | 0.50 | 0.50 |

### 정규화의 한계

- 점수의 범위 Scale을 맞춤 ✅
- 서로 다른 검색 알고리즘 점수의 의미와 분포 반영 ❌

#### 예시: 순위별 분포가 다른 경우

```text
A 검색 알고리즘 [100, 99, 98] → [1.0, 0.5, 0.0]
B 검색 알고리즘 [100, 50, 0] → [1.0, 0.5, 0.0]
```

**문제점**

- A 검색 알고리즘 : 순위 간 점수가 거의 유사
- B 검색 알고리즘 : 순위 간 점수 차이 매우 큼

→ 각 결과의 점수 관계가 다르지만 정규화 이후 동일한 형태로 표현됨

#### 예시: 특정 검색 알고리즘 결과에 극단적인 점수가 포함된 경우

```text
[100, 10, 9, 8] → [1.000, 0.022, 0.011, 0.000]
```

**문제점**

극단값을 제외한 나머지 값들이 좁은 구간에 몰리게 됨

## RRF

**Reciprocal 상호 간의 + Rank 순위 + Fusion 연합**

→ 다양한 검색 결과의 순위를 종합해 검색 순위를 다시 매긴다

➡️ 서로 다른 점수 체계를 직접 정규화해야 하는 문제를 보완

### Q. 각 결과값의 범위와 분포가 다른데 어떤 방식으로 결합할까?

#### 1. Ranking _ 점수의 순위화

- 점수 자체는 신경쓰지 X
- 각 결과 내에서의 “순위”만을 추출

#### 2. Reciprocal Scoring _ 역수 순위 점수 계산

: 상위 순위일수록 더 높은 점수 부여해 각 검색 결과의 순위를 RRF 점수로 변환

$$
RRF\_Score(d \in D) = \sum_{m \in M} \frac{1}{k + r_m(d)}
$$

- 역수 `1/순위` : 상위권 순위 간의 점수 격차 >>> 하위권 순위 간 점수 격차

  ```text
  1위 1/1 = 1.0 - 2위 1/2 = 0.5 → 0.5점 차이
  100위 1/100 = 0.01 - 101위 1/101 → 0.0099점 차이
  ```

  **`k=0`이라고 가정한 단순 예시**

- 상수 `k` : 순위가 RRF 점수에 미치는 영향의 크기를 조절하는 상수
  - 일반적으로 `60`이 자주 사용됨
  - `k ↓` : 상위 순위의 영향력이 상대적으로 커짐<br>
    → 상위권 문서의 순위 차이를 더 강하게 반영
  - `k ↑` : 순위 간 점수 차이가 완만해짐<br>
    → 더 넓은 순위 범위를 비슷하게 반영

### 알고리즘 코드

> 참고 자료: [Elastic 공식 문서 — Reciprocal rank fusion](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

```python
score = 0.0
for q in queries: # 결합할 각 검색 질의
    if d in result(q): # 문서 d가 해당 결과에 존재하면
        score += 1.0 / (k + rank(result(q), d)) # d의 순위를 RRF 점수로 변환하여 누적
return score
```

- `d` : 순위를 매길 대상인 문서
- `score` : d의 RRF 점수
- `queries` : 결합할 검색 결과를 생성하는 검색 방식들의 집합
- `result(q)` : 검색 방식 q의 검색 결과 목록
- `rank(result(q), d)` : 해당 검색 결과에서 문서 d의 순위

## 결론 : 점수 정규화 VS RRF

### 점수 정규화

- 서로 다른 점수의 Scale은 맞출 수 있음
- 점수의 분포·의미 차이까지 맞추기는 어려움
- 극단값 등에 정규화 결과가 영향을 받을 수 있음

### RRF 순위 융합

- 원래 점수 자체를 사용하지 않음
- 각 검색 결과에서의 상대적 순위만 사용
- 서로 다른 점수 체계를 직접 정규화할 필요없이 단순하고 안정적으로 결합

### Q. 점수 정규화 대신 순위 융합인 이유

점수의 절대값은 검색 알고리즘마다 범위와 분포, 의미가 다르기 때문에 완전히 동일한 기준으로 비교하기 어렵다.

RRF는 각 검색 결과에서의 상대적 순위만을 사용하기 때문에 점수 체계 차이에 영향을 덜 받으면서 결과를 결합한다.

## RAG 루프

### 질문

사용자가 RAG 시스템에게 질문

> “지난번에 제주도 여행 가면서 묵기로 한 숙소가 어디였지?”

### 검색

DB에서 질문과 가까운 문서/대화 청크 검색

- “제주도 숙소 여기 어때?”
- “난 협재 쪽이 좋아”
- “그러면 바다정원 게스트하우스로 예약할게”

```text
키워드 검색  ─┐
           ├─ RRF → 후보 Top-K → Reranker → 최종 Top-N → Context 조립
벡터 검색 ───┘
```

#### 벡터 검색

사전에 사용했던 임베딩 모델로 질문 벡터화

[02. 검색의 세 세대를 직접 만든다 — 2세대: 벡터 검색](./02-search-generations.md#2세대-벡터-검색)


- 코사인 유사도 : 방향이 얼마나 비슷한가?
- 내적 : 두 벡터가 얼마나 같은 방향으로 강하게 향하는가?
- 유클리드 거리 : 두 좌표가 물리적으로 얼마나 가까운가?

#### Hybrid Search

여러 가지 검색 방식을 함께 보는 것 [ 키워드 검색 + 벡터 검색 ]

- 키워드 검색 : 토큰, 고유명사, 모델명과 같은 정확한 표현을 잘 찾음
- 벡터 검색 : 다른 표현, 유사 의미를 잘 찾음

➡️ 정확한 표현과 의미 유사 표현을 모두 검색 후보에 포함 가능

#### + Reranker

검색 결과에서 더 관련 있는 문서를 선별 및 재정렬하는 과정

- (1차)검색 : 관련 후보를 넓게 가져온다.
- Reranker : 후보 중 질문과 실제로 관련성이 높은 문서를 정밀하게 평가한다.

### 컨텍스트 조립

검색된 메시지를 시간과 발신자를 포함해 하나로 구성

- 민지: “제주도 숙소 여기 어때?”
- 수현: “난 협재 쪽이 좋아”
- 민지: “그러면 바다정원 게스트하우스로 예약할게”

검색으로 가져온 문서를 LLM이 답변 생성에 사용할 수 있는 형태로 정리해 프롬프트에 주입

1. 사용할 검색 결과 선택
2. 컨텍스트 구성
   - 중복되는 내용 제거
   - 관련도순, 시간순 등 목적에 맞게 재배치
   - 문서ID, 출처와 같은 메타데이터 추가
3. 컨텍스트 길이 조절 : 불필요한 내용 제거 - Context Window / Token Budget에 맞춤
4. 컨텍스트 포맷팅 : `[Context 1]`, `[Context 2]` 등으로 구분

#### 예시: “지난번에 제주도 여행 가면서 묵기로 한 숙소가 어디였지?”

**검색 결과**

```text
문서 17
내용: "그러면 바다정원 게스트하우스로 예약할게"
발신자: 민지
시간: 2026-07-10 14:40

문서 42
내용: "난 협재 쪽이 좋아"
발신자: 수현
시간: 2026-07-10 14:35

문서 51
내용: "제주도 숙소 여기 어때?"
발신자: 민지
시간: 2026-07-10 14:32
```

**컨텍스트 조립**

```text
[Context 1]
source_id: 51
sender: 민지
time: 2026-07-10 14:32
content: 제주도 숙소 여기 어때?

[Context 2]
source_id: 42
sender: 수현
time: 2026-07-10 14:35
content: 난 협재 쪽이 좋아

[Context 3]
source_id: 17
sender: 민지
time: 2026-07-10 14:40
content: 그러면 바다정원 게스트하우스로 예약할게
```

### LLM 답변 + 근거 인용

LLM에게 `질문 + 조립된 컨텍스트`를 전달 → LLM에게 제공된 컨텍스트를 근거로 답변하도록 지시


#### RAG Citation Grounding

LLM 답변의 각 주장을 실제 검색된 근거(Evidence)와 연결하고 - **Citation**<br>
해당 근거가 답변의 주장을 실제로 뒷받침하도록 하는 것 - **Grounding**

**Citation - 출처 연결**

LLM 답변이 어떤 원본 문서/검색 결과를 출처로 사용했는지 표시

**Grounding - 내용의 근거성 확인**

LLM 답변의 주장을 뒷받침하는 근거를 실제 컨텍스트에서 확인할 수 있는 상태

#### 예시: Citation + Grounding 모두 잘 된 경우

**원본 문서**

```text
[문서 17]
"그러면 바다정원 게스트하우스로 예약할게."
```

**LLM 답변 → [문서 17]이라는 Citation 완료**

```text
제주도 숙소는 바다정원 게스트하우스로 정했어. [문서 17]
```

**Evidence**

```text
"그러면 바다정원 게스트하우스로 예약할게."
                         ↕ 의미 비교 ✅ → Grounded ⭕️
"제주도 숙소는 바다정원 게스트하우스로 정했어."
```

#### 예시: Citation은 성공, Grounding은 실패한 경우

**원본 문서**

```text
[문서 17]
"그러면 바다정원 게스트하우스로 예약할게."
```

**LLM 답변 → [문서 17]이라는 Citation 완료**

```text
제주도 숙소는 바다정원 게스트하우스로 정했고,
숙박비는 1박에 10만 원이야. [문서 17]
```

```text
주장 1
"제주도 숙소는 바다정원 게스트하우스로 정했다."
→ Citation: [문서 17]
→ 해당 주장을 뒷받침하는 Evidence 존재 ⭕
→ Grounded ⭕

주장 2
"숙박비는 1박에 10만 원이다."
→ Citation: [문서 17]
→ 해당 주장을 뒷받침하는 Evidence 없음 ❌
→ Grounded ❌
```

### Q. 검색이 잘 되었는지는 어떤 기준으로 판단할까?

`Recall@K` : 질문 관련 Evidence 중 검색 결과 상위 K개 안에 포함된 Evidence의 비율<br>
→ 질문과 관련된 Evidence를 얼마나 놓치지 않고 검색했는지 평가

```text
Top-K에 포함된 질문 관련 Evidence 수 / 질문 관련 Evidence 수 (Ground Truth)
```

- 계산을 위해 어떤 Evidence가 질문과 관련 있는지에 대한 Ground Truth 필요

<details>
<summary>그 외 다른 지표</summary>

<br>

| 지표 | 평가 내용 |
|---|---|
| **Precision@K** | 가져온 문서 중 **관련 문서가 많은가?** |
| **MRR** | 첫 관련 문서를 **얼마나 상위에 배치했는가?** |
| **NDCG@K** | 관련도가 높은 문서들을 **전반적으로 상위에 잘 배치했는가?** |

</details>

## Multi-hop Question

두 개 이상의 정보를 단계적으로 연결해 대답해야 하는 질문

### Hop

정보 → 정보 과정의 추론 단계

```text
“부산 같이 간 사람들 중 같은 회사 다니는 사람?”
```

**부산 같이 간 사람**

```text
[정보 1]
"부산은 민지, 수현, 지훈이랑 같이 갔어."
```

↓ 민지, 수현, 지훈에 대한 다음 Evidence 필요


**같은 회사인 사람 → 각 사람의 회사 정보 필요**

```text
[정보 2]
"민지는 A회사에 다녀."

[정보 3]
"수현은 B회사에 다녀."

[정보 4]
"지훈도 A회사에 다녀."
                ↓ 관계 추론
[답]
민지와 지훈
```

## RAG의 한계

### RAG란

필요한 모든 데이터를 LLM에 미리 학습시키지 않고 질문 시점에 필요한 정보를 검색해서 제공

- 모델을 재학습하지 않고 외부 데이터 활용 가능
- 최신 정보, 개인 또는 내부 데이터 활용 가능
- 검색된 근거를 기반으로 답변하여 Hallucination 완화

### 올바른 RAG의 전제 조건

1. 질문의 답변에 필요한 Evidence가 검색되고,
2. 최종 Context 안에 포함되어 있어야 한다.

### RAG의 한계 : 전제 조건이 성립되기 어려운 이유

RAG의 성능은 LLM 자체의 능력뿐 아니라, 답변에 필요한 Evidence를 검색하여 Context에 충분히 제공할 수 있는가에 의존한다.

그러나 실제 질문에서는 필요한 정보가 검색에서 누락되거나, 여러 정보가 서로 떨어져 있거나, 첫 번째 검색 결과를 바탕으로 추가 탐색이 필요한 경우가 존재한다.

**검색 실패**

질문과 정답 근거의 표현이 다르면 관련 문서를 찾지 못할 수 있다.

**Ranking 실패**

검색은 됐지만 순위가 낮으면 `Top-K → Reranker → Top-N` 과정에서 탈락할 수 있다.

**Context 한계**

필요한 근거가 너무 많거나 Context Window / Token Budget을 초과하면 일부 정보가 제외될 수 있다.

‼️ **[Multi-hop Question](#multi-hop-question)**

여러 Evidence를 단계적으로 연결해야 하며, 경우에 따라 한 단계에서 얻은 정보를 바탕으로 추가 Evidence를 탐색해야 하기 때문에 단일 Retrieval만으로 모든 근거를 확보하기 어려울 수 있다.

#### 예시: “부산 같이 간 사람들 중 같은 회사 다니는 사람?”

DB에는 필요한 정보가 모두 존재한다.

```text
[문서 1]
"부산은 민지, 수현, 지훈이랑 같이 갔어."

[문서 2]
"민지는 A회사에 다녀."

[문서 3]
"수현은 B회사에 다녀."

[문서 4]
"지훈도 A회사에 다녀."
```

질문을 해결하기 위해 서로 떨어져 있는 여러 Evidence를 연결해야 하므로, 한 번의 검색에서 필요한 Evidence가 일부 누락될 수 있다.

```text
"부산 같이 간 사람들 중 같은 회사 다니는 사람?"

                         ↓ 검색

[문서 1] "부산은 민지, 수현, 지훈이랑 같이 갔어."    ⭕

[문서 2] "민지는 A회사에 다녀."                  ❌ 누락 가능
[문서 3] "수현은 B회사에 다녀."                  ❌ 누락 가능
[문서 4] "지훈도 A회사에 다녀."                  ❌ 누락 가능
```

또는

```text
"부산 같이 간 사람들 중 같은 회사 다니는 사람?"

                         ↓ 검색

[문서 1] "부산은 민지, 수현, 지훈이랑 같이 갔어."    ❌ 누락 가능

[문서 2] "민지는 A회사에 다녀."                  ⭕
[문서 3] "수현은 B회사에 다녀."                  ⭕
[문서 4] "지훈도 A회사에 다녀."                  ⭕
```

즉,

**Multi-hop Question은 여러 Evidence를 단계적으로 연결해야 하기 때문에**

원래 질문을 이용한 단일 Retrieval만으로는 필요한 모든 Evidence를 확보하기 어려울 수 있다.
