# 지식 그래프와 온톨로지

## 1. 문서에서 대상을 구분하기

프로젝트 자료에는 서비스 이름, API, 담당자, 설계 결정처럼 여러 대상이 등장한다. 이 중 개별적으로 식별해 다루는 대상을 **개체(entity)**라고 한다.

예를 들어 “주문서비스는 배송서비스를 호출한다”에는 주문서비스와 배송서비스라는 두 개체가 있다. ‘호출한다’는 두 개체 사이의 **관계(relation)**다.

```text
주문서비스 ──호출한다──▶ 배송서비스
```

대상을 점으로, 관계를 선으로 연결한 구조가 그래프다. 점은 노드(node), 선은 엣지(edge)라고 부른다. 지식 그래프는 이런 구조로 대상의 속성과 관계를 표현한 것이다. 아래의 서비스·정책 예시는 개념 설명을 위한 가상 데이터다.

## 2. 단어를 찾는 것과 관계를 찾는 것

### 검색은 문서의 관련성을 판단한다

BM25는 질문과 문서의 단어 일치를 중심으로 관련성을 계산한다. 한국어에서는 검색 전에 문장을 분석하는 과정도 중요하다.

예를 들어 ‘배송서비스에서’라는 표현은 ‘배송서비스’와 조사 ‘에서’로 나누어 생각할 수 있다. **Nori는 Elasticsearch에서 한국어를 분석해 검색에 사용할 단위를 얻는 도구**다. 이렇게 나눈 단위를 토큰이라고 한다. 실제 분해 결과는 사전과 복합어·품사 처리 설정에 따라 달라진다. [Nori 소개](https://www.elastic.co/blog/nori-the-official-elasticsearch-plugin-for-korean-language-analysis)

```text
문서·질문 → Nori로 분석 → 단어를 비교 → BM25로 순위 계산
```

Nori가 비교할 단위를 준비한다면 BM25는 그 단위를 바탕으로 점수를 매긴다. 형태소 분석만으로 ‘취소’와 ‘철회’ 같은 표현 차이가 모두 해결되지는 않는다. 벡터 검색은 질문과 문서를 임베딩으로 바꾸어 의미상 가까운 문서를 찾는 다른 접근이다.

하이브리드 검색은 여러 검색 방식을 결합한다. RRF는 각 검색 목록의 순위를 점수로 바꾸어 같은 문서끼리 합치는 방법이다. 검색한 본문을 생성 모델에 전달해 답변을 작성하는 구성은 RAG다. [검색과 RRF 계산 예시](03-week3-hybrid-rag.md)

### 관계 질문에는 문서 사이의 연결이 필요하다

두 문서에 다음 내용이 나뉘어 있다고 하자.

```text
문서 A: 주문서비스는 배송서비스를 호출한다.
문서 B: 배송서비스는 배송완료 이벤트를 발행한다.
```

“주문서비스가 호출하는 서비스가 발행하는 이벤트는?”에 답하려면 A와 B를 찾고, 두 문서의 배송서비스가 같은 대상임을 연결해야 한다.

```text
주문서비스 ──호출한다──▶ 배송서비스 ──발행한다──▶ 배송완료 이벤트
```

이처럼 여러 관계를 이어 답을 찾는 질문을 다중 홉 질문이라고 한다. 관계 하나를 건너가는 것이 한 홉이다. 문서 검색으로도 답할 수 있지만, 관련 문서를 찾았다는 사실만으로 연결 조건까지 정확히 처리했다는 보장은 없다.

관계를 미리 기록하면 같은 질문을 경로 조회로 처리할 수 있다. 대신 잘못 추출한 관계도 조회되므로, 관계의 근거와 품질을 관리해야 한다.

위 예시에서 답을 얻는 과정은 다음과 같다.

1. 주문서비스에서 ‘호출한다’ 관계를 따라 배송서비스를 찾는다.
2. 그 배송서비스에서 ‘발행한다’ 관계를 따라 배송완료 이벤트를 찾는다.
3. 각 관계의 근거인 문서 A·B를 함께 확인한다.

검색이 문서 B를 놓친 경우와, 두 문서를 찾았지만 대상을 잘못 연결한 경우는 다른 오류다. 그래프는 연결 조건을 명시하지만, 추출 단계에서 B의 관계를 누락했다면 그래프에서도 답을 얻을 수 없다. 이 예시는 관계 질의를 설명하기 위한 것으로 실제 RAG 실패를 측정한 결과는 아니다.

## 3. 이름과 식별자를 구분하는 이유

‘배송서비스’, ‘shipping-service’, ‘배송 서버’가 같은 대상을 가리킬 수 있다. 반대로 서로 다른 프로젝트가 같은 ‘배송서비스’라는 이름을 사용할 수도 있다. 이름만 기준으로 합치면 다른 대상이 섞이고, 이름이 다르다는 이유로 분리하면 같은 대상의 정보가 끊어진다.

그래서 표시 이름과 식별자(ID)를 나눈다.

```text
식별자: service:shipping
표시 이름: 배송서비스
확인한 별칭: shipping-service
```

식별자는 대상의 이름이 바뀌어도 관계를 유지하는 기준이다. 다른 시스템이 같은 대상에 별도의 ID를 사용한다면 공통 키나 검토한 매핑으로 연결해야 한다. 유사한 이름이나 벡터만으로 동일성을 확정하지 않는다.

## 4. RDF: 사실을 공통 구조로 표현하기

팀 A는 호출 관계를 JSON으로, 팀 B는 엑셀로 기록한다고 하자. 두 자료를 함께 사용하려면 서로 다른 형식과 항목 이름을 해석해야 한다.

**RDF(Resource Description Framework)는 정보를 주어·술어·목적어로 표현하는 데이터 모델**이다. 세 요소의 묶음을 트리플(triple)이라고 한다.

| 주어: 무엇이 | 술어: 어떤 관계로 | 목적어: 무엇과 연결되는가 |
|---|---|---|
| 주문서비스 | 호출한다 | 배송서비스 |
| 배송서비스 | 발행한다 | 배송완료 이벤트 |

각 시스템이 공통 구조와 식별자·어휘를 사용하면 정보를 교환하고 함께 질의할 기반이 생긴다. RDF는 DB 제품이나 자동 추출 모델이 아니다. 같은 구조를 쓰더라도 ‘호출한다’의 정의가 다르거나 대상 ID가 연결되지 않으면 의미를 맞추는 작업은 남는다. [RDF Primer](https://www.w3.org/TR/rdf11-primer/)

### 식별자, 값, 접두어

RDF 1.1에서는 대상을 IRI로 식별한다. IRI는 URI를 확장해 국제 문자를 허용하는 식별자다. 주소처럼 보이지만 반드시 웹페이지 자체를 뜻하는 것은 아니다.

```turtle
@prefix ex: <https://example.org/project/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ex:order ex:calls ex:shipping .
ex:shipping rdfs:label "배송서비스"@ko .
```

`ex:shipping`은 대상의 식별자이고 `"배송서비스"@ko`는 한국어 이름이라는 값이다. 문자열·숫자·날짜 같은 값을 리터럴(literal)이라고 한다. `ex:`는 긴 주소의 공통 앞부분을 줄여 쓰는 네임스페이스 접두어다.

위 문법은 RDF를 파일에 표현하는 **Turtle**이다. `calls`는 ‘호출한다’는 뜻으로 선택한 관계 이름이며 RDF에 내장된 명령어가 아니다. `emits`도 ‘이벤트를 발행한다’는 의미로 정할 수 있다. 관계를 기록하는 것과 실제 서비스 호출·이벤트 발행을 실행하는 것은 다르다.

## 5. RDFS: 대상의 종류와 관계의 기본 의미

사실을 기록한 뒤에는 대상의 종류도 구분해야 한다. 배송서비스와 배송완료 이벤트를 같은 종류로 다루면 잘못된 관계를 만들기 쉽다.

클래스(class)는 대상을 의미에 따라 분류하는 개념이다. 예를 들어 Service는 서비스라는 종류를 나타내고, 배송서비스는 그 클래스에 속하는 개별 대상, 즉 인스턴스다. 객체지향의 클래스·인스턴스 구분과 비슷하지만, 여기서는 객체의 실행 동작보다 대상의 종류와 관계의 의미를 표현하는 데 초점을 둔다.

Service와 Event는 이 예시에서 정의한 클래스 이름이다. `배송서비스 rdf:type Service`라는 표현은 배송서비스의 종류를 기록하는 것이며, 객체를 생성하거나 실행하는 코드는 아니다.

RDFS(RDF Schema)는 클래스, 하위 클래스, 속성의 기본 의미를 표현하는 어휘를 제공한다.

```text
배송서비스는 BackendService에 속한다.
BackendService는 Service의 하위 클래스다.
따라서 배송서비스는 Service에도 속한다.
```

명시한 사실과 규칙에서 추가 결론을 얻는 것이 **추론(inference)**이다. 실제 결과에 반영하려면 해당 의미 규칙을 처리하는 시스템이 필요하다. [RDFS](https://www.w3.org/TR/rdf-schema/)

속성의 domain과 range는 각각 주어와 목적어의 종류를 추론하는 데 사용한다. 예를 들어 emits의 domain을 Service, range를 Event로 정의하면 `A emits B`에서 A를 Service, B를 Event로 해석할 근거가 된다. 잘못된 입력을 거부하는 SQL 제약과 같은 역할은 아니다.

## 6. OWL: 더 풍부한 의미와 논리적 규칙

**OWL(Web Ontology Language)은 클래스와 관계의 의미를 더 풍부하게 표현하는 온톨로지 언어**다. 클래스의 동등성·배타성, 역관계 등을 정의할 수 있다.

예를 들어 이 모델에서 Service와 Event가 서로 겹치지 않는 클래스라고 명시했다고 하자. 같은 대상을 두 클래스에 동시에 속한다고 기록하면 그 정의와 충돌한다. 추론기는 이런 모순을 찾을 수 있다. [OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)

OWL이 현실의 의미를 알아서 결정하는 것은 아니다. 판단은 명시한 사실과 정의를 바탕으로 한다. LLM이 문맥에서 관계 후보를 추출하는 작업과도 구분된다.

또한 담당 팀이 기록되지 않았다고 ‘담당 팀이 없다’고 단정할 수는 없다. OWL의 열린 세계 가정에서는 아직 모르는 정보일 수 있다. ‘담당 팀 필드는 반드시 있어야 한다’ 같은 검증은 SHACL이나 애플리케이션 규칙으로 별도 처리할 수 있다. [SHACL](https://www.w3.org/TR/shacl/)

## 7. 온톨로지와 지식 그래프의 관계

온톨로지는 어떤 대상을 어떤 종류로 보고, 관계를 어떤 의미로 사용할지 명시한 체계다. 지식 그래프에는 그 의미 체계를 바탕으로 개별 대상과 사실을 기록할 수 있다.

| 구분 | 예시 |
|---|---|
| 의미 정의 | Service와 Event를 구분하고 emits를 이벤트 발행 관계로 사용 |
| 개별 사실 | 배송서비스가 배송완료 이벤트를 발행함 |

스키마도 의미를 담기 때문에 스키마와 온톨로지에 절대적인 경계가 있는 것은 아니다. DB 스키마가 저장 구조·자료형·키 제약에 초점을 둔다면, 온톨로지는 개념과 관계의 의미·계층·논리를 명시하는 데 초점을 둔다.

RDF는 사실을 표현하는 구조, RDFS와 OWL은 의미를 정의하는 도구로 연결된다. 모든 지식 그래프가 반드시 OWL을 사용하는 것은 아니다.

## 8. 시맨틱 웹에서 기업 지식 그래프까지

### 시맨틱 웹과 링크드 데이터

시맨틱 웹은 웹의 데이터를 컴퓨터가 의미 구조에 따라 연결하고 활용하도록 하려는 구상이다. 예를 들어 서로 다른 사이트의 기업 정보와 제품 정보를 공통 식별자로 연결하면 어느 기업이 어떤 제품을 만드는지 함께 조회할 수 있다. [W3C 시맨틱 웹 소개](https://www.w3.org/2001/sw/)

링크드 데이터는 URI로 대상을 식별하고, 조회 가능한 정보와 다른 대상의 링크를 제공해 데이터들을 연결하는 원칙이다. [Linked Data 원칙](https://www.w3.org/DesignIssues/LinkedData.html)

형식을 마련해도 정보의 작성·갱신과 용어 합의는 필요하다. 기술 표준과 데이터 운영은 함께 다뤄야 한다.

### DBpedia와 Wikidata

DBpedia는 Wikipedia 문서의 구조화된 정보를 추출해 연결 가능한 데이터로 제공하는 프로젝트다. Wikidata는 항목·속성·진술을 공동 편집하고 여러 곳에서 재사용하는 지식베이스다. 두 프로젝트는 관련 생태계에 속하지만 같은 시스템의 이전·다음 버전은 아니다. [DBpedia](https://www.dbpedia.org/about/), [Wikidata](https://www.wikidata.org/wiki/Wikidata:Introduction)

```text
DBpedia: 문서의 정보 → 추출 → 구조화된 데이터
Wikidata: 구조화된 데이터를 공동 관리 → 여러 서비스에서 재사용
```

### 주요 흐름

| 시기·접근 | 확장된 관심 |
|---|---|
| 2001년 시맨틱 웹의 대표 구상 | 웹 정보를 기계가 의미에 따라 활용 |
| 2004년 RDF·OWL 주요 권고안 | 사실과 의미를 공통 방식으로 표현 |
| 2007년 DBpedia 시작 | 기존 문서에서 구조화된 지식 추출 |
| 2012년 구글 KG·Wikidata | 대상 중심 검색과 공동 지식 관리 |
| 기업 KG | 부서·시스템 사이의 데이터를 업무 대상 중심으로 연결 |
| LLM 시대의 GraphRAG | 추출·요약·검색과 그래프의 결합 |

앞 기술이 사라지고 뒤 기술로 교체된 순서는 아니다. RDF 관련 작업은 2001년 이전에도 있었으며, 시맨틱 웹과 기업 KG를 단순한 실패·성공 관계로 구분하기 어렵다. [2001년 글](https://lassila.org/publications/2001/SciAm.html), [구글 KG 발표](https://blog.google/products/search/introducing-knowledge-graph-things-not/), [Wikidata 출범](https://www.wikidata.org/wiki/Wikidata:First_Birthday)

## 9. RDF 그래프와 프로퍼티 그래프

RDF와 Neo4j를 직접 비교하면 데이터 모델과 제품을 비교하게 된다. 모델 수준에서는 RDF와 Neo4j가 사용하는 프로퍼티 그래프를 비교할 수 있다.

| 관점 | RDF | 프로퍼티 그래프 |
|---|---|---|
| 기본 표현 | 주어·술어·목적어 트리플 | 노드·관계·속성 |
| 식별·의미 | IRI와 공통 어휘, RDFS/OWL 등 | 라벨·관계 타입·속성과 애플리케이션 정의 |
| 관계의 부가 정보 | 진술 노드 등으로 모델링 가능 | 관계에 속성을 부여 가능 |
| 대표 질의 언어 | SPARQL | Cypher |

예를 들어 호출 관계의 통신 방식이 동기식임을 프로퍼티 그래프에서는 관계 속성으로 붙일 수 있다. RDF에서도 표현할 수 있지만 모델링 방식이 다르다. 선택은 표준 교환, 의미 추론, 경로 조회, 운영 환경 등 요구사항에 따라 달라진다. [Neo4j 그래프 개념](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)

### 두 접근이 강조하는 설계 관점

RDF는 서로 다른 곳의 데이터를 공통 식별자와 어휘로 기술하고 교환하는 데 강점을 둔다. 예를 들어 여러 조직이 같은 제품 정보를 주고받을 때, ID와 속성의 의미를 공유하고 표준 질의 도구를 적용하는 관점이다. RDF 트리플 스토어는 이러한 RDF 데이터를 저장·질의하는 저장소다. [RDF 활용 목적](https://www.w3.org/TR/rdf11-primer/)

프로퍼티 그래프는 애플리케이션에서 다루는 노드·관계에 속성을 붙이고 경로를 조회하는 방식이 자연스럽다. 서비스 호출 관계에 `mode: "sync"`를 붙이고, 특정 서비스에서 몇 단계 이내에 연결된 서비스를 찾는 식이다. [Neo4j 그래프 개념](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)

이는 절대적인 기능 구분은 아니다. RDF로 경로를 찾을 수도 있고 프로퍼티 그래프로 조직 간 정보를 연결할 수도 있다. 공통 표준과 의미 정의가 중요한지, 애플리케이션의 관계 탐색과 도구 지원이 중요한지에 따라 선택 기준이 달라진다.

## 10. SPARQL: 연결 패턴으로 질의하기

SPARQL은 RDF 그래프에서 조건에 맞는 연결을 찾는 언어다. SQL의 `SELECT`로 테이블을 조회하듯, RDF에 기록된 관계에서 조건에 맞는 대상을 조회한다.

### 서비스 관계를 읽는 예제

다음 코드는 앞에서 사용한 가상 서비스 데이터에 대한 질의다. 그 데이터가 저장된 RDF 환경을 전제로 하므로 Wikidata에 그대로 실행할 예제는 아니다.

```sparql
PREFIX ex: <https://example.org/project/>
SELECT ?service ?event WHERE {
  ex:order ex:calls ?service .
  ?service ex:emits ?event .
}
```

첫 패턴은 주문서비스가 호출하는 대상을 찾는다. 두 번째 패턴은 그 대상이 발행하는 이벤트를 찾는다. 같은 변수 `?service`가 두 관계를 연결하는 기준이다.

### 공개 데이터로 실행할 예제

Wikidata는 여러 사람이 관리하는 공개 지식베이스다. 공개 엔드포인트는 질의를 보내고 결과를 받는 접속 지점이다. 웹 화면에서 사용할 수 있으므로 로컬 DB 설치 없이 아래 예제를 실행할 수 있다.

질문은 **“Wikidata에 기록된 대한민국의 수도는 무엇인가?”**다.

```sparql
PREFIX wd: <http://www.wikidata.org/entity/>
PREFIX wdt: <http://www.wikidata.org/prop/direct/>
SELECT ?capital WHERE {
  wd:Q884 wdt:P36 ?capital .
}
```

코드를 문장으로 풀면 다음과 같다.

| 코드 | 의미 |
|---|---|
| `PREFIX wd: ...` | 항목 ID의 긴 주소를 `wd:`로 줄여 씀 |
| `PREFIX wdt: ...` | 직접 관계를 나타내는 속성 주소를 `wdt:`로 줄여 씀 |
| `SELECT ?capital` | 찾은 수도를 결과에 표시 |
| `WHERE { ... }` | 중괄호 안의 관계 조건과 일치하는 데이터를 찾음 |
| `wd:Q884 wdt:P36 ?capital` | 대한민국 — 수도 — 빈칸의 형태에서 빈칸을 찾음 |

`?capital`은 아직 모르는 값이 들어갈 변수다. 생성 모델이 답을 작성하는 것이 아니라, 저장된 관계의 목적어를 조회한다.

**실행 방법:** [Wikidata Query Service](https://query.wikidata.org/)의 편집기에 위 코드를 붙여넣고 실행 버튼을 누른다. 결과의 `capital` 열에는 수도를 나타내는 항목 URI가 표시된다. 사람이 읽는 이름 대신 ID가 보일 수 있으며, 결과 항목을 열어 이름과 내용을 확인할 수 있다. 이 절은 실행 예제이며 실행 결과를 기록한 실습 보고서는 아니다.

Q884는 대한민국 항목, P36은 수도 속성이다. 위 서비스 예시와 달리 공개된 Wikidata를 대상으로 한다. `wdt:`는 직접 관계를 조회하며, 진술의 조건과 출처까지 조회하려면 진술 노드를 거치는 표현을 사용한다. [Wikidata Query Service](https://query.wikidata.org/), [SPARQL 튜토리얼](https://www.wikidata.org/wiki/Wikidata:SPARQL_tutorial)

## 11. 그래프와 답변 생성을 연결하기

GraphRAG는 그래프에서 얻은 정보를 검색·답변 생성에 활용하는 접근이다. 특정 대상의 주변 관계를 찾는 방식과 전체 그래프를 묶어 요약하는 방식은 목적이 다르다.

Microsoft의 2024년 연구는 그래프의 밀접하게 연결된 집단인 커뮤니티를 찾고 요약을 만들어, 문서 전체의 공통 주제 같은 질문에 활용한다. 모든 GraphRAG가 같은 구현을 의미하지는 않는다. [GraphRAG 논문](https://arxiv.org/abs/2404.16130)

팔란티어의 Ontology는 객체·관계뿐 아니라 Action을 통해 업무 변경을 수행하는 기능까지 연결한다. 사실을 표현하거나 추론하는 것과 업무 동작을 실행하는 것은 다른 기능이다. [Palantir Ontology](https://www.palantir.com/docs/foundry/architecture-center/ontology-system)

그래프는 관계를 명시적으로 다루게 해주지만, 누락된 사실이나 잘못 연결된 ID를 없애주지는 않는다. 문서에서 관계를 추출하고 근거를 검증하는 과정이 다음 과제가 된다.
