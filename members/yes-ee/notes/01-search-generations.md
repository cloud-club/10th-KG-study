# 01. Search Generations

## 한 줄 요약

검색은 문자열 일치 → 키워드 기반 관련도 순위화 → 의미 기반 벡터 유사도 검색으로 발전해 왔다.

## 0~2세대 비교

### 0세대 grep

**grep이란**

- 정확히 같은 문자열/패턴이 존재하는지 확인한다.
- 패턴 기반 텍스트 매칭이다.

**한계**

1. **표현 불일치**
   - 문서: "퇴근 후 달리기를 하고 집중력이 좋아졌다."
   - 검색: "운동"
   - 결과: **검색 실패** — 같은 뜻이어도 단어가 다르면 못 찾는다.
2. **순위가 없음**
   - 결과가 많을 때, 검색 결과에 순위를 매길 수 없다.
   - 아래처럼 문서가 여러 개 존재할 때 사용자는 보통 내 검색어와 가장 관련 있는 문서부터 보고 싶어 한다. 그런데 `grep`에는 이런 순위화 개념이 없다.

   ```
   문서1: Kubernetes 공부
   문서2: Kubernetes 설치
   문서3: Kubernetes Kubernetes Kubernetes 네트워크 정리
   문서4: Kubernetes를 잠깐 언급함
   ```

### 1세대 키워드 검색

문서를 토큰 단위로 분석하고 역색인을 구축하여 관련 문서를 빠르게 찾은 뒤, TF-IDF/BM25 기반 점수로 검색 결과의 순위를 매긴다.

- Tokenization: 문장을 검색 가능한 단위(token)로 분리한다.
- Inverted Index: `단어 → 해당 단어가 등장한 문서` 구조로 저장한다.
- TF-IDF:
  - TF: 해당 문서에서 단어가 얼마나 자주 등장하는지를 나타낸다.
  - IDF: 전체 문서에서 단어가 얼마나 희귀한지를 나타낸다.
- BM25: TF-IDF 아이디어에 단어 빈도 포화와 문서 길이 보정 등을 추가한 순위화 방식이다.

**grep 대비 개선**

- 문서를 빠르게 검색할 수 있다.
- 관련도 순위화를 할 수 있다.

**한계**

- 기본적으로 lexical(단어 기반) 검색이다.
- 같은 의미라도 표현이 크게 다르면 찾기 어렵다.

**Tokenization**

검색 엔진이 역색인을 만들기 위해 문장을 **검색 가능한 token 단위로 분해**하는 과정이다.
한국어는 조사·어미가 붙기 때문에 단순 공백 분리만으로는 검색 품질이 떨어질 수 있다.

- **Nori**
  - 한국어 형태소 분석을 기반으로 한다.
  - 문법을 고려해 의미 있는 단위로 분리한다.
  - 일반적인 한국어 자연어 검색에 적합하다.
  - 신조어·전문용어·고유명사 등은 사전과 분석 방식의 영향을 받을 수 있다.
- **n-gram**
  - 문법과 관계없이 문자열을 N글자 단위로 분리한다.
  - 부분 문자열, 고유명사, 신조어 등의 검색에 유리하다.
  - 토큰 수가 많아져 인덱스 크기와 검색 노이즈가 증가할 수 있다.

#### 실습
BM25는 검색 결과의 관련도 점수를 계산하는 방식이다.
관련도 점수를 판단하는 기준은 3가지가 존재한다.
1. 검색한 말이 글에 얼마나 나오나
여러번 나올수록 점수가 높아진다. 그러나 반복에 따른 추가 점수는 점점 줄어든다.
2. 희귀성: 그 단어를 포함한 문서가 몇 개인가
검색에 쓰인 각 단어의 중요도를 결정한다. 적은 문서에만 있는 단어일수록 더 높은 가중치를 부여한다.
3. 글 길이
검색어 등장 횟수가 같다면 보통 짧은 글이 유리한다.

또한, Elasticsearch는 문서를 저장하고 검색하며, BM25로 결과의 순위를 매길 수 있는 검색 엔진이다.
이번 실습에서는 Elasticsearch를 사용한다.

> 로컬 파일이나 DB에 저장하면 되는데 검색 엔진이 왜 필요할까? 

grep은 기본적으로 검색 대상 파일을 읽으면서 문자열이나 패턴이 있는지 확인하고, 일치하는 줄을 출력한다.

그런데 문서가 많아지면 매번 전체 내용을 읽는 건 비용이 커진다. 이를 줄이기 위해 책 뒤의 찾아보기처럼 `토큰 → 해당 토큰이 등장한 문서`를 미리 정리한 **역색인(inverted index)** 을 만든다.
역색인을 만들 때는 **토큰화(tokenization)** 로 문장을 검색 가능한 단위로 나눈다.

예를 들어 다음 두 개의 문서가 있다.

```text
문서 A: CloudFormation으로 Lambda를 배포한다.
문서 B: Lambda 실행 시간을 확인한다.
```

분석기가 서비스 이름을 각각의 토큰으로 추출한다면, 역색인은 아래처럼 구성될 수 있다.

```text
CloudFormation → 문서 A
Lambda         → 문서 A, 문서 B
```

검색할 때는 역색인으로 후보 문서를 찾고, **BM25로 관련도 점수를 계산해 높은 점수부터 보여준다.**
점수 계산 등에 필요한 토큰의 등장 빈도와 문서 길이 같은 정보도 함께 관리한다.

```text
[문서를 등록할 때]
문서 → 토큰화 → 역색인 생성

[검색할 때]
검색어 → 토큰화 → 역색인으로 후보 문서 찾기
                  → BM25 점수 계산 → 점수순으로 출력
```

**검색 엔진**은 이런 문서 저장·분석·색인·검색 기능을 제공하는 시스템이며, 대표적인 예로 Elasticsearch가 있다.

### 2세대 벡터 검색

**1세대의 한계 보완**

- 1세대의 “같은 뜻인데 단어가 다르면 어떻게 찾지?”라는 한계에서 출발한다.
- 예: "퇴근 후 러닝을 하고 나니 집중력이 좋아졌다." / "운동이 생산성에 도움이 됐던 경험"
- 두 문장은 단어 자체가 많이 다르기 때문에 BM25는 약할 수 있다.
- 문장을 단어로만 보지 않고 의미를 숫자 벡터로 바꾸어 비교한다.

**2세대 벡터 검색**

- 텍스트의 의미를 embedding vector로 변환하고, 질문과 문서 vector 간 유사도를 계산하여 의미적으로 가까운 문서를 찾는다.

**Embedding**

- 텍스트를 고차원 숫자 vector로 변환한다.
- 의미가 비슷한 텍스트가 vector 공간에서도 가까워지도록 표현한다.

**Cosine Similarity**

- 두 vector의 방향이 얼마나 비슷한지 측정한다.
- 질문 vector와 문서 vector의 의미적 유사도를 판단하는 데 사용한다.

**Vector Search**

1. 문서를 embedding하여 vector로 저장한다.
2. 질문도 같은 모델로 embedding한다.
3. 질문 vector와 가까운 문서 vector를 검색한다.

**ANN**

- 데이터가 많아 모든 vector를 비교하면 느리기 때문에 정확도를 일부 양보하고 가까운 vector를 빠르게 찾는 방식이다.

**HNSW**

- ANN을 구현하는 대표적인 vector index 구조이다.

**한계**

- 정확한 고유명사, 숫자, 코드, 버전 등은 keyword search가 더 유리할 수 있다.
- embedding 모델 품질에 검색 성능이 의존한다.
- 대규모 환경에서는 빠른 검색을 위해 HNSW 같은 ANN 인덱스와 운영 비용이 필요하다.
