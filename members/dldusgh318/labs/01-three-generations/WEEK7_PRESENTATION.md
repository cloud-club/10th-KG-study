# 7주차: 프로젝트 기록을 정리하고 MCP로 조회하기

지난주까지는 내 프로젝트 문서를 검색하고, 문서에서 뽑은 사실을 지식 그래프로 연결하는 데 집중했다. 이번에는 이 데이터를 실제로 쓸 수 있을지 확인해 보고 싶었다. 예를 들어 이력서를 쓰다가 “Kafka를 사용해 봤다고 적어도 되나?”가 궁금해졌을 때, AI가 내 기록을 조회하고 구현 경험과 검토 기록을 구분해 주는 식이다.

이를 위해서는 AI에 도구만 연결해서는 부족했다. 그래프에 기술 이름만 들어 있거나, 제안한 내용을 구현한 것으로 저장했다면 조회 결과도 믿기 어렵기 때문이다. 그래서 이번 실습은 **스키마 수정과 표본 검수, 전체·증분 추출, 재평가, MCP 서버 연결** 순서로 진행했다.

## 검색만으로 부족했던 정보

RAG는 질문과 관련된 문서를 찾아 LLM의 답변 근거로 주는 방식이다. 내 구현에서는 단어가 잘 맞는 문서를 찾는 BM25 검색과 문장 의미가 가까운 문서(청크)를 찾는 벡터 검색을 합쳤다.

문제는 필요한 연결이 질문에 직접 드러나지 않는 경우였다. 내가 진행한 AI 코드 보안 분석 프로젝트인 **SeCause**에서는 분석 요청을 백그라운드 작업으로 넘기기 위해 Redis와 RQ를 사용했다. Redis는 데이터를 빠르게 읽고 쓰는 저장소이고, RQ는 Redis를 이용해 Python 작업을 백그라운드에서 실행하는 도구다. 그런데 “SeCause 작업 큐에 쓴 기술을 다른 프로젝트에서도 썼나?”라고 물으면 질문에 Redis라는 이름이 없다. 검색기가 SeCause 설명만 가져오면 다른 프로젝트의 Redis 경험으로 넘어가기 어렵다.

팀빌딩 서비스인 **TEAMFICIAL(팀피셜)**에서는 같은 Redis를 지원자 수 조회 캐시로 사용했다. 두 프로젝트는 Redis로 연결되지만 용도는 다르다. 이처럼 문서 사이에 숨어 있는 연결을 따라가기 위해 지식 그래프를 만들었다. 다만 그래프를 추가했다고 답변이 자동으로 좋아지는 것은 아니었고, 이후 전체 데이터 평가에서 그 한계가 드러났다.

## 기술 사용과 장애를 구분하도록 스키마 수정

처음 스키마는 프로젝트, 기술, 기술 사용례의 세 종류로 시작했다. 프로젝트와 기술만 연결하면 “Redis를 썼다”까지만 표현할 수 있어서, 그 사이에 `TechnologyUse`라는 사용례 노드를 넣었다. 사용례 하나가 “어느 프로젝트에서 어떤 기술을 무슨 목적으로, 어떤 상태로 사용했는가”를 나타낸다.

예를 들어 팀피셜의 Redis 사용례에는 지원자 수 캐시라는 목적과 구현 상태를 붙인다. 반면 채용공고·통근 시간 관련 기업과제인 **직행**에는 통근 시간을 저장하기 위한 Redis 활용이 제안 상태로 남아 있다. 같은 Redis라도 `implemented`는 구현, `proposed`는 제안·검토, `not_implemented`는 명시적인 미구현으로 구분한다. 상태를 찾지 못한 경우는 비워 두며, 구현으로 간주하지 않는다.

그런데 트러블슈팅 문서를 추출하면서 문제가 생겼다. 기존 스키마에는 장애를 담을 자리가 없어, Redis 타입 불일치 같은 문제까지 별도의 기술 사용례로 표현하게 됐다. 이 구조로는 “어떤 기술을 썼나?”와 “그 기술을 쓰다 무슨 문제가 생겼나?”를 구분하기 어려웠다.

그래서 실제 발생한 문제를 나타내는 `Issue`를 추가했다. Issue는 문제가 발생한 사용례에 연결하고 원인·해결·검증을 따로 기록한다. 기존 술어 중 `replaces`는 v0 추출에서 사용이 없고 이번 질문에도 필요하지 않아 제거했다. 술어는 노드 사이의 관계나 값을 나타내는 이름으로, 변경 후 스키마는 클래스 4종과 술어 8종이 됐다.

| 표현하려는 정보 | 스키마 |
|---|---|
| 사용례가 속한 프로젝트와 사용 기술 | `partOf`, `usesTechnology` |
| 사용 목적과 구현 상태 | `hasPurpose`, `hasStatus` |
| 문제가 발생한 사용례 | `occurredIn` |
| 문제의 원인·해결·검증 | `hasCause`, `hasFix`, `hasVerification` |

이때 “발생할 수 있다”는 잠재 위험을 실제 장애로 저장하지 않도록 했다. 원인·해결·검증 값도 원문 표현을 사용하게 바꿨다. 표본에서 근거 문구는 실제로 존재하지만, 추출한 원인은 원문에 없는 내용으로 해석한 경우가 있었기 때문이다. **근거가 원문에 있다는 검사와 그 근거가 주장을 뒷받침한다는 검사는 다르다.**

## 검증을 강화했더니 정상 데이터도 사라졌다

스키마를 바꾼 뒤에는 같은 청크 20개로 추출을 반복했다. 기술 목록만 나열된 줄에서 사용례를 만들지 않고, 메시지 큐나 아웃박스 패턴 같은 일반 범주·설계 패턴도 구체적인 기술로 뽑지 않도록 했다. 특히 제목만 보고 구현 여부나 원인을 판단하는 것을 막으려고 검증 코드에서 헤더·제목 근거를 차단했다.

그런데 모든 관계에 이 규칙을 적용하자 유효한 사용례까지 대거 사라졌다. 본문에는 기술 사용 사실이 있지만 어느 프로젝트의 문서인지는 경로 헤더에만 적힌 경우가 있었기 때문이다. 프로젝트 연결인 `partOf`가 탈락하고, 필수 연결이 없다는 이유로 사용례를 삭제하자 여기에 연결된 Issue까지 연쇄적으로 삭제됐다.

이를 고치기 위해 사실의 근거와 문서 소속 정보를 분리했다. 프로젝트가 명확한 문서는 코드가 문서·헤더 경로를 보고 `partOf`를 붙이고 출처를 `metadata`로 기록한다. 상태·목적·기술 사용·원인·해결·검증에는 계속 본문 근거를 요구한다. 여러 프로젝트가 섞여 귀속을 결정하지 못하면 사용례를 지우는 대신 프로젝트 미확정으로 남겼다.

| 같은 20개 청크의 추출 버전 | TechnologyUse 출현 수 | Issue 출현 수 |
|---|---:|---:|
| Issue를 추가한 첫 v1 표본 | 41 | 3 |
| 헤더 차단·필수 연결 제거를 강하게 적용 | 6 | 0 |
| 프로젝트 귀속을 메타데이터로 분리 | 35 | 2 |

위 수치는 청크별 노드 출현 횟수의 합이며, 병합 후 고유 노드 수가 아니다. 매번 LLM을 새로 호출했으므로 변화 전체를 검증 코드 하나의 효과로 단정할 수도 없다. 다만 삭제 로그에서 `partOf` 손실이 사용례와 Issue의 연쇄 삭제로 이어진 것은 확인했다. 규칙을 강하게 만들기보다 **어떤 정보에 어떤 근거를 요구할지 나누는 것**이 필요했다.

## 문서 업데이트와 출처 구분

표본 검수 후 전체 추출을 진행했고, 새 노션 export를 받으면서 증분 처리도 추가했다. 검색 코퍼스는 기존 1,562개 청크에서 새 버전 1,925개 청크로 바뀌었다. 전체를 다시 추출하는 대신 내용이 같은 청크와 이동한 청크는 기존 결과를 재사용하고, 변경·추가 및 프로젝트 매핑을 다시 확인해야 하는 청크만 처리했다. 청크 ID는 문서 경로·헤더 경로·헤더 내 순번으로 만들고, 내용 해시와 옛 ID 매핑도 보존했다.

여기서 출처 등급도 나눴다. 프로젝트 작업·PR·트러블슈팅 기록은 1차 출처로, 면접 준비를 위해 다시 가공한 문서는 2차 출처로 구분했다. 2차 문서도 검색에는 필요하지만, 같은 경험을 반복해서 요약하거나 검토한 기술을 언급할 수 있어 새 그래프 추출에서는 제외했다. 기존에 적재된 2차 근거는 지우지 않고 `source_tier=secondary`로 표시했다. 따라서 검색 코퍼스 1,925개 전체를 모두 새로 그래프 추출한 것은 아니다.

| 고유 노드 | 증분 전 | 증분 직후 |
|---|---:|---:|
| Project | 3 | 5 |
| Technology | 111 | 131 |
| TechnologyUse | 416 | 543 |
| Issue | 31 | 55 |

프로젝트 범위에는 운영·배포 장애 기록이 있는 **청바지**, 알림과 거리순 조회 등의 기능을 다룬 **모앤디**도 추가했다. 증분 추출 API 호출은 413회, 사용례 병합 판정 호출은 361회였고, 애매한 병합 집합 13개는 적용하지 않았다. 기존 그래프는 보존하고 새 버전을 별도 스키마와 Neo4j 인스턴스에 적재했다.

숫자가 늘었다고 실제 경험이 그만큼 늘어난 것은 아니다. 같은 경험을 여러 문서에 적으면 중복 노드가 생긴다. 사용례 병합은 프로젝트·기술·상태가 같은 후보 안에서 목적과 근거를 비교하고, 확실히 같은 경우만 적용했다. 프로젝트·기술·상태가 같아도 목적이 다르면 별도 사용례이므로 이 세 값만으로 무조건 합치지는 않았다.

## 전체 그래프에서 다시 평가한 결과

평가는 검색만 사용하는 v1, 검색 결과에서 그래프를 확장하는 v2.1, 질문을 Neo4j 질의 언어인 Cypher로 바꾸는 Text2Cypher를 비교했다. 정답 근거로 미리 지정한 문서 조각을 정답 청크라고 하고, 그 조각이 실제 답변 컨텍스트에 들어왔는지도 확인했다. 질문 7개를 방식별로 3회씩 실행했지만 전체 그래프가 표본 그래프보다 항상 좋은 결과를 내지는 않았다.

앞서 소개한 “SeCause 작업 큐의 기술을 다른 프로젝트에서도 썼나?”가 평가 ID `X01`이다. 이 질문에서는 Redis 사용례가 49개로 늘면서 기존 허브 차수 제한 20에 걸렸다. 허브는 여러 대상을 연결하는 중심 노드인데, 가장 필요한 연결점인 Redis를 오히려 확장에서 제외한 것이다.

이를 고치면서 차수를 사용례 수가 아니라 서로 다른 프로젝트 수로 세도록 바꿨다. Redis는 이 기준에서 5였고 상한은 10으로 설정했다. 확장 후보도 프로젝트·기술·상태별로 묶어 질문과 관련도가 가장 높은 사용례 하나만 근거 회수 대상으로 삼았다. X01의 필요한 경력기술서 청크는 수정 전 0/3회에서 수정 후 3/3회 그래프 경유로 포함됐다.

장애 기록도 청크마다 별도 Issue로 갈라져 있었다. 처음에는 같은 문서·상위 헤더의 연속 청크이면서 동일한 사용례를 가리킬 때만 합쳤다. 이후 사용례가 달라도 같은 기술을 가리키거나 한쪽 기술이 미확정이면 병합하도록 완화했다. 두 차례 규칙 병합으로 전체 Issue는 55개에서 51개, 다시 49개가 됐다. 원인·해결·검증과 각 청크 근거는 합쳐 보존했다.

| 재평가 대상 | 수정 전 | 수정 후 3회 | 남은 문제 |
|---|---|---|---|
| X01: 프로젝트 사이 Redis 경험 연결 | 오답 | 모두 부분 정답 | 근거 포함률은 0.5에서 1.0으로 개선했지만 갱신 경로 설명 누락, 인용 실패 2/3 |
| H01: 운영 배포 중 DB 인증 장애의 원인·수정 | 부분 정답 | 모두 부분 정답 | 필요한 원인·수정 설명이 여전히 빠짐 |

이 재평가는 두 질문의 v2.1만 총 6회 추가 실행했고, 나머지 57건은 기존 결과를 재사용했다. Issue를 합쳐도 모델이 처음부터 추출하지 않은 검증 사실이 생기지는 않았다. 필요한 근거를 회수하는 것, 그래프에 사실을 정확히 저장하는 것, 답변과 인용을 올바르게 생성하는 것은 각각 확인해야 했다.

## 조회 기능을 MCP 도구로 제공하기

데이터를 정리하고 나니 매번 스크립트나 DB에서 직접 조회하기보다, 이력서나 면접 답변을 작성하는 대화에서 바로 쓰고 싶었다. 이를 위해 MCP(Model Context Protocol)를 사용했다. MCP는 AI 클라이언트가 외부 프로그램의 도구를 호출하고 결과를 받는 연결 규약이다. 이번에는 기존 검색·DB 조회 코드를 `my-kg`라는 로컬 서버의 도구로 제공했다.

서버는 질문의 최종 답변을 만들지 않는다. 데이터와 근거를 반환하면 대화 중인 Claude가 이를 해석한다. 그래프 쿼리도 서버가 별도 LLM을 호출해 만드는 대신, Claude가 스키마를 확인하고 직접 작성하도록 했다. 따라서 서버가 추가 LLM API 호출을 만들지는 않지만 Claude 이용 비용까지 없어지는 것은 아니다.

| 도구 | 용도 |
|---|---|
| `search_documents` | 과정이나 설명을 문서에서 검색 |
| `explore_graph` | 같은 기술을 쓰는 다른 사용례로 확장. 다른 도구로 교차 확인 필요 |
| `technology_experience` | 기술별 프로젝트·목적·상태·근거 조회 |
| `list_issues` | 장애의 원인·해결·검증 조회 |
| `proposed_only` | 제안 상태 사용례 점검 |
| `get_graph_schema` | 실제 그래프 구조와 값 확인 |
| `run_cypher` | 개수·순위·상태 조건을 그래프 쿼리로 조회 |

설명형 질문은 검색이, 집계형 질문은 Cypher가 맞힌 평가 결과를 도구 설명에 반영했다. 실패가 남아 있는 관계형 조회는 확정 답으로 사용하지 말고 교차 확인하도록 적었다. 별도 라우터는 만들지 않았으며, AI가 설명을 보고 적절한 도구를 선택하는지는 별도로 검증해야 한다.

서버는 표준 입출력으로 통신하는 로컬 stdio 방식이며 MCP용 네트워크 포트를 열지 않는다. DB는 읽기 전용으로 사용하고, Cypher는 쓰기·CALL·주석·다중 문장을 차단하며 10초·200행 제한을 둔다. 다만 로컬이라고 원문이 AI 서비스에 전달되지 않는 것은 아니다. 도구 결과에 포함한 원문 일부와 근거는 Claude 대화로 넘어간다.

한 가지 구현 범위도 구분해야 한다. 앞서 프로젝트 수 기준 허브 확장을 평가한 코드는 별도 실행기이고, **현재 MCP의 `explore_graph`에는 여전히 기존 이웃 수 20 기준이 남아 있다.** 수정 후 평가 결과를 그대로 MCP 성능으로 설명할 수는 없다.

## Kafka 질문으로 확인한 것

실사용 테스트에서 확인하고 싶었던 질문은 “이력서에 Kafka를 써봤다고 써도 돼?”였다. Kafka는 메시지·이벤트를 저장하고 전달하는 플랫폼이다. 작업 큐를 구현한 내 기록에 대안 비교 대상으로 등장할 수 있지만, 기술명이 문서에 있다는 사실과 실제 구현 경험은 다르다.

기존 도구 로직 직접 호출 테스트에서는 Kafka 구현을 뒷받침하는 1차 근거가 0건이었고, 확인된 기록은 2차 문서의 대안 비교 내용이었다. 반면 SeCause의 Redis + RQ 작업 큐는 구현 상태의 근거가 있었다. 이 결과라면 Kafka를 구현했다고 적기보다, 검토한 대안으로 설명하고 실제 구현 경험은 Redis + RQ 중심으로 쓰는 편이 맞다. 다만 0건이라는 결과만으로 내 모든 경험에 Kafka가 없었다고 단정할 수는 없다. 현재 기록에서 구현 주장을 확인하지 못했다는 의미다.

여기서 `proposed_only`만 호출하면 충분한 것은 아니다. 이 도구는 그래프에 제안 상태로 저장된 사용례를 찾는다. 2차 문서의 대안 비교에만 있는 기술은 그 목록에 없을 수도 있으므로, 기술 경험 조회와 문서 검색을 함께 확인해야 한다.

시연도 이 질문으로 진행한다. 먼저 Claude Code의 `/mcp`에서 `my-kg` 연결과 도구 7개를 확인한 뒤, 아래 질문을 입력해 실제 호출 도구와 조회 범위를 보여준다. 화면에서는 긴 원문 대신 문서 경로·근거 ID·구현 상태를 중심으로 확인한다.

```text
이력서에 Kafka를 써봤다고 써도 돼?
my-kg로 1차 구현 근거와 2차 검토 기록을 구분해서 확인해줘.
원문은 길게 인용하지 말고 문서 경로와 근거 ID를 보여줘.
확인 가능한 비동기 처리 경험이 있으면 함께 알려줘.
```

현재 검증 범위에는 주의가 필요하다. 실제 stdio 클라이언트로 서버 초기 연결과 도구 목록 조회를 확인했고, 도구 7개도 각각 실DB 호출에 성공했다. 하지만 Redis 경험 정리·기술 집계·장애 사례·Kafka 질문의 네 가지 실사용 테스트에서는 MCP 세션이 붙지 않아 Claude Code가 `kg_tools.py`를 직접 호출했다. 같은 도구 로직의 결과이지만, **MCP를 통한 자동 도구 선택까지 성공한 결과는 아니다.** 발표 전에는 연결된 세션에서 Kafka 질문을 다시 확인해야 한다.

## 남은 문제와 다음 확인

이번에는 그래프의 규모를 늘리는 것보다 데이터가 어떤 주장을 뒷받침하는지 구분하는 과정이 중요했다. 사용 목적과 상태를 분리해 둔 덕분에 검토한 기술을 구현 경험으로 쓰는 오류를 점검할 수 있었고, 출처 등급을 나누면서 2차 문서에만 있는 경험도 발견했다. 반면 그래프의 구조가 맞아도 잘못된 원인 해석이 남을 수 있었고, 근거 회수에 성공해도 답변이나 인용은 틀릴 수 있었다.

증분 직후에는 사용례 543개 중 목적 결측이 92개, 프로젝트 미확정이 258개였다. Issue 55개 중 검증 내용이 채워진 것은 10개뿐이었다. 이는 해당 시점의 추출 그래프 기준이며, 원문에도 정보가 없다는 뜻은 아니다. 후속 병합으로 Issue 수는 줄었지만 누락된 사실까지 복구되지는 않았다.

다음에는 MCP 세션에서 Kafka 질문의 실제 도구 선택을 검증하고, 평가한 허브 확장 개선을 MCP에도 반영해야 한다. 프로젝트 미확정과 보류 병합도 확인하되, 목적이 다른 경험을 노드 수를 줄이려고 합치지는 않을 생각이다. 그래프가 커졌는지보다 **근거가 있는 경험을 정확하게 꺼내 쓸 수 있는지**를 기준으로 계속 확인하려 한다.
