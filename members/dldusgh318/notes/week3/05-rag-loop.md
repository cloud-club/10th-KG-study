# **05. RAG — 검색 결과에서 근거 있는 답변까지**

앞에서는 **BM25 + Vector Search를 RRF로 합쳐 Hybrid Search**를 만들었다.

```
질문
 ↓
BM25 + Vector
 ↓
RRF
 ↓
관련 chunk Top-k
```

이제 관련 문서는 꽤 잘 찾을 수 있다.

하지만 아직 시스템이 해주는 것은 **“관련 문서를 찾아주는 것”**뿐이다. 우리가 원하는 건 내 데이터에 자연어로 질문했을 때 **검색된 기록을 바탕으로 답변하고, 그 답변의 근거까지 보여주는 것**이다.

→ 검색 결과를 LLM의 Context로 넣어 답변을 생성하는 **RAG(Retrieval-Augmented Generation)** 를 붙여보자.

---

## **핵심 개념**

RAG의 기본 흐름은 다음과 같다.

```
[1] 질문
     ↓
[2] 검색
     ↓
[3] Context 조립
     ↓
[4] LLM 답변 생성
     ↓
[5] 근거 인용
```

**RAG = LLM이 기억만으로 답하게 하지 않고, 먼저 관련 데이터를 검색해서 근거와 함께 답하게 만드는 구조**

중요한 것은 **각 단계가 따로 실패할 수 있다는 것**이다.

| **실패 지점** | **무슨 문제인가** |
| --- | --- |
| 검색 | 필요한 chunk를 못 찾음 |
| Context 조립 | 찾았는데 LLM에게 제대로 못 넘김 |
| 생성 | 정보가 있는데 LLM이 제대로 활용하지 못함 |
| 인용 | 답은 했는데 엉뚱한 근거를 제시함 |

따라서 에이전트가 틀렸을 때 단순히 **“LLM이 틀렸다”**고 하면 안 된다.

**어느 단계에서 실패했는지 찾는 것이 RAG 디버깅의 핵심이다 ‼️**

---

## **1. 검색 — 무엇을 LLM에게 줄까?**

검색은 앞에서 만든 Hybrid Search를 그대로 활용한다.

```
BM25 ─────┐
          ├─ RRF → 관련 chunk
Vector ───┘
```

그렇다고 검색 결과를 전부 LLM에게 넣는 것은 아니다.

```
너무 적게 가져옴
→ 필요한 정보가 빠질 수 있음

너무 많이 가져옴
→ 관련 없는 정보 증가
→ Context가 길어짐
```

우선 **Top-5 정도를 Context에 넣고 실험**해보는 것으로 시작한다.

여기서 중요한 점은 **검색 단계에서 놓친 정보는 이후 LLM이 복구할 수 없다는 것**이다.

```
정답 chunk 검색 실패
        ↓
Context에 없음
        ↓
LLM도 해당 정보를 볼 수 없음
```

그래서 앞에서 `Recall@k`를 측정했던 것이 RAG에서도 중요해진다.

---

## **2. Context 조립 — 검색 결과를 어떻게 넘길까?**

검색된 chunk를 그냥 이어 붙이는 것보다 **LLM이 사용할 수 있는 형태로 정리해서 전달**해야 한다.

예를 들어:

```
[1] (Notion / 2026-03-14)
캡스톤 발표 자료 만드느라 밤새웠다...

[2] (Kakao / 2026-03-12)
연호: 발표 준비 어떻게 돼가?
동욱: 아직 데모가 안 붙었어...

[3] (Notion / 2026-03-15)
발표 끝났다. 질문이 예상보다 많이 나왔다...
```

처럼 각 chunk에:

- 번호
- 출처
- 날짜
- 본문

을 붙여준다.

특히 `[1]`, `[2]`처럼 짧은 번호를 붙여두면 나중에 LLM이 **어떤 chunk를 근거로 사용했는지 표시**하기 쉬워진다.

---

## **3. Context가 길면 다 읽을까? — `Lost in the Middle`**

LLM의 Context Window가 크다고 해서 **모든 위치의 정보를 똑같이 잘 사용하는 것은 아니다.**

연구에서는 관련 정보가 긴 Context의 **중간에 있을 때 성능이 떨어지는 현상**이 관찰됐다.

→ 이를 **`Lost in the Middle`**이라고 한다.

```
Context

[중요한 정보]   ← 비교적 잘 봄

[정보]
[정보]
[중요한 정보]   ← 놓칠 가능성 ↑
[정보]
[정보]

[중요한 정보]   ← 비교적 잘 봄
```

따라서 Context가 길어질수록 **무작정 많은 chunk를 넣는 것이 항상 좋은 것은 아니다.**

필요하다면 관련도가 높은 chunk를 앞뒤에 배치하는 식으로 순서를 조정할 수 있다.

또 토큰 예산을 초과한다면 문장을 중간에서 잘라내기보다 **관련도가 낮은 chunk부터 통째로 제외하는 편이 낫다.**

검색만 중요한 게 아니라 **검색 결과를 LLM에게 어떻게 보여주는지도 RAG 품질에 영향을 준다.**

---

## **4. 생성 — 내 데이터만 보고 답하게 하기**

Context를 만들었다면 질문과 함께 LLM에게 전달한다.

프롬프트에서 가장 중요한 규칙은 단순하다.

```
아래 Context에 있는 정보만 사용해서 답하세요.

Context에 답을 뒷받침할 정보가 없다면
추측하지 말고 "기록에서 찾을 수 없습니다"라고 답하세요.

답변에는 사용한 근거 번호를 표시하세요.
```

왜 이게 중요할까?

😱 LLM은 Context에 정보가 없어도 **자신이 알고 있는 일반 지식으로 답을 만들어낼 수 있기 때문**이다.

개인 데이터 에이전트에서는:

```
내 기록에는 없음
      ↓
LLM이 추측
      ↓
마치 내 기록에 있던 것처럼 답변
```

하는 것이 가장 위험한 실패 중 하나다.

그래서 **“Context에 없으면 모른다고 답한다.”**는 규칙이 필요하다.

---

## **5. 근거 인용 — 답변이 어디에서 나왔는가?**

단순히:

“캡스톤 준비하면서 밤을 샜습니다. [1]”

라고 하면 출처는 알 수 있다. 하지만 `[1]`이 긴 chunk라면 **정확히 어느 문장을 근거로 답했는지**는 알기 어렵다.

그래서 이번 실습에서는 근거 문장까지 같이 반환하게 할 수 있다.

```json
{
  "answer": "캡스톤 발표 준비로 밤을 샜습니다.",
  "citations": [
    {
      "source": 1,
      "snippet": "캡스톤 발표 자료 만드느라 밤새웠다"
    }
  ]
}
```

여기서 `snippet`은 **원문의 문장을 그대로 가져오도록** 한다.

그러면 프로그램에서도 간단하게 확인할 수 있다.

```python
snippet in original_chunk
```

결과가 `False`라면?

→ LLM이 실제 원문에 없는 근거를 만들어냈을 가능성이 있다.

즉,

```
답변 생성
 ↓
근거 문장 반환
 ↓
원문에 실제 존재하는지 확인
 ↓
검증된 인용
```

까지 해야 단순히 **“인용이 달린 답변”**이 아니라 **“검증 가능한 답변”**이 된다.

---

## **6. 모르면 모른다고 해야 한다..**

개인 데이터 에이전트에서 가장 피하고 싶은 것은:

**근거가 없는데 자신 있게 답하는 것** 이다.

이를 줄이기 위해 여러 단계에서 방어할 수 있다.

```
① 검색
관련 정보가 없으면 중단
        ↓
② 생성
Context 밖의 내용은 추측 금지
        ↓
③ 인용 검증
근거 문장이 원문에 실제 존재하는지 확인
```

최종적으로:

```json
{
  "answer": "기록에서 찾을 수 없습니다.",
  "citations": [],
  "grounded": false
}
```

처럼 **답변에 충분한 근거가 있는지 표시**할 수도 있다.

좋은 개인 데이터 에이전트는 모든 질문에 답하는 에이전트가 아니라, **모르는 질문을 구분할 수 있는 에이전트**다.

---

## **7. 실패했으면 어디서 실패했는지 기록한다**

이번 주에는 에이전트가 못 답한 질문도 중요한 결과다.

예를 들어:

**“부산 같이 간 사람들 중 같은 회사 다니는 사람?”** 에 실패했다고 하자.

여기서 그냥 `답변 실패 ❌` 로 기록하면 왜 실패했는지 알 수 없다.

대신!!

```
질문
 ↓
부산 관련 chunk 검색 성공
 ↓
같이 간 사람 확인
 ↓
그 사람들의 회사 정보는 검색되지 않음
 ↓
답변 실패
```

처럼 **어느 단계에서 필요한 정보가 끊겼는지** 기록해야 한다.

실패 유형도 다음처럼 나눌 수 있다.

```
retrieval  → 필요한 정보를 검색하지 못함
assembly   → 검색했지만 Context에서 빠짐
generation → Context에 있는데 LLM이 활용 못함
citation   → 답변의 근거가 잘못됨
no_data    → 애초에 내 데이터에 정보가 없음
```

이렇게 해야 다음에 **무엇을 개선해야 하는지** 알 수 있다~

## **더 충격 실화‼️ RAG도 만능은 아니다**

Hybrid Search와 RAG를 붙이면 단일 질문에는 꽤 잘 답할 수 있다.

하지만 이런 질문은 여전히 어렵다.

**“부산 같이 간 사람들 중 같은 회사 다니는 사람?”**

왜냐하면 한 번의 검색으로 끝나는 질문이 아니기 때문이다.

```
① 부산에 같이 간 사람은?
        ↓
② 그 사람들은 어디에 다니지?
        ↓
③ 같은 회사인 사람은?
```

현재 RAG가 첫 질문으로 검색하면 `부산`과 관련된 여행 기록은 찾을 수 있다.

하지만 **그 사람들의 회사 정보는 부산과 전혀 관계없는 다른 chunk에 있을 수 있다.**

```
Query: "부산 같이 간 사람들 중 같은 회사 다니는 사람?"

검색
 ↓
[부산 여행 기록] ← 가져옴
[동욱 회사 정보] ← 못 가져옴
[채영 회사 정보] ← 못 가져옴
```

LLM이 아무리 똑똑해도 **Context에 없는 정보로 근거 있는 답을 만들 수는 없다.**

이것이 **Multi-hop Question**에서 기본 RAG가 부딪히는 문제다.

---

## **그래서 다음은?**

여기까지 오면 개인 데이터 에이전트 v1의 기본 구조가 완성된다.

```
사용자 질문
    ↓
BM25 + Vector
    ↓
RRF
    ↓
Context 조립
    ↓
LLM
    ↓
답변 + 근거
```

그런데 다중 홉 질문을 보면 새로운 문제가 보인다.

현재 시스템이 저장하고 있는 것은 결국:

```
Chunk A → 부산 여행 이야기
Chunk B → 동욱의 회사 이야기
Chunk C → 채영의 회사 이야기
```

처럼 **서로 떨어져 있는 문서 조각**이다.

하지만 우리가 정말 알고 싶은 것은:

```
나 ──같이 여행함──> 동욱
나 ──같이 여행함──> 채영

동욱 ──다님──> X회사
채영 ──다님──> X회사
```

같은 **정보 사이의 관계**다.

즉❗️ **청크는 문서 조각이지 관계가 아니다.**

검색을 더 잘하는 것만으로는 이 관계를 따라가기 어렵다.

그렇다면 문서 속 정보를 **`사람 - 관계 - 대상` 형태로 구조화해서 저장하면 어떨까?**

→ 다음 단계에서는 텍스트에서 **Entity와 Relation을 추출해 Triple 형태로 저장하는 방법**을 살펴본다.
