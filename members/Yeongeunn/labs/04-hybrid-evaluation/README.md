# BM25·벡터·RRF 검색 비교

같은 Notion 청크와 질문으로 키워드 검색, 벡터 검색, 순위 융합을 비교했다. 검색 결과를 본 뒤 설정을 바꾸지 않고 첫 설정의 결과와 실패 사례를 남겼다.

## 실험 설정

| 항목 | 설정 |
|---|---|
| 원본 가공 데이터 | Markdown 628개, 청크 1,477개 |
| 중복 처리 | 본문 공백 정규화 후 완전히 같은 청크를 하나로 합침 |
| 공통 검색 대상 | 중복 제거 후 1,369개 청크; 제목 + 본문 |
| BM25 | Elasticsearch nori, 검색기별 후보 30개 |
| 임베딩 | 로컬 `intfloat/multilingual-e5-small`, 384차원, CPU |
| 모델 revision | `614241f622f53c4eeff9890bdc4f31cfecc418b3` |
| 입력 구분 | 문서 `passage: `, 질문 `query: ` |
| 긴 청크 | 448토큰 창, 384토큰 간격으로 전 구간 처리; 창 벡터 평균 후 재정규화 |
| 벡터 검색 | pgvector 코사인 거리 정확 검색 |
| RRF | 두 검색기의 순위, c=60, 동일 청크 ID로 병합 |
| 평가 | 질문 10개, 상위 5개, 지정 근거 그룹 기준 Recall@5 |

원래 청크를 임베딩 모델의 길이에 맞춰 잘라 버리지 않도록 내부 창을 사용했다. 이 창 평균 방식은 실험에서 선택한 집계 방법이며 모델의 기본 문서 인코딩과 동일한 설정은 아니다. 같은 본문이 아닌 겹치는 청크나 유사 문서는 그대로 남아 있어 상위 결과를 여러 개 차지할 수 있다.

### 정답 근거의 범위

질문과 필수 근거 그룹은 검색 실행 전에 원문을 대조해 지정했다. AI 보조로 작성한 평가 초안이며 작성자 검토가 남아 있다. 각 그룹은 특정 사실을 뒷받침하는 지정 청크들을 포함하고, 복제 청크는 같은 것으로 처리한다. 하나의 청크가 여러 필수 사실을 포함하면 여러 그룹을 충족할 수 있다.

다른 문서에도 같은 사실이 있을 수 있으므로 **여기서 측정한 것은 지정한 근거의 회수율**이다. 모든 의미상 관련 문서에 대한 완전한 정답셋이나 일반적인 검색 성능으로 해석하지 않는다. 실제로 q05에서는 지정 문서를 놓쳤지만 다른 문서의 근거로 답한 경우가 있었다. 별도 테스트셋을 둔 최종 평가가 아닌 10문항 파일럿이다.

## 결과

| 검색 방식 | 평균 지정 근거 Recall@5 | 필수 근거 전체 회수 |
|---|---:|---:|
| BM25 | 0.60 | 5/10 |
| 벡터 | 0.70 | 7/10 |
| RRF | 0.55 | 5/10 |

| 질문 ID | 유형 | BM25 | 벡터 | RRF |
|---|---|---:|---:|---:|
| q01 | 정확한 용어 | 1.0 | 0.0 | 0.0 |
| q02 | 다른 표현 | 0.0 | 0.0 | 0.0 |
| q03 | 정확한 용어 | 1.0 | 1.0 | 1.0 |
| q04 | 조건 | 1.0 | 1.0 | 1.0 |
| q05 | 다른 표현 | 0.0 | 1.0 | 0.0 |
| q06 | 다른 표현 | 0.0 | 0.0 | 0.0 |
| q07 | 정확한 용어 | 1.0 | 1.0 | 1.0 |
| q08 | 조건 | 1.0 | 1.0 | 1.0 |
| q09 | 다중 홉 | 0.5 | 1.0 | 0.5 |
| q10 | 다중 홉 | 0.5 | 1.0 | 1.0 |

### RRF가 항상 좋아지지는 않았다

- q01의 지정 근거는 BM25 1위였으나 벡터 후보 30개에는 없었다. RRF에서는 6위로 밀려 상위 5개에서 빠졌다.
- q05는 반대로 벡터 1위의 지정 근거가 BM25 후보에 없었고 RRF에서는 7위였다.
- 두 검색기에 함께 등장하는 문서는 두 번 점수를 받는다. c=60에서는 한 검색기의 높은 순위 하나보다 양쪽의 중간 순위가 더 유리할 수 있다.
- q10에서는 두 검색 결과가 보완되면서 BM25만으로 놓친 지정 근거를 RRF가 회수했다.

이 결과만으로 RRF를 버리거나 파라미터를 튜닝하지 않았다. 다음 비교에서는 평가셋의 대체 근거를 먼저 검토하고, 별도의 개발 질문으로 후보 수·가중치·중복 제거를 실험할 수 있다.

### grep과 HNSW의 위치

질문 문장 전체를 고정 문자열로 찾는 기준선은 10문항 모두 일치 결과가 없었다. 반면 실제 문자열 `회원탈퇴`를 JSONL에서 `rg -c -F`로 찾으면 24개 줄이 일치했다. 문자열 검색은 동작하지만 자연어 질문 전체와 같은 문장이 문서에 있어야 한다. 이 기준선은 형태소 분석이나 관련성 순위가 있는 검색기와 같은 조건의 키워드 검색으로 해석하지 않는다.

HNSW는 별도 인덱스로 생성해 정확 검색의 상위 5개 이웃과 비교했다. `m=16`, `ef_construction=64`, `ef_search=100`에서 10질의 평균 이웃 일치율은 1.0이었다. 이는 **정확 검색 결과와 일치한 비율**이며 위 표의 정답 근거 Recall@5와 다르다. 작은 데이터의 한 설정에서 확인한 결과다.

## 검색과 생성의 차이

대표 질문 4개를 세 방식으로 답변 생성해 12개 답변을 비교하고, 누락 질문 1개에 지정 근거를 직접 넣는 oracle 실험을 추가했다. 모델은 `gemini-3.1-flash-lite`, 같은 프롬프트와 상위 근거 5개를 사용했다. 대표 질문은 검색 결과를 확인한 뒤 진단 목적으로 선택했으므로 독립적인 생성 평가셋이 아니다.

| 관찰 | 해석 |
|---|---|
| q01: BM25는 구체 조건에 답했지만 벡터·RRF는 근거 부족으로 답변을 보류 | 필요한 근거 회수 실패 |
| q05: RRF가 지정 문서를 놓쳤지만 대체 문서에서 핵심 인증 방식을 답함 | 평가 라벨의 대체 근거 누락 |
| q09: BM25 답변이 상태값과 소프트 삭제를 서로 충돌한다고 단정 | 의미 검토 필요; 두 표현은 함께 성립할 수도 있음 |
| q10: 벡터가 필수 근거를 모두 찾았지만 서비스와 거래 유형을 혼동 | 검색 성공과 답변 정확성은 별개 |
| q10: RRF는 필요한 서비스·메서드·경로를 답함 | 이번 다중 홉 질문은 텍스트 RAG로도 답할 수 있었음 |
| q02: 지정 근거를 직접 제공하자 필요한 상태 조건을 답함 | 이 사례는 검색 개선 여지가 있음; 모든 실패의 원인을 증명하지는 않음 |

정답률 하나로 합치지 않고 핵심 사실, 근거, 조건, 범위 표현을 따로 검토했다. 원문과 실제 답변은 로컬 평가 폴더에 보관한다.

## 실행

Python 3.11에서 실행했다. 저장소 루트 기준:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r members/Yeongeunn/labs/04-hybrid-evaluation/requirements.txt
docker compose up -d postgres elasticsearch
```

모델은 최초 실행 때 다운로드하며 문서 임베딩은 로컬에서 계산한다. `.env`의 기존 DB 설정을 사용한다.

### 저장된 결과만 확인

```bash
python -m json.tool data/Yeongeunn/evaluation/results.json
python -m json.tool data/Yeongeunn/evaluation/ann-check.json
```

### 벡터 생성·적재와 평가 재현

먼저 로컬 `data/Yeongeunn/evaluation/qrels.json`에 질문과 근거를 작성한다. 기존 실험 파일을 사용할 때는 같은 청크 파일이 필요하다. 개인 원문을 포함하므로 qrels는 저장소에 넣지 않았다. 파일 구조는 아래와 같으며 값은 설명용이다.

```json
{
  "labeling": "근거 선정 및 검토 방법",
  "corpus_sha256": "가공 JSONL 파일의 SHA-256",
  "questions": [{
    "id": "q01", "type": "exact", "question": "질문",
    "evidence_groups": [{"id": "required-fact", "chunk_ids": ["실제 청크 ID"]}]
  }]
}
```

```bash
python members/Yeongeunn/labs/04-hybrid-evaluation/src/search_lab.py build
python members/Yeongeunn/labs/04-hybrid-evaluation/src/search_lab.py evaluate
python members/Yeongeunn/labs/04-hybrid-evaluation/src/check_ann.py
```

`build`는 전용 실험 테이블 `yeongeunn_search_eval.chunks`와 인덱스 `yeongeunn-notion-eval-v1`을 같은 스냅샷으로 교체한다. 기존 W3 테이블·인덱스는 유지한다. 벡터 캐시와 모델 revision을 기록하며, 원문 해시가 달라지면 중단한다. 평가의 벡터 검색은 HNSW 생성 이후에도 정확 검색을 사용한다.

### 자연어 질문과 답변 비교

```bash
python members/Yeongeunn/labs/04-hybrid-evaluation/src/search_lab.py ask \
  --method rrf --query '<질문>'
python members/Yeongeunn/labs/04-hybrid-evaluation/src/answer_check.py
```

`ask`는 새 Gemini 호출이다. `answer_check.py`는 q01·q05·q09·q10 × 세 방식과 q02 oracle을 실행하며 이미 저장된 답변은 재사용한다. 다른 평가셋에서 쓰려면 해당 ID와 진단 질문을 먼저 조정한다. 새 실험을 시작할 때 이전 답변을 로컬에 보존하고 별도 실행 폴더를 사용하는 방식으로 관리한다.

## 검증과 한계

- 두 저장소의 실험 청크 수 1,369개 일치.
- RRF 순서, 한 검색기에만 있는 후보, 복제 근거와 복수 근거 그룹의 채점 검사.
- HNSW 인덱스 사용을 실행 계획으로 확인.
- 지연은 단회 관측이며 워밍업·반복 측정·동시 부하 실험은 하지 않았다. 이 결과로 검색 속도 우열을 주장하지 않는다.
- 평가 라벨은 AI 보조 초안으로 대체 근거 보완과 작성자 검토가 필요하다.
