# 02. grep, BM25, 벡터 검색 비교

> 참고 자료:
>
> - GNU grep manual
> - Elasticsearch similarity settings

## 한 줄 요약

grep은 정확한 문자열을 빠르게 찾고, BM25는 키워드 중요도로 순위를 매기며, 벡터 검색은 표현이 달라도 의미가 비슷한 문서를 찾는다. 실제 서비스에서는 질문 종류에 따라 한 가지 또는 여러 방식을 함께 선택한다.

## 핵심 개념

- 문자열 매칭(String Matching): 검색어와 문서의 글자 또는 정규식 패턴이 일치하는지를 확인하는 검색 방식이다.
- 역색인(Inverted Index): 단어를 기준으로 해당 단어가 등장한 문서 목록을 미리 저장한 구조다.
- TF-IDF: 문서 안에서 자주 나오고 전체 문서에서는 드문 단어에 더 높은 중요도를 주는 방식이다.
- BM25: TF-IDF를 발전시켜 단어 반복과 문서 길이를 보정하는 관련도 점수 방식이다.
- 임베딩(Embedding): 문장의 의미적 특징을 숫자 배열인 벡터로 변환한 표현이다.
- ANN(Approximate Nearest Neighbor): 모든 벡터를 정확히 비교하지 않고 가까울 가능성이 높은 후보를 빠르게 찾는 방법이다.

## 상세 정리

### grep은 언제 가장 단순하고 정확할까?

grep은 파일을 읽으면서 입력한 문자열 또는 정규식 패턴이 들어 있는 줄을 찾는다. 별도의 데이터베이스나 인덱스 없이 바로 실행할 수 있어, 파일 수가 적고 찾는 값이 정확할 때 유용하다.

~~~bash
grep -Rni "URX-1423" docs/
~~~

위 명령은 docs 아래에서 URX-1423이 들어 있는 줄을 파일 이름과 줄 번호까지 함께 보여준다. 이슈 번호, 에러 코드, 환경 변수 이름처럼 정확한 문자열이 중요한 질문에 잘 맞는다.

반면 grep은 단어의 의미나 중요도를 판단하지 않는다. 서버 연결 실패라는 문서에서 네트워크 장애를 찾고 싶어도 두 표현이 다르면 결과가 없을 수 있다. 여러 결과가 나왔을 때 어느 문서가 더 관련 있는지도 기본적으로 정렬해 주지 않는다.

### BM25는 왜 문서에 순위를 매길 수 있을까?

BM25는 검색어의 각 단어가 문서에서 얼마나 중요한지 점수로 계산해 결과를 정렬한다. 이 계산의 출발점은 역색인이다.

~~~text
문서 1: 프로세스 스케줄링
문서 2: 프로세스와 스레드
문서 3: 스레드 동기화

역색인
프로세스 → 문서 1, 문서 2
스레드   → 문서 2, 문서 3
~~~

검색할 때 원문 전체를 모두 읽는 대신 검색어가 가리키는 문서 목록부터 빠르게 확인할 수 있다.

BM25는 단순히 단어가 많이 나올수록 점수를 무한히 올리지 않는다. 같은 단어가 반복될 때 추가 점수를 완만하게 만들고, 문서가 길다는 이유만으로 유리해지지 않도록 길이를 보정한다. 그래서 검색어가 문서의 핵심 주제인가에 가까운 순위를 만들 수 있다.

한국어는 조사와 어미가 붙기 때문에 공백만으로 단어를 나누면 검색 품질이 떨어질 수 있다. Elasticsearch의 nori 분석기처럼 한국어 형태소를 고려해 토큰을 만드는 과정이 중요한 이유다.

### 벡터 검색은 같은 의미를 어떻게 찾을까?

임베딩 모델은 문장을 숫자 배열로 변환한다.

~~~text
서버 연결에 실패했다.
↓
[0.12, 0.83, -0.31, 0.44, ...]
~~~

의미가 비슷한 문장은 벡터 공간에서 가까운 위치가 되도록 모델이 학습된다. 따라서 문서에 질문과 정확히 같은 단어가 없더라도 의미가 가까운 후보를 찾을 수 있다.

하지만 벡터 검색에는 조건이 있다.

- 질문과 문서는 같은 임베딩 모델로 변환해야 비교 기준이 맞는다.
- 전문 용어나 이슈 번호는 정확히 구분하지 못할 수 있다.
- 청크의 문맥이 부족하면 의미가 잘못 표현될 수 있다.
- 거리 점수만 높다고 해서 사용자가 원하는 정답 문서라는 보장은 없다.

pgvector는 PostgreSQL 안에 벡터를 저장하고 거리 기반 검색을 할 수 있게 해 주는 확장 기능이다. 코사인 거리를 쓴다면 거리 값이 작을수록 두 벡터 방향이 더 가깝다.

### 정확 검색과 ANN 인덱스는 무엇이 다를까?

벡터가 적을 때는 질문 벡터와 모든 문서 벡터를 비교하는 정확 검색이 가능하다. 그러나 데이터가 늘어나면 비교 대상도 함께 늘어나므로 응답 시간이 길어질 수 있다.

ANN은 모든 벡터를 비교하는 대신 가까울 가능성이 높은 후보를 먼저 탐색한다. HNSW는 벡터를 여러 층의 그래프처럼 연결해 빠르게 후보를 찾아가는 ANN 인덱스의 한 종류다.

~~~text
정확 검색: 모든 문서 벡터와 비교한다. 정확하지만 데이터가 많으면 느리다.
ANN / HNSW: 가까울 후보를 먼저 탐색한다. 빠르지만 일부 좋은 결과를 놓칠 수 있다.
~~~

따라서 실습에서는 속도만 보지 않고 원하는 문서가 상위 결과에 남는 비율도 함께 확인해야 한다.

### Hybrid Search는 왜 필요할까?

키워드 검색과 벡터 검색은 서로 잘하는 일이 다르다.

~~~text
질문: URX-1423의 원인은 무엇인가?
→ 이슈 번호가 중요하므로 BM25 또는 grep 결과가 필요하다.

질문: 서버 접속이 안 됐던 사례가 있나?
→ 표현이 달라질 수 있으므로 벡터 검색 후보가 도움이 된다.
~~~

Hybrid Search는 두 검색 결과를 함께 사용한다. 예를 들어 BM25와 벡터 검색에서 각각 상위 문서를 받고, RRF(Reciprocal Rank Fusion)처럼 각 결과의 순위를 합치는 방법을 사용할 수 있다.

## 예시 / 코드

같은 문서 집합을 대상으로 검색 방식을 비교할 때 사용할 수 있는 질문 예시다.

~~~text
문서 A: 외부 서버와 TCP 연결이 실패했다.
문서 B: URX-1423 티켓에서 인증서 만료를 확인했다.
문서 C: 네트워크 정책 변경 후 API 호출이 성공했다.

질문 1: URX-1423
질문 2: 서버 접속이 안 된 사례
질문 3: 인증서 문제가 있었나
~~~

pgvector에서 코사인 거리로 가까운 청크를 찾는 SQL 형태는 아래와 같다. 아직 실제 데이터와 임베딩 값은 넣지 않았으므로 다음 실습에서 테이블과 모델을 정한 뒤 실행할 예정이다.

~~~sql
SELECT content, embedding <=> :query_embedding AS cosine_distance
FROM chunks
ORDER BY embedding <=> :query_embedding
LIMIT 5;
~~~

## 스터디에서 나눌 이야기

- 검색 품질을 비교할 때 속도, 상위 결과의 관련성, 구현 난이도 중 무엇을 우선 기준으로 삼을지 논의하고 싶다.
- 키워드 검색과 벡터 검색 결과를 합칠 때 단순 RRF가 충분한지, 질문 유형에 따라 가중치를 바꿔야 하는지 이야기해 보고 싶다.
