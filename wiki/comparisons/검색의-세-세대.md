> 스터디 2주차의 공통 골격. 0세대 grep은 문자열이 같은가, 1세대 BM25는 토큰이 얼마나 관련 있는가, 2세대 벡터는 의미가 얼마나 가까운가를 묻는다. 열 명이 같은 구조로 노트를 썼고 아홉 명이 자기 데이터로 돌렸다. 결론은 대체가 아니라 **누적**: 각 세대는 앞 세대의 실패 지점을 보완할 뿐 없애지 않는다.

## 한 표로

| | 0세대 [[grep-문자열-매칭|grep]] | 1세대 [[역색인과-BM25|BM25]] | 2세대 [[임베딩과-벡터-검색|벡터]] |
|---|---|---|---|
| 핵심 질문 | 문자열이 같은가 | 어떤 문서가 질의와 더 관련 있는가 | 표현이 달라도 의미가 가까운가 |
| 저장 | 원본 파일 그대로 | 토큰 → 문서 역색인 (+빈도·위치) | 청크 → 벡터 (+HNSW) |
| 사전 준비 | 없음 | 토큰화·역색인 | 청킹·임베딩·벡터 인덱스 |
| 결과 순위 | 없음 (파일·줄 순) | BM25 점수 | 유사도 |
| 강점 | 정확한 코드·ID·오류 문구, 설명 가능 | 희귀어·고유명사·제품 코드, 빠른 순위화 | 패러프레이즈·자연어 질문 |
| 약점 | 표현 불일치, 순위 없음, 줄 단위 | 토큰이 안 겹치는 동의 표현, 기본 OR로 후보 폭발 | 정확 용어·ID, top-k가 항상 뭔가를 돌려줌, 시간 조건 모름 |
| 저장 비용 (dldusgh318, 1,562청크) | 0.95MB (1×) | 5.1MB (5.4×), 색인 1.5초 | 22MB (23×), 임베딩 약 2분 |
| 검색 시간 | 20~30ms (dldusgh318), 6.2ms (e0ng), 4.37ms (jjinthung) | 5~6ms n-gram (dldusgh318), 2ms 내부 (e0ng), 5.5ms (lys0611) | 임베딩 26~32ms + DB 2~8ms (lys0611, e0ng) |

## 멤버들이 확인한 것

- **dldusgh318** (Notion, 프로브 10개): 고유명사(`SeCause` grep 50 / BM25 65)와 코드 심볼은 셋 다 잡고, 의미 질의 3개는 grep 0건, 오타·띄어쓰기·한영 혼용은 grep 0~1건에서 BM25 7~41건. "많이 찾는 것과 잘 찾는 것은 다르다."
- **do-dop** (카카오톡 1,203건, 11질의): `다음 모임 날짜` grep 0 / nori 3 / 2-gram 3, `몇시` grep 5 / nori 75 / 2-gram 5, `곡` grep 38 / nori 27 / 2-gram 0. 자연어 질문 "우리 팀명 뭐였지?"는 grep 0줄, BM25 74문서(답이 다른 메시지에 있어 확인 어려움), pgvector가 팀명 논의 청크를 상위에 올려 확인 가능. 단 같은 발신자 청킹이라 "몇시였더라"의 실제 시간은 못 답함.
- **e0ng** (채팅 9,491건, `수강 신청`): grep 0건(`수강신청`은 5건) / BM25 17건 Precision@5 0.6 / pgvector Precision@5 1.0.
- **kdyann** (Instagram 13개): `야구` 셋 다 찾지만 grep에는 순위가 없고, `집중 시간을 관리하는 생산성 도구`는 벡터만 결과. 기대한 게시물이 3위.
- **heebindev** (Notion 454청크): `CPU 작업 순서` grep 0 / BM25 85청크(SJF·Round Robin 상위) / 벡터 0.89대 3건이 BM25보다 덜 정확. "벡터가 항상 BM25보다 좋은 것은 아니다."
- **lys0611** (카카오톡 1,922청크, 10문항 정성): grep이 이긴 질문 1(정확 문구 1건), BM25·벡터 공동승 2, 벡터 3~4, 셋 다 실패 3(회식 장소, 집계 2). BM25 top-5 ∩ 벡터 top-5 = 0~2개 → 하이브리드의 근거. 이후 27문항 Recall@5: BM25 0.833 / 벡터 0.815 / RRF 0.907.
- **jjinthung** (카카오톡 753청크, 정답 40개): Hit@5 grep 0% / BM25 45% / 벡터 2.5%. 원인 진단 없음.
- **ur2e** (합성 vault 19문항): 벡터가 "의미로 이긴" 줄 알았던 결과가 단어 겹침이었다. BM25 Hit@3 0.79~0.84, pgvector 0.68~0.79(청킹 설정에 따라).
- **sese2204** (카카오톡 11,985청크): grep 세대를 pg_trgm `word_similarity`로 재현. `수강신청` 1.0/1.0/0.8, `머리 자른 얘기`는 벡터만.

> ⚠️ Contradiction: **검색 단위.** ur2e는 "grep, BM25, 벡터가 같은 청크를 써야 비교가 의미 있다"고 못 박았지만, do-dop(ES=메시지 1건, pgvector=1분 청크, grep=원본 txt)·heebindev·yujeong430(grep=원본)은 방식별 단위가 다르다. lys0611은 grep이 메시지 단위·순위 없음이라 Recall 표에서 아예 뺐다. dldusgh318은 세 방식에 동일한 `chunks.jsonl`을 넣었다("서로 다른 데이터를 넣으면 비교할 수 없다"). 결과 표를 읽을 때 단위를 먼저 본다. 출처: [ur2e dataset README](../../members/ur2e/labs/01-worklog-search/dataset/README.md) §청킹 방침, [do-dop 실습](../../members/do-dop/labs/02-kakaotalk-search/README.md) §grep, [dldusgh318 WEEK2](../../members/dldusgh318/labs/01-three-generations/WEEK2.md) §1.

> ⚠️ Contradiction: **질의.** yujeong430은 방식마다 다른 질의(`재수강` / `재수강 신청` / `수업을 다시 듣는 신청`)를 썼고, kdyann·lys0611·do-dop·ur2e는 같은 질의를 세 방식에 던졌다. kdyann: "같은 문서와 쿼리를 써야 검색 방식 자체의 차이를 비교할 수 있다."

## 그래서 다음은

- 두 방식의 실패 지점이 다르니 합친다 → [[하이브리드-검색과-RRF]]. 후보를 정교하게 줄 세운다 → [[리랭커]]. 검색만으로 안 되는 질문(집계·멀티홉·시간)은 [[멀티홉-질문과-Bridge-Entity]]와 [[지식그래프와-온톨로지]]로. dldusgh318의 누적관: grep → BM25 → Vector → Hybrid RAG → Relation/Graph.
- yujeong430이 정리한 RAG 파이프라인의 위치: 인덱싱 → pre-retrieval → retrieval → post-retrieval (Weaviate). 검색은 그중 한 단계다 → [[RAG-루프와-근거-인용]].
- sunghyun의 열린 질문 네 개(한국어 토큰화 / 결과 비교 기준 / 평가 / 결과 합치기)는 각각 [[한국어-토크나이징-nori와-n-gram]], [[RAG-평가-지표]], [[하이브리드-검색과-RRF]]에 답이 있다.
