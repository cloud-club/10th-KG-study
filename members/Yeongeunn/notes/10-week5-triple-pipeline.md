# 이룸페이 문서 기반 미니 온톨로지와 트리플 추출

## 1. 질문에서 설계 범위 정하기

이룸페이 Notion에는 금융 도메인 조사, API 명세, 서비스 간 통신, 회의·설계 기록이 함께 있다. 미니 온톨로지 v0는 이 중 **회원탈퇴와 미결제·미정산 거래 확인 흐름**을 대상으로 한다. 실제로 검색했던 질문에서 출발해 API·서비스·조건을 연결한다.

- 회원탈퇴를 처리하는 API와 제공 서비스는 무엇인가?
- 탈퇴 처리 중 어떤 서비스를 호출하며, 그 서비스가 제공하는 확인 API는 무엇인가?
- 탈퇴 전에 어떤 정책을 확인하며 어떤 거래 유형이 그 정책의 대상인가?
- 그 정책은 어떤 조건에서 탈퇴를 차단하는가?

회원탈퇴 명세, 사용자 미결제 내역 조회 명세, MSA 통신 기록과 가이드에서 대상·업무·호출·차단 조건을 확인해 스키마를 설계했다. 그래프가 나타내는 것은 **문서에 기록된 설계**이며 실제 배포 동작과는 구분한다.

## 2. 닫힌 스키마: 추출할 종류와 관계를 먼저 정하기

회원탈퇴 명세에서 API 제공 주체를 추출한다고 생각해보자. 관계 이름을 자유롭게 만들도록 두면 같은 의미가 `제공한다`, `가지고 있다`, `담당한다` 등으로 흩어질 수 있다. 사람은 문맥으로 이해하지만, 프로그램은 서로 다른 관계로 처리한다. 나중에 ‘API를 제공하는 서비스’를 조회할 때 어떤 관계 이름을 찾아야 하는지도 모호해진다.

그래서 추출 전에 **대상의 종류와 사용할 관계 이름을 정한다.** 이것이 이번 실습에서 말하는 닫힌 스키마다.

```text
대상 종류: Service, API, Operation, Policy, TransactionType
관계 이름: exposesAPI, implementsOperation, callsService 등 7종

인증 서비스 [Service] ─exposesAPI→ 회원탈퇴 API [API]
```

`Service`와 `API`는 대상의 종류인 클래스이고, 인증 서비스와 회원탈퇴 API는 그 종류에 속하는 개별 대상이다. `exposesAPI`는 둘 사이의 관계 이름이다. 관계의 방향도 Service → API로 고정한다.

LLM은 이 목록 안에서 추출하고, 목록에 맞지 않는 정보는 검토 대상으로 남긴다. 스키마를 영원히 바꿀 수 없다는 뜻은 아니다. 새로운 질문에 필요한 관계가 생기면 정의를 수정하고 추출·검증 기준도 함께 바꿀 수 있다. 또한 **목록 밖의 사실이나 문서에 없는 사실이 모두 거짓이라는 뜻도 아니다.** 여기서 닫혀 있는 것은 추출에 사용하는 어휘의 범위다.

## 3. RDF·Turtle·Cypher는 각각 무엇을 하는가

스키마를 정한 다음에는 사실을 어떤 구조로 표현하고, 어떤 형식으로 저장하고, 어떻게 조회할지 구분해야 한다.

| 구분 | 역할 | 이번 실습에서의 예 |
|---|---|---|
| 닫힌 스키마 | 사용할 클래스와 관계를 정하는 추출 규칙 | Service, API, exposesAPI |
| RDF | 사실을 주어–술어–목적어로 표현하는 데이터 모델 | 인증 서비스–API를 제공한다–회원탈퇴 API |
| RDFS | RDF로 클래스·속성·계층 등의 의미를 정의하는 어휘 | exposesAPI의 주어는 Service, 목적어는 API |
| Turtle / JSON-LD | RDF를 텍스트로 표현하는 형식 | 같은 관계를 Turtle 문법 또는 JSON-LD로 작성 |
| SPARQL | RDF 데이터에 질의하는 언어 | 어떤 서비스가 어떤 API를 제공하는가? |
| Cypher | Neo4j 등의 프로퍼티 그래프에 질의하는 언어 | 서비스 노드에서 API 노드로 연결을 따라 조회 |

RDF의 기본 단위인 **트리플**은 다음 세 항목의 묶음이다.

| 주어: 무엇이 | 술어: 어떤 관계로 | 목적어: 무엇과 |
|---|---|---|
| 인증 서비스 | API를 제공한다 | 회원탈퇴 API |

RDF에서는 이런 대상과 관계를 식별자로 구분한다. 사람이 읽는 이름이 같거나 바뀌더라도 어느 대상을 가리키는지 명확하게 하기 위해서다. 목적어에는 다른 대상의 식별자뿐 아니라 이름·숫자 같은 값인 리터럴도 올 수 있다.

**Turtle은 도구가 아니라 RDF를 적는 문법**이다. JSON-LD는 같은 RDF 데이터를 JSON 형태로 표현할 수 있는 형식이다. RDF를 Turtle로 ‘질의’하는 것이 아니라, Turtle로 작성한 RDF를 해당 형식을 지원하는 프로그램이 읽는다.

이번 실습의 흐름은 다음과 같다. RDFS는 스키마의 의미를 표현하며, 허용 목록과 출력 형식을 강제하는 검증은 별도로 구현한다.

```text
Notion 문서 → 정해진 스키마로 사실 추출 → 근거 검토
                                      ├─ Postgres: 엔티티·관계·근거 저장
                                      ├─ Turtle: RDF 형태로 내보내기
                                      └─ Neo4j: 노드·관계로 적재 → Cypher 질의
```

Turtle 파일을 생성하는 일과 Neo4j에 적재하는 일은 별도다. 같은 검토 결과를 각각의 형식으로 변환한다.

## 4. 클래스 5종

클래스는 데이터에서 어떤 종류의 대상을 구분할지 정의한다. 이번 범위는 실제 고객이나 거래 내역이 아니라 프로젝트의 설계 문서다.

| 클래스 | 정의 | 선정 이유 | 구분할 것 |
|---|---|---|---|
| `Service` | API 제공 주체·호출 대상인 소프트웨어 서비스 | API 담당과 서비스 간 연결을 조회 | 배포 인스턴스·개발자와 구분 |
| `API` | 제공 서비스·메서드·경로로 식별하는 엔드포인트 | 회원탈퇴와 미결제 조회 명세를 구분 | 업무 개념·호출 한 건과 구분 |
| `Operation` | API가 수행하는 업무 기능 | 회원탈퇴, 미결제 내역 확인을 경로와 독립적으로 표현 | 버튼·페이지 제목만으로 생성하지 않음 |
| `Policy` | 기능 수행 여부를 판단하는 조건과 처리 규칙 | 탈퇴 선행 검사와 차단 사유를 표현 | 미정산이라는 단어 자체가 아닌 조건 전체 |
| `TransactionType` | 문서에서 구분하는 거래 종류 | 더치페이·원격결제 등 정책의 검사 대상을 연결 | 실제 거래 한 건·상태 코드와 구분 |

예를 들어 미결제 여부를 확인하는 **기능**과 그 기능을 제공하는 **API**는 다르다. API 경로가 바뀌어도 같은 기능일 수 있다. 거래 유형도 현재 어떤 고객에게 미결제건이 있다는 뜻이 아니라, 문서에서 어떤 종류의 거래를 검사하는지 표현한다.

설계 의사결정의 이유까지 찾는 최종 목표는 유지한다. 다만 v0에서는 직접 확인 가능한 기능·API·정책 관계부터 다룬다. 결정·대안·이유를 추출하는 스키마는 별도 범위로 확장한다.

## 5. 술어 7종

술어는 두 대상 사이의 관계 이름이다. 이름뿐 아니라 방향과 포함·제외 기준을 정해야 같은 문장에서 일관된 결과를 얻을 수 있다.

| 술어 | 주어 → 목적어 | 의미·추출 기준 |
|---|---|---|
| `exposesAPI` | Service → API | 해당 서비스가 엔드포인트를 제공한다고 명시되거나 API 명세의 소속으로 확인됨 |
| `implementsOperation` | API → Operation | API가 해당 업무를 수행한다는 설명이 있음 |
| `callsService` | API → Service | 해당 API 처리 중 호출하는 서비스가 명시됨 |
| `requiresPolicy` | Operation → Policy | 기능 수행 전에 해당 조건을 확인해야 함 |
| `checksPolicy` | API → Policy | 정책 조건을 확인하거나 그 판단에 필요한 검사 결과를 제공함 |
| `blocksOperation` | Policy → Operation | 정책의 차단 조건이 충족되면 해당 기능을 제한함 |
| `concernsTransactionType` | Policy → TransactionType | 정책이 검사하는 거래 유형이 명시됨 |

`callsService`의 주어는 Service가 아니라 **API**다. 어느 처리 과정에서 호출하는지 보존하기 위해서다. 통신표에 서비스 간 호출만 적혀 있고 호출 API가 명시되지 않았다면 특정 API에 임의로 붙이지 않는다.

`requiresPolicy`는 업무의 선행 조건을, `checksPolicy`는 그 조건을 확인하는 엔드포인트를 구분한다. `blocksOperation`은 조건부 제한이다. 거래 유형이 정책의 대상이라는 이유만으로 그 유형의 모든 거래가 탈퇴를 막는다고 해석하지 않는다.

## 6. 원문을 스키마로 읽는 기준

| 검토한 자료 유형 | 확인한 정보의 종류 | 스키마에서의 처리 |
|---|---|---|
| 회원탈퇴 API 명세 | 제공 서비스, 업무 설명, 다른 서비스 호출, 오류 조건 | Service·API·Operation 및 호출·정책 관계 |
| 사용자 미결제 내역 조회 명세 | 조회 업무와 엔드포인트 | API·Operation, 확인 대상 정책 |
| 서비스 간 통신 기록 | 송신·수신·통신 목적·트리거 | 호출 정보의 교차 확인; API가 특정될 때만 API 관계로 연결 |
| MSA 통신 가이드 | 검증 순서, 거래 존재 여부와 차단의 연결 | 정책의 조건·결과 확인 |

자료마다 미결제·미정산·진행 중이라는 표현이 다를 수 있다. 이를 모두 동의어로 합치지 않고 각 문서의 조건과 적용 대상을 유지한다. 상태값은 거래 유형별로 의미가 다르므로 코드 문자열만 같다고 하나로 합치지 않는다.

정책의 각 개별 조건을 별도 Policy로 나누고, 조건식·문서 버전·근거를 함께 저장한다. 제목이 같거나 복제된 페이지는 독립적인 근거의 수로 중복 집계하지 않는다.

## 7. RDFS 스타일 정의

[미니 온톨로지 v0](../schemas/erumpay-ontology-v0.ttl)에 클래스 5종과 관계 술어 7종을 정의했다. 다음은 일부다.

```turtle
@prefix kg: <https://example.org/erumpay/ontology/> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

kg:Service a rdfs:Class .
kg:API a rdfs:Class .
kg:exposesAPI a rdf:Property ;
    rdfs:domain kg:Service ;
    rdfs:range kg:API .
```

`domain`은 관계의 주어, `range`는 목적어의 종류를 표현한다. RDFS에서는 타입을 추론하는 의미를 가지므로 추출 결과를 거부하는 검증은 코드에서 별도로 수행한다. 클래스 이름·관계 이름은 이 스키마가 정한 것이고, `rdf:type`과 `rdfs:domain` 등은 표준 어휘다. [RDFS](https://www.w3.org/TR/rdf-schema/)

관계 술어 7종과 별도로 ID·표시명·메서드·경로·조건·근거 같은 값도 필요하다. 이 값들은 레코드 필드로 관리한다. Turtle 파일에는 클래스와 관계의 정의를 담았다.

## 8. LLM 추출: 형식과 근거를 함께 받기

닫힌 스키마는 모델이 사용할 클래스와 관계 이름을 제한한다. 새 술어를 발명하게 두지 않고 허용 목록 밖의 정보는 검토 대상으로 남긴다.

추출 출력은 다음 필드를 가진다. 원문 인용문과 실제 내부 ID가 포함되는 결과는 로컬 데이터로 관리한다.

```text
subject: 원문 표현, 클래스
predicate: 허용 술어 7개 중 하나
object: 원문 표현, 클래스
evidence: 청크 ID, 원문 인용 구간
qualifiers: 조건·적용 범위·문서 버전
```

모델에 필요한 API 소속 문맥도 함께 전달한다. 제목과 상위 서비스 분류를 제공하지 않은 상태에서 본문만 보고 API 제공 주체를 추측하게 하지 않는다. 두 문서를 연결해서 만든 관계는 한 문장에 직접 존재하는 관계와 구분하고 두 근거를 모두 보관한다.

검증은 세 층으로 나눈다.

1. **형식:** JSON 파싱, 필수 필드, 클래스·술어 허용 목록, 주어·목적어 타입 검사.
2. **근거:** 인용 구간이 해당 청크에 실제 존재하는지 검사. 오프셋은 문자 기준 등을 명시하고 프로그램으로 확인.
3. **의미:** 호출 방향, 정책 조건, 부정·제안·과거 설계 여부를 검토.

JSON Schema를 적용해 형식을 제한하더라도 관계의 진실성은 보장되지 않는다. 특히 ‘미결제 확인을 요청한다’만으로 실제 사용자의 미결제 상태가 존재한다고 추출하지 않는다.

### few-shot 예시의 구성

few-shot은 실제 입력과 원하는 출력 몇 개를 프롬프트에 함께 제공하는 방법이다. 로컬 원문에서 다음 유형을 골라 예시를 구성한다.

| 유형 | 기대 처리 |
|---|---|
| 제공 서비스와 API 소속이 명시된 명세 | `exposesAPI` |
| API의 처리 설명에 서비스 호출이 명시됨 | `callsService` |
| 거래 조건이 있을 때 업무를 차단한다고 명시됨 | 조건을 포함한 Policy와 `blocksOperation` |
| 해당 호출을 검토한다는 제안 | 확정 호출 관계로 저장하지 않음 |
| 문서에 서비스 이름만 함께 등장함 | 호출 관계를 만들지 않음 |

명시된 관계뿐 아니라 제안이나 단순 동시 등장처럼 관계로 추출하면 안 되는 예시도 함께 구성한다.

## 9. ID와 근거 관리

- Service: 프로젝트 범위를 포함한 표준 서비스 ID. 별칭은 확인한 경우에만 연결.
- API: 제공 서비스 + HTTP 메서드 + 경로 템플릿. 실제 사용자 ID가 들어간 URL은 사용하지 않음.
- Operation: API 경로와 독립적인 업무 ID.
- Policy: 조건·대상·결과가 같은지 검토한 후 부여하는 ID. 다른 버전의 정책을 무조건 덮어쓰지 않음.
- TransactionType: 프로젝트가 사용하는 거래 분류 ID. 상태값과 별도 관리.

모든 관계에는 근거 청크와 문서 버전을 연결한다. 같은 관계를 지지하는 근거가 여러 개일 수 있어 관계와 근거를 분리한다.

```text
entities(id, class, label)
assertions(id, subject_id, predicate, object_id, qualifiers, review_status)
evidence(id, assertion_id, chunk_id, quote, source_version)
```

## 10. Turtle과 JSON-LD로 내보내기

직렬화는 데이터를 파일이나 전송 가능한 문자열로 표현하는 일이다. RDF 모델을 Turtle이나 JSON-LD로 표현하면 표준 파서로 읽을 수 있다. 이름과 ID의 의미까지 자동으로 합의되는 것은 아니다.

다음 문법 예시에서 `serviceA`는 인증 서비스, `apiA`는 회원탈퇴 API를 가리키는 설명용 식별자로 사용한다. 실제 내부 ID·경로 대신 이 식별자로 같은 관계의 두 표현을 비교한다.

```turtle
@prefix kg: <https://example.org/erumpay/ontology/> .
@prefix demo: <https://example.org/demo/> .
demo:serviceA kg:exposesAPI demo:apiA .
```

`@prefix`는 긴 식별자의 앞부분에 짧은 이름을 붙이는 선언이다.

- `kg:`는 클래스와 관계를 정의한 어휘의 주소를 줄인다.
- `demo:`는 예시에 등장하는 개별 대상의 주소를 줄인다.
- 마지막 줄은 ‘serviceA가 apiA를 제공한다’는 트리플이다. 마침표는 문장의 끝을 표시한다.

예를 들어 `kg:exposesAPI`를 펼치면 `https://example.org/erumpay/ontology/exposesAPI`가 된다. 주소 모양이지만 여기서는 관계의 식별자로 사용한다. 웹사이트에 접속하거나 API를 호출하는 코드가 아니다. `example.org`는 예시용 주소이며, `kg`와 `demo`라는 접두어 이름 자체는 바꿀 수 있다.

같은 관계를 JSON-LD로 표현하면 다음과 같다.

```json
{
  "@context": {
    "kg": "https://example.org/erumpay/ontology/",
    "demo": "https://example.org/demo/",
    "exposesAPI": {"@id": "kg:exposesAPI", "@type": "@id"}
  },
  "@id": "demo:serviceA",
  "exposesAPI": "demo:apiA"
}
```

`@context`는 키를 공통 식별자에 연결하고 `@id`는 대상을 식별한다. 위처럼 관계 목적어를 ID로 지정하는 것과 단순 문자열로 저장하는 것은 다르다. [JSON-LD 1.1](https://www.w3.org/TR/json-ld11/)

## 11. Postgres·Neo4j에 같은 승인 결과 저장하기

Postgres에는 엔티티·관계·근거를 행으로 보관하고, 같은 승인 결과를 Turtle과 Neo4j로 변환한다. 저장소별로 독립 추출하지 않아야 서로 다른 사실이 생기는 것을 줄일 수 있다.

Cypher는 저장된 노드와 관계에서 원하는 연결을 찾는 질의 언어다. 서비스가 제공하는 API를 찾는 가장 짧은 예는 다음과 같다.

```cypher
MATCH (s:Service)-[:EXPOSES_API]->(a:API)
RETURN s, a
```

`(s:Service)`는 Service 노드, `(a:API)`는 API 노드이고, 사이의 화살표는 `EXPOSES_API` 관계의 방향이다. `MATCH`는 이 모양의 연결을 찾고 `RETURN`은 찾은 대상을 반환한다. RDF는 데이터 모델이고 Cypher는 질의 언어이므로 역할이 다르다. RDF 데이터에 질의할 때 대응되는 언어는 SPARQL이다.

Neo4j 노드에는 안정적인 ID를 사용하고 유일성 제약을 둔다. MERGE는 지정한 패턴을 찾거나 생성하는 기능이며, 별칭이 같은 대상인지 판단하지 않는다. [Neo4j MERGE](https://neo4j.com/docs/cypher-manual/current/clauses/merge/)

예를 들어 미결제 확인 흐름을 조회할 때는 다음과 같이 범위를 나누어 생각한다.

```text
기능 ←수행─ 탈퇴 API ─호출→ 확인 담당 서비스 ─제공→ 후보 API
```

서비스가 제공하는 후보 API 중 실제 확인 기능·정책과 연결된 것을 추가로 제한해야 한다. ‘해당 서비스를 호출한다’는 정보만으로 그 서비스의 모든 API를 호출했다고 해석하면 안 된다.

다음은 그래프 적재 후 사용할 Cypher 형태다. `$operationId`는 로컬 기능 ID를 넣는 매개변수이며 실행 결과는 아니다.

```cypher
MATCH (a:API)-[:IMPLEMENTS_OPERATION]->(o:Operation {id: $operationId})
MATCH (a)-[:CALLS_SERVICE]->(s:Service)-[:EXPOSES_API]->(candidate:API)
MATCH (o)-[:REQUIRES_POLICY]->(p:Policy)<-[:CHECKS_POLICY]-(candidate)
RETURN a.id, s.id, candidate.id, p.id;
```

RDF의 술어와 Neo4j 관계 타입은 `callsService → CALLS_SERVICE`처럼 명시적으로 매핑한다. 연결된 사실을 찾았더라도 정확한 실제 호출 엔드포인트의 확정에는 그 연결을 지지하는 추가 원문이 필요할 수 있다.

## 12. 평가와 다음 실습

원문을 보고 정답 엔티티·관계·근거를 사람이 확인한 작은 평가셋을 만든다. 출력 중 올바른 관계의 비율인 Precision과, 정답 관계 중 찾은 비율인 Recall을 구분한다. ID·술어·방향뿐 아니라 정책 조건과 근거도 검토한다.

첫 실습에서는 문서 일부에서 후보를 추출하고, 검토한 관계를 Postgres·Turtle·Neo4j에 저장한다. 재실행 시 중복 여부, 1-hop과 다중 홉 질의, 원문으로 돌아가는 근거 연결을 확인한다. 모델 호출·적재·평가 결과는 이 스키마 설계와 별도로 기록한다.
