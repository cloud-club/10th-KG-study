# **W5-1. 닫힌 스키마 설계 : 무엇을 트리플로 뽑을 것인가**

W4에서는 기존 RAG가 못 답했던 질문을 그래프로 표현해봤다. 특히 서로 다른 프로젝트에 흩어진 정보를 `Redis` 같은 공통 개체로 연결하면, 검색으로는 찾기 어려웠던 관계를 그래프 탐색으로 풀 수 있다는 걸 확인했다.

이제 W5에서는 실제 문서를 LLM에게 넘겨서 이런 관계를 자동으로 추출하려고 한다.

그런데 바로 추출부터 시작하면 문제가 하나 있다.

**LLM에게 “이 문서에서 관계를 찾아줘”라고만 하면 어떤 관계를 뽑을지 기준이 없다.**

`SeCause에서 Redis를 작업 큐로 사용했다`는 문장 하나도 `USES`, `USES_TECHNOLOGY`, `ADOPTS`, `USES_AS_QUEUE`처럼 여러 방식으로 표현할 수 있다. 문서마다 새로운 관계가 생기기 시작하면 나중에는 같은 의미의 관계조차 서로 연결하기 어려워진다.

그래서 추출하기 전에 먼저 **“나는 어떤 개체와 관계만 저장할 것인가”를 제한한다.** 이번에 만드는 **닫힌 스키마(Closed Schema)** 다.

## **1. 스키마는 어디서 가져와야 할까?**

처음에는 내 문서를 전부 보고 등장하는 개념을 정리하면 될 것 같았다. 그런데 이렇게 접근하면 끝이 없다. 프로젝트 문서에는 기술, 장애, 사람, API, 서버, 기능, 원인, 해결 방법 등 수많은 개념이 등장하기 때문이다.

그래서 이번에는 반대로 접근한다.

**데이터 → 스키마가 아니라, 질문 → 필요한 관계 → 스키마**

이 방식은 온톨로지 설계에서 말하는 **역량 질문(Competency Questions)** 과도 연결된다. 먼저 이 지식베이스가 답해야 할 질문을 정하고, 그 질문에 답할 만큼의 정보가 스키마에 들어있는지 확인하는 방식이다. Noy와 McGuinness의 *Ontology Development 101*에서도 역량 질문을 온톨로지의 범위를 정하고 이후 충분한 정보가 포함됐는지 확인하는 기준으로 설명한다.

생각해보면 W4에서 이미 비슷한 일을 했다.

**“SeCause에서 작업 큐로 사용한 기술을 다른 프로젝트에서도 사용했는가?”**

이 질문에 답하려면 최소한 `프로젝트`, `기술`, `어떤 목적으로 사용했는지`, `실제로 적용했는지`가 필요했다. 그래서 질문에서 필요한 정보만 거꾸로 따라가며 스키마를 정할 수 있었다.

다만 W4에서 한계도 확인했다. 장애 분석 질문에서 필요했던 관계와 기술 사용 질문에서 필요했던 관계가 거의 겹치지 않았다.

즉 **이 스키마는 세상의 모든 프로젝트 정보를 표현하기 위한 스키마가 아니다. 지금 풀고 싶은 질문을 표현하기 위한 v0다.**

## **2. 무엇을 개체로 만들고, 무엇을 값으로 둘까?**

다음으로 헷갈렸던 건 모든 정보를 노드로 만들어야 하느냐였다.

예를 들어 다음 사실이 있다고 하자.

`SeCause → Redis → AI 분석 작업 큐 → implemented`

여기서 `SeCause`, `Redis`, `AI 분석 작업 큐`, `implemented`를 전부 노드로 만들 필요는 없다.

내가 잡은 기준은 **“다른 관계에서 다시 참조할 필요가 있는가?”**다.

| **정보** | **표현** | **이유** |
| --- | --- | --- |
| SeCause | `Project` | 여러 기술 사용 사례가 같은 프로젝트를 참조함 |
| Redis | `Technology` | 여러 프로젝트를 연결하는 브릿지가 될 수 있음 |
| SeCause의 Redis 사용 | `TechnologyUse` | **목적**과 **상태**를 붙여야 하는 하나의 사용 사례 |
| AI 분석 작업 큐 | 문자열 속성 | 이 값 자체를 다시 탐색할 필요가 없음 |
| implemented | 상태값 | 별도의 개체로 설명하거나 탐색할 필요가 없음 |

그래서 우선 클래스는 세 개만 둔다.

**`Project` / `Technology` / `TechnologyUse`**

여기서 `TechnologyUse`는 W4에서 만들었던 **중간 노드**다.

단순히 `SeCause → USES → Redis`라고 저장하면 Redis를 어떤 목적으로 사용했는지, 실제 구현한 것인지 검토만 한 것인지 같은 정보를 붙일 자리가 애매해진다.

그래서 다음처럼 한 번 감싼다.

**SeCause ← PART_OF — TechnologyUse — USES_TECHNOLOGY → Redis**

그리고 `TechnologyUse`에 `purpose`, `status` 같은 정보를 붙인다.

W4에서 RDF의 reification과 Wikidata의 statement 구조를 보면서 확인했던 문제를 이번에는 실제 내 데이터 모델에 적용하는 셈이다.

> 쉽게 말하면, **단순한 `SeCause → Redis` 관계 하나로는 ‘왜 썼는지’, ‘실제로 적용했는지’ 같은 추가 정보를 담을 수 없어서 관계 자체를 하나의 중간 노드로 만들고 그 노드에 목적과 상태를 붙이는 방식**이다. RDF의 reification과 Wikidata의 statement도 같은 이유로 관계를 하나의 대상으로 만들어 추가 정보를 연결한다.
> 

## **3. 어떤 관계까지 허용할까?**

클래스를 정했으면 LLM이 추출할 관계도 제한해야 한다.

초기 후보는 다음 정도다.

| **관계** | **시작** | **도착** | **의미** |
| --- | --- | --- | --- |
| `PART_OF` | TechnologyUse | Project | 어떤 프로젝트의 기술 사용인지 |
| `USES_TECHNOLOGY` | TechnologyUse | Technology | 어떤 기술을 사용했는지 |
| `HAS_PURPOSE` | TechnologyUse | 문자열 | 무엇을 위해 사용했는지 |
| `HAS_STATUS` | TechnologyUse | 문자열 | 실제 구현/제안/미구현 상태 |
| `REPLACES` | TechnologyUse | TechnologyUse | 기존 방식을 다른 방식으로 대체한 경우 |

여기서 중요한 건 **관계를 많이 만드는 게 목표가 아니라는 것**이다.

`RELATED_TO`처럼 애매한 관계를 하나 만들어두면 거의 모든 개체를 연결할 수 있지만, 그만큼 그래프의 의미는 사라진다. 반대로 관계의 판정 기준을 한 문장으로 설명할 수 있다면 LLM에게도 같은 기준을 줄 수 있다.

예를 들어 `USES_TECHNOLOGY`는 다음 정도로 제한할 수 있다.

문서에서 해당 기술을 실제로 사용했거나 도입을 검토했다고 명시한 경우에만 추출한다. 단순히 기술 이름이 언급된 경우는 제외한다.

`HAS_STATUS`도 마찬가지다.

| **값** | **기준** |
| --- | --- |
| `implemented` | 실제 적용했다고 명시 |
| `proposed` | 검토하거나 제안한 단계라고 명시 |
| `not_implemented` | 구현하지 않았다고 명시 |

그리고 **문서에 근거가 없으면 추측해서 채우지 않는다.**

이 규칙이 이후 LLM 정보 추출에서 꽤 중요해질 것 같다. 닫힌 스키마의 목적은 무엇을 많이 뽑느냐보다 **무엇을 뽑지 않을지를 정하는 것**에 가깝다.

## **4. RDFS 스타일로 명세하기**

이번 커리큘럼에서는 스키마를 RDFS 스타일로 정의한다.

> **RDFS(RDF Schema)**는 RDF 데이터에 **클래스와 속성의 구조를 정의하기 위한 간단한 스키마 언어**다. 예를 들어 `Project`, `Technology` 같은 클래스와, 특정 관계의 주어·목적어가 어떤 클래스여야 하는지를 `domain`과 `range`로 표현할 수 있다.
> 

여기서 필요한 건 복잡한 OWL 온톨로지가 아니다. 각 관계가 **어떤 타입에서 출발해서 어떤 타입으로 가는지**, 즉 `domain`과 `range` 정도만 명시하면 된다.

예를 들면 다음과 같다.

| **Property** | **Domain** | **Range** |
| --- | --- | --- |
| `partOf` | TechnologyUse | Project |
| `usesTechnology` | TechnologyUse | Technology |
| `hasPurpose` | TechnologyUse | string |
| `hasStatus` | TechnologyUse | string |
| `replaces` | TechnologyUse | TechnologyUse |

W3C의 RDFS 정의에서 `domain`은 해당 속성을 사용하는 주어의 클래스를, `range`는 목적어의 클래스를 나타낸다. 다만 W4에서 봤듯 이것은 원래 **입력 검증 규칙이 아니라 타입을 유도하는 의미론**이다. 예를 들어 `P rdfs:range Technology`라면 `P`의 목적어를 `Technology`로 추론한다.

그래서 우리는 RDFS 추론 엔진을 돌리려는 게 아니다.

**RDFS 형식은 스키마를 명확하게 문서화하는 용도**, 실제 `domain/range` 제한은 다음 단계에서 **LLM 추출 규칙**으로 사용한다.

W4에서 “우리는 엄밀한 OWL 온톨로지를 만드는 게 아니다”라고 했던 내용이 여기서 실제 설계로 이어진다.

## **5. 실제 데이터는 이런 모습이 된다**

예를 들어 SeCause와 TEAMFICIAL 두 프로젝트에서 Redis를 사용했다면 최종적으로 중요한 구조는 이렇다.

**SeCause ← TechnologyUse → Redis ← TechnologyUse → TEAMFICIAL**

각 `TechnologyUse`에는 서로 다른 목적과 상태가 붙는다.

| **Project** | **Technology** | **Purpose** | **Status** |
| --- | --- | --- | --- |
| SeCause | Redis | AI 분석 작업 큐 | implemented |
| TEAMFICIAL | Redis | 지원자 수 집계 캐시 | implemented |

여기서 중요한 건 두 사용 사례가 **동일한 `Redis` 개체를 가리킨다는 것**이다.

W3의 기존 검색에서는 “SeCause 작업 큐에 사용한 기술을 다른 프로젝트에서도 사용했는가?“라는 질문에 `Redis`라는 단어가 없어서 다른 프로젝트의 Redis 관련 청크를 찾지 못했다.

하지만 그래프에서는**SeCause → 기술 사용 → Redis → 다른 기술 사용 → TEAMFICIAL** 처럼 Redis를 브릿지로 따라갈 수 있다.

결국 스키마를 설계하는 목적도 예쁜 그래프를 만드는 게 아니라, **원래 못 풀었던 질문을 실제 경로로 만들기 위해서다.**

## **6. 같은 개체를 어떻게 같은 것으로 볼까?**

여기까지 정하고 나니 바로 다음 문제가 보인다.

문서마다 같은 기술이 다르게 적혀 있을 수 있다.

`Redis` / `redis` / `레디스`

LLM이 이것들을 각각 새로운 노드로 만들면 그래프에서는 서로 다른 기술이 된다. 그러면 Redis를 브릿지로 프로젝트를 연결하려던 목적 자체가 깨진다.

그래서 최소한 ID 규칙은 먼저 고정해둔다.

| **종류** | **예시** |
| --- | --- |
| Project | `secause` |
| Technology | `tech-redis` |
| TechnologyUse | `use-secause-redis-1` |

우선 소문자와 하이픈을 사용하는 정도로 통일한다.

하지만 이것만으로 `Spring`과 `Spring Boot`, `Postgres`와 `PostgreSQL`처럼 의미적으로 같은지 다른지 판단하는 문제까지 해결되지는 않는다. 이건 뒤에서 다룰 **Entity Resolution(신원해소)** 문제로 남는다.

## **7. 이 스키마가 원래 질문을 풀 수 있는지 확인하기**

마지막으로 처음 질문으로 돌아가본다. 스키마를 만들었는데 원래 못 풀었던 질문조차 표현하지 못하면 의미가 없다.

| **질문** | **필요한 정보** | **가능?** |
| --- | --- | --- |
| SeCause에서 **쓴 기술**을 **다른 프로젝트**에서도 썼나? | Project + Technology | ✅ |
| **제안했던 기술**을 다른 곳에서는 **실제 적용**했나? | Technology + Status | ✅ |
| 각 프로젝트에서 **기술**을 **어떤 목적**으로 사용했나? | Technology + Purpose | ✅ |
| 문서에 없는 미구현 기능은 무엇인가? | 부재 정보 | ⚠️ |

마지막 질문은 여전히 완전히 풀리지 않는다. `not_implemented`라고 **명시된 사실**은 저장할 수 있지만, 문서에 아예 등장하지 않는 기능까지 “구현하지 않았다”고 판단할 수는 없다.

즉 **스키마를 만든다고 모든 질문이 풀리는 것은 아니다.** W4에서 봤던 부정·부재 정보의 한계가 그대로 남아 있다.

> 즉, **그래프에 `구현하지 않았다`는 사실이 명시돼 있으면 찾을 수 있지만, 아무 정보가 없다는 이유만으로 `구현하지 않았다`고 판단할 수는 없다.** RDF의 열린 세계 가정에서는 기록되지 않은 사실을 `거짓`이 아니라 `모름`으로 보기 때문이다.
> 

## **이번 단계에서 확정한 것**

이번 v0에서는 욕심내지 않고 여기까지만 가져간다.

**클래스 3종:** `Project`, `Technology`, `TechnologyUse`

**관계 5종:** `PART_OF`, `USES_TECHNOLOGY`, `HAS_PURPOSE`, `HAS_STATUS`, `REPLACES`

그리고 모든 관계에는 **명시적인 판정 기준을 둔다.**

이 스키마가 완성된 온톨로지라고 생각하지 않는다. 실제로 온톨로지 설계 방법론에서도 초기 버전을 만든 뒤 애플리케이션이나 질문을 통해 평가하고 수정하는 반복적 설계를 전제로 한다.

**v0의 목적은 완벽한 스키마를 만드는 것이 아니라, LLM의 추출 결과를 같은 기준으로 비교할 수 있게 만드는 것이다.**

다음 단계에서는 이제 이 스키마를 LLM에게 실제로 넘겨본다.

**문서 청크 → 스키마를 강제한 LLM 추출 → Entity/Relationship + 원문 evidence**

여기서 확인할 건 단순하다. **관계를 제한한다고 정말 LLM이 우리가 원하는 사실만 안정적으로 뽑아줄까?** 그리고 같은 문장을 여러 번 추출했을 때도 같은 결과가 나올까? 이게 다음 실습인 **LLM 정보 추출**에서 확인할 문제다.

참고로 Turtle은 RDF 그래프를 텍스트로 표현하기 위한 W3C 직렬화 문법이므로, `schema.ttl`로 내보내는 건 새로운 데이터 모델을 하나 더 만드는 게 아니라 **방금 정의한 스키마를 표준 RDF 표현으로 적어두는 것**이라고 이해하면 충분하다.
