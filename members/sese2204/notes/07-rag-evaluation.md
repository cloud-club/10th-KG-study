# 07. RAG 평가와 실습 로드맵

> 참고 자료:
> - RAGAS (LLM-as-judge)
> - recall@k, NDCG@k, MRR (IR 지표)

## 한 줄 요약

모든 RAG 기법의 도입 여부는 측정으로 결정하며, 검색 단계(골든셋 IR 지표)와 생성 단계(RAGAS)를 분리해서 재는 게 핵심이다.

## 핵심 개념

- 검색 실패(관련 청크가 top-k에 없었다)와 생성 실패(있었는데 못 썼다)를 반드시 구분
- 골든셋 200개면 의사결정에 충분
- 골든셋 IR 지표와 RAGAS는 대체재가 아니라 서로 다른 층을 재는 도구
- 기법을 하나씩 누적해서 붙이고 매번 같은 골든셋으로 측정

## 상세 정리

위 기법 전부의 도입 여부는 결국 **측정으로** 결정된다.
검색 단계와 생성 단계를 **분리해서** 재는 게 핵심.

### 층위별 지표

| 층위 | 지표 | 도구 |
|---|---|---|
| 검색 | recall@k, NDCG@k, MRR | 골든셋 (200개면 의사결정에 충분) |
| 생성 | faithfulness, answer relevance | RAGAS 등 LLM-as-judge |

### 실패 분해

답이 틀렸을 때 반드시 구분:
- **검색 실패** — 관련 청크가 top-k에 없었다
- **생성 실패** — 있었는데 못 썼다

### 골든셋 vs RAGAS

- 골든셋 기반 IR 지표 → **검색 단계**를 정확히 측정
- RAGAS류 → 정답 레이블 없이 **생성 단계**의 근거 충실도를 근사

**대체재가 아니라 서로 다른 층을 재는 도구.**
검색 지표를 RAGAS로 대신하려 들면 노이즈만 늘어난다.

### 실습 로드맵

기법을 하나씩 **누적해서** 붙이고, 매번 **같은 골든셋**으로 측정.

```
① baseline   : 고정 청킹 + dense only
      ↓ 측정
② +하이브리드 : BM25 추가 + RRF 융합
      ↓ 측정
③ +리랭커     : top-100 회수 → cross-encoder 재정렬
      ↓ 측정
④ +쿼리 재작성 : multi-query 또는 HyDE
      ↓ 측정
```

**왜 이 순서인가**
- 어떤 게 실제로 얼마나 벌어주는지가 숫자로 남는다
- 그 숫자가 나중에 에이전트 설계에서
  "검색을 **도구**로 노출할지 **메모리**로 자동 주입할지" 판단하는 근거가 된다

**측정 준비물**
- 골든셋 200개 (쿼리 + 정답 청크 ID)
- recall@5 / recall@100 / NDCG@10 계산 스크립트
- 각 단계의 p50 / p99 지연 기록
