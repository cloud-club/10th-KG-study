# **빌드 시점 선지불 : GraphRAG 인덱싱은 왜 배치인가**

앞에서는 기존 Hybrid RAG에 그래프를 결합해, 벡터 검색으로 진입점을 찾고 그래프를 따라 기존 검색이 놓친 정보까지 가져오는 방법을 살펴봤다. 그런데 여기까지 만들고 보면 한 가지 특징이 있다. 사용자가 질문하기도 전에 이미 상당히 많은 일을 해두고 있다는 점이다.

W5에서는 원본 문서를 청크로 나누고, LLM으로 Entity와 Relationship을 추출한 뒤 정규화해 PostgreSQL과 Neo4j에 저장했다. Global Search까지 구현한다면 그래프에서 커뮤니티를 찾고 각각의 요약까지 미리 만들어야 한다. 사용자가 아직 아무 질문도 하지 않았는데 비용이 꽤 많이 들어간다.

왜 이렇게 하는 걸까?

핵심은 **계산 비용을 없애는 것이 아니라 언제 지불할지를 선택하는 것**에 있다.

## **1. 질문할 때 계산할까, 미리 계산해둘까?**

같은 데이터에 답하는 시스템도 필요한 계산을 언제 수행하느냐에 따라 구조가 달라질 수 있다.

한쪽 극단에는 질문이 들어온 뒤 필요한 자료를 그때그때 찾아보는 방식이 있다.

```
질문
→ 검색
→ 문서 읽기
→ 부족한 정보 판단
→ 다시 검색
→ 답변
```

미리 준비할 것이 거의 없고 원본 데이터가 방금 바뀌었더라도 바로 검색할 수 있다는 장점이 있다. 대신 질문이 들어올 때마다 검색과 판단을 반복해야 한다. 질문이 많아질수록 같은 계산을 여러 번 수행할 수도 있다.

GraphRAG는 반대쪽에 가깝다.

```
[질문이 오기 전]

원본 문서
→ 청크
→ LLM 정보 추출
→ Entity 정규화
→ 그래프 구축
→ 커뮤니티 탐지·요약

[질문이 들어온 뒤]

질문
→ 이미 만들어진 그래프 조회
→ 답변
```

질문 전에 비싼 계산을 미리 해두고, 실제 질문이 들어왔을 때는 만들어둔 결과를 빠르게 조회한다. 이런 관점에서 GraphRAG의 인덱싱 과정은 **빌드 시점에 비용을 먼저 지불하는 구조**라고 볼 수 있다.

둘 중 하나가 항상 좋은 것은 아니다. 데이터는 거의 바뀌지 않는데 같은 데이터에 계속 질문한다면 미리 계산해두는 편이 유리하다. 반대로 데이터가 계속 바뀌고 질문은 몇 번 하지 않는다면, 비싼 인덱스를 미리 만드는 것보다 질문이 들어왔을 때 필요한 부분만 찾는 편이 나을 수 있다.

결국 중요한 것은 **계산을 하느냐 마느냐가 아니라, 그 비용을 언제 내는 것이 유리한가**이다.

## **2. DDIA의 배치 처리 관점으로 다시 보기**

*Designing Data-Intensive Applications(DDIA)* 10장에서는 대규모 데이터를 한 번에 처리하는 일괄 처리, 즉 **Batch Processing**을 다룬다. 여기서 이번 GraphRAG 파이프라인과 연결되는 중요한 관점이 하나 있다.

**원본 입력을 직접 수정하지 않고, 입력을 읽어 새로운 결과물을 만든다.**

```
원본 입력
   ↓
배치 처리
   ↓
파생된 결과
```

예를 들어 원본 문서에서 그래프를 만든다고 해서 원본 문서 자체를 그래프로 바꾸는 것이 아니다. 원본은 그대로 남겨두고, 그것을 읽어 Entity와 Relationship이라는 새로운 결과물을 만든다.

이 구조가 중요한 이유는 **다시 만들 수 있기 때문**이다. LLM 추출 프롬프트에 문제가 있었다면 프롬프트를 수정한 뒤 원본 청크부터 다시 실행할 수 있다. Entity 정규화 방식이 잘못됐다면 정규화 로직을 고쳐 그래프를 다시 만들 수 있다. 중간 작업이 실패하더라도 원본 문서까지 망가지는 것은 아니다.

즉 그래프는 원본 데이터 그 자체가 아니라 **원본으로부터 언제든 다시 만들 수 있는 파생물**로 보는 것이 중요하다.

## **3. 지금까지 만든 파이프라인도 이미 비슷한 구조였다**

W2부터 만든 파이프라인을 이 관점으로 다시 보면 꽤 비슷한 구조를 가지고 있다.

```
Notion 원본 문서
      ↓
chunks.jsonl
      ↓
LLM 정보 추출
      ↓
extracted.review20.jsonl
      ↓
검증 / 정규화
      ↓
PostgreSQL entities / edges
      ↓
Neo4j / Turtle / JSON-LD
```

예를 들어 W5에서는 전체 1,562개 청크를 바로 LLM에 넣지 않고 20개 표본부터 추출했다. 그 결과 긴 출력이 잘리면서 JSON 파싱에 실패하는 문제, TechnologyUse ID가 잘못 만들어지는 문제, 같은 사용 사례가 여러 노드로 나뉘는 문제를 먼저 발견할 수 있었다.

만약 처음부터 원본 데이터를 직접 수정하는 구조였다면 이런 문제를 고친 뒤 데이터를 되돌리는 작업까지 필요했을 것이다. 하지만 원본 청크를 그대로 두고 그 위에서 새로운 결과를 만드는 구조였기 때문에, 추출이나 정규화 방식을 고쳐 다시 실행하면 된다.

W5에서 `extraction_run`처럼 어떤 추출 과정에서 만들어진 결과인지 구분하려 했던 것도 같은 이유다. 결과에 버전이나 실행 정보를 남겨두면 새로운 방식으로 다시 추출했을 때 이전 결과와 비교하기 쉬워진다.

따로 “배치 시스템을 설계하자”고 시작한 것은 아니었지만, 돌아보면 **원본은 남겨두고 그 위에서 검색 인덱스와 그래프 같은 파생 데이터를 계속 만들어온 셈이다.**

## **4. GraphRAG는 왜 질문 전에 할 일이 많을까?**

GraphRAG의 주요 인덱싱 작업을 보면 질문이 들어올 때마다 하기에는 부담스러운 작업이 많다.

먼저 **트리플 추출**은 여러 청크를 LLM에 넣어 Entity와 Relationship을 구조화해야 한다. 사용자가 질문할 때마다 전체 문서를 다시 읽어 트리플을 추출한다면 그래프를 미리 만들어둘 이유가 없다.

**Entity 정규화와 병합**도 마찬가지다. W5에서는 같은 TEAMFICIAL의 Redis 사용 경험이 표현 차이 때문에 여러 TechnologyUse로 만들어지는 문제를 발견했다. 어떤 노드가 실제로 같은 대상을 의미하는지 판단하는 작업까지 질문할 때마다 반복하는 것은 비효율적이다.

Global Search에서 사용하는 **커뮤니티 탐지와 커뮤니티 요약**은 더 명확하다. 특정 질문과 관련된 일부 노드만 보는 것이 아니라 그래프 전체의 연결 구조를 살펴 서로 밀접한 노드들을 묶어야 한다. 이후 각 커뮤니티의 내용을 LLM으로 요약하는 작업까지 필요하다.

```
원본 문서
   ↓
Triple 추출
   ↓
Entity 정규화
   ↓
Knowledge Graph
   ↓
Community Detection
   ↓
Community Summary
   ↓
──────── 여기까지 질문 전에 수행 ────────
   ↓
사용자 질문
   ↓
미리 만들어둔 구조를 조회
```

이런 계산을 미리 수행했기 때문에 실제 질문 시점에는 훨씬 적은 데이터를 조회해 답할 수 있다.

즉 **GraphRAG의 빠른 조회는 공짜가 아니다. 질문 전에 비용을 먼저 지불했기 때문에 가능한 것이다.**

## **5. 미리 계산하면 새로운 문제가 생긴다**

선지불 구조에는 분명한 대가도 있다. **미리 만든 결과는 원본이 바뀌는 순간 과거의 상태가 될 수 있다.**

예를 들어 월요일에 300개의 청크로 그래프를 만들었다고 해보자.

```
월요일
청크 300개 → Knowledge Graph 생성

화요일
새 문서 추가 → 청크 320개

하지만 Knowledge Graph
→ 여전히 300개 기준
```

새로 추가된 20개 청크에 Redis 사용 경험이 있어도 기존 그래프에는 나타나지 않는다. 검색 대상인 원본 문서는 최신인데, 검색을 돕기 위해 만든 그래프는 오래된 상태가 되는 것이다.

이를 해결하는 가장 단순한 방법은 **전체를 다시 만드는 것**이다. 원본을 그대로 보존하고 있다면 새로운 320개 청크를 기준으로 추출부터 다시 실행할 수 있다. 데이터가 작을 때는 오히려 이 방법이 가장 관리하기 쉽다.

하지만 데이터가 수천, 수만 건으로 늘어나면 매번 전체 LLM 추출을 다시 수행하는 것은 비싸다. 그때부터는 **바뀐 부분만 다시 처리하는 증분 갱신**이 필요해진다.

```
전체 재계산

320개 전체
→ 다시 추출
→ 다시 그래프 생성

증분 갱신

기존 300개
       +
새로운 20개만 추출
       ↓
기존 그래프에 반영
```

증분 갱신은 계산량을 줄일 수 있지만 훨씬 복잡하다. 새로운 청크에서 `Redis`라는 Entity가 나왔다고 해서 새로운 Redis 노드를 만들면 안 되고, 기존 그래프의 Redis와 같은 Entity인지 먼저 판단해야 한다. W5에서 발견했던 Entity Resolution 문제가 데이터 갱신에서도 다시 등장하는 것이다.

Global Search의 커뮤니티 요약까지 있다면 더 어렵다. 새로운 노드 하나가 추가되면서 커뮤니티의 구성 자체가 달라질 수도 있고, 그렇다면 기존에 만들어둔 커뮤니티 요약도 다시 계산해야 한다.

## **6. 결국 선지불은 성능과 신선도의 교환이다**

여기까지 보면 GraphRAG에서 왜 인덱싱이 중요한지도 조금 다르게 보인다.

처음에는 단순히 “질문에 답하려면 그래프를 만들어야 한다.” 정도로 생각할 수 있다.

하지만 시스템 관점에서 보면 GraphRAG는 **질문 시점의 일을 줄이기 위해 상당한 계산을 빌드 시점으로 옮긴 구조**다.

```
질문 시점 계산을 많이 함
→ 준비 비용 ↓
→ 최신 데이터 반영 쉬움
→ 질문 비용 ↑

미리 계산함
→ 준비 비용 ↑
→ 질문 비용 ↓
→ 데이터가 바뀌면 갱신 필요
```

그래서 어느 방식이 더 좋은지는 데이터와 사용 패턴에 따라 달라진다. 거의 변하지 않는 문서를 대상으로 많은 질문을 받는다면 미리 그래프와 요약을 만들어두는 것이 유리하다. 반대로 데이터가 계속 변하고 질문은 거의 없다면 비싼 그래프 인덱싱이 오히려 낭비가 될 수 있다.

GraphRAG의 **빌드 시점 선지불**은 결국 질의 성능을 얻는 대신 **갱신과 신선도 관리라는 새로운 비용을 떠안는 선택**이다.

## **7. 다음 문제는 “어떻게 최신 상태를 유지할 것인가”**

이번 주까지는 원본 문서에서 그래프를 만들고, 그 그래프를 기존 RAG 검색과 결합하는 데 집중했다.

```
W3
문서를 어떻게 잘 찾을까?
→ Hybrid Search

W4
문서가 아니라 관계를 따라가면 어떨까?
→ Knowledge Graph

W5
그 관계를 실제 문서에서 어떻게 만들까?
→ LLM Extraction + Graph 구축

W6
그래프를 실제 검색에 어떻게 사용할까?
→ GraphRAG
```

여기까지는 모두 **이미 만들어진 데이터를 어떻게 검색할 것인가**에 가까웠다.

그런데 실제 개인 데이터는 계속 변한다. 새로운 프로젝트가 생기고, 기존 문서가 수정되고, 새로운 기술 사용 경험도 추가된다. 그때마다 전체 그래프를 처음부터 다시 만드는 것은 데이터가 커질수록 부담이 된다.

그래서 다음 질문은 자연스럽게 바뀐다.

**미리 만들어둔 그래프의 장점은 유지하면서, 원본 데이터가 바뀌었을 때 그래프도 자동으로 최신 상태로 만들 수 있을까?**

DDIA에서 Batch Processing 다음에 Stream Processing이 이어지는 것처럼, 이번에 확인한 **“미리 계산한 파생 데이터를 어떻게 최신 상태로 유지할 것인가”**가 다음 단계로 이어진다.
