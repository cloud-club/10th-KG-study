# 3. 하이브리드 검색과 RAG

> 관련 실습: `../labs/02-hybrid-search-rag/README.md`

지난번에는 검색의 세 가지 방식인 grep, BM25, 벡터 검색의 개념을 공부하고 간단한 실습을 해보았다.

그때 문서에 있는 `스케줄링`이라는 표현을 `CPU 작업 순서`처럼 다르게 바꾸어 검색했다.
같은 검색어를 사용해도 검색 방식에 따라 결과가 달랐다.

BM25는 SJF와 Round Robin처럼 검색어의 키워드와 직접 관련된 결과를 찾았다.
반면 벡터 검색은 문맥 교환과 프로세스 상태처럼 의미가 넓게 관련된 결과를 찾았다.

또한 BM25 점수와 벡터 유사도는 점수의 의미와 범위가 다르다.

```text
BM25 점수: 8.6146
벡터 유사도: 0.8967
```

따라서 두 점수를 그대로 더해서 비교하기는 어렵다.

## 1. RRF
https://gaejabong.com/wiki/rrf

RRF는 Reciprocal Rank Fusion의 약자다.
서로 다른 검색 방식의 점수를 직접 더하지 않고, 각 검색 결과의 순위를 이용해 결과를 합치는 방법이다.

```text
RRF 점수 = 1 / (k + 순위)
```

BM25와 벡터 검색을 함께 사용하면 최종 점수는 다음과 같다.

```text
최종 점수
= 1 / (k + BM25 순위)
+ 1 / (k + 벡터 순위)
```

보통 `k=60`을 사용한다.
k는 특정 검색 시스템이 결과를 지배하는 것을 방지(평활화)한다.
60이라는 수치는 실험적으로 가장 좋은 성능을 보였기 때문이다.

어떤 청크가 BM25와 벡터 검색에 모두 높은 순위로 등장하면 두 검색의 점수가 더해지므로 최종 순위에서도 높아진다.
한쪽 검색에만 등장한 청크도 제외하지 않고 해당 검색의 순위 점수를 받는다.

### 간단한 예시

| 청크 | BM25 순위 | 벡터 순위 |
| --- | ---: | ---: |
| SJF | 1위 | 5위 |
| 문맥 교환 | 4위 | 1위 |
| 프로세스 상태 | 3위 | 3위 |

`k=60`일 때 프로세스 상태의 RRF 점수는 다음과 같다.

```text
1 / (60 + 3) + 1 / (60 + 3)
= 약 0.0317
```

RRF는 원래의 BM25 점수나 벡터 유사도를 사용하지 않는다.
검색 결과가 몇 위인지에만 집중하기 때문에 점수 범위가 다른 검색 결과도 비교적 간단하게 합칠 수 있다.

## 2. 하이브리드 검색

하이브리드 검색은 두 가지 이상의 검색 방식을 함께 사용하는 방법이다.
이번 실습에서는 BM25와 벡터 검색을 사용한다.

```text
질문
├── Elasticsearch BM25 검색
└── PostgreSQL pgvector 검색
          ↓
       RRF 순위 결합
          ↓
    하이브리드 검색 결과
```

BM25는 검색어와 문서에 같은 단어가 들어 있는 경우에 강하다.
벡터 검색은 표현이 달라도 의미가 비슷한 문서를 찾는 데 강하다.
두 결과를 합치면 서로 놓친 문서를 보완할 수 있다.

하지만 두 검색을 합쳤다고 항상 결과가 좋아지는 것은 아니다.
한쪽 검색의 좋지 않은 결과가 최종 순위에 들어올 수도 있기 때문에 실제 질문으로 평가해야 한다.

## 3. Recall@k
[참고 블로그](https://blog.nerdfactory.ai/2021/09/23/recommend-system-classification-metric-1.html)

검색 결과가 좋아 보인다는 느낌만으로는 검색 방식을 정확하게 비교하기 어렵다.
Recall@k는 실제로 관련 있는 청크 중 상위 k개의 검색 결과 안에 몇 개가 포함되었는지를 나타낸다.

```text
Recall@k
= 상위 k개에서 찾은 정답 청크 수 / 전체 정답 청크 수
```

예를 들어 어떤 질문의 정답 청크가 총 2개이고, 상위 5개 결과에서 정답 청크 1개를 찾았다면 다음과 같다.

```text
Recall@5 = 1 / 2 = 0.5
```

Recall@k를 계산하려면 먼저 질문마다 어떤 청크가 정답인지 직접 정해야 한다.
이처럼 사람이 미리 정답을 표시해둔 데이터를 골드셋이라고 한다.

이번 실습에서는 운영체제 Notion을 보고 질문 5개 정도를 만든 뒤, 각 질문의 정답 청크를 직접 고를 것이다.

### 평가 질문 후보

1. SJF는 어떤 프로세스를 먼저 실행하는가?
2. 문맥 교환이 일어날 때 운영체제는 무엇을 저장하는가?
3. Round Robin에서 quantum은 어떤 역할을 하는가?
4. 교착상태가 발생하기 위한 조건은 무엇인가?
5. Running 상태와 Blocked 상태는 어떻게 다른가?

같은 질문에 대해 BM25, 벡터 검색, RRF 하이브리드 검색의 Recall@k를 비교한다.

## 4. RAG

RAG는 Retrieval-Augmented Generation의 약자로, 한국어로는 검색 증강 생성이라고 한다.

LLM이 자신의 학습 데이터만 이용해서 답하지 않고, 먼저 외부 문서에서 질문과 관련된 내용을 검색한 뒤 검색 결과를 참고해 답변한다.

```text
질문
→ 관련 청크 검색
→ 상위 청크를 컨텍스트로 조립
→ 질문과 컨텍스트를 LLM에 전달
→ 답변과 근거 생성
```

이번 실습에서는 RRF로 합친 상위 청크를 OpenAI API에 전달한다.

### 컨텍스트

컨텍스트는 LLM이 답변할 때 참고하도록 함께 전달하는 내용이다.
검색된 청크의 문서 제목, 소제목, 본문을 하나로 묶어 질문과 함께 전달한다.

검색 결과가 좋지 않으면 LLM에 전달되는 컨텍스트도 좋지 않다.
따라서 RAG에서는 LLM뿐만 아니라 검색 품질도 중요하다.

## 5. 근거 인용

RAG의 답변에는 어떤 문서를 참고했는지 근거를 함께 표시해야 한다.

예시는 다음과 같다.

```text
답변:
SJF는 예상 CPU 사용 시간이 가장 짧은 작업을 먼저 실행한다.

근거:
[1] 2 Process & Thread _3 — Algorithm #2: SJF
```

답변에 근거를 표시하면 사용자가 원문을 다시 확인할 수 있다.
또한 검색된 문서에 답이 없다면 LLM이 아는 척하지 않고, 제공된 문서에서 답을 찾지 못했다고 말하도록 해야 한다.

## 6. 다중 홉 질문

다중 홉 질문은 답을 구하기 위해 두 개 이상의 정보를 연속해서 연결해야 하는 질문이다.

```text
희빈 → 참여한다 → KG 스터디
KG 스터디 → 사용한다 → PostgreSQL
```

위 관계에서 `희빈이 참여한 스터디에서 사용하는 데이터베이스는 무엇인가?`라는 질문에 답하려면 두 관계를 따라가야 한다.

일반적인 RAG는 질문과 비슷한 청크를 한 번 검색한다.
필요한 정보가 서로 다른 청크에 나뉘어 있으면 일부 청크만 검색될 수 있다.
검색되지 않은 정보를 LLM이 추측하면 근거가 없는 답변이 만들어질 수도 있다.

### 운영체제 데이터로 시도할 질문

- 프로세스가 I/O를 기다리면 상태가 어떻게 변하고, 그동안 CPU는 어떤 프로세스를 선택하는가?
- SJF의 장점과 한계를 함께 고려하면 어떤 상황에서 사용하기 어려운가?
- TLB miss와 page fault는 주소 변환 과정에서 어떻게 이어지는가?

이런 질문을 개인 데이터 에이전트에게 물어보고, 답변하지 못하거나 근거가 부족한 이유를 기록한다.
