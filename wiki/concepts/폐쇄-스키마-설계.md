> LLM에 "관계를 찾아줘"라고만 하면 같은 문장 하나도 `USES`·`USES_TECHNOLOGY`·`ADOPTS`로 갈라지고 문서마다 새 관계가 생긴다. 그래서 추출 전에 **허용하는 클래스·술어 목록을 닫는다.** 설계 순서는 데이터 → 스키마가 아니라 **질문 → 필요한 관계 → 스키마**(역량 질문, Competency Questions)이며, dldusgh318과 e0ng이 같은 출처(Noy & McGuinness, Ontology Development 101)에서 독립적으로 이 방법에 도달했다. 그리고 heebindev가 그 부작용을 처음 실측했다 — **적절한 항목이 없으면 LLM이 기존 스키마에 억지로 맞춘다.**

## 정의

- 닫힌 스키마 = 쓸 수 있는 클래스·술어를 미리 정한 목록으로 제한한다. 정의 밖 종류는 사용 불가, 새 개념은 스키마 수정이 필요. 열린 스키마 = 필요에 따라 추가. 트리플 추가가 컬럼 변경보다 쉽지만 같은 의미가 여러 표현으로 나뉘어 일관성이 떨어진다 (e0ng).
- **RDF 자체는 열린 스키마**이고, 허용 목록과 검증 규칙을 따로 두면 닫힌 스키마가 된다 — 닫힘/열림은 RDF의 성질이 아니라 운영 규율이다 (e0ng).
- 노드로 만들 기준은 **"다른 관계에서 다시 참조할 필요가 있는가"** (dldusgh318). 프로젝트·기술은 노드, 목적은 문자열 속성, 상태는 값. `RELATED_TO` 같은 애매한 관계 하나를 두면 거의 모든 개체를 연결할 수 있지만 그만큼 의미가 사라진다 — **판정 기준을 한 문장으로 설명할 수 있는 관계만** 둔다.
- RDFS는 추론 엔진용이 아니라 **스키마를 문서화하는 형식**으로 쓰고, 실제 domain/range 제한은 LLM 추출 규칙으로 집행한다 (dldusgh318). "처음부터 복잡한 OWL 추론이 아니라 RDFS 스타일로 클래스와 관계를 제한하는 것부터" (heebindev). 필수·선택은 사용 규칙이고 데이터 검증이 필요하면 SHACL (e0ng) → [[온톨로지와-추론]].
- v0의 목적은 완벽한 스키마가 아니라 **LLM의 추출 결과를 같은 기준으로 비교할 수 있게 만드는 것** (dldusgh318). "완성된 온톨로지가 아니라 내 데이터로 먼저 실험하기 위한 미니 온톨로지 v0" (heebindev).

## 설계 방법론 (e0ng)

| 방법 | 질문 | 강점 / 약점 |
|---|---|---|
| Top-down | 이 도메인의 핵심 개념은? | 일관된 체계 / 초기 추상화 어려움 |
| Bottom-up | 어떤 대상과 관계가 반복되는가? | 실제 데이터와 맞음 / 데이터에 없는 개념 누락, 파편화 |
| Middle-out | 가장 자주 쓰는 개념은? | 빠른 시작 / 핵심 선택에 따라 편향 |
| 역량 질문(CQ) | 이 온톨로지로 어떤 질문에 답해야 하는가? | 불필요한 개념 증가 방지 / 질문 밖 활용에 대응 못 함 |
| 기존 온톨로지 재사용 | schema.org·FOAF·Dublin Core에 있는가? | 다른 시스템과 연결 용이 / 도메인 의미와 불일치 가능 |

- e0ng의 실제 순서: **CQ로 범위 → Bottom-up으로 데이터 확인 → Middle-out으로 핵심 선정 → 기존 어휘 비교 → 정의·검증.** "기존 어휘를 먼저 적용하면 실제 데이터의 의미를 표준 어휘에 억지로 맞출 수 있다"며 핵심 개념 정리를 먼저 했다. "취업 준비를 하나로 묶으면 어느 회사를 준비했는지 답할 수 없다" → 활동을 폴더 단위로. 역할 요약: **질문은 설계 범위를, 데이터는 설계 근거를 준다.**
- 검증 실패의 2분 (e0ng): ① 필요한 개념·관계가 없음 → 설계 수정 ② 개념은 있지만 값이 없음 → 데이터 부족으로 기록. 기간 정보가 없는 활동을 잘못된 데이터로 판단하지 않는다 → [[온톨로지와-추론]] 열린 세계.
- do-dop의 방법론적 주장: **그래프 스키마는 "뭘 실패했는지"를 알아야 설계할 수 있다.** 이론만 보고 정하면 대부분 틀린다. 실제로 부딪힌 문제(엔티티 혼동, 정답 없는 질문의 과잉 확신)가 없었다면 "회사–공급–회사, 회사–투자–클러스터 관계가 필요하다"는 결론을 구체적으로 낼 수 없었다 → [[RAG-vs-그래프-질의]].

- **클래스 5·술어 7에 수렴**: kdyann·Yeongeunn·yujeong430이 독립적으로 같은 규모에 닿았다(dldusgh318 3·5, heebindev 5·8, e0ng 5·8). "작게 시작한다"의 경험적 상한으로 읽을 만하다. 시맨틱 웹이 웹 전체의 기본이 되기 어려웠던 이유(식별자·어휘를 유지할 사람, 조직 간 합의)가 스터디가 작은 닫힌 스키마로 시작하는 이유다 (yujeong430) → [[시맨틱-웹에서-지식그래프까지]].
- 닫혀 있는 것은 **추출에 쓰는 어휘의 범위**이지 세계가 아니다 — "목록 밖의 사실이나 문서에 없는 사실이 모두 거짓이라는 뜻이 아니다" (Yeongeunn).

- 역량 질문 커버리지 (dldusgh318): "A에서 쓴 기술을 다른 프로젝트에서도 썼나" ✅ / "제안했던 기술을 다른 곳에서 실제 적용했나" ✅ / "각 프로젝트에서 어떤 목적으로 썼나" ✅ / "문서에 없는 미구현 기능은?" ⚠️ — `not_implemented`로 **명시된** 것만 저장할 수 있고 기록 부재를 미구현으로 판단할 수 없다(열린 세계 가정).
- 4주차의 교훈: 장애 분석 질문에 필요한 관계와 기술 사용 질문에 필요한 관계가 거의 겹치지 않았다. **질문이 바뀌면 필요한 관계도 바뀐다** (dldusgh318) → [[멀티홉-질문과-Bridge-Entity]].

## 멤버들이 확인한 것 — 부작용

- **닫힌 스키마의 억지 매핑** (heebindev, 운영체제 노트 3청크, gpt-5-mini): 추출된 관계 8개 중 **3개가 의미적으로 틀렸다.** `SJF → IS_A → Non-preemptive`(종류가 아니라 특성), `SJF → PREVENTS → 평균 Turnaround time`(방지가 아니라 단축), `job A → REQUIRES → A arrival`(도착 시간은 자원이 아님). 진단: "미리 정한 클래스와 관계만 쓰게 했기 때문에 적절한 항목이 없을 때 LLM이 기존 스키마에 내용을 억지로 맞춘 것으로 보인다." **JSON Schema로 형식·허용값은 제한할 수 있지만 의미까지 정확해지지는 않는다.** 처방은 사람이 근거를 검토하고 클래스·관계를 고친 뒤 재추출.
- dldusgh318의 20청크 표본은 형식·근거 검증 통과율 99.38%였지만 **의미 정확도는 세지 않았다.** 5주차에 의미 정확도를 센 멤버는 heebindev 한 명이고 결과는 8건 중 3건 오류다. 두 수치를 따로 읽어야 한다 → [[LLM-트리플-추출]].
- `replaces` 0건 (dldusgh318): 표본 데이터 부족이 주원인이지만 전용 판정 절·few-shot이 없어 실제 사례가 와도 재현율이 낮을 가능성. 전체 추출 후에도 0건이면 술어에서 제외하기로.
- **문자열 검증이 의미를 보장하지 않는다** (kdyann): 근거 스팬이 원문과 일치해도 "그 문구가 내 Project의 기능을 말하는지, 다른 회사 소식 소개인지는 판단하지 못한다". 뉴스 요약을 자기 Project/Feature로 오분류한 후보가 실제로 나왔다. Yeongeunn 1차 추출은 API 경로만 보고 제공 서비스를 단정했고, 문맥을 보강하자 정책 관계가 빠졌다 → [[LLM-트리플-추출]].
- 닫힌 스키마가 술어는 고정해도 **문자열 속성 값은 자유 텍스트로 남는다.** "작업 큐"로 질의했는데 적재된 목적은 "큐 기반 비동기 처리"라 `CONTAINS '작업 큐'`로는 0건 (dldusgh318) → [[그래프-적재-Postgres와-Neo4j]].
