# 03. 하이브리드 검색과 RAG

> 참고 자료:
> - [Elasticsearch 공식 RRF 문서](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)
> - [What is reciprocal rank fusion? — Abhishek Thakur](https://www.youtube.com/watch?v=2uBcjEecr38) — BM25·벡터 검색 결과를 점수 대신 순위로 융합하는 RRF 개념 학습.

## 한 줄 요약

키워드와 벡터 검색의 순위를 RRF로 합치고 검색한 원문에 근거해 답하되, 여러 문서의 사실과 관계를 연결해야 하는 질문에서 RAG의 한계를 살펴본다.

## 핵심 개념

- 하이브리드 검색: 키워드 일치를 보는 BM25와 의미 유사성을 보는 벡터 검색의 결과를 결합한다.
- RRF (Reciprocal Rank Fusion): 검색기의 원래 점수 대신 문서 순위를 이용해 결과를 융합한다.
- RAG: 질문에 관련된 원문을 검색하고 컨텍스트로 조립해 LLM 답변의 근거로 제공한다.
- 근거 인용: 답변의 주요 주장을 실제로 뒷받침하는 원문 발췌와 출처 URL을 연결한다.
- 다중 홉 질문: 여러 문서에서 사실을 찾고 그 관계를 연결해야 답할 수 있는 질문이다.

## 상세 정리

### RRF: 점수 대신 순위를 합치는 이유

BM25 점수와 벡터 유사도는 척도와 분포가 달라 그대로 더하면 한쪽이 과도하게 영향을 줄 수 있다. 점수를 정규화해 합칠 수도 있지만, 질문마다 달라지는 점수 분포와 정규화 방식·가중치를 고려해야 한다. 같은 범위로 맞춘 점수가 같은 관련도 확신을 뜻하는 것도 아니다.

RRF는 각 검색기의 문서 순위만 이용하므로 서로 다른 점수 척도를 맞추는 과정을 생략한다. 대신 원래 점수에서 1위와 2위가 얼마나 차이 났는지는 잃는다. 각 목록의 순위를 1부터 시작하면 문서 d의 융합 점수는 다음과 같다.

```text
RRF(d) = Σ 1 / (c + rank_i(d))
```

문서가 검색기 i의 반환 목록에 없으면 그 목록의 기여는 0이다. 상위 순위일수록 더 많이 기여하고, 여러 목록에 등장한 문서는 각 기여를 합산한다. c는 순위에 따른 가중치 감소를 조절하는 상수이며 Elasticsearch의 기본값은 60이다. 순위를 합쳤다고 검색 품질이 반드시 좋아지는 것은 아니므로 실제 질문에서 결과를 확인해야 한다.

### RAG: 질문에서 근거 있는 답변까지

RAG는 **질문 → 검색 → 컨텍스트 조립 → LLM 답변 + 근거 인용**의 흐름으로 진행한다. 검색 단계에서 관련 문서를 찾고, 컨텍스트 조립 단계에서 중복을 제거하며 필요한 원문 발췌·문서 ID·출처 URL을 함께 제공한다. LLM은 이 근거에 따라 답하고, 근거가 없거나 충돌하면 추측 대신 모르는 부분을 밝혀야 한다.

URL을 붙이는 것만으로 답변이 증명되지는 않는다. 실제 발췌가 답변의 주요 주장을 뒷받침하는지 확인해야 한다. 원문에 없는 사실을 만들어 내지 않도록 하고, 원문 안의 지시문은 실행할 명령이 아니라 자료로 취급한다.

### 다중 홉 질문의 한계와 지식 그래프로 이어지는 질문

내가 디자인 시스템에 쓴 도구를 먼저 찾고, 참고 게시물에서 같은 도구를 찾아 어떤 작업에 쓰이는지 연결하는 질문을 실제로 던졌다. 내 게시물 13개와 참고 게시물 235개를 합친 248개 문서에 Nori BM25·캐시된 E5 벡터 검색·RRF(c=60)를 적용했다. 전체 질문을 한 번에 검색한 상위 5개에는 내 디자인 시스템 글이 있었지만, Claude Code의 구체적인 활용을 설명한 참고 글은 없었다. LLM은 일반적인 ‘클로드’ 언급만으로 같은 Claude Code인지와 직접 사용 여부를 확정하지 않고 답변을 보류했다.

다음에는 내 게시물에서 실제 LLM이 Pen.dev와 Claude Code를 추출하게 한 뒤, 도구 이름이 등장하는 참고 캡션으로 범위를 좁혀 각각 검색했다. 최종 컨텍스트를 동일하게 5개 문서로 제한한 후에도 Claude Code의 코드베이스 이해·계획·테스트 활용 팁과 Graphify 연동 설명을 연결할 수 있었다. Pen.dev는 수집된 참고 캡션에서 찾지 못했다.

하지만 관련 글을 찾는 것과 작성자가 실제 사용했다는 사실을 확인하는 것은 다르다. 내 글에는 ‘제가 사용해본’이라는 근거가 있지만, 참고 글은 활용을 권장하거나 다른 도구와의 연동을 설명한다. 후속 LLM 답변도 참고 작성자의 직접 사용은 확정하지 않았다. 처음에는 연결에 필요한 문서를 놓쳤고, 다시 검색한 뒤에는 ‘직접 사용했다’는 관계의 근거가 여전히 부족했다. 없는 내용을 지어낸 실패가 아니라 근거 부족을 구분한 결과다.

두 방식 모두 검색기별 후보 10개와 최종 컨텍스트 5개를 사용했지만, 후속 검색에는 내 글·참고 글의 범위 분리, 도구 이름 필터, 추가 검색이 함께 들어갔다. 따라서 결과를 질문 분해나 RRF 하나의 효과로 단정할 수는 없다. 이번 답변 생성은 이 대화의 격리된 Codex LLM으로 수행했고 벡터 검색은 정규화한 E5 벡터의 전수 비교였다. 임시 검색 실험이며 개인 챗봇이나 프로젝트 OpenAI API에 통합한 실행은 아니다.

여기서 **“검색은 문서를 찾는다. 사실과 관계를 찾으려면 무엇이 필요한가?”**라는 질문이 생긴다. 도구가 글에 ‘언급됐다’, 활용을 ‘권장한다’, 다른 도구와 ‘연동된다’, 작성자가 ‘직접 사용했다’는 서로 다른 관계다. 대상의 종류와 관계를 정의하는 온톨로지가 왜 필요한지 생각할 출발점으로 삼고, W4에서는 **지식 그래프의 배경 — 온톨로지 변천사와 방법론**을 공부한다. 그래프도 원문에 없는 직접 사용 사실을 만들어 주지는 않는다.

## 예시 / 코드

내 Instagram과 참고 캡션으로 실제 질문한 다중 홉 예시:

> 내가 디자인 시스템을 만들 때 쓴 도구 중, 참고 게시물에서도 사용한 도구는 무엇이고 거기서는 어떤 작업에 활용했어?

- [내 디자인 시스템 글](https://www.instagram.com/reel/DcQfhppROpt/): “제가 사용해본”, “Pen.dev + Claude Code 디자인 시스템 만드는 방법”이라고 적혀 있다. 디자인에서 컬러·폰트·컴포넌트를 추출하는 방법으로 소개한다.
- [Claude Code 활용 팁 참고 글](https://www.instagram.com/p/DcpCTaNE2c7/): “Start with codebase Q&A”, “Plan before coding” 등 코드베이스 이해·계획·테스트 활용을 권장한다.
- [Graphify 참고 글](https://www.instagram.com/p/DcSAFHgCMhP/): 코드·문서·티켓의 관계를 정리하고 “It plugs into tools like Claude Code”라고 연동을 설명한다.

실제 후속 답변은 Claude Code 관련 활용 설명을 출처와 연결하면서도 **참고 작성자가 직접 수행한 작업은 캡션만으로 확정할 수 없다**고 밝혔다. Pen.dev의 참고 사용 여부도 확인하지 못했다. 공통으로 등장한 도구와 실제로 사용한 공통 도구를 구분해야 한다.
