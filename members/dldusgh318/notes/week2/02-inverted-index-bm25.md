# **02. 1세대 — 역색인과 BM25**

## **grep의 다음 단계: “찾았다” -> “관련 있는 순서대로”**

0세대 grep에서는 두 가지 문제가 있었다.

```
"캐시" → 407건       # 너무 많이 찾음
"성능을 개선한 경험" → 0건  # 표현이 달라 못 찾음
```

특히 `캐시`처럼 결과가 많을 때 **어떤 문서부터 봐야 하는지 알 수 없었다.**

이를 해결하기 위해 검색엔진은 문서를 매번 처음부터 훑는 대신 **단어 → 문서 방향으로 정보를 미리 저장**한다. 이것이 **역색인(Inverted Index)** 이다.

---

## **1. 역색인 — 검색 방향을 뒤집는다**

일반적인 문서는 이런 구조다.

```
doc1 → [지식, 그래프, 검색]
doc2 → [지식, 베이스]
doc3 → [검색, 엔진]
```

역색인은 이걸 반대로 저장한다.

```
지식   → [doc1, doc2]
그래프 → [doc1]
검색   → [doc1, doc3]
```

따라서 `검색`이라는 단어를 찾기 위해 모든 문서를 다시 훑을 필요 없이, `검색`에 연결된 문서 목록을 확인할 수 있다.

실제로는 문서 번호뿐 아니라 추가 정보도 저장한다.

```
"검색"
→ doc1: 2번 등장
→ doc3: 5번 등장
```

이런 통계를 이용하면 단순히 `MATCH / NOT MATCH`에서 끝나지 않고 **문서마다 관련도 점수를 계산할 수 있다.**

---

## **2. BM25 — 어떤 문서가 더 관련 있을까?**

BM25는 검색어와 문서가 얼마나 관련 있는지 점수를 계산해 **검색 결과에 순위를 매긴다.**

핵심 아이디어는 생각보다 단순하다.

- **TF**: 검색어가 이 문서에서 많이 등장하면 중요할 가능성이 높다.
- **IDF**: 모든 문서에 흔하게 나오는 단어라면 중요도를 낮춘다.
- **문서 길이 보정**: 긴 문서가 단순히 단어를 많이 포함했다는 이유로 유리해지는 것을 보정한다.

BM25에서는 `k1`이 단어가 반복될 때 점수가 끝없이 증가하지 않도록 조절하고, `b`가 문서 길이를 보정한다.

즉,

```
grep
"캐시 있음?" → YES

BM25
"이 문서가 캐시라는 검색어와 얼마나 관련 있지?"
→ 점수 계산 → 관련도 순 정렬
```

로 발전한 것이다.

## **3. 그런데 한국어에서는 토크나이징이 중요하다..**

역색인을 만들려면 먼저 문장을 **어떤 단어로 나눌지** 결정해야 한다.

예를 들어 단순히 띄어쓰기 기준으로 처리하면,

```
학교에서 지식그래프를 배웠다

→ 학교에서 / 지식그래프를 / 배웠다
```

`학교`를 검색했을 때 `학교에서`와 일치하지 않는 문제가 생길 수 있다.

그래서 Elasticsearch에서는 한국어 형태소 분석기인 **nori**를 사용할 수 있다.

실제로 내 데이터에서도

```
"학교에서 지식그래프를 배웠다"

nori
→ 학교 / 지식 / 그래프 / 배웠 / 배우
```

처럼 조사와 어미를 처리해 검색에 활용할 수 있는 형태로 만들었다.

### **nori만 사용하면 될까???**

그렇지는 않았다.

신조어나 기술 용어처럼 사전에 없는 표현에서는 예상하지 못한 형태로 단어가 분리될 수 있다.

그래서 이번 실습에서는 **n-gram 필드도 함께 사용**했다.

```
지식그래프

2-gram
→ 지식 / 식그 / 그래 / 래프
```

n-gram은 사전을 사용하지 않고 일정한 글자 수로 잘라 저장하기 때문에 **오타·신조어·띄어쓰기 차이**에 상대적으로 강하다.

대신 토큰이 많이 생성되어 저장 공간이 커지고, 관련 없는 결과가 검색될 가능성도 증가한다.

따라서 하나만 고르지 않고 같은 문서를 두 방식으로 색인했다.

```
text
├─ nori   → 형태소 기반 검색
└─ ngram  → 글자 조각 기반 검색
```

**nori로 정밀하게 찾고, n-gram으로 놓치는 표현을 보완하는 방식**이다.

## **4. 내 데이터로 직접 확인해보기**

개인 Notion 데이터를 Elasticsearch에 색인해 grep과 비교했다.

### **Case 1. 한국어 형태 처리**

```
학교에서 → 학교
배웠다   → 배우
```

grep에서 문제가 되었던 조사·어미를 nori가 처리하는 것을 확인했다.

반면 `지식그래프` 같은 기술 용어는 원하는 형태로 처리되지 않았다. **형태소 분석 역시 사전과 analyzer 설정에 영향을 받는다**는 것을 확인했다.

### **Case 2. 오타 `쿠버네티즈`**

```
Query: 쿠버네티즈
grep → 0건
BM25 → 7건
```

BM25에서는 실제 Kubernetes 관련 문서가 상위에 등장했다.

처음에는 “BM25가 오타에도 강하다”고 생각했지만 analyzer 결과를 확인하니 이유가 달랐다.

```
쿠버네티즈 → 쿠 / 버네 / 티즈
쿠버네티스 → 쿠 / 버네 / 티스
               ↑    ↑
             일부 token 일치
```

즉, **오타를 이해한 것이 아니라 형태소 분석 결과 일부가 우연히 겹쳐 검색된 것**이었다..

검색 결과만 보는 것이 아니라 **analyzer가 실제로 어떤 token을 만들었는지 확인해야 하는 이유**를 알 수 있었다.

### **Case 3. BM25 점수 확인**

Elasticsearch의 `explain`을 이용해 `트러블슈팅` 검색 결과의 점수를 확인했다.

```
총점 13.63

검색어 등장 횟수(tf)
문서 길이(dl)
전체 평균 문서 길이(avgdl)
단어 희소성(idf)
        ↓
BM25 점수 계산
```

특히 짧은 문서가 문서 길이 보정으로 영향을 받는 것을 확인했다.

→ **청크의 길이가 크게 달라지면 BM25 순위에도 영향을 줄 수 있다!**

## **5. 비용도 생긴다**

역색인은 검색을 위해 추가 데이터를 미리 저장한다.

이번 데이터에서는:

```
원본 데이터     0.95MB
역색인          5.1MB
               약 5.4배

색인            1,562 chunks / 약 1.5초

검색
grep            약 20~30ms
n-gram 검색     약 5~6ms
```

특히 n-gram은 하나의 단어에서 많은 token을 만들기 때문에 저장 공간 증가에 영향을 준다.

즉, 역색인은 **저장 공간과 사전 색인 비용을 사용하는 대신 검색 시 전체 스캔을 피하고 랭킹까지 가능하게 만드는 구조**라고 이해할 수 있다.

## **이번 학습에서 가져갈 것**

```
grep
│
│ 문자열이 있나?
↓
역색인
│
│ 어떤 단어가 어떤 문서에 있나?
↓
BM25
│
│ 그중 어떤 문서가 더 관련 있나?
↓
관련도 순 검색
```

하지만 BM25 역시 기본적으로 **token이 얼마나 잘 일치하는가**를 기반으로 한다.

따라서

```
문서: API 응답시간을 750ms → 150ms로 단축했다.
질문: 성능을 개선한 경험
```

처럼 **사용한 단어는 다르지만 의미가 같은 경우**에는 여전히 한계가 있다.

이 문제를 해결하기 위해 다음 단계에서는 문장을 숫자 벡터로 표현해 **의미가 비슷한 문서를 찾는 Vector Search**를 사용해본다.
