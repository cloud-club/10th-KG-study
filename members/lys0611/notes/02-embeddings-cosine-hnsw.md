# 02. 임베딩·코사인 유사도·HNSW — 의미 검색을 직접 돌려 본 기록

`마감 일정`으로 검색했을 때 벡터 검색은 `제출일`, `언제까지 완성` 같은 표현을 가져왔다. 같은 단어가 없어도 찾는다는 장점은 확인했다. 다만 벡터가 가깝다는 것만으로 질문의 정답이라는 보장은 없다.

## 임베딩 모델 선택

검색용 임베딩은 관련 있는 질문과 문서의 벡터가 가깝도록 학습한다. 문서 벡터를 미리 만들면 검색할 때는 질문만 인코딩한다. 질문·후보를 쌍으로 읽는 cross-encoder보다 1차 검색에 쓰기 쉽다. ([Sentence-BERT](https://aclanthology.org/D19-1410/))

차원만 같다고 서로 다른 모델의 벡터를 비교할 수는 없다. 같은 모델을 쓰되, query/document 지시문이 따로 있는 모델은 각 용도에 맞게 적용해야 한다. 모델을 바꾸면 문서도 다시 임베딩한다.

이번에는 한국어 검색 모델 `nlpai-lab/KURE-v1`을 로컬에서 사용했다. `bge-m3` 기반의 1024차원 모델이고 MIT 라이선스다. 카톡 데이터를 임베딩 API에 보내지 않기 위해 선택했다. ([모델 카드](https://huggingface.co/nlpai-lab/KURE-v1))

[W2 측정 기록](../labs/01-ingest/README.md)에서는 Apple Silicon MPS, batch 32로 1,922개 청크를 처리했다. 모델 로딩 10.31초, 인코딩 519.29초로 총 약 8분 50초였다. 이미 캐시된 모델을 썼으므로 최초 다운로드 시간은 제외된 값이다.

## 코사인 유사도와 거리

```text
cos(a, b) = (a · b) / (|a| × |b|)
cosine distance = 1 - cos(a, b)
```

0이 아닌 벡터에서 코사인 유사도는 -1~1, 거리는 0~2다. L2 정규화로 벡터 길이를 1로 만들면 코사인 유사도와 내적이 같아진다. 현재 저장 파이프라인도 임베딩을 정규화한다.

pgvector의 연산자와 인덱스 설정은 맞춰야 한다.

| 연산자 | 의미 | 인덱스 opclass |
|---|---|---|
| `<=>` | 코사인 거리 | `vector_cosine_ops` |
| `<->` | L2 거리 | `vector_l2_ops` |
| `<#>` | 음의 내적 | `vector_ip_ops` |

지금은 `vector_cosine_ops`를 사용한다. 정렬은 `ORDER BY embedding <=> query_vector LIMIT k`처럼 거리 오름차순으로 쓰고, 표시할 유사도만 `1 - 거리`로 계산한다. `ORDER BY 1 - 거리 DESC`로 바꾸면 근사 인덱스를 활용하는 쿼리 형태에서 벗어난다. ([pgvector 문서](https://github.com/pgvector/pgvector#querying))

코사인 0.59를 “정답일 확률 59%”로 해석하면 안 된다. 모델과 데이터마다 점수 분포가 다르므로, 임계값도 실제 정답·오답 분포를 보고 정해야 한다.

## HNSW로 후보 줄이기

정확 검색은 전체 문서 벡터와 거리를 비교한다. HNSW는 여러 층의 근접 그래프를 만들고 위층에서 크게 이동한 뒤 아래층에서 가까운 후보를 좁힌다. 비교량을 줄이는 대신 정확 검색의 상위 결과를 일부 놓칠 수 있다. ([HNSW 논문](https://arxiv.org/abs/1603.09320))

pgvector의 기본값은 `m=16`, `ef_construction=64`, `hnsw.ef_search=40`이다. 각각 그래프 연결 수, 구축 후보 폭, 검색 후보 폭을 조절한다. 값을 키우면 대체로 재현율은 좋아지지만 메모리·구축 시간·검색 시간이 더 든다. HNSW는 IVFFlat과 달리 별도 학습 단계가 없으며, `vector` 기준 최대 2,000차원을 색인하므로 KURE의 1024차원은 범위 안이다. ([HNSW 설정](https://github.com/pgvector/pgvector#hnsw))

W2의 코사인 top-5는 `chunk_embeddings_hnsw`를 사용했고 약 1.6~1.9ms였다. 이 노트북과 캐시 상태에서의 값이다. 1,922개 규모에서는 정확 검색도 비교해 봐야 한다.

### 방 필터를 붙이면

HNSW 후보를 찾은 뒤 방 조건을 적용하면 `LIMIT 10`인데도 결과가 10개보다 적을 수 있다. pgvector 0.8.0부터는 iterative scan으로 추가 탐색을 할 수 있다. 탐색 한도에 도달하면 여전히 부족할 수 있으며, `strict_order`도 정확 검색을 뜻하지는 않는다.

```sql
BEGIN;
SET LOCAL hnsw.ef_search = 100;
SET LOCAL hnsw.iterative_scan = strict_order;
-- 이 트랜잭션 안에서 거리순 검색 실행
COMMIT;
```

필터가 자주 쓰이면 후보 폭뿐 아니라 필터 컬럼 인덱스, 부분 인덱스, 파티셔닝도 검토한다. ([필터링](https://github.com/pgvector/pgvector#filtering))

## 카톡 청킹

메시지를 한 건씩 넣으면 `넵`, `ㅋㅋ` 같은 짧은 반응이 따로 검색된다. 하루 전체를 묶으면 여러 주제가 한 벡터에 섞인다. 현재 규칙은 다음과 같다.

- 30분 이상 끊기면 새 세션.
- 세션 안에서 최대 30건 또는 700자, 다음 청크에 3건 겹침.
- 사진·이모티콘·시스템 메시지는 청크에서 제외하고 `messages`에는 보존.

날짜·참여자 헤더는 맥락을 주지만 반복되는 이름이 검색에 영향을 줄 수도 있다. 헤더 유무와 청크 길이부터 비교해 볼 생각이다.

팀리더 방의 `마감 일정` 검색에서는 벡터 1위가 제출일 대화 `#1653`(0.592)이었다. BM25 top-5와 겹친 청크는 하나뿐이었다. 표현이 다른 대화를 찾은 사례이지, 집계나 여러 대화의 관계까지 해결한 결과는 아니다.

## 비교할 때 볼 것

- 정확 검색 top-10을 기준으로 HNSW top-10의 겹침 비율과 지연을 잰다.
- 검색 정답 라벨의 Recall@k와 위 근사 검색 재현율은 별개로 기록한다.
- 청킹이나 모델은 한 번에 하나씩 바꾼다. 모델끼리 코사인 점수 자체를 비교하지 않는다.

3주차의 융합 검색·평가 결과는 [RRF 노트](04-hybrid-search-rrf-recall.md)에 이어 적었다.
