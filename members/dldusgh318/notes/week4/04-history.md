# **변천사 — 시맨틱 웹에서 Knowledge Graph, GraphRAG까지**

앞에서는 RDF로 사실을 표현하고, SPARQL로 관계를 조회하고, RDFS와 OWL로 그 관계에 의미와 추론 규칙을 더하는 방법까지 봤다.

여기까지 보면 오히려 궁금한 점이 생긴다. **이렇게 오래전에 잘 만들어진 표준이 있는데, 왜 지금의 웹은 RDF와 OWL로 이루어져 있지 않을까?** 그리고 반대로 Knowledge Graph는 왜 Google, Wikidata를 넘어 최근 GraphRAG나 기업의 Ontology까지 다시 주목받고 있을까?

이 흐름을 따라가 보니 기술 자체가 완전히 새로워졌다기보다, **비슷한 아이디어에서 무엇을 포기하고 무엇을 가져갔는지가 계속 달라져 왔다.**

전체 흐름부터 보면 이렇다.

**Semantic Web → RDF/OWL → DBpedia·Linked Data → Google Knowledge Graph·Wikidata → 기업 Knowledge Graph → GraphRAG → Palantir Ontology**

연도를 외우기보다는 각 단계가 **이전 방식의 어떤 문제를 보고 방향을 바꿨는지** 중심으로 정리했다.

## **1. Semantic Web : 웹 전체에 의미를 붙이자**

시작은 2001년 팀 버너스리 등이 제안한 **Semantic Web** 비전이다.

당시 웹은 사람이 문서를 읽고 이해하는 공간이었다. 검색엔진이나 프로그램 입장에서는 웹페이지에 `홍익대학교`, `컴퓨터공학`, `학생`이라는 단어가 있어도 **이 셋이 어떤 관계인지 명확하게 알기 어려웠다.**

Semantic Web이 생각한 해결책은 꽤 거대했다.

→ 웹의 데이터에 기계가 이해할 수 있는 의미와 관계를 명시적으로 붙이자!

그렇게 되면 소프트웨어 에이전트가 단순히 문서를 검색하는 것을 넘어 데이터를 연결하고, 추론하고, 사람을 대신해 작업까지 수행할 수 있다고 봤다.

예를 들어 병원, 의사, 진료시간, 위치 같은 정보가 모두 공통된 의미 체계로 표현되어 있다면 에이전트가 여러 웹사이트의 정보를 직접 연결해 적절한 병원과 시간을 찾는 식이다.

지금 AI Agent에게 기대하는 모습과 꽤 비슷하다. 다만? **목표가 달랐다기보다 그 목표를 이루려는 방법이 달랐다.**

## **2. 문제는 웹 전체가 같이 움직여야 했다는 것**

Semantic Web이 제대로 동작하려면 몇 가지 전제가 필요했다.

1. 웹사이트가 데이터를 기계가 이해할 수 있는 형태로 제공해야 한다.
2. 서로 RDF 같은 공통 표준을 사용해야 한다.
3. 같은 개념을 어떤 이름과 관계로 표현할지 합의해야 한다.
4. 만들어진 데이터를 연결하고 추론할 수 있어야 한다.

문제는 **이 작업의 비용과 이득을 얻는 사람이 달랐다는 것**이다.

웹사이트 운영자는 기존 페이지 외에 기계가 읽을 수 있는 메타데이터까지 잘 관리해야 한다. 그런데 그렇게 데이터를 만들어놓았을 때 가장 큰 이득은 그 데이터를 가져다 사용하는 검색엔진이나 외부 서비스가 얻을 수도 있다.

즉 모두가 참여하면 가치가 커지지만, **내가 먼저 참여해야 할 이유는 약한 구조**였다.

그래서 Semantic Web의 어려움은 단순히 RDF나 OWL이라는 기술이 부족해서라기보다 **웹 전체의 참여와 합의를 요구했다는 조정 문제(coordination problem)**로도 볼 수 있었다.

## **3. RDF와 OWL : 더 정확하게 표현하려고 했다**

이후 RDF와 OWL이 W3C 표준으로 자리 잡으면서 **세상의 의미를 얼마나 정확하게 표현할 수 있는가**에 대한 기술도 발전했다.

앞에서 본 것처럼 클래스의 계층을 표현하고, 동일성을 정의하고, 관계의 성질을 선언하고, 저장하지 않은 사실을 추론할 수도 있다.

문제는 표현력이 올라갈수록 이를 제대로 설계하고 사용하는 일도 어려워진다는 점이었다.

**더 정교한 의미 표현 → 더 복잡한 온톨로지 설계 → 더 높은 구축·추론 비용**

특히 현실에서는 완벽한 의미 체계를 설계하는 것만큼 중요한 문제가 하나 더 있었다.

**그래서 실제 데이터는 누가 넣을 것인가?**

아무리 정교한 온톨로지가 있어도 그 안에 들어갈 데이터가 없다면 활용할 수 없다. 이후 흐름에서는 점점 **완벽한 의미 모델보다 실제 데이터를 확보하는 것**이 중요해지기 시작한다.

## **4. DBpedia와 Linked Data : 일단 이미 있는 데이터를 가져오자**

2000년대 후반에는 방향이 조금 달라진다.

대표적인 사례가 **DBpedia**다. 사람들이 새로운 지식 그래프 데이터를 처음부터 직접 입력하게 하는 대신, 이미 Wikipedia에 사람들이 작성해놓은 정보를 구조화해서 가져왔다.

즉, **완벽한 온톨로지를 먼저 설계 → 사람이 데이터 입력** 보다는…

**→ 이미 존재하는 데이터 → 구조화 → 서로 연결** 쪽으로 현실적인 방향을 잡은 것이다.

Linked Data 역시 각자 만든 데이터를 URI를 이용해 서로 연결하자는 아이디어였다. Semantic Web의 비전을 유지하면서도 **우선 실제 데이터를 만들고 연결해보자**는 쪽으로 무게가 이동했다.

여기서 얻은 교훈은 단순했다.

**아무리 좋은 형식이 있어도 결국 데이터가 있어야 한다.**

다만 여러 주체가 같은 표준과 식별자를 사용하고 데이터를 지속적으로 관리해야 한다는 문제 자체가 사라진 것은 아니었다.

## **5. Google Knowledge Graph : 웹이 안 해주면 직접 만든다**

2012년 Google이 Knowledge Graph를 발표하면서 방향이 크게 달라진다.

Google이 내세운 표현이 **“things, not strings”**, 즉 문자열이 아니라 실제 개체를 이해하겠다는 것이었다.

예를 들어 사용자가 `Jaguar`를 검색했을 때 단순히 문자열이 포함된 문서를 찾는 것에서 끝나는 게 아니라, 이것이 자동차 브랜드인지 동물인지 등을 **Entity와 관계를 통해 이해해서 검색 결과에 활용하는 것**이다.

Semantic Web과 목표 자체는 비슷해 보이지만 접근 방식에는 큰 차이가 있었다.

| **Semantic Web** | **Google Knowledge Graph** |
| --- | --- |
| 웹 전체가 구조화된 데이터를 제공 | Google이 여러 데이터 소스를 직접 통합 |
| 공통 표준과 어휘 합의가 중요 | 내부에서 필요한 스키마를 직접 관리 |
| 여러 주체가 데이터를 연결 | 한 조직이 품질을 통제 |
| 개방된 웹 전체가 대상 | Google 서비스에서 사용할 그래프 |

즉 Google은 **“웹 전체가 표준을 지켜주기를 기다리는 방식”을 포기했다.**

Wikipedia, Freebase를 비롯한 여러 소스의 정보를 가져와 직접 통합하고, 그 결과를 자사의 검색 경험 개선에 사용했다.

여기서는 데이터를 구축하는 비용을 Google이 내지만, 검색 품질이 좋아지면서 생기는 이득도 Google이 가져간다.

Semantic Web에서 있었던 **“누가 먼저 데이터를 만들 것인가?”라는 조정 문제를 한 조직 내부로 가져와버린 것**이다.

## **6. Wikidata : 개방성과 실용 사이**

비슷한 시기에 시작된 Wikidata는 또 다른 방향을 보여준다.

Wikidata는 데이터를 공개하고 SPARQL을 통해 누구나 질의할 수 있다는 점에서는 Semantic Web과 Linked Data의 철학을 상당 부분 이어간다.

하지만 앞에서 직접 봤듯 실제 데이터를 표현하는 방식은 꽤 현실적이다.

단순히 `사람 → 학교`라고만 표현하는 것이 아니라 **statement에 qualifier와 reference를 붙여 기간이나 출처 같은 정보도 함께 관리**한다.

즉 현실 세계에서는 하나의 사실이 언제나 절대적인 참/거짓으로 깔끔하게 떨어지는 것이 아니라, **언제 성립했는지, 어떤 출처에서 나온 정보인지**도 중요하다는 점을 데이터 모델에 반영한다.

그래서 Wikidata는 Semantic Web의 개방성과 표준화 방향을 어느 정도 유지하면서도, 실제 대규모 지식베이스 운영에 필요한 현실적인 데이터 모델을 함께 발전시킨 사례로 볼 수 있었다.

## **7. 기업 Knowledge Graph : 세상 전체가 아니라 우리 데이터만**

이후 Knowledge Graph는 검색엔진뿐 아니라 여러 기업 내부에서도 사용되기 시작했다.

여기서 또 한 번 범위가 줄어든다.

**“세상의 모든 지식을 연결하자” → “우리 서비스에 필요한 지식만 연결하자”**

예를 들어 상품 서비스라면 상품·브랜드·카테고리 관계에 집중할 수 있고, 채용 서비스라면 사람·회사·직무·기술의 관계에 집중할 수 있다.

범위를 좁히면 큰 장점이 있다. 세상 모든 사람이 동의할 수 있는 `Technology`의 정의를 만들 필요가 없다. **우리 서비스에서 Technology를 무엇으로 볼지만 정하면 된다.**

이건 현재 우리 실습 방향과도 꽤 비슷하다.

우리는 세상의 모든 관계를 표현하려는 게 아니라 **개인 프로젝트 문서에서 검색에 도움이 될 관계**만 대상으로 한다. 그래서 우선 `프로젝트에 포함됨`, `사용 기술`, `사용 목적`, `구현 상태` 정도의 작은 관계 집합부터 시작한다.

즉 범용 온톨로지를 만드는 대신 **문제와 도메인을 좁혀 실제로 사용할 수 있는 그래프를 만드는 방향**이다.

## **8. GraphRAG : 그래프를 만드는 비용을 LLM으로 줄인다**

Knowledge Graph에는 여전히 큰 문제가 남아 있었다.

**그래프를 누가 만드느냐?** 다..

문서가 수천 개 있다면 그 안에서 Entity를 찾고, 관계를 추출하고, 같은 대상을 합치고, 그래프를 지속적으로 업데이트해야 한다.

최근 LLM이 등장하면서 이 부분을 자동화할 수 있는 가능성이 커졌고, Microsoft Research의 **GraphRAG**도 이런 흐름에서 등장했다.

GraphRAG의 대표적인 파이프라인을 단순화하면 다음과 같다.

**문서 → LLM으로 Entity·Relationship 추출 → Graph 생성 → Community 탐지 → Community 요약 → 질문에 활용**

여기서 일반적인 Vector RAG와 차이가 드러난다.

일반 RAG는 보통 질문과 가까운 top-k 청크를 찾는다. 그래서 **“이 프로젝트에서 Redis를 왜 사용했어?”**처럼 특정 정보가 필요한 질문에는 잘 맞는다.

그런데 **“이 문서 전체에서 반복적으로 나타나는 주요 주제는 무엇인가?”** 같은 질문은 top-k 청크 몇 개만 봐서는 답하기 어렵다.

| **질문** | **성격** |
| --- | --- |
| 특정 프로젝트에서 Redis를 왜 사용했는가? | Local한 정보 탐색 |
| 전체 문서에서 주요 기술적 관심사는 무엇인가? | Global한 정보 종합 |

GraphRAG에서는 그래프를 여러 Community로 나누고 각 Community의 정보를 요약해두는 방식 등을 통해 이런 **전체 데이터에 대한 질문**을 다루려고 한다.

여기서 중요한 변화는 Knowledge Graph의 오래된 문제였던 **구축 비용 일부를 LLM을 통해 자동화하려 한다는 점**이다.

## **9. 우리도 사실 GraphRAG의 앞부분과 비슷한 일을 하려 한다는 것**

이번 실습에서 하려는 것도 문서에서 Entity와 관계를 추출해 작은 그래프를 만드는 것이다.

**개인 문서 → LLM으로 관계 추출 → PostgreSQL에 Entity/Edge 저장 → Graph Retrieval → 기존 RAG와 비교**

GraphRAG 전체를 구현하는 것은 아니다. Community Detection이나 Community Summary 같은 단계도 현재 실험 범위에는 없다. (나중에 클클용 graphRAG실습을 한다면, 이것도 하는 거 같습니다..)

다만 **비정형 문서에서 LLM을 이용해 그래프를 자동으로 구축한다**는 앞단의 문제는 겹친다.

그리고 여기서 지난주 질문으로 다시 돌아간다.

필요한 정보가 문서 여러 곳에 흩어져 있어서 Retrieval이 실패했다면, 관계를 미리 추출해 연결해두는 것이 도움이 될까?

이번 실습에서는 Knowledge Graph가 무조건 더 좋다고 가정하는 게 아니라 **어떤 종류의 Retrieval Failure에서 실제로 도움이 되는지**를 확인하는 쪽에 가깝다.

## **10. Palantir Ontology : 그래프를 읽는 것에서 행동하는 것으로**

최근 기업에서 사용하는 Ontology를 보다 보면 Semantic Web에서 말했던 Ontology와 꽤 다른 모습도 나타난다. 대표적으로 Palantir Foundry의 Ontology가 있다.

여기서는 조직의 데이터를 현실의 업무 개체와 연결한다.

| **개념** | **의미** |
| --- | --- |
| Object Type | 주문, 직원, 설비 같은 업무 개체 |
| Property | 개체의 속성 |
| Link Type | 개체 사이의 관계 |
| Action Type | 개체의 상태를 실제로 변경하는 업무 행동 |
| Function | 관련 비즈니스 로직 |

여기서 특히 눈에 들어온 것은 **Action**이었다.

지금까지 우리가 본 Knowledge Graph는 주로 **“무엇이 무엇과 연결되어 있는가?”를 조회하는 것**에 초점이 있었다.

Palantir의 Ontology는 여기서 더 나아가 그래프에 표현된 업무 개체를 기반으로 **실제 시스템의 상태를 변경하는 행동**까지 연결한다.

예를 들어 단순히

**주문 → 상태 → 승인 대기**

를 조회하는 데서 끝나는 게 아니라,

**주문 → 승인 Action 실행 → 실제 상태 변경**

으로 이어지는 식이다.

즉 그래프가 단순한 **조회 대상**에서 실제 업무를 수행하기 위한 **운영 인터페이스**로 확장된다.

이 부분이 처음 Semantic Web의 비전을 다시 떠올리게 했다. 2001년에는 웹 전체의 의미를 표준화해서 에이전트가 사람 대신 일을 하도록 만들려고 했다면, 최근에는 범위를 **한 조직의 데이터와 업무**로 좁혀 비슷한 목표를 현실적으로 구현하려는 모습으로 볼 수도 있다.

## **11. 25년 동안 무엇이 달라졌을까?**

전체 흐름을 다시 놓고 보면 기술 이름보다 **각 단계에서 무엇을 포기하고 무엇을 얻었는지**가 더 잘 보였다.

| **단계** | **방향** | **얻은 것 / 남은 문제** |
| --- | --- | --- |
| Semantic Web | 웹 전체의 의미를 표준화 | 큰 비전 / 모두의 참여가 필요 |
| RDF·OWL | 의미를 정교하게 표현 | 표현력·추론 / 복잡한 설계 |
| DBpedia·Linked Data | 기존 데이터를 구조화·연결 | 실제 데이터 / 품질·협업 문제 |
| Google KG | 한 조직이 직접 그래프 구축 | 품질·통제·실용성 / 개방성 감소 |
| Wikidata | 공개 지식 그래프 운영 | 개방성 + 실제 운영 가능한 지식 모델 |
| 기업 KG | 특정 도메인으로 범위 축소 | 도메인에 맞는 실용성 |
| GraphRAG | LLM으로 그래프 구축 일부 자동화 | 구축 비용 감소 가능성 / 추출 품질 문제 |
| Palantir Ontology | 데이터와 실제 업무 행동 연결 | 조회를 넘어 운영까지 연결 |

처음 자료를 읽을 때는 **“보편성과 논리를 포기할수록 성공했다”** 정도로 이해했는데, 조금 더 정확히 말하면 **문제의 범위를 좁히고, 외부 참여자와의 합의를 덜 요구하며, 실제 사용 목적에 맞는 모델을 선택할수록 적용하기 쉬워졌다**고 보는 게 맞을 것 같다.

Semantic Web의 이상이 틀렸다기보다는 **웹 전체를 하나의 의미 체계로 연결하기 위해 필요한 조정 비용이 너무 컸던 것**이다.

Google과 기업 Knowledge Graph는 이 문제를 **“모두와 합의하지 말고 우리가 필요한 범위에서 직접 만들자”**는 방식으로 줄였다.

GraphRAG에서는 여기에 **“그래프 구축의 일부도 LLM에게 맡겨보자”**는 변화가 추가됐고, Palantir에서는 **“그래프를 실제 업무 행동과 연결하자”**는 방향까지 간다.

## **12. 그런데 우리도 결국 같은 문제를 다시 만나게 된다**

현재 실습은 오히려 편하다.

개인 문서를 대상으로 하고 있고, 사용할 관계도 우리가 직접 정했다. 누군가와 `USES_TECHNOLOGY`가 정확히 무엇을 의미하는지 합의할 필요도 없다.

그런데 이후 여러 스터디원의 그래프를 하나로 합치기 시작하면 상황이 달라진다.

**각자 개인 문서에서 그래프 생성 → 공통 그래프로 통합**

이 순간부터 문제가 생긴다.

누군가는 `USES`라고 저장하고 누군가는 `USES_TECHNOLOGY`라고 저장했다면 어떻게 할까? `Spring`, `Spring Boot`, `SpringBoot`는 같은 기술로 볼까? 서로 다른 문서에 등장하는 같은 사람은 어떻게 하나의 Entity로 합칠까?

결국 우리가 앞에서 봤던 문제가 그대로 돌아온다.

| **우리가 만나게 될 문제** | **과거 Semantic Web에서도 있었던 문제** |
| --- | --- |
| 어떤 관계를 사용할지 합의 | 공통 Vocabulary |
| 같은 대상을 하나로 합치기 | Entity Resolution |
| 각자 다른 데이터 구조 통합 | Schema/Ontology Alignment |
| 빠진 정보 처리 | 불완전한 데이터 |

그래서 여러 사람의 데이터를 합치기 전에 **공통 스키마를 합의하는 단계**가 필요한 이유도 이해할 수 있었다.

웹 전체에서는 해결하기 매우 어려웠던 조정 문제를 우리는 **작은 스터디라는 제한된 범위 안에서 직접 경험해보게 되는 셈**이다.

## **그래서 다음은?**

여기까지는 Semantic Web에서 시작한 “**세상의 사실과 관계를 그래프로 표현하자”**는 아이디어가 어떻게 Google Knowledge Graph, GraphRAG, 기업 Ontology까지 변해왔는지를 봤다.

그런데 아직 한 가지 중요한 선택이 남아 있다. **그래프를 실제 데이터베이스에 어떤 형태로 저장할 것인가?**

앞에서는 RDF처럼 모든 사실을 Triple로 표현하는 방법을 배웠지만, Neo4j 같은 시스템에서는 노드와 엣지 자체에 속성을 붙이는 **Property Graph**라는 다른 모델을 사용한다. 

실제로 우리도 PostgreSQL에 `Entity + Edge + JSONB Property` 형태로 저장하려고 해서 순수한 RDF보다는 이쪽에 더 가까운 부분이 있다.

그래서 다음에는 **RDF와 Property Graph가 같은 그래프를 어떻게 다르게 바라보는지**, 그리고 DDIA 2장에서 다루는 관계형·문서·그래프 데이터 모델의 차이까지 이어서 정리한다.
