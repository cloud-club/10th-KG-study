## 하는 일: 읽은 근거를 이용해 출력 만들기

가상 근거가 “발송 전에는 취소할 수 있고 발송 후에는 반품을 안내한다”라면 생성 모델은 질문에 맞춰 “이미 발송됐다면 반품 절차를 확인해야 합니다 [1]”처럼 답변할 수 있다. 같은 모델에 추출 스키마를 주면 정책과 조건을 JSON으로 출력하게 할 수도 있다.

생성 모델은 문장이나 구조화된 텍스트를 만든다. 임베딩 모델은 검색에 쓸 숫자 표현을 만들고, 전용 NER 모델은 보통 원문 구간과 타입을 예측한다. 기능은 겹칠 수 있지만 출력 목적과 평가 기준이 다르다.

## 발전 과정과 기존 방식의 차이

정해진 템플릿에 값을 채우는 시스템은 출력 형식이 예측 가능하지만 예상하지 못한 질문에 유연하게 답하기 어렵다. 통계적 언어 모델과 신경망 언어 모델은 문맥에 맞는 다음 표현을 학습했고, Transformer 기반 모델은 대규모 사전학습의 주요 기반이 됐다. Transformer는 2017-06-12 사전공개된 연구다. [Attention Is All You Need](https://arxiv.org/abs/1706.03762)

사전학습한 언어 모델을 지시·예시와 사람의 선호 피드백 등으로 추가 학습하면 사용자의 요청을 따르는 데 도움이 된다. InstructGPT 연구는 그 접근을 보여주는 2022년 사례다. 이것이 모든 최신 모델의 학습 방법을 완전히 설명하는 것은 아니다. [InstructGPT](https://arxiv.org/abs/2203.02155)

현재 모델은 요약·질문 분해·관계 후보 추출·설명 생성을 하나의 인터페이스로 시도하기 쉽게 만든다. 대신 유창하지만 근거가 없는 내용, 조건 누락, 문서 내부의 명령을 따르는 문제 등을 검토해야 한다.

## 익숙한 제품과의 관계

| 이름 | 주체 | 이 프로젝트에서 가능한 역할 |
|---|---|---|

제품 화면의 기능·기본 지시·도구 구성과 API에 직접 보낸 요청은 다를 수 있다. “앱에서 잘 답했다”와 “고정된 프롬프트의 API 실험에서 잘 답했다”를 구분한다. 제공 주체와 제품 정보는 [OpenAI](https://openai.com/index/chatgpt/), [Anthropic](https://www.anthropic.com/claude), [Google](https://deepmind.google/models/gemini/) 공식 자료를 기준으로 한다.

## 대표 평가셋과 평가 체계

아래 날짜는 논문 최초 사전공개 또는 공식 발표 기준이다. 최신 모델 순위를 제시하는 표가 아니다.

| 이름 | 출처·시점 | 평가 대상과 데이터 | 내 RAG에 바로 대입할 수 없는 이유 |
|---|---|---|---|
| MMLU | Hendrycks 등; arXiv 2020-09-07, ICLR 2021 | 57개 학술·전문 분야 객관식 문제의 정확도 | 내 문서 검색·인용 능력을 직접 측정하지 않음 |
| TruthfulQA | Lin·Hilton·Evans; arXiv 2021-09-08, ACL 2022 | 흔한 오해에 속기 쉬운 질문, 진실성·정보성 및 객관식 평가 설정 | 공개 상식 질문과 사내/개인 문서 근거성은 다름 |
| HELM | Stanford CRFM 연구진; arXiv 2022-11-16 | 다양한 시나리오·데이터셋에서 정확도뿐 아니라 여러 측면 평가 | 단일 평가셋이 아니라 평가 프레임워크 |
| Ragas | Es 등; arXiv 2023-09-26 | RAG의 검색 문맥·답변을 자동 평가하는 방법 | 고정 골드셋이 아니며 평가 모델의 오류·편향이 존재 |

원자료: [MMLU](https://arxiv.org/abs/2009.03300), [TruthfulQA](https://arxiv.org/abs/2109.07958), [HELM](https://arxiv.org/abs/2211.09110), [Ragas](https://arxiv.org/abs/2309.15217).

평가에는 데이터셋명뿐 아니라 버전·분할·프롬프트·few-shot 예시 수·채점 방식을 함께 적어야 한다. 학습 중에 공개 문제를 접했을 가능성과 도메인 차이 때문에 공개 벤치마크만으로 내 과제의 우열을 확정하지 않는다.

## 평가를 어떻게 이해할까

정답 번호가 있는 객관식이면 정확도를 계산하기 쉽다. 자유로운 설명은 같은 뜻을 다르게 표현할 수 있어 정답 문자열의 완전 일치만으로 판단하기 어렵다. ROUGE처럼 단어·구간의 겹침을 보는 지표도 사실성과 인용의 정확성을 모두 보증하지 않는다.

이 실습에서는 사람이 다음 네 가지를 따로 확인한다.

| 항목 | 가상 사례 |
|---|---|
| 정답성 | 질문이 발송 후 상황인데 발송 전 조건으로 답하지 않았나? |
| 근거성 | 원문에 없는 환급 기한을 추가하지 않았나? |
| 인용 지지 | `[2]`가 실제 그 조건을 설명하는 문서인가? |
| 보류·충돌 표시 | 두 명세가 다르면 한쪽을 임의로 확정하지 않았나? |

인용 번호가 존재하는지 검사하는 것은 형식 검사다. 답변의 모든 핵심 주장에 적절한 근거가 붙어 있는지는 의미 검사가 필요하다. LLM 평가자를 쓰더라도 일부는 사람이 교차 검토하고, 평가자 모델·프롬프트를 고정한다.

## 생성 모델 비교 조건

먼저 검색을 고정한다. 질문마다 동일한 근거를 모델 A와 B에 전달하고, 핵심 사실·금지된 추측·보류 기준을 미리 만든다. 가능하면 모델 이름을 가리고 사람이 채점한다. 입력/출력 토큰·지연·실패 응답도 함께 기록한다.

다음으로 검색까지 포함한 end-to-end 평가를 별도로 수행한다. 답변이 틀렸을 때 정답 근거를 직접 넣는 oracle context 실험으로 검색 누락과 생성 실패를 구분한다. 근거가 없는 질문, 서로 충돌하는 문서, 조건이 긴 질문을 포함한다.

## RAG와 파인튜닝

지금 코드는 매 요청에 근거를 첨부한다. 이것만으로 모델의 가중치를 바꾸는 파인튜닝을 한 것은 아니다. 검색용 임베딩 생성도 별도 모델 추론이며, 온톨로지 설계도 학습과는 다른 작업이다.

따라서 현재 개발의 핵심은 모델을 새로 학습시키는 것이 아니라 **필요한 근거를 찾고, 읽을 수 있게 전달하고, 근거 범위 안에서 답했는지 확인하는 것**이다.
