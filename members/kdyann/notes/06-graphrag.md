# 06. GraphRAG — 검색과 그래프의 결합

> 그래프를 RAG의 검색과 컨텍스트 구성에 어떻게 활용할까?

## GraphRAG 패턴 3종

| 패턴 | 흐름 | 특징 |
| --- | --- | --- |
| 로컬 서치 | 질문의 엔티티를 그래프 노드에 연결 → 주변 서브그래프 탐색 → 관련 근거를 컨텍스트로 구성 | 특정 대상과 그 관계를 묻는 질문에 사용 |
| 글로벌 서치 | 그래프의 커뮤니티 탐지 → 커뮤니티별 요약 → 여러 요약을 종합 | 그래프 전반의 주제나 흐름을 묻는 질문에 사용 |
| Text2Cypher | 질문을 바탕으로 LLM이 Cypher 질의를 생성 → 그래프 조회 | 정해진 그래프 스키마에서 조건·관계를 질의할 때 사용 |

- 로컬 서치는 질문에서 찾은 노드 주변의 좁은 범위를 읽는다. 
- 글로벌 서치는 미리 만든 커뮤니티 요약을 모아 넓은 범위를 읽는다.
- Text2Cypher는 자연어 질문을 그래프 질의로 바꾸는 방식이다.

## 하이브리드 리트리버

```text
질문 → 벡터 검색으로 관련 진입 노드 찾기 → 그래프 관계를 따라 확장 → 원문 근거와 함께 컨텍스트 구성
```

벡터 검색은 질문과 의미가 비슷한 시작점을 찾고, 그래프 탐색은 그 시작점에 연결된 노드와 관계를 찾는다. 확장된 경로가 답의 근거가 되는지는 연결된 원문과 함께 확인해야 한다.

## 그래프 인덱싱: 빌드 시점 선지불

글로벌 서치에 쓸 커뮤니티 탐지와 커뮤니티 요약은 질문이 들어올 때마다 처음부터 만들기보다 **미리 배치 작업으로 생성**할 수 있다. 그래프를 구축할 때 계산·요약 비용을 먼저 내고, 질의 시점에는 저장된 요약을 검색하고 종합하는 방식이다. 데이터가 바뀌면 영향을 받은 그래프와 요약을 갱신해야 한다.

## 회사에서는 어떻게 활용할까? — 토스증권 사례

GraphRAG가 실제 서비스에서 어떻게 쓰이는지 궁금해 토스증권 Tech Talk Talk의 세 글을 함께 읽어봤다.

### 3편. 추천과 검색 — 공통 RAG 플랫폼에서 그래프 검색까지

[「토스증권 추천과 검색은 어떻게 진화하고 있을까?」](https://toss.tech/article/tech_talk_talk_3)에서 RAG를 공통 플랫폼으로 만든 배경과 관계 탐색이 필요한 질문을 그래프 검색으로 확장한 과정을 살펴봤다.

#### 공통 RAG 플랫폼이 필요한 이유

- 키워드·필터 검색은 원하는 검색어와 조건이 명확할 때 강력하다. 하지만 정확한 검색어를 모르거나 상황과 맥락으로 뉴스를 찾으려면 한계가 있다.
- LLM의 답변 품질을 높이려면 적절한 컨텍스트가 필요하다. 어떤 데이터를 찾고, 어떤 검색을 수행하고, 어떤 문서를 답변 근거로 쓸지 판단해야 한다.
- 서비스마다 데이터 식별 → 쿼리 작성 → 결과 유효성 검증을 반복하면 비슷한 작업이 중복되고 검색 품질과 운영 방식도 달라진다. 토스증권은 이 과정을 공통 RAG 플랫폼으로 제공하려 했다.

#### 뉴스 RAG 파이프라인

```text
질문 → 질문 이해·검색 조건 구성 → 하이브리드 검색 → 리랭킹 → 정제된 컨텍스트 → 각 서비스의 답변 생성
```

1. 질문 이해: 뉴스 카테고리, 날짜 조건, 검색 범위를 정하고 질문을 임베딩해 쿼리 벡터를 만든다. 이 조건들을 합쳐 Elasticsearch 쿼리를 구성한다.
2. 하이브리드 검색: 텍스트 검색과 벡터 검색에 메타데이터 필터를 결합해 후보 뉴스를 찾는다.
3. 리랭킹: 후보 중 불필요한 결과를 걸러내고 관련성이 높은 순서로 다시 정렬한다. 정제된 결과를 각 서비스의 생성 단계에 전달한다.

파이프라인의 모델은 대부분 LLM 호출로 시작하고 우선순위가 높은 모델부터 점진적으로 내재화했다. 시황 요약이나 기업의 가격 변동 설명처럼 제품의 목적이 달라도 뉴스를 찾아 컨텍스트를 만드는 과정은 공통화할 수 있었다.

#### 관계를 따라가야 하는 질문은 그래프 RAG로 확장

기업이 어떤 산업 이벤트와 연결되는지와 제품·공급망을 통해 다른 기업과 어떻게 이어지는지 묻는 질문은 문서 유사도 검색만으로 충분하지 않을 수 있다. 이런 질문에는 회사·종목·제품·이벤트·테마 사이의 관계를 탐색하는 그래프 RAG를 활용한다.

이 글의 그래프 검색기는 이미 정의된 금융 온톨로지 위에서 질문과 관련된 서브그래프를 찾아 반환한다.

1. 질문과 관련된 시작 엔티티 후보를 Elasticsearch 기반 검색 파이프라인으로 찾는다.
2. 시작점에서 관계를 따라 경로를 확장한다. 무작정 확장하면 3홉에서 후보 경로가 약 4,924만 개까지 늘어나므로, 홉마다 점수를 매기고 상위 후보만 다음 홉으로 넘긴다.
3. 질문 관련성에 더해 시가총액·최신성 같은 금융 신호와 제품별 `path_preference`를 반영해 남길 경로를 고른다.

#### Cypher 최적화와 그래프 검색의 핵심

- Cypher 최적화: 후보가 어느 지점에서 늘어나는지 찾고, 다음 탐색 전에 줄이는 것이 핵심. 인덱스로 시작점을 찾고 관계의 방향·타입과 필터를 확장 초기에 적용한다. `EXPLAIN`과 `PROFILE`로 실행계획과 실제 비용을 확인한다.
- 그래프 검색 품질: 어디서 시작해 어떤 경로를 남기느냐가 중요하다. 탐색 깊이를 늘리는 것만으로 품질이 높아지지는 않으며 질문에 맞는 시작점과 유용한 관계 경로를 선별해야 한다.

### 1편. 투자정보 생성 — 찾은 근거로 무엇을 말해도 될까?

[「AI에게 투자정보를 말하게 하기까지」](https://toss.tech/article/tech_talk_talk_1)는 투자정보 서비스에서 근거를 고르고 생성을 통제하고, 결과를 평가하는 과정을 설명한다. 뉴스에 기업 이름이 나온다는 사실만으로 그 기업의 주가 변동을 설명할 근거가 되지는 않기 때문에 검색 결과와 답변의 주장이 실제로 연결되는지 확인해야 한다.

1. 무엇을 말할지 고르기: 시장에는 정보가 너무 많다. 그중에는 답변의 근거로 쓰기 어려운 정보도 많다. 기업 이름이 등장하는지만 보지 않고 질문과 관련이 있고 설명을 뒷받침할 수 있는 정보를 선별한다.
2. 어떻게 생성할지 통제하기: 모든 판단을 LLM에게 한 번에 맡기지 않고 단계로 나눈다. 각 단계에서 모델이 선택할 수 있는 행동 범위를 제한해 오류가 다음 단계로 이어지는 것을 관리한다.
3. 평가 가능한 구조로 만들기: 프롬프트를 한 번 만드는 것으로 끝내지 않는다. 결과와 실패 유형을 평가할 수 있게 기록하고 실제 실패 사례를 평가셋과 프롬프트 예시에 반영해 개선한다.

내 실습에서도 원문 발췌가 실제로 존재하는지 확인하는 것에 더해서 그 발췌가 추천 이유나 대본의 주장을 충분히 뒷받침하는지 살펴봐야 한다. 그래프 검색 이후의 답변 품질을 생각해봐야겠다.

### 2편. LLM 서빙 — 답변을 안정적으로 제공하려면?

[「LLM 서빙, 띄우는 것과 잘 띄우는 것 사이」](https://toss.tech/article/tech_talk_talk_2)는 토스증권이 LLM을 운영하면서 지표와 로그로 문제 원인을 찾은 사례에 대한 설명이다.

- 사용자가 기다리는 시간: 첫 토큰이 나올 때까지의 시간인 TTFT와 초당 생성 토큰 수를 관찰한다.
- 캐시와 자원 사용: 공통 프롬프트의 계산을 재사용하는 Prefix Cache의 적중률과 KV 캐시 사용량을 확인해 지연·처리량 문제를 진단한다.
- 개별 실패 확인: 전체 지표에 이상이 없어 보여도 응답의 종료 사유와 개별 로그를 확인한다. 설정 변경은 부하 테스트로 검증하고, 문제가 생기면 되돌릴 수 있게 운영한다.

검색 시간과 생성 시간을 나눠 기록하고 응답이 실패하거나 잘린 이유를 남기는 방식을 참고할 수 있을 것 같다.

### 세 글을 읽고 느낀 점

3편을 읽고 로컬 서치에서 어디서 시작하고 어떤 경로를 남길지가 중요하다는 것을 알게 됐다.

그래프에 관계를 많이 담고 더 멀리 탐색하면 다양한 답을 찾을 수 있을 것 같지만, 토스증권 사례에서는 3홉만 가도 후보 경로가 크게 늘어났다. 그래프를 활용하려면 연결을 만드는 것만큼 질문과 무관한 경로를 일찍 줄이는 기준이 필요하다는 점이 인상적이었다.

내 콘텐츠 그래프에도 `내 게시물 → 주제 ← 참고 게시물` 경로가 있다. 같은 주제로 연결됐다는 사실은 확인할 수 있지만, 그 참고 글이 내 계정에 어울리는지까지 자동으로 증명하지는 않는다. 지금도 원문 근거·최근성·관심 분야를 확인하지만, 좋은 추천을 위해서는 여러 후보 중 어떤 경로를 우선할지 더 고민해야 한다.

1편을 읽으면서 검색에 성공한 뒤에도 검증할 일이 남아 있다는 점이 더 잘 이해됐다. 원문에 있는 문장을 인용했더라도 그 문장이 답변 전체를 뒷받침하지 않을 수 있다. 내 대본 생성에서도 참고 글의 설명을 내 경험처럼 바꾸거나 단순한 주제 연결을 강한 추천 이유로 확대하지 않는지 확인해야겠다.

2편에서는 답변의 품질과 함께 응답 시간과 실패 원인을 관찰하는 일이 중요하게 느껴졌다. 그래프를 붙인 뒤 답이 좋아져도 기다리는 시간이 크게 늘 수 있으므로 검색 결과와 답변뿐 아니라 걸린 시간도 남겨봐야겠다. 그래야 근거를 찾는 단계가 느린지, LLM 생성 단계가 느린지도 나눠 볼 수 있다.
