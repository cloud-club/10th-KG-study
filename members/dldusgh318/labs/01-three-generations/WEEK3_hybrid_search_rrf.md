# **W3 — Hybrid Search와 Personal Data Agent**

**핵심 질문:** BM25와 Vector Search의 서로 다른 장점을 합치면 검색 성능이 좋아질까? 그리고 그 검색 결과를 LLM에 연결하면 내 데이터에 근거해 답하는 에이전트를 만들 수 있을까?

---

## **0. W2에서 W3로 — 검색 결과를 하나로 합쳐보자**

W2에서는 같은 1,562개의 청크를 세 가지 방식으로 검색해보았다.

```
0세대  grep
        ↓
1세대  Elasticsearch + BM25
        ↓
2세대  pgvector + BGE-M3
```

실험하면서 BM25와 Vector Search가 **서로 다른 상황에서 강하다는 것**을 확인했다.

- **BM25**는 `@Transactional`, `Write-Behind`, `SeCause`처럼 정확한 단어나 기술명을 찾는 데 강했다.
- **Vector Search**는 검색어가 정확히 일치하지 않아도 의미가 비슷한 내용을 찾을 수 있었다.
- 반대로 Vector Search에서는 `Write-Behind`를 검색했는데 `Write Around`가 더 높은 순위에 등장하는 등 의미적으로 비슷하지만 원하는 답은 아닌 결과도 나타났다.

즉, 어느 한 검색 방식이 항상 좋은 것은 아니었다.

```
BM25
"정확한 표현을 잘 찾는다"

Vector
"비슷한 의미를 잘 찾는다"
```

그렇다면 자연스럽게 다음 질문이 생긴다.

**둘의 결과를 합치면 서로의 약점을 보완할 수 있지 않을까?**

W3에서는 이 질문에서 출발해 **BM25 + Vector Search를 RRF로 결합한 Hybrid Search**를 만들고, 그 결과를 LLM에 연결해 **내 개인 데이터에 질문할 수 있는 RAG Agent**까지 구현했다.

최종 구조는 다음과 같다.

```
                 ┌─ BM25 top-50 ─────┐
사용자 질문 ─────┤                    ├─ RRF
                 └─ Vector top-50 ───┘
                                      ↓
                                  Hybrid top-5
                                      ↓
                                Context 조립
                                      ↓
                                     LLM
                                      ↓
                               답변 + Citation
                                      ↓
                                Citation 검증
```

# **1. Hybrid Search — BM25와 Vector를 합치기**

## **1.1 왜 그냥 점수를 더하지 않았나?**

W2에서 확인한 BM25와 Vector Search의 점수는 서로 의미가 다르다.

```
BM25 Score
4.36
8.12
15.3
...

Cosine Similarity
0.579
0.812
0.653
...
```

BM25 Score는 단어 빈도와 희소성 등을 기반으로 계산된 **검색 관련도 점수**이고, Vector Search의 값은 두 벡터가 얼마나 가까운지를 나타내는 **코사인 유사도**다.

따라서 다음과 같이 단순히 더하는 것은 의미가 없다.

```
BM25 4.36 + Cosine 0.579 = ?
```

두 값은 같은 척도가 아니기 때문이다.

그래서 이번 실습에서는 **점수 대신 순위를 합치는 RRF(Reciprocal Rank Fusion)** 를 사용했다.

---

## **1.2 RRF — 점수가 아니라 순위를 합친다**

RRF의 아이디어는 단순하다.

```
BM25                     Vector
1. chunk_A               1. chunk_C
2. chunk_B               2. chunk_A
3. chunk_C               3. chunk_F
```

각 검색기의 원래 점수는 무시하고 **몇 등으로 검색되었는지만 사용한다.**

```
RRF Score = Σ 1 / (k + rank)
```

이번 구현에서는 `k=60`을 사용했다.

예를 들어 `chunk_A`는

```
BM25   → 1위
Vector → 2위
```

이므로

```
1 / (60 + 1)
+
1 / (60 + 2)
```

가 된다.

반면 `chunk_F`가 Vector에서만 3위라면

```
1 / (60 + 3)
```

만 가진다.

결과적으로 **두 검색기에서 모두 높은 순위에 등장한 청크가 자연스럽게 위로 올라온다.**

**RRF의 핵심:**
“각 검색기가 얼마나 높은 점수를 줬는가?”보다**“여러 검색기가 이 문서를 중요하다고 판단했는가?”** 를 본다.

Elasticsearch의 RRF도 서로 다른 relevance indicator를 가진 검색 결과를 이런 방식으로 하나의 순위로 합친다. `rank_constant`의 기본값 역시 60이다. (Elastic)

---

## **1.3 실제 구현**

이번 실습에서는 두 검색기에서 각각 **top-50**을 가져왔다.

```
BM25 top-50 ─────┐
                 ├─ RRF ─→ Hybrid Ranking
Vector top-50 ───┘
```

실행:

```bash
./.venv/bin/python src/hybrid_search.py "캐시 전략"
```

여기서 중요한 점은 **RRF Score 자체를 검색 결과의 신뢰도로 사용하지 않았다는 것**이다.

RRF Score는 문서의 절대적인 관련도를 의미하지 않는다.

```
RRF Score가 높다
≠
이 문서가 질문과 90% 관련 있다
```

단지 **여러 검색 결과의 순위를 합치기 위한 값**이다.

# **2. Hybrid Search가 정말 더 좋은가?**

구현했다고 끝내지 않고 실제 내 데이터에서 검색 성능을 비교했다.

이를 위해 10개의 검색 질문을 만들었다.

```
정확한 용어 / 심볼 / 프로젝트
의미 기반 검색
표기·오타 비교
```

그리고 각 질문에 대해

```
이 청크는 질문과 관련 있다     → relevant
이 청크는 관련 없다            → irrelevant
```

를 직접 판정했다.

이렇게 사람이 정답이라고 판단한 청크 집합을 **Gold Set(qrels)** 으로 사용했다.

---

## **2.1 Recall@k**

검색 성능은 `Recall@5`, `Recall@10`으로 비교했다.

```
             top-k 안에 찾은 정답 청크 수
Recall@k = ─────────────────────────────
                 전체 정답 청크 수
```

쉽게 말하면,

**“정답 청크를 검색기가 얼마나 놓치지 않고 가져왔는가?”**

를 측정한 것이다.

RAG에서는 검색 단계에서 놓친 정보는 뒤의 LLM이 복구하기 어렵기 때문에 Recall이 특히 중요하다.

---

## **2.2 실제 결과**

10개 질문을 평가한 결과는 다음과 같았다.

| **검색 방식** | **Recall@5** | **Recall@10** |
| --- | --- | --- |
| BM25 | 0.469 | 0.610 |
| Vector | 0.407 | 0.682 |
| **Hybrid** | **0.534** | **0.734** |

이번 평가셋에서는 **Hybrid Search가 평균적으로 가장 높은 Recall을 기록했다.**

특히 Recall@10 기준으로 보면

```
BM25      0.610
Vector    0.682
Hybrid    0.734
```

로 나타났다.

즉, W2에서 관찰했던

```
BM25의 강점
+
Vector의 강점
```

을 RRF로 결합했을 때 실제로 정답 청크를 더 많이 확보할 수 있었다.

---

## **2.3 그렇다고 Hybrid가 항상 최고는 아니었다**

**모든 질문에서 Hybrid가 가장 좋았던 것은 아니다.**

대표적으로 R02 질문: `@Transactional에서 같은 클래스 내부 호출이 문제가 되는 이유는?`

에서는 다음과 같은 결과가 나왔다.

| **방식** | **Recall@5** |
| --- | --- |
| **BM25** | **1.000** |
| Hybrid | 0.500 |

이 질문은 `@Transactional`이라는 **정확한 코드 심볼**이 포함되어 있어 BM25가 특히 잘 처리할 수 있는 유형이었다. 반면 Hybrid에서는 Vector 검색 결과가 RRF에 함께 반영되면서 BM25가 잘 찾아낸 관련 청크 일부의 최종 순위가 밀렸고, 결과적으로 top-5 Recall이 낮아졌다.


```
BM25가 이미 매우 잘 찾은 질문
        ↓
Vector 결과까지 RRF로 융합
        ↓
일부 Vector 후보가 상위권에 진입
        ↓
BM25의 관련 청크 일부가 top-5 밖으로 밀림
        ↓
Recall@5
1.000 → 0.500
```

**RRF의 목적은 모든 개별 질문에서 최고 성능을 보장하는 것이 아니라, 서로 다른 검색기의 실패 패턴을 보완해 전체적인 검색 안정성을 높이는 것이다.**

실제로 이번 10개 질문의 Macro Recall에서는 Hybrid가 가장 높았지만, R02처럼 **정확한 코드 심볼 검색에서는 BM25 단독 검색이 더 좋은 경우도 있었다.**

## 다음으로..
RRF를 통해 BM25와 Vector Search의 서로 다른 검색 결과를 하나로 결합했고, 실제 10개 질문에서도 Hybrid Search가 가장 높은 Macro Recall을 기록했다. 

하지만 좋은 검색 결과를 얻는 것과 그 결과를 이용해 질문에 답하는 것은 다른 문제다. 다음 실습에서는 Hybrid Search의 top-5를 LLM의 Context로 전달해, 실제 내 데이터에 근거해 답하는 Personal Data Agent를 구현하고 어느 단계에서 실패하는지 확인한다.
