# 4. 지식 그래프의 배경과 기업 사례

3주차에는 내 운영체제 노트를 청크로 나누고, BM25와 벡터 검색으로 관련 문서를 찾은 뒤 LLM이 답변하도록 만들었다.

RAG는 질문과 관련된 **문서 조각**을 찾는 데 유용했다. 하지만 여러 대상의 관계를 차례대로 따라가야 하는 질문은 필요한 정보가 서로 다른 청크에 흩어져 있어 답하기 어려울 수 있다.

이번 주에는 문서를 검색하는 것에서 더 나아가, 현실의 대상과 관계를 구조화하는 지식 그래프의 배경을 공부한다.

## 1. 시맨틱 웹

기존 웹은 사람이 읽는 문서를 서로 링크한 형태다. 컴퓨터는 문서에 어떤 문자열이 있는지는 찾을 수 있지만, 그 문자열이 현실의 어떤 대상을 의미하는지 바로 알기 어렵다.

시맨틱 웹은 웹의 정보에 기계가 이해할 수 있는 의미를 부여하려는 생각이다.

```text
기존 웹: 문서와 문서를 링크한다.
시맨틱 웹: 대상과 대상의 관계를 표현한다.
```

예를 들어 `윤희빈`, `Cloud Club`, `KG 스터디`를 단순한 문자열이 아니라 각각 구분되는 대상으로 만들고, 다음과 같은 관계를 표현할 수 있다.

```text
윤희빈 -- 참여한다 --> KG 스터디
KG 스터디 -- 소속된다 --> Cloud Club
```

이렇게 정보를 표현하면 컴퓨터가 대상을 구분하고 관계를 따라갈 수 있다.

## 2. 지식 그래프의 흐름

지식 그래프는 어느 날 갑자기 등장한 기술이 아니라, 웹에 의미를 표현하려는 기술이 발전하면서 만들어졌다.

```text
시맨틱 웹
→ RDF·RDFS·OWL 같은 웹 표준
→ Linked Data와 공개 지식 그래프
→ 검색·추천·가상 비서 등에 사용되는 기업 지식 그래프
→ LLM과 지식 그래프를 함께 사용하는 GraphRAG
```

- **시맨틱 웹**: 기계가 웹 정보의 의미와 관계를 이해하도록 하려는 생각
- **RDF·RDFS·OWL**: 의미와 관계를 공통 형식으로 표현하기 위한 표준
- **Linked Data**: 서로 다른 데이터의 대상을 URI로 연결하여 웹에서 함께 사용할 수 있게 하는 방식
- **DBpedia·Wikidata**: 여러 사람이 활용할 수 있는 공개 지식 그래프
- **기업 지식 그래프**: 검색, 쇼핑, 추천, 질의응답 등 특정 서비스에 맞게 구축한 그래프
- **GraphRAG**: 그래프에 저장된 관계와 LLM을 함께 이용하는 방식

## 3. RDF와 트리플

RDF(Resource Description Framework)는 웹에서 정보를 표현하기 위한 데이터 모델이다. 정보 하나를 **주어, 술어, 목적어**로 구성된 트리플로 표현한다.

```text
윤희빈 -- 참여한다 --> KG 스터디
```

| 구성 | 예시 | 의미 |
| --- | --- | --- |
| 주어 | 윤희빈 | 설명하려는 대상 |
| 술어 | 참여한다 | 두 대상의 관계 |
| 목적어 | KG 스터디 | 관계가 향하는 대상 또는 값 |

여러 트리플을 연결하면 그래프가 된다.

```text
윤희빈 → 참여한다 → KG 스터디
KG 스터디 → 사용한다 → PostgreSQL
```

이 그래프에서는 `윤희빈이 참여한 스터디에서 사용하는 데이터베이스는 무엇인가?`라는 질문에 답하기 위해 두 관계를 따라갈 수 있다.

## 4. URI, 리터럴, 네임스페이스

### URI

사람이나 장소처럼 이름이 같은 대상이 여러 개 있을 수 있다. RDF에서는 URI를 이용하여 대상을 고유하게 식별한다.

```text
https://example.org/person/heebin
https://example.org/study/kg
```

이름이 같더라도 URI가 다르면 서로 다른 대상으로 구분할 수 있다.

### 리터럴

리터럴은 다른 대상이 아니라 문자열, 숫자, 날짜처럼 실제 값을 나타낸다.

```text
윤희빈 -- 이름 --> "윤희빈"
윤희빈 -- 학년 --> 4
```

여기서 `"윤희빈"`과 `4`는 리터럴이다.

### 네임스페이스

URI를 매번 길게 쓰기 불편하므로 앞부분에 짧은 별칭을 붙여 사용한다.

```text
@prefix ex: <https://example.org/> .

ex:heebin ex:participatesIn ex:kgStudy .
```

`ex:`가 `https://example.org/`를 대신하는 네임스페이스 접두어다.

## 5. RDFS와 OWL

RDF가 개별 사실을 표현한다면, RDFS와 OWL은 데이터에 사용할 개념과 규칙을 정의한다.

### RDFS

RDFS는 클래스, 속성, 상하위 관계 같은 기본 구조를 정의한다.

```text
학생은 사람의 하위 클래스다.
참여한다의 주어는 사람이다.
참여한다의 목적어는 스터디다.
```

### OWL

OWL은 RDFS보다 더 자세한 제약과 논리 관계를 표현할 수 있다.

```text
모든 대학생은 학생이다.
모든 학생은 사람이다.
→ 대학생은 사람이라고 추론할 수 있다.
```

### 스키마와 온톨로지

- **스키마**는 데이터에 어떤 구조와 속성을 사용할지 정한다.
- **온톨로지**는 개념의 의미, 관계, 제약과 추론 규칙까지 더 구체적으로 표현한다.

두 용어가 실제로는 겹쳐 사용되기도 한다. 처음에는 `온톨로지가 스키마보다 의미와 규칙을 더 풍부하게 표현한다` 정도로 이해했다.

### 추론

추론은 직접 저장하지 않은 사실을 규칙을 이용해 새로 알아내는 것이다.

```text
윤희빈은 대학생이다.
대학생은 학생이다.
학생은 사람이다.

따라서 윤희빈은 사람이다.
```

## 6. SPARQL

SPARQL은 RDF 그래프를 조회하기 위한 질의 언어다. 관계형 데이터베이스에서 SQL을 사용하는 것과 비슷하다.

```sparql
PREFIX ex: <https://example.org/>

SELECT ?database
WHERE {
  ex:heebin ex:participatesIn ?study .
  ?study ex:uses ?database .
}
```

이 쿼리는 다음 두 관계를 차례대로 따라간다.

```text
윤희빈 → 참여한다 → 어떤 스터디
어떤 스터디 → 사용한다 → 데이터베이스
```

이번 주에는 실습이 필수가 아니므로 SPARQL의 문법을 외우기보다, 그래프의 패턴을 적어서 관계를 찾는 언어라고 이해했다.

## 7. 프로퍼티 그래프와 RDF

Neo4j는 대표적인 프로퍼티 그래프 데이터베이스다. RDF와 프로퍼티 그래프는 모두 노드와 관계를 표현하지만 중심 생각이 조금 다르다.

| 구분 | RDF | 프로퍼티 그래프 |
| --- | --- | --- |
| 기본 단위 | 주어-술어-목적어 트리플 | 노드와 관계 |
| 식별 | URI를 이용한 전역 식별 | 데이터베이스 내부 ID나 속성 |
| 속성 표현 | 속성도 트리플로 표현 | 노드와 관계에 속성을 직접 저장 |
| 질의 언어 | SPARQL | Cypher 등 |
| 강점 | 표준과 데이터 연결, 의미 표현 | 애플리케이션의 그래프 탐색과 구현 |

RDF는 서로 다른 조직의 데이터를 공통 표준으로 연결하는 데 초점을 둔다. 프로퍼티 그래프는 하나의 서비스 안에서 노드와 관계를 편리하게 저장하고 탐색하는 데 초점을 둔다고 이해했다.

## 8. 기업의 지식 그래프 사례

### Google: 검색어가 아니라 대상을 이해하는 검색

Google은 2012년에 Knowledge Graph를 소개하면서 `things, not strings`라는 표현을 사용했다. 검색어를 단순한 문자열로만 보는 것이 아니라 사람, 장소, 작품 같은 현실의 대상으로 구분하고 그 관계를 이해하려는 것이다.

예를 들어 `Taj Mahal`이라는 문자열은 건축물, 음악가 또는 다른 대상을 의미할 수 있다. 지식 그래프는 사용자가 어떤 대상을 찾는지 구분하고, 그 대상의 주요 사실과 관련 대상을 검색 결과에 보여주는 데 사용된다.

Google 사례에서 지식 그래프의 역할은 다음과 같다.

- 같은 이름을 가진 서로 다른 대상을 구분한다.
- 검색한 대상의 주요 사실을 요약한다.
- 인물, 장소, 작품 사이의 관계를 이용해 관련 정보를 보여준다.
- 사용자가 다음에 궁금해할 만한 대상을 연결한다.

### Amazon: 상품 정보를 구조화하는 그래프

Amazon은 매우 많은 종류의 상품을 다룬다. 상품마다 브랜드, 재질, 색상, 크기, 용도처럼 필요한 속성이 다르고 판매자가 작성한 표현도 일정하지 않다.

Amazon의 AutoKnow 연구는 상품의 분류 체계와 속성을 자동으로 찾고, 웹의 상품 지식을 대규모로 수집하는 방법을 다룬다.

```text
노트북 -- 브랜드 --> Apple
노트북 -- 화면 크기 --> 13인치
노트북 -- 메모리 --> 16GB
```

상품 지식 그래프를 사용하면 다음과 같은 작업에 도움이 될 수 있다.

- 같은 상품이나 비슷한 상품을 구분한다.
- 판매자마다 다르게 작성한 상품 속성을 정리한다.
- 상품 검색과 추천에 사용할 관계를 만든다.
- 누락되거나 이상한 상품 정보를 찾는다.

### Apple: 지식 그래프 구축과 가상 비서 연구

Apple이 Siri의 전체 지식 구조를 공개한 것은 아니다. 따라서 `Siri가 특정 지식 그래프 하나로 동작한다`고 단정하기는 어렵다.

다만 Apple의 공개 연구에서는 대규모 오픈 도메인 지식 그래프를 계속 구축하고 제공하는 `Saga` 플랫폼과, 가상 비서의 질의를 처리할 때 지식 그래프를 활용하는 연구를 확인할 수 있다.

공개된 내용에서 확인할 수 있는 활용은 다음과 같다.

- 웹 문서에 등장한 표현을 지식 그래프의 엔티티와 연결한다.
- 사실의 순위를 정하고 사실이 맞는지 검증한다.
- 관련 엔티티를 찾는다.
- 가상 비서가 사용자의 질의에서 엔티티를 더 정확하게 인식하도록 돕는다.

### 세 기업 사례 비교

| 기업 | 주요 대상 | 지식 그래프가 돕는 일 |
| --- | --- | --- |
| Google | 사람, 장소, 작품 등 | 검색 의도 파악, 지식 패널, 관련 대상 탐색 |
| Amazon | 상품과 상품 속성 | 상품 분류, 속성 정리, 검색과 추천 |
| Apple | 웹의 엔티티와 가상 비서 질의 | 엔티티 연결, 사실 검증, 질의 이해 |

세 기업 모두 단순히 같은 단어를 찾는 것을 넘어서, **사용자가 말한 대상이 무엇이고 다른 대상과 어떤 관계가 있는지 파악하기 위해** 지식 그래프를 사용한다는 공통점이 있다.

## 9. 지난주 RAG와 연결

지난주에 만든 RAG는 질문과 비슷한 청크를 검색해 LLM에 전달했다.

```text
RAG: 질문 → 관련 문서 청크 검색 → LLM 답변
KG: 질문 → 엔티티와 관계 탐색 → 연결된 사실 확인
```

예를 들어 다음 질문은 문서 검색만으로는 필요한 청크를 모두 찾아야 한다.

```text
희빈이 참여한 스터디에서 사용하는 데이터베이스는 무엇인가?
```

지식 그래프에서는 다음 경로를 명시적으로 따라갈 수 있다.

```text
희빈 → 참여한다 → KG 스터디 → 사용한다 → PostgreSQL
```

내가 이해한 핵심은 다음과 같다.

> RAG는 관련 문장을 찾는 데 강하고, 지식 그래프는 대상 사이의 명시적인 관계를 따라가는 데 강하다. 둘을 함께 사용하면 문서의 자세한 설명과 그래프의 관계 정보를 모두 활용할 수 있다.

## 10. 발표용 요약

> 저는 구글, 아마존, 애플의 지식 그래프 사례를 간단히 살펴봤습니다. 구글은 검색어를 문자열이 아니라 현실의 대상으로 이해하고, 대상의 주요 사실과 관계를 검색 결과에 보여주기 위해 Knowledge Graph를 사용합니다. 아마존은 다양한 상품의 분류와 속성을 구조화해 상품 검색과 추천에 활용할 수 있도록 상품 지식 그래프를 구축합니다. 애플은 전체 서비스 구조를 공개하지는 않았지만, 공개 연구를 통해 웹의 엔티티를 연결하고 사실을 검증하거나 가상 비서의 질의 이해에 지식 그래프를 활용하는 것을 확인할 수 있었습니다. 세 사례의 공통점은 같은 단어를 찾는 것에서 끝나지 않고, 사용자가 말한 대상이 무엇이며 다른 대상과 어떤 관계를 갖는지 구조화한다는 점입니다. 지난주 RAG가 관련 문서 청크를 찾았다면, 지식 그래프는 여러 관계를 명시적으로 따라갈 수 있다는 차이가 있습니다.
