# **03. 2세대 — 임베딩과 벡터 검색**

## **BM25의 다음 단계: “단어가 달라도 의미가 같다면?”**

1세대 BM25에서는 검색 결과에 **관련도 순위**를 만들 수 있었다.

하지만 여전히 이런 문제가 남는다.

```
Query: 학교 그만두고 싶다
문서: 휴학을 고민 중이다

→ 의미는 비슷하지만 겹치는 단어가 거의 없음
```

형태소 분석을 아무리 잘해도 `학교 그만두다`와 `휴학`이 같은 의미라는 사실까지 알기는 어렵다.

그래서 2세대에서는 **단어 자체를 비교하는 대신 문장의 의미를 숫자 벡터로 바꿔 거리를 비교한다.**

---

## **1. 임베딩 — 문장을 숫자로 바꾼다**

이번 실습에서는 `BAAI/bge-m3` 모델을 사용했다.

```
"Redis 캐시 전략을 적용했다"
            ↓
[-0.026, -0.011, 0.038, ...]
       1024개의 숫자
```

이 숫자 배열이 **Embedding Vector**다.

비슷한 의미를 가진 문장은 벡터 공간에서도 가까워지도록 모델이 학습되어 있다.

따라서 검색할 때도 질문을 임베딩한 뒤,

```
Query → Vector
Document → Vector

→ 가장 가까운 Document 찾기
```

를 수행한다.

여기서 중요한 점은 **1024개의 숫자 각각에 사람이 이해할 수 있는 의미가 있는 것은 아니라는 것**이다.

우리가 사용하는 것은 각 숫자의 의미가 아니라 **벡터끼리 얼마나 가까운가**이다.

---

## **2. 코사인 거리 — 얼마나 비슷한가?**

이번 실습에서는 벡터 사이의 거리를 비교하기 위해 **Cosine Distance**를 사용했다.

pgvector에서는 다음 연산자로 계산할 수 있다.

```sql
embedding <=> query_embedding
```

값이 **작을수록 두 벡터가 가깝다.**

필요하면 다음처럼 유사도로 바꿔 확인할 수도 있다.

```sql
1 - (embedding <=> query_embedding)
```

핵심은 수식보다 간단하다.

```
BM25
→ 같은 단어를 얼마나 잘 공유하는가?

Vector Search
→ 문장의 의미가 얼마나 가까운가?
```

---

## **3. HNSW — 모든 벡터를 비교하지 말자**

벡터 검색을 정확하게 하려면 query와 **모든 문서 벡터의 거리**를 계산하면 된다.

하지만 데이터가 커지면 매번 전체를 비교하는 것은 비싸다.

그래서 이번 실습에서는 **HNSW** 인덱스를 사용했다.

쉽게 생각하면 지하철 급행과 비슷하다.

```
상위 Layer → 멀리 빠르게 이동
     ↓
하위 Layer → 후보를 점점 좁힘
     ↓
가까운 Vector 탐색
```

모든 벡터를 확인하지 않고 가까울 가능성이 높은 곳을 탐색하기 때문에 빠르다.

대신 **근사 검색(ANN)**이므로 정확한 검색 결과 일부를 놓칠 수도 있다.

즉,

**검색 속도를 얻는 대신 일부 recall을 포기한다.**

---

## **4. 내 데이터로 직접 확인해보기**

Notion 데이터 `1,562 chunks`를 `BAAI/bge-m3`로 임베딩하여 pgvector에 저장했다.

### **저장 비용**

| **방식** | **크기** | **원문 대비** |
| --- | --- | --- |
| 원본 | 0.95MB | 1× |
| Elasticsearch | 5.1MB | 5.4× |
| pgvector | 22MB | 23× |

1024차원 벡터를 모든 청크에 저장하기 때문에 저장 공간이 크게 증가했다.

색인 과정도 Elasticsearch는 약 `1.5초`, 임베딩 생성 및 적재는 약 `2분`이 걸렸다.

즉, **의미 검색 능력을 얻는 대신 저장 공간과 임베딩 계산 비용이 추가된다.**

---

### **Case 1. 의미 검색이 강했던 경우**

```
Query: 성능을 개선한 경험
```

BM25도 많은 결과를 반환했지만 1위는 `Observability의 주요 역할` 문서였다.

반면 Vector Search의 1위는:

```
장애 인지·복구 시간 기존 대비 30% 단축
```

관련 경력기술서였다.

검색어와 정확히 같은 표현은 없지만 **“성능 개선 경험”이라는 의미가 가까운 문서**를 찾아낸 것이다.

여기서 알게 된 점은:

**검색 결과가 많다고 검색을 잘한 것은 아니다.**

검색 건수보다는 실제 관련 문서가 상위에 등장하는지가 중요하다.

---

### **Case 2. 벡터가 틀린 경우**

Vector Search가 항상 좋은 것은 아니었다.

```
Query: Write-Behind

Vector 1위 → Write Around
```

둘 다 캐시 쓰기 전략이라 의미적으로는 가깝지만 **서로 다른 개념**이다.

반면 정확한 용어를 검색하는 grep/BM25에서는 `Write-Behind` 정의를 정확하게 찾을 수 있었다.

즉,

```
Vector Search
"비슷한 개념인데?" → 찾음

하지만 사용자는
"비슷한 거 말고 Write-Behind를 찾는 건데?"
```

라는 문제가 생길 수 있다.

**의미를 잘 찾는 것이 항상 정확한 답을 찾는다는 뜻은 아니다.**

---

## **5. HNSW가 놓친 걸까, 임베딩이 틀린 걸까?**

Vector Search 결과가 이상할 때는 원인이 두 가지다.

```
1. 임베딩 모델이 의미를 잘못 표현했다.
2. HNSW 근사 검색 과정에서 좋은 후보를 놓쳤다.
```

이를 구분하려면 **HNSW 결과와 완전 탐색 결과를 비교**해야 한다.

```sql
-- Exact Search
SET enable_indexscan = off;

-- HNSW
SET enable_indexscan = on;
```

두 검색의 Top 10 결과를 비교해 `recall@10`을 측정하면 HNSW가 얼마나 결과를 잘 보존하는지 확인할 수 있다.

이 검증은 아직 진행하지 않았기 때문에 현재 결과만으로 **임베딩 모델의 문제인지 HNSW의 문제인지 단정할 수는 없다.**

---

## **이번 학습에서 가져갈 것**

세 검색 방식은 서로를 완전히 대체하지 않는다.

```
grep
→ 정확한 문자열에 강함

BM25
→ 검색어와 관련 있는 문서를 순위화

Vector Search
→ 표현이 달라도 의미가 비슷한 문서를 검색
```

하지만 Vector Search도 `Write-Behind → Write Around` 사례처럼 **의미적으로 가까우면서 실제로는 다른 개념**을 가져올 수 있다.

결국 검색 방법마다 잘하는 영역이 달랐다.

```
정확한 ID / 코드 / 고유명사
→ Lexical Search가 유리

자연어 질문 / 표현 불일치
→ Vector Search가 유리
```

따라서 다음 단계에서는 하나를 선택하는 대신 **BM25와 Vector Search의 결과를 합치는 Hybrid Search / RRF**를 알아본다.
