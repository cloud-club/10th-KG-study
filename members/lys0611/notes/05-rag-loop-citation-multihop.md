# 05. RAG 루프와 근거 인용 — 검색 이후의 실패

로컬 모델로 돌린 34문항에서 정답 청크를 찾고도 과잉 거절, 근거 혼동, 관계 방향 오류가 나왔다. 검색 성능과 답변 품질을 나눠 봤다.

## 한 번 검색하고 한 번 답하기

RAG는 검색한 자료를 생성 모델의 입력에 넣어 답변에 활용한다. 모델의 지식과 외부 문서를 결합하지만, 근거 없는 생성을 막아 주는 것은 아니다. ([Lewis et al., 2020](https://arxiv.org/abs/2005.11401))

v1은 재질의나 도구 호출 없이 단일 턴으로 만들었다.

1. 질문의 실명·연락처를 가명화·마스킹한다.
2. BM25와 벡터에서 각각 50개를 검색해 RRF로 합친다.
3. 같은 방에서 메시지 구간이 60% 이상 겹치는 청크를 걸러 상위 3~5개를 고른다. 겹침 비율의 분모는 짧은 쪽 구간이다.
4. Postgres의 전체 청크 본문에 날짜·방·`[C1]` 같은 근거 ID를 붙여 전달한다.
5. 답변의 인용 ID와 인용 표기 비율을 확인한다.

120자 검색 스니펫 대신 전체 청크를 넘긴다. 프롬프트에는 근거 안에서 답하기, 사실 문장에 인용 붙이기, 근거가 없으면 거절하기를 넣었다.

다만 코드가 모든 사실 문장의 인용을 강제하는 것은 아니다. 미제공 ID와 인용이 전혀 없는 비거절 답변은 막지만, 문장별 커버리지는 따로 기록한다. 인용이 있다고 실제로 주장을 지지하는지도 보장하지 않는다. ALCE가 구분한 인용 precision·recall을 참고해 내용상 지지 여부를 별도로 평가했다. ([ALCE](https://aclanthology.org/2023.emnlp-main.398/))

대화는 명령이 아닌 데이터로 취급한다. 읽기 전용이어도 악성 지시가 답변을 왜곡할 수 있어 구분자와 프롬프트만으로 충분하지는 않다. ([OWASP RAG 보안](https://cheatsheetseries.owasp.org/cheatsheets/RAG_Security_Cheat_Sheet.html))

생성 모델은 Ollama의 `exaone3.5:7.8b` Q4다. 호환 API에서 쓸 컨텍스트 길이를 Modelfile에 `PARAMETER num_ctx 8192`로 지정하고 `kakao-rag`로 실행했다. ([Ollama 문서](https://docs.ollama.com/api/openai-compatibility#setting-the-local-context-size))

## 34문항 평가

[생성 결과 파일](../labs/02-hybrid-rag-agent/results/generation-summary.md)의 수치다. Claude의 1차 채점이며 아직 사용자 검토 전이다. 사람이 확정한 점수나 ALCE 공식 평가 실행 결과로 보면 안 된다.

| 지표 | 결과 |
|---|---:|
| 답 있는 30문항 정확도, 0/0.5/1 평균 | 0.583 |
| 인용 precision | 0.807 |
| 인용 recall | 0.774 |
| 답 없는 4문항 거절 성공률 | 0.500 |
| 제공하지 않은 근거 ID 인용 | 0건 |

기존 라벨 기준으로 검색 실패 2건, 근거가 컨텍스트에 있지만 정확도가 1 미만인 답변이 12건이었다. 후자에는 청크 라벨 오류와 모호한 질문도 포함돼 있어 전부 모델의 생성 실패로 세면 안 된다.

인용 precision은 붙인 인용의 지지 여부, recall은 사실 문장이 인용으로 뒷받침되는지를 봤다. ID는 유효해도 주장을 지지하지 않는 인용이 있었다.

## 실패 사례

자세한 기록은 [실패 목록](../labs/02-hybrid-rag-agent/results/failures.md)에 두고, 수정할 지점이 다른 사례만 추렸다.

- 과잉 거절: 답이 있는 청크를 인용하면서도 “확인할 수 없습니다”로 끝냈다. 마스킹된 값과 근거 자체가 없는 경우를 구분할 필요가 있다.
- 근거 무시·일반 지식 혼입: 이체 날짜가 있는데 다른 지급 이야기로 답하거나, S3 명령에 근거 없는 `--region us-west-2`를 붙였다.
- 시간 혼동: 서로 다른 시기의 요금 문제 세 건을 한 사건의 원인으로 합쳤다. 헤더의 날짜만으로는 사건이 구분되지 않았다.
- 관계 방향 오류: 수정한 사람을 답하면서 요청자까지 포함했다. 요청과 수행 대화는 찾았지만 역할을 잘못 연결했다.
- 조립·라벨 오류: 장소를 확정한 문장은 다음 청크에 있었는데 앞 청크만 전달됐다. 둘을 대체 가능한 근거로 묶은 라벨도 잘못이었다.
- 질문 모호성: 날짜 없는 세미나 질문에 다른 회차의 시간을 답했다. 근거 있는 답이라면 모델 오류로 단정하기 전에 질문부터 고쳐야 한다.

청킹·프롬프트로 고칠 문제와 시간·관계를 저장해 볼 문제를 나눠야 한다.

## 집계와 답 없는 질문

최다 발신자·회의 참석자·언급 기능을 묻는 3문항에는 모두 답하지 못했다. 검색된 청크 몇 개로 전체 빈도를 셀 수는 없다. 최다 발신자는 정본 테이블의 `GROUP BY`로 풀 수 있다. 회의 참석자는 먼저 실제 참석 근거를 추출해야 하고, 이 정보는 그래프나 관계형 테이블로 표현할 수 있다.

답 없는 4문항 중 전화번호와 현재 같은 회사인지 묻는 질문은 거절했다. 나머지는 거절하면서도 회의실 예약을 워크숍과 연결하는 등 근거 없는 내용을 덧붙였다.

그래프에도 없는 정보가 새로 생기지는 않는다. 특히 “그래프에 노드가 없다”는 것만으로 “원문에도 없다”고 단정할 수 없다. 추출 누락일 수 있으므로 답변은 “현재 확보한 근거로 확인할 수 없다”는 범위에 머물러야 한다.

## 다음에 할 일

먼저 청크 라벨과 질문 날짜를 수정해 다시 채점한다. 이후 마스킹된 값의 처리, 답변에 사건 날짜 표시, 인접 청크 확장을 각각 적용해 변화를 볼 생각이다. 관계 추출은 요청자·수행자와 사건 시점을 구분하는 질문부터 시도한다. 재질의 루프는 그 뒤에 붙여도 늦지 않다.

다중 홉 평가 설계 참고: [MultiHop-RAG](https://arxiv.org/abs/2401.15391).
