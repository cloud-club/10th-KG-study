# 05. RDF·OWL 데이터 파이프라인

> 내 게시물의 콘셉트와 최근 참고 게시물을 연결하려면, 캡션에서 무엇을 사실로 뽑고 그 사실을 어떻게 검증·저장해야 할까?

## 핵심 개념

- 트리플: `주어 — 술어 → 목적어` 형태의 작은 사실. 예: `게시물 — coversTopic → AI`.
- 닫힌 추출 스키마: 모델이 미리 정한 클래스와 관계만 출력하게 제한한다. 이번 v0는 클래스 5개와 콘텐츠 관계 7개로
- 근거 스팬: 사실을 뒷받침하는 원문 부분 문자열과 시작·끝 문자 위치. 출처 문서 ID도 함께 저장한다.
- 직렬화: 같은 RDF 그래프를 Turtle이나 JSON-LD 문법으로 내보내는 것. 
- 엔티티 정규화: 표기가 다른 이름이 같은 대상을 가리키는지 근거를 확인해 하나의 식별자로 연결하는 과정.
- 다중 홉 경로: 한 노드에서 여러 관계를 따라 다른 노드에 이르는 경로. 각 경로가 답변의 근거가 되는지는 별도로 확인해야 한다.

## 1. 내 데이터에 맞는 작은 온톨로지

[W5 온톨로지](../labs/05-content-graph/ontology.ttl)는 `Post`, `Concept`, `Topic`, `Project`, `Feature`를 `rdfs:Class`로 정의한다. 콘텐츠 관계는 아래 7개다.

| 관계 | 연결 또는 값 | 이 데이터에서의 의미 |
| --- | --- | --- |
| `expressesConcept` | Post → Concept | 게시물이 명시한 계정 콘셉트 |
| `coversTopic` | Post → Topic | 직접 다룬 주제 |
| `describesProject` | Post → Project | 설명한 프로젝트 |
| `describesFeature` | Post → Feature | 설명한 기능 |
| `hasFeature` | Project → Feature | 같은 캡션이 프로젝트와 기능을 직접 연결 |
| `statesReleaseStatus` | Post → 리터럴 | 당시 밝힌 출시 상태 |
| `availableOn` | Post → 리터럴 | 이용 플랫폼·스토어 |

`rdfs:domain`과 `rdfs:range`는 관계의 주어·목적어 타입을 해석하기 위한 선언이다. 이번 파이프라인의 입력 제한은 JSON Schema의 허용 클래스·술어·필수 필드와 로컬 검증 코드가 담당한다. v0는 RDFS 스타일 어휘 정의와 RDF 직렬화를 실습했다.

## 2. LLM 추출과 검토는 두 단계

모델에는 허용되는 관계, JSON 출력 형식, 합성 few-shot 예시를 준다. 추출 결과마다 출처 문서 ID와 `evidence`, `start`, `end`를 요구한다. 코드는 `원문[start:end] == evidence`인지 확인하고, 리터럴 값도 근거 문구 안에 있는지 검사한다.

이 검사는 인용 문구가 실제로 존재하는지 확인한다. 그 문구가 `Project`의 기능을 말하는지, 단순히 다른 회사의 소식을 소개하는지는 판단하지 못한다. 실제 추출에서도 뉴스 요약을 내 프로젝트나 기능으로 잘못 분류한 후보가 있어 의미 검토 후 제외했다. 따라서 모델 출력은 검토 전 후보이며, 원문·대상·관계의 뜻을 살펴야 그래프의 사실로 채택할 수 있다.

엔티티 정규화에도 같은 원칙이 적용된다. 같은 프로젝트의 별칭이라면 한 노드로 합칠 수 있지만, `AI` 같은 넓은 단어를 공유한다는 이유로 서로 다른 프로젝트나 콘셉트를 동일시하면 안 된다. 특히 다국어·약어·해시태그는 표현과 뜻을 각각 확인해야 한다.

## 3. 세 가지 저장 형태의 역할

| 형태 | 이번 실습에서 담은 것 | 주 용도 |
| --- | --- | --- |
| Turtle·JSON-LD | 사실, 타입, 문서·근거 메타데이터를 RDF 트리플로 직렬화 | 표준 형식으로 내보내고 다른 RDF 도구와 교환 |
| PostgreSQL | 문서·엔티티·엣지·근거를 테이블로 저장 | 원문과 추출 사실의 관리·검사 |
| Neo4j | 노드·관계와 근거를 그래프로 적재 | 공통 주제와 여러 홉 경로 탐색·시각화 |

Turtle과 JSON-LD는 서로 다른 저장소가 아니라 같은 RDF 데이터의 표현 형식이다. `38개 사실`과 `589개 RDF 트리플`도 같은 단위가 아니다. RDF에는 각 사실 외에 노드 타입·이름·원문 출처·근거 문구·문자 위치 등의 트리플이 함께 들어간다. Neo4j는 RDF 저장소가 아니라 속성 그래프이므로, RDF 파일을 저장했다는 사실만으로 두 모델이 완전히 같아지는 것은 아니다.

Neo4j 적재에는 안정적인 ID와 `MERGE`를 사용한다. `MERGE`는 지정한 노드·관계 패턴이 있으면 재사용하고 없으면 만든다. 다시 적재할 때 중복을 막으려면 같은 실체에 같은 ID를 부여하는 규칙이 먼저 필요하다. 이름만으로 다른 대상을 합치거나 매번 새 ID를 만들면 `MERGE`만으로 엔티티 해소가 되지는 않는다.

## 4. 1-hop에서 다중 홉으로

1-hop은 게시물에서 직접 `Topic`으로 가는 관계를 본다. 공통 주제를 확인하려면 두 관계를 따라간다.

```text
내 Post ──coversTopic──▶ Topic ◀──coversTopic── 다른 Post
```

이 경로는 관계 2개를 거치므로 2-hop이다. Cypher의 가변 길이 패턴 `*1..3`은 1~3개 관계를 따라가는 경로를 탐색할 수 있다. 하지만 길이만 맞는 경로가 전부 의미 있는 답은 아니다. 관계 방향, 술어, 출처 집합(`own`/`reference`), 시간 조건, 중복 경로를 함께 제한해야 한다. 이번 공통 주제 질의는 두 `W5_FACT` 관계의 술어가 모두 `coversTopic`인지 검사한다.

야구 시각화의 게시물 4개는 모두 내 게시물이다. 따라서 서로 다른 내 글 두 개를 잇는 조합은 `4 × 3 ÷ 2 = 6`개다. 화면의 6개 경로는 이 조합이며, 최근 외부 게시물을 추천한 결과가 아니다.

반면 이번 검토본의 `AI` 경로 2개는 내 글과 최근 참고 글 사이를 잇는다. 다만 `AI`는 범위가 넓어서 두 글의 주제 이름이 같다는 사실만 보여준다. 추천하려면 참고 글의 실제 아이디어, 내 계정 콘셉트, 새로움, 원문 근거를 더 확인해야 한다. 

## 이번 실습에서 확인한 수치와 다음 질문

2026-09-30 검토본은 내 게시물 13건 + 참고 게시물 26건 = 문서 39건, 채택한 사실 38건, RDF 트리플 589개다. 최근 참고 글은 당시의 최근 7일·게시 후 24시간 이상·관찰 좋아요 100개 이상 조건으로 고른 결과다.

이번 그래프는 “왜 이 게시물들이 연결됐나?”를 경로와 캡션 근거로 보여준다. 다음 단계의 질문은 “이 연결이 내 계정에 맞는 새 주제 제안으로 이어지는가?”다. 이를 위해서는 넓은 `AI`보다 세부 주제·콘셉트·콘텐츠 형식을 더 잘 구분하고, 후보를 사람이 확인한 뒤 대본 생성으로 이어가야 할 것 같다.

구현과 실행 결과는 [W5 lab README](../labs/05-content-graph/README.md)에 정리했다.

## 작은 로컬 채팅으로 확인하기

[준영피티](../labs/05-content-graph/src/local_chat.py)는 v0 그래프를 질문으로 조회하는 로컬 화면이다. `내 게시물의 주제는 뭐야?`는 내 글의 근거 있는 Topic을 보여주고, `최근 유행한 것 중 참고할 만한 거 있어?`는 최근 7일의 `내 글 → Topic ← 참고 글` 경로와 양쪽 원문 발췌를 보여준다. 검토본에서 확인한 결과는 내 주제 6개와 AI 연결 후보 2개였다. 선택한 후보의 대본 초안은 별도 요청 때만 생성.
