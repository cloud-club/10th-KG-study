# **W4. 못 답한 질문을 그래프로 표현해보기**

W3에서는 BM25와 Vector Search를 RRF로 결합해 관련 청크를 찾고, 이를 LLM에게 전달하는 RAG를 만들었다.

이 과정에서 **문서 안에 답이 존재하는데도 필요한 청크를 검색하지 못해 답하지 못하는 경우**가 있었다.

이번에는 이 실패를 단순히 “검색이 잘 안 됐다”로 끝내지 않고,

**문서 속 사실을 Entity와 Relationship으로 미리 연결해두면 어떻게 달라질까?**

라는 관점에서 그래프로 표현해봤다.

## **1. W3에서 어떤 문제가 있었나?**

대표적으로 이런 질문을 만들었다.

**“SeCause에서 작업 큐에 사용한 기술을 다른 프로젝트에서도 사용했는가?”**

사람이 문서를 읽으면 다음 두 사실을 연결할 수 있다.

```
SeCause
→ 작업 큐로 Redis를 사용함

TEAMFICIAL
→ 지원자 수 집계 캐시로 Redis를 사용함
```

하지만 질문에는 **Redis라는 단어가 없다.**

기존 검색에서는 먼저 `SeCause`, `작업 큐`와 관련된 청크를 찾게 되고, 여기서 Redis를 알아낸 뒤 다시 다른 프로젝트의 Redis 사용 기록까지 찾아가야 한다.

실제 W3 실험에서도 첫 번째 정보는 찾았지만 두 번째 정보가 검색되지 않아 답변에 실패했다.

반면 정답 청크를 직접 넣어준 **Oracle Context에서는 답변에 성공했다.**

```
Normal Context → 실패
Oracle Context → 성공

→ LLM이 답을 만들 능력이 없었던 게 아니라
   필요한 근거를 검색하지 못했던 문제
```

## **2. 이걸 그래프로 표현하면?**

문서에서 다음과 같은 관계를 미리 만들어둘 수 있다.

```
[SeCause의 Redis 사용]
 ├─ PART_OF ──────────> [SeCause]
 ├─ USES_TECHNOLOGY ─> [Redis]
 ├─ HAS_PURPOSE ──────> [AI 분석 작업 큐]
 └─ HAS_STATUS ───────> [implemented]

[TEAMFICIAL의 Redis 사용]
 ├─ PART_OF ──────────> [TEAMFICIAL]
 ├─ USES_TECHNOLOGY ─> [Redis]
 ├─ HAS_PURPOSE ──────> [지원자 수 집계 캐시]
 └─ HAS_STATUS ───────> [implemented]
```

여기서는 **Redis가 두 프로젝트를 연결하는 브릿지**가 된다.

기존 검색에서는 질문에 Redis가 없기 때문에 TEAMFICIAL 문서를 바로 찾기 어려웠지만, 그래프에서는

```
SeCause
→ Redis 사용
→ Redis
→ Redis를 사용한 다른 프로젝트
→ TEAMFICIAL
```

처럼 관계를 따라갈 수 있다.

즉 기존에는 **“질문과 비슷한 문서를 찾아라”**였다면, 그래프에서는 **“찾은 Entity와 연결된 관계를 따라가라”**는 문제가 된다.

## **3. 그래프로 그리면서 생긴 문제**

처음에는 단순히 다음처럼 표현하려고 했다.

```
SeCause ──USES_TECHNOLOGY──> Redis
```

그런데 이렇게 하면 중요한 정보가 빠진다.

```
왜 사용했는가? → 작업 큐
실제로 구현했는가? → implemented
```

그래서 **“특정 프로젝트에서 특정 기술을 사용한 경험” 자체를 하나의 중간 노드**로 만들었다.

```
TechnologyUse
 ├─ PART_OF → Project
 ├─ USES_TECHNOLOGY → Technology
 ├─ HAS_PURPOSE → Purpose
 └─ HAS_STATUS → Status
```

RDF를 공부하면서 봤던 **2항 관계만으로 관계 자체의 맥락을 표현하기 어려운 문제**를 실제 내 데이터에서도 만난 셈이다.

## **4. 우선 이 네 관계만 사용한다**

이번 실습에서는 모든 문서를 완벽한 Knowledge Graph로 만드는 것이 목적이 아니다.

W3에서 실제로 실패했던 질문을 그래프로 개선할 수 있는지 확인하는 게 먼저다.

그래서 우선 다음 네 관계만 사용한다.

| **관계** | **의미** |
| --- | --- |
| `PART_OF` | 어떤 프로젝트의 기술 사용인지 |
| `USES_TECHNOLOGY` | 어떤 기술을 사용했는지 |
| `HAS_PURPOSE` | 왜 사용했는지 |
| `HAS_STATUS` | 실제 구현인지 제안인지 |

질문이 바뀌면 필요한 관계도 달라질 수 있다. 따라서 이 네 개를 **범용 Ontology라고 생각하지 않고, 개인 KG v1을 위한 작은 실험 스키마**로 사용한다.

## **5. 그래서 W5에서는?**

가장 먼저 위 사례를 실제로 구현해본다.

```
기존 방식
질문
→ Hybrid Search
→ Top-k Chunk
→ LLM

실험할 방식
질문
→ Entity / Relation 탐색
→ Redis라는 브릿지 발견
→ 연결된 다른 프로젝트 탐색
→ 원문 Chunk
→ LLM
```

그리고 동일한 질문에 대해 **기존 Hybrid RAG와 Graph 기반 탐색 중 어떤 방식이 필요한 근거를 더 잘 가져오는지** 비교한다.

여기서 중요한 건 그래프가 기존 검색을 전부 대체한다고 가정하지 않는 것이다.

W3에서도 기존 Hybrid Search만으로 잘 답한 질문이 있었다. 따라서 현재 가설은 이 정도다.

**서술적으로 비슷한 문서를 찾는 질문은 기존 검색이 잘 처리할 수 있다. 반면 여러 문서에 흩어진 관계를 따라가야 하는 질문에서는 명시적인 그래프 구조가 도움이 될 수 있다.**

이 가설을 W5에서 직접 확인해본다.
