# **RDF 기본 — 문서가 아니라 사실과 관계를 저장하려면?**

지난주에는 BM25와 Vector Search를 RRF로 결합해 개인 Notion 문서에서 관련 청크를 찾고, 이를 LLM에게 전달해 답변하는 RAG를 만들었다. 

실험하면서 알게 된 건 **답이 내 문서에 존재한다고 해서 항상 답할 수 있는 건 아니라는 점**이었다. 필요한 정보가 여러 청크에 흩어져 있으면 검색 단계에서 일부를 놓칠 수 있었고, 실제로 정답 청크를 직접 넣어주자 같은 LLM이 제대로 답한 사례도 있었다.

여기서 한 가지 생각이 들었다. 지금까지는 계속 **질문과 관련된 문서가 무엇인가?**를 찾고 있었는데, 내가 궁금한 건 사실 문서 자체가 아니라 그 안에 들어 있는 **사실과 관계**일 수도 있다.

예를 들어 어떤 프로젝트에서 Redis를 사용했다는 기록이 여러 문서에 흩어져 있다고 해보자. 내가 알고 싶은 건 단순히 Redis가 등장하는 문서가 아니라 **어떤 프로젝트에서 Redis를 사용했고 → 왜 사용했고 → 실제 구현까지 했는지**일 수 있다.

`질문 → 관련 문서 검색`에서 `개체 → 관계 → 개체`로 관점을 바꾸기 시작한 것이다. 이번 주에는 이런 관계를 표현하는 가장 기본적인 모델인 **RDF**부터 살펴봤다.

## **1. RDF와 Triple**

RDF(Resource Description Framework)는 하나의 사실을 **주어(Subject) - 술어(Predicate) - 목적어(Object)** 세 요소로 표현한다. 이 하나의 사실을 **Triple**이라고 한다.

예를 들어 `SeCause는 Redis를 사용한다`라는 사실이 있다고 해보자. 여기서 SeCause는 내가 진행한 **AI 코드 보안 분석 프로젝트**이고, 분석 작업을 비동기로 처리하는 과정에서 Redis 같은 기술을 사용할 수 있다.

이를 Triple로 표현하면 `(SeCause, 사용한다, Redis)`가 된다.

그래프로 생각하면 더 단순하다.

**SeCause → 사용한다 → Redis**

결국 RDF의 기본 아이디어는 **“무엇이 어떤 관계로 무엇과 연결되어 있는가?”를 같은 형식으로 계속 쌓는 것**이다.

### **왜 굳이 모든 사실을 Triple로 표현할까?**

관계형 DB에서는 보통 테이블 구조를 먼저 정하고 그 구조에 맞춰 데이터를 넣는다. 새로운 종류의 정보가 생기면 스키마 변경이 필요할 수도 있다.

RDF에서는 새로운 사실이 생기면 새로운 Triple을 추가한다.

| **특징** | **의미** |
| --- | --- |
| 단일 구조 | 모든 사실을 Subject-Predicate-Object 형태로 표현한다. |
| 유연한 확장 | 새로운 종류의 관계를 Triple로 추가할 수 있다. |
| 데이터 연결 | 서로 다른 출처의 데이터도 같은 대상을 중심으로 연결할 수 있다. |

특히 RDF는 웹에 흩어진 데이터를 연결하는 것을 염두에 두고 만들어졌다. 서로 다른 곳에서 만든 데이터라도 동일한 대상을 같은 식별자로 표현한다면 하나의 그래프로 이어 붙일 수 있다.

즉 한 개체의 정보를 한 행에 모아두는 것보다는 **여러 개체 사이의 사실과 관계를 공통된 방식으로 표현하고 연결하는 데 초점**이 있다.

## **2. 그런데 같은 대상을 어떻게 알아볼까? → IRI**

여기서 바로 문제가 하나 생긴다.

`홍익대`, `홍익대학교`, `Hongik University`라는 세 문자열이 있다면 사람은 같은 학교를 의미한다고 쉽게 생각할 수 있지만 컴퓨터에게는 서로 다른 문자열이다.

그래서 RDF에서는 대상을 단순한 이름 대신 **IRI(Internationalized Resource Identifier)**로 식별한다. 

: 쉽게 생각하면 웹 전체에서 어떤 대상을 가리키기 위한 고유한 주소

예를 들어 `ex:secause`, `ex:redis`처럼 각각의 대상을 식별하고, `ex:secause → usesTechnology → ex:redis`처럼 관계를 표현할 수 있다.

다만 여기서 주의할 점이 있다. **IRI를 쓴다고 같은 대상을 자동으로 찾아주는 것은 아니다.**

어떤 데이터에서는 한 사람을 `ex:yeonho`라고 부르고 다른 데이터에서는 `other:leeYeonho`라고 부른다면, 이 둘이 실제로 같은 사람인지 판단하는 문제는 그대로 남는다.

즉 IRI는 **대상에게 고유한 식별자를 부여하는 방법**이지, 서로 다른 두 식별자가 현실에서 같은 대상을 의미하는지 알아서 판단해주는 기술은 아니다. 여러 데이터셋을 실제로 합치기 시작하면 이 문제가 **Entity Resolution**로 다시 등장한다.

## **3. RDF에서 사용하는 세 종류의 값**

RDF를 읽을 때는 IRI, Literal, Blank Node 세 가지를 구분하면 된다.

| **종류** | **의미** | **예시** |
| --- | --- | --- |
| IRI | 식별자를 가진 대상 | 프로젝트, 사람, 기술 |
| Literal | 문자열·숫자·날짜 같은 값 | `"연호"`, `25`, `"implemented"` |
| Blank Node | 구조상 필요하지만 별도 이름이 없는 대상 | 이름 없는 중간 노드 |

여기서 기억할 부분은 **Literal은 목적어 자리에만 올 수 있다는 것**이다.

예를 들어 `"연호"`라는 문자열은 하나의 값일 뿐이다. 이 문자열 자체를 다시 주어로 삼아 학교, 프로젝트, 기술 같은 관계를 계속 연결할 수는 없다. 어떤 대상에 대해 계속 설명하고 다른 관계를 연결하고 싶다면 단순한 Literal이 아니라 **IRI를 가진 Resource로 표현하는 것이 자연스럽다.**

Blank Node는 아직 조금 애매하다. 
“이름도 없는 노드를 왜 만들지?” 싶었는데, 뒤에서 관계에 추가 정보를 붙이려고 하면서 필요성이 보였다.

## **4. Turtle — RDF를 읽는 방법**

RDF는 데이터를 표현하는 모델이고, 실제 파일에 RDF를 적는 방법은 여러 가지다. 그중 사람이 읽기 편한 표현 방식이 **Turtle**이다.

이번 주에는 문법을 깊게 보지않고 세 가지만 알아보았다

| **문법** | **의미** |
| --- | --- |
| `;` | 같은 주어를 반복해서 쓰지 않는다 |
| `,` | 같은 주어와 술어를 반복해서 쓰지 않는다 |
| `a` | `rdf:type`, 즉 “~의 타입이다” |

예를 들어 `ex:yeonho a ex:Student`라고 되어 있다면 **“yeonho라는 대상은 Student 타입이다”** 정도로 읽으면 된다.

RDF/XML, JSON-LD 등 다른 표현 방식도 있지만 이번 주의 목적은 포맷을 외우는 게 아니라 **Triple이 어떻게 표현되는지 읽을 수 있는 정도**이므로 Turtle까지만 보고 넘어간다.

## **5. 그런데 Triple 하나로는 부족한 경우가 있다**

여기가 이번 내용에서 가장 중요했다.

이번 주 실습에서는 내 프로젝트 경험을 그래프로 표현해보려고 했다. 예를 들어 앞에서 말한 AI 코드 보안 분석 프로젝트 `SeCause`에서 Redis를 사용했다고 해보자.

가장 먼저 떠오르는 표현은 단순하다.

**SeCause → USES_TECHNOLOGY → Redis**

그런데 실제 경험을 기록하려고 하니 이걸로는 부족했다. 내가 표현하고 싶은 건 단순히 Redis를 사용했다가 아니기 때문이다.

예를 들어 한 프로젝트에서는 Redis를 **AI 분석 작업을 전달하기 위한 큐 용도로 실제 구현해서 사용**했을 수 있고, 다른 프로젝트에서는 Redis를 **캐시 용도로 검토하거나 제안만 했을 수도 있다.**

그렇다면 기술을 사용한 사실에는 적어도 이런 정보가 따라온다.

| **알고 싶은 것** | **예시** |
| --- | --- |
| 어느 프로젝트인가? | SeCause |
| 어떤 기술인가? | Redis |
| 왜 사용했는가? | AI 분석 작업 큐 |
| 어떤 상태인가? | 실제 구현됨 |

하지만 `SeCause → Redis`라는 단순한 2항 관계에는 **목적과 상태를 추가할 자리가 없다.**

즉 현실의 관계에는 때때로 두 대상을 연결하는 것 이상의 정보가 필요하다. 이런 문제를 **n항 관계(n-ary relation) 문제**라고 한다.

## **6. 관계에 정보가 더 필요하면 관계 자체를 노드로 만든다**

이번 주 스키마를 설계하면서 이 문제를 해결하기 위해 **“특정 프로젝트에서 특정 기술을 사용한 경험” 자체를 하나의 중간 노드로 만들었다.**

이 중간 노드를 편의상 `TechnologyUse`라고 이름 붙였다.

그러면 하나의 TechnologyUse를 기준으로 **어느 프로젝트에서 사용했는지(`PART_OF`) → 어떤 기술인지(`USES_TECHNOLOGY`) → 왜 사용했는지(`HAS_PURPOSE`) → 어떤 상태인지(`HAS_STATUS`)**를 각각 연결할 수 있다.

즉,

**TechnologyUse → 프로젝트 / 기술 / 사용 목적 / 구현 상태**

라는 구조가 된다.

처음에는 RDF 이론을 보고 이 구조를 만든 게 아니었다. 실제 데이터를 표현하려고 보니 `SeCause → Redis`만으로는 목적과 상태를 담을 수 없어서 중간 노드를 만들었는데, RDF를 공부해보니 **관계나 진술 자체를 하나의 대상으로 만들어 추가 정보를 표현하는 reification과 비슷한 문제를 풀고 있었다.**

개인적으로 이번 내용에서 가장 재밌었던 부분이었다. 스키마를 직접 짜다가 부딪힌 문제가 RDF에서도 오래전부터 다뤄온 모델링 문제였던 것이다.

앞에서 봤던 **Blank Node**도 여기서 이해할 수 있다. 모든 기술 사용 경험에 `secauseRedisUse` 같은 고유한 이름을 꼭 붙일 필요가 없다면, 구조상 중간 노드는 존재하지만 별도의 전역 식별자는 없는 Blank Node로 표현할 수도 있다.

## **7. Wikidata도 비슷한 문제를 가지고 있다**

이 문제는 개인 프로젝트 데이터를 표현할 때만 생기는 게 아니다.

예를 들어 Wikidata에서 어떤 사람과 학교의 관계를 단순하게 표현하면 **사람 → 교육기관 → 대학교** 정도가 된다.

그런데 실제로는 언제부터 다녔는지, 어떤 전공이었는지, 이 사실의 출처는 무엇인지 같은 추가 정보가 필요할 수 있다.

그래서 Wikidata에서는 하나의 **statement에 qualifier와 reference 같은 추가 정보를 붙일 수 있는 구조**를 사용한다.

우리의 `TechnologyUse`와 Wikidata의 데이터 모델이 완전히 같은 것은 아니다. 다만 **단순한 A → 관계 → B만으로는 부족해서, 그 관계나 진술 주변에 추가적인 구조를 만든다**는 문제의식은 비슷하다.

결국 실제 Knowledge Graph를 만들다 보면 **“A와 B가 연결되어 있다”를 저장하는 것에서 끝나는 게 아니라, 그 관계 자체를 어떻게 설명할 것인가**도 중요한 모델링 문제가 된다.

## **8. 그렇다고 이번 실습에서 RDF를 그대로 구현하는 것은 아니다**

이번 주 RDF를 공부하는 이유는 RDF 저장소를 직접 만들기 위해서라기보다 **사실과 관계를 그래프로 표현하는 기본적인 사고방식을 이해하기 위해서**다.

실제 실습에서는 PostgreSQL에 직접 그래프 구조를 저장할 예정이라 RDF와 의도적으로 다르게 가져가는 부분도 있다.

| **RDF에서 배운 방식** | **이번 실습에서 가져갈 방식** |
| --- | --- |
| 사실을 Triple 중심으로 표현 | Entity와 Edge로 나누어 저장 |
| 값도 Triple의 Object로 표현 가능 | 목적·상태 같은 값은 필요에 따라 JSONB 속성으로 저장 |
| 관계의 출처를 별도로 모델링해야 함 | Edge에 원본 `chunk_id`와 `evidence`를 직접 저장 |
| RDF 표준과의 호환성을 고려 | 이번 실험에서는 검색과 평가가 쉬운 구조를 우선 |

특히 `chunk_id`와 `evidence`를 남기는 건 지난주 실험에서 이어진 부분이다.

지난주에는 LLM이 답변과 함께 Citation을 반환하도록 했지만, 단순히 “이 문서가 근거입니다”라고 말하는 것만으로는 부족했다. 그래서 실제 Context 안에 해당 근거가 존재하는지 다시 검증했다.

그래프에서도 마찬가지다. **“SeCause가 Redis를 사용했다”라는 관계를 저장했다면, 이 사실을 원본 문서의 어디에서 추출했는지 다시 찾아갈 수 있어야 한다.**

**Graph Fact → 원본 Chunk → 실제 Evidence**

라는 연결을 남겨두려는 이유다.

## **9. RDF가 있다고 모든 문제가 해결되는 건 아니다**

RDF가 해주는 것은 결국 **사실을 공통된 구조로 표현하고, 대상을 식별하고, 서로 연결할 수 있게 만드는 것**이다. 데이터의 모든 의미까지 자동으로 이해해주는 것은 아니다.

예를 들어 `BackendEngineer는 Engineer의 한 종류이고, Engineer는 Person의 한 종류다`라는 정보가 있다고 하자. 그리고 `연호는 BackendEngineer다`라는 사실도 있다.

그러면 사람은 자연스럽게 **“연호는 Person이기도 하다”**고 생각한다.

하지만 지금까지 배운 RDF만으로는 **이런 클래스의 계층 관계를 어떻게 정의할지, 그리고 이미 저장된 사실을 바탕으로 새로운 사실을 어떻게 유도할지**에 대한 규칙이 부족하다.

또 `USES_TECHNOLOGY`라는 관계의 주어에는 Project만 올 수 있고 목적어에는 Technology만 와야 한다는 식의 의미도 아직 정의하지 않았다.

즉 지금까지는 **“사실과 관계를 어떻게 표현할 것인가?”**를 배웠다면, 다음에는 한 단계 더 나아가 **“그 관계가 어떤 의미를 가지며, 어떤 규칙을 만족해야 하는가?”**를 표현해야 한다.

그래서 다음에는 RDF 위에 클래스, 속성, 계층 등의 의미를 더하는 **RDFS와 OWL**을 살펴보고, 여기서부터 **스키마와 온톨로지는 무엇이 다른지, 추론(Inference)은 어떻게 가능한지** 이어서 정리해본다.
