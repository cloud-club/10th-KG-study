> 정보를 "대상과 관계"로 저장하는 방식. 트리플(주어-술어-목적어)이 단위이고, 온톨로지가 그 위에 개념·관계의 의미와 규칙을 정의한다. 이 스터디의 최종 목표(개인 데이터로 지식그래프 만들기)의 개념 층이며, 2026-09-16 기준 아직 실제로 그래프를 구축한 멤버는 없다.

## 용어

| 용어 | 정의 (heebindev · sunghyun 합성) |
|---|---|
| 엔티티 | 구분할 수 있는 현실의 대상이나 개념 |
| 트리플 | 하나의 사실을 주어 – 술어 – 목적어(Subject – Predicate – Object) 세 요소로 표현한 것. 트리플 하나가 그래프의 연결 하나 |
| 지식 그래프 | 실제 엔티티와 관계를 저장한 **데이터** |
| 온톨로지 | 그 데이터에 어떤 개념과 관계를 쓸지 정의하는 **의미 체계**. 개념 종류, 관계의 의미, 상위·하위 개념, 동일 개념, 역관계, 규칙(도메인·레인지)을 정의한다. "관계 이름을 통일하는 것보다 넓은 개념" |
| RDF | 정보를 트리플로 표현하기 위한 표준. **RDF 자체는 저장소가 아니다.** 저장은 Triplestore(GraphDB, Stardog, Apache Jena, Amazon Neptune의 RDF 기능)가 한다 |
| URI · Turtle | URI는 대상을 구분하는 고유 식별자(웹페이지가 실재할 필요 없음). Turtle은 긴 URI를 사람이 읽기 쉽게 쓰는 RDF 문법 |
| SPARQL | RDF 지식그래프의 질의 언어. RDB의 SQL에 해당 |
| Reasoning | 온톨로지 규칙으로 직접 저장하지 않은 사실을 도출. 예: `PostgreSQL rdf:type Database` + `Database subClassOf Technology` ⇒ `PostgreSQL rdf:type Technology` |
| 다중 홉 질문 | 두 개 이상의 관계를 연속해서 따라가야 답이 나오는 질문 → [[멀티홉-질문과-Bridge-Entity]] |

OWL과 RDFS는 두 노트 모두 정의하지 않았다(sunghyun의 열린 질문에만 등장). 두 멤버의 멀티홉 예시는 구조가 같다: "나 → 참여한다 → KG 스터디 → 사용한다 → PostgreSQL".

## Neo4j(Property Graph) vs RDF + 온톨로지 (sunghyun)

| | Neo4j | RDF + Ontology |
|---|---|---|
| 모델 | Property Graph. 노드·관계에 속성을 붙이기 쉬움 | 트리플 + 의미 규칙 |
| 핵심 질문 | "어떤 관계를 따라가면 원하는 노드에 도착하는가" | "이 대상과 관계는 무슨 뜻이며, 그 의미로 무엇을 더 알 수 있는가" |
| 강점 | 관계·경로 탐색 | 의미 정의, 규칙, 추론 |
| 추론 | 쿼리나 애플리케이션 로직으로 구현 | 의미 규칙 자체를 데이터 모델에 정의 |

- 선택 기준은 데이터 크기가 아니라 **어떤 질문을 풀려는지**다. RDBMS도 나쁜 게 아니라 문제 성격이 다르다(표·정형 관리 vs 관계를 여러 단계 따라가기).
- 오해 교정: "모호한 자연어 질문을 RDF가 자동으로 더 잘 이해하는 것은 아니다." 자연어 해석은 LLM이나 검색 계층이 하고, RDF·온톨로지는 해석된 질문에 쓸 의미 구조를 준다.
- sunghyun의 판단: 개인 Notion 데이터라면 **Neo4j부터** 시작하는 게 이해하기 쉽고, 의미 규칙·추론까지 가고 싶어지면 같은 데이터를 RDF로 다시 표현해 본다. 레포 공용 인프라([[로컬-인프라]])에 Neo4j 5.26 + APOC가 준비되어 있다.

## 왜 검색 다음이 그래프인가

- dldusgh318은 3주차 RAG 실습에서 3-hop 질문(H01)이 검색 단계에서 실패하는 것을 확인하고 "청크는 문서 조각이지 관계가 아니다. 청크는 문서 조각이고, Triple은 관계다"라고 정리했다. 관계가 저장돼 있지 않으니 검색기가 조각 세 개를 모두 찾아줘야만 LLM이 연결할 수 있다. 4주차에 청크 위에 엔티티·관계를 추출해 `(RDS 인증 실패, caused_by, 오래된 운영 비밀번호)` 같은 트리플을 쌓고, **같은 H01 질문과 Gold Chunk로 청크 하이브리드 검색 vs 관계/그래프 검색을 비교**하겠다고 예고했다. "그래프가 더 좋다"를 가정하는 게 아니라 관찰된 검색 실패를 관계 탐색이 해결하는지 검증하는 것이 목적이다.
- kdyann이 정리한 Microsoft GraphRAG: 원문에서 엔티티·관계를 추출해 그래프를 만들고 커뮤니티별 요약을 생성한다. 개별 엔티티 주변을 탐색하는 local search와 커뮤니티 요약을 종합하는 global search("이 문서 전체의 주제는?")를 구분한다. 단순 벡터 검색의 대체재가 아니라 관계·전체 주제 질문을 위한 **추가** 검색 구조이며, 추출과 요약 비용·추출 오류가 부담이다.
- kungbi는 경계를 그었다. [[OpenViking-컨텍스트-데이터베이스|OpenViking]]은 자료·기억·절차를 찾고 상세 수준을 고르는 것이고, Knowledge Graph는 엔티티와 관계를 명시하고 관계 경로를 질의하는 것이다.

## 저장소 아키텍처

> ⚠️ Contradiction: **정본(canonical)이 어디인가.** sunghyun은 Notion → (청킹 → PostgreSQL+pgvector → 벡터 검색)과 (엔티티 추출 → Neo4j → 관계 탐색)을 **병렬 경로**로 그려 RAG에서 합류시킨다([sunghyun 01](../../members/sunghyun/note/01-knowledge-graph-and-ontology.md) §11). kungbi는 PostgreSQL을 canonical source로 두고 graph DB와 vector index를 "필요할 때 다시 만들 수 있는 projection"으로 격하한다([kungbi lab 01](../../members/kungbi/labs/01-data-collection-practice/README.md) §3). 같은 스택, 다른 정본 개념. 실습이 합쳐질 때 정해야 한다. [[데이터-수집과-출처-추적]] 참조.

## 멤버들이 확인한 것

- 실측은 없다. heebindev와 sunghyun의 노트는 `status: in-progress` 개념 정리이고, kungbi의 수집 실습은 설계·발표 자료까지 완료, 적재는 미구현이다. dldusgh318의 그래프 비교는 4주차 예고 상태.
- sunghyun이 스터디에 제안한 것: 같은 문장으로 각자 트리플을 만들어 엔티티·관계가 어떻게 달라지는지 비교, 개인 Notion에서 엔티티 기준 정하기, 같은 데이터를 Neo4j와 RDF로 표현해 차이 확인, 관계 탐색만으로 충분한 질문과 온톨로지 추론이 필요한 질문 만들기.

## 열린 질문

- Notion·카카오톡에서 엔티티와 관계를 자동으로 어떻게 추출할까 (sunghyun, dldusgh318 4주차)
