# 임베딩 모델 · 문장을 검색 가능한 숫자로 바꾸기

## 참고자료

- [임베딩이란 무엇인가요? — IBM](https://www.ibm.com/kr-ko/think/architectures/rag-cookbook/embedding) — 한국어. 텍스트를 숫자로 표현해 검색에 사용하는 흐름.
- [Cohere 의미 검색 튜토리얼](https://docs.cohere.com/docs/semantic-search-with-cohere) — 문서와 질문을 각각 임베딩하고 검색 결과를 얻는 과정.

## 하는 일: 표현이 달라도 가까운 내용을 찾기

가상 문서에 “발송 전 철회가 가능하다”라고 쓰여 있고 질문은 “배송 시작 전에 취소하려면?”이라고 하자. 키워드는 다르지만 관련된 내용이다. 임베딩 모델은 텍스트를 벡터로 바꾸고, 검색기는 질문 벡터와 문서 벡터의 가까움을 계산한다.

```text
문서 청크 → 임베딩 모델 → [0.12, -0.35, 0.08, ...]
질문      → 같은 검색 설정 → [0.11, -0.30, 0.09, ...]
```

숫자는 설명용 가상 값이다. 첫 좌표가 “배송”, 둘째가 “취소”를 뜻하는 식으로 사람이 의미를 지정한 표는 아니다. 비슷한 벡터가 답을 포함하는지는 실제 질문으로 평가해야 한다.

임베딩 모델은 답변 문장을 만드는 역할이 아니다. DB도 아니다. 모델이 숫자를 만들고, DB/검색기가 저장·비교하며, 생성 모델이 선택된 원문으로 답한다.

## 발전 과정

| 접근 | 표현 방식 | 다음 접근이 보완하려는 점 |
|---|---|---|
| Bag-of-words·TF-IDF | 단어 등장과 가중치로 만든 희소 벡터 | 같은 뜻의 다른 단어를 직접 연결하기 어려움 |
| Word2Vec 등 | 학습된 단어 단위 밀집 벡터 | 문장 전체 의미·문맥에 따른 변화는 별도 처리 |
| BERT 등 문맥 표현 | 주변 문맥에 따라 토큰 표현 변화 | 기본 출력이 곧 최적의 문장 검색 벡터인 것은 아님 |
| Sentence-BERT | 문장을 비교하기 좋은 임베딩으로 학습 | 의미 유사도·검색 활용을 효율적으로 구성 |
| 검색용 임베딩 모델 | 질의와 관련 문서, 다국어 등 검색 과제에 맞춰 학습 | 실제 언어·도메인·길이 조건에서 검증 필요 |

대표 출처: [Word2Vec, 2013](https://arxiv.org/abs/1301.3781), [Sentence-BERT, EMNLP 2019](https://aclanthology.org/D19-1410/). 사전·동의어 관리 없이 표현 변형을 다룰 가능성이 커졌지만 정확한 버전 번호·부정·예외를 자동으로 해결한 것은 아니다.

## 개발 주체와 모델 선택의 예

| 모델·접근 | 개발·공개 주체 | 특징과 확인할 설정 |
|---|---|---|
| Sentence-BERT | Reimers·Gurevych, TU Darmstadt UKP, 2019 | 문장 임베딩 접근. 라이브러리 이름과 개별 체크포인트 구분 |
| Cohere Embed | Cohere | 문서와 검색 질문의 입력 용도를 구분해 의미 검색에 사용 |
| Gemini Embedding | Google / Google DeepMind | 호스팅 모델 계열. 생성용 Gemini와 별도 역할·모델 설정 |

공식 자료: [Sentence-BERT 논문](https://aclanthology.org/D19-1410/), [Cohere 의미 검색 예제](https://docs.cohere.com/docs/semantic-search-with-cohere), [Google 임베딩](https://ai.google.dev/gemini-api/docs/embeddings).

이 목록은 예시이며 최신 순위표나 채택 결정이 아니다. 모델 카드는 언어·입력 길이·차원·접두어·정규화·라이선스를 확인하는 출발점이다. 같은 계열이어도 체크포인트가 다르면 설정이 달라질 수 있다.

## 평가셋과 벤치마크의 출처·시점

평가셋은 정답이 붙은 문제 모음이다. 벤치마크는 여러 평가셋과 실행·집계 규칙을 묶을 수 있다. MTEB를 단일한 질문 파일 하나처럼 생각하지 않는다.

| 이름 | 주체·발표 시점 | 무엇을 모았나 | 어떤 지표를 볼까 |
|---|---|---|---|
| BEIR | Thakur 등; arXiv 2021-04-17, NeurIPS 2021 Datasets and Benchmarks | 여러 도메인의 기존 검색 데이터셋을 모아 일반화 평가 | 대표적으로 nDCG@10, 검색 Recall 등 |
| MTEB | Muennighoff 등; arXiv 2022-10-13, EACL 2023 | 검색·문장 유사도·분류·군집 등 임베딩 과제 | 과제별 지표, 검색과 무관한 전체 평균에 주의 |
| MMTEB | Enevoldsen 등 국제 공동 연구·커뮤니티; arXiv 2025-02-19 | MTEB를 확장한 대규모 다국어 과제 모음 | 한국어·검색 과제와 해당 버전의 구성 확인 |

출처: [BEIR 원 논문](https://arxiv.org/abs/2104.08663), [MTEB 최초 공개 이력](https://arxiv.org/abs/2210.07316), [EACL 발표](https://aclanthology.org/2023.eacl-main.148/), [MMTEB](https://arxiv.org/abs/2502.13595), [MTEB 공식 문서](https://docs.mteb.org/).

각 날짜는 논문 기준이며 포함된 원본 코퍼스의 수집 시점은 서로 다르다. 실제 실행 시에는 하위 데이터셋 출처와 버전·분할까지 기록해야 한다. 현재 리더보드가 최초 논문의 구성과 같다고 가정하지 않는다.

## 검색 평가 지표를 쉽게 구분하기

- **Recall@5**: 필요한 근거 중 상위 5개에 얼마나 들어왔나? 여러 근거가 필요한 내 RAG의 첫 지표다.
- **MRR**: 첫 정답이 얼마나 빨리 나왔나? 1위면 1, 2위면 1/2, 5위면 1/5다. 여러 필수 근거를 모두 찾았는지는 설명하지 못한다.
- **nDCG@10**: 관련성이 높은 문서가 앞에 왔는가? 순위가 뒤일수록 기여를 줄이고 이상적인 순위와 비교한다. 정답 관련성 등급이 있어야 해석할 수 있다.
- **STS 상관계수**: 문장 두 개의 유사도 순서가 사람 판단과 얼마나 맞나? 검색에서 필요한 근거를 회수하는 것과 같은 과제가 아니다.

임베딩 모델의 벤치마크 점수와 HNSW의 근사 탐색 회수율도 다르다. HNSW가 정확 검색의 이웃을 얼마나 보존했는지는 **인덱스 근사 오차**이고, 그 이웃들이 질문의 정답 근거인지는 **검색 관련성** 문제다.

## 임베딩 비교 조건

처음에는 모델 하나로 정확 벡터 검색을 만든다. 모델 두 개를 비교하는 것과 청킹 전략을 바꾸는 것을 동시에 하지 않는다. 결과 차이의 원인을 추적할 수 있어야 한다.

| 고정·기록 항목 | 이유 |
|---|---|
| 청크와 내용 해시 | 입력 데이터 변경과 모델 차이를 분리 |
| 모델 ID·revision·차원 | 같은 이름의 모델 변경, 재현성 관리 |
| 질문/문서 입력 규약 | 접두어·지시문 누락으로 성능 달라질 수 있음 |
| 최대 길이·truncation | 긴 청크의 뒷부분이 사라지는지 확인 |
| 정규화·거리 함수 | 모델이 의도한 비교 방법과 일치 |
| 한국어 질문 유형별 점수 | 전체 평균이 숫자·약어·부정 실패를 숨길 수 있음 |
| 지연·메모리·호출 비용 | 품질이 같아도 운영 선택 달라짐 |

임베딩 생성은 기존 모델을 이용한 **추론**이다. 내 문서를 임베딩했다고 모델을 새로 학습시킨 것은 아니다. 문서 벡터는 적재할 때 계산·저장하고, 질문 벡터는 질문할 때 계산한다. 모델 변경 시 같은 차원이어도 공간이 다를 수 있으므로 재임베딩과 인덱스 버전을 함께 관리한다.
