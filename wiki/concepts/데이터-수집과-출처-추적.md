> 지식그래프·검색에 넣을 데이터를 모을 때 "이 사실은 어느 원본의 어느 시점에서 왔는가"를 되짚을 수 있게 설계하는 문제. kungbi의 수집 실습 설계와, 카카오톡 실습들이 각자 도달한 "정본과 파생물 분리" 원칙, 그리고 5주차 그래프 실습 다섯 건이 실제로 구현한 **원문 → 검토 파일 → 모든 저장소**의 3단과 엣지 단위 provenance를 모은다. Citation(사용자向 출처 표시)과 Provenance(시스템 내부向 추적 메타데이터)는 다른 것이다 (do-dop).

## kungbi의 수집 계약 (설계, 미구현)

- 목표는 무작정 많이 모으는 게 아니라 작은 공개 데이터 하나로 **수집 → 원문 보존 → 정규화 → 관계 생성 → 근거 확인** 경로를 검증하는 것. 첫 대상은 공개 Git 저장소 1개 — commit SHA와 blob ID라는 안정적 식별자가 있고, 이력을 로컬에서 재현할 수 있고, Slack·Notion·AWS보다 개인정보·인증정보 통제가 쉽다.
- **수집 계약** 항목: source, scope, native ID, `observed_at`(수집기가 실제로 관측한 시각), redaction 규칙, `completeness`(complete / partial / denied / error).
- 저장 계층 분리: 원문 payload → 현재 commit/file 상태 → commit과 변경 이력 → 검색용 document/chunk → `commit -[CHANGED]-> file` 관계. **PostgreSQL을 canonical source로 두고 graph DB와 vector index는 언제든 다시 만들 수 있는 projection으로 취급한다.**
- provenance 경로: file relation → commit → ingestion run → source payload → 실제 diff. 성공 기준은 관계가 존재하는 것만이 아니라 **관계를 만든 근거와 관측 시점까지** 확인되는 것.
- 멱등성: payload가 같으면 같은 hash로 판별, 값이 바뀌면 현재 상태를 갱신하고 이전 관측은 이력으로 남긴다. 순서는 **Backfill → Enrichment → Incremental → Reconciliation**. 실시간 이벤트보다 정확한 backfill을 먼저 만들어야 누락·중복이 보인다.
- 검증 표 6항목: 재현성, 멱등성, 완전성(성공·부분·권한 거부·실패 구분), provenance(정규화한 사실에서 원문과 diff로 복귀), 관계 질의, 개인정보(비공개 원문·토큰·계정 식별자 미포함).
- 확장 단위: Slack = channel → thread → message → revision, Notion = data source → page → block tree → revision, GitHub = PR → review → commit → diff, AWS = account → resource → observation.
- 2026-09-12 기준 상태: 수집 대상·저장 계층·수집 순서 설계와 17장 발표 자료 완료, **Git fixture 수집·PostgreSQL 적재·증분 수집·검색/그래프 평가는 미구현.** kungbi는 "아직 실행하지 않은 환경을 완료된 구성처럼 기록하지 않는다"는 규율을 문서에 적어 두었다.

## 카카오톡 실습들이 도달한 같은 원칙

- lys0611: `messages`(원문 1건 1행)가 **정본**이고 `chunks` → `chunk_embeddings` / ES 인덱스는 언제든 다시 만들 수 있는 **파생물**. 같은 파일을 다시 넣어도 `(room_id, seq)`·`content_hash` 유니크로 중복되지 않는다. 가명화를 임베딩 **앞**에 두어 파생물을 공개할 수 있게 했다 → [[개인-데이터-가명화와-공개-범위]].
- sese2204: `kakao.rooms.source_file` 기준으로 방을 upsert하고 기존 메시지를 지운 뒤 COPY. 같은 파일 재적재 시 방 1개, 메시지 수 동일, `(room_id, seq)` 중복 0. 원본 txt에는 초 단위가 없어 같은 분 안의 순서를 `seq`로, 파싱 검증용으로 원본 줄 번호 `line_no`를 함께 저장한다.
- 이 셋은 표현이 다를 뿐 같은 원칙이다: **원문은 불변으로 한 번 저장하고, 검색용 구조는 파생물로 재생성 가능하게, 재적재는 멱등하게.** 이 위키의 세 층(`members/` 불변 소재 → `wiki/` 파생)도 같은 구조다([[LLM-위키-패턴]]).

> ⚠️ Contradiction (해소 방향): kungbi의 "PostgreSQL 단일 정본 + projection" 모델과 sunghyun의 "pgvector 경로와 Neo4j 경로 병렬" 모델은 정본 개념이 달랐다. 5주차에 그래프를 만든 다섯 멤버(dldusgh318, e0ng, heebindev, kdyann, Yeongeunn) 전원이 **중립적인 추출·검토 결과 하나에서 PG·Turtle·Neo4j로 변환**했다 — "저장소별로 독립 추출하지 않아야 서로 다른 사실이 생기는 것을 줄일 수 있다"(Yeongeunn). 단 정본의 위치가 kungbi와 다르다: kdyann·Yeongeunn은 git 밖의 검토 파일이 정본이고 PG도 파생물이다. Yeongeunn의 질문 경로(`질문 → ES → 본문 → Gemini`)는 PG를 읽지도 않는다. 3단 구분 = 원문 → 검토 파일 → 모든 저장소 → [[그래프-적재-Postgres와-Neo4j]].

## 수집 대상 선정 (Yeongeunn, sdunge, do-dop, sunghyun)

- Yeongeunn은 원래 쓰려던 회의 녹음이 **유실**돼 팀 Notion을 골랐다 — 하위 페이지까지 export 가능하고 회의록·멘토링·명세가 공존한다는 이유. 찾고 싶은 질문(어떤 문제를 해결하려 추가했나 / 어떤 대안을 검토했나 / 멘토링 피드백이 어떤 설계 변경으로 이어졌나)을 먼저 적었다. "구현 코드만으로 당시 의도를 단정하기 어렵다."
- sunghyun은 개인 Notion(관계 구조 단순, "개인 문서 검색"으로 보일 위험)과 기업 정보(관계 정의 어려움, 최신성)를 견주어 회사 기술 문서를 골랐다 — "문서가 많은 것보다 Entity·Relation을 찾을 수 있는지". JSON은 메타데이터 보존(`id`·`title`·`parent`·`createdAt`·`updatedAt`), Markdown은 청킹·임베딩용으로 역할을 분리.
- do-dop은 코퍼스 편향을 의도적으로 완화했다: HBM·AI 중심으로 고른 10건에 **무관한 문서 4건**을 더해 "키워드로 좁혀 고른 데이터만 쓰면 질문도 정답도 그 안에 있어 검색 성능이 실제보다 좋게 보인다"를 막았다. 수집은 공식 뉴스룸 HTML 본문 영역 + OpenDART 원문 API, 접수번호를 config에 고정 — "작은 실험 데이터셋을 위한 임시 규칙".
- **법제처 판례 OPEN API의 함정** (sdunge): 목록 조회(`lawSearch.do`) → 본문 조회(`lawService.do`) 2단계인데, 검색어로 받은 목록에 다른 출처의 행정 판례가 섞여 **본문 조회 시 "일치하는 판례가 없습니다"**를 돌려준다. `search=2` + 선고일자 범위로 형사 판례만 걸러 해결. 참조판례·참조조문을 그래프 엣지로 쓰겠다는 구상은 스터디에서 유일하다.
- 제3자 데이터의 수집 기준을 명시한 사례 (kdyann): 공식 Instagram 해시태그 API, 게시 후 24시간 이상·최근 7일·관측 좋아요 100개 이상, 좋아요·댓글 순위를 RRF로 합쳐 최대 50건. "수집한 후보 안에서의 순위이며 전체 인기 순위가 아니다." 날짜가 지나면 후보가 사라지므로 재수집이 필요하다.

## Citation vs Provenance (do-dop)

- **Citation** = 답변의 주장에 출처를 붙이는 것(사용자向). **Provenance** = 어디서·언제·어떤 문서·버전·처리를 거쳤는지 추적 가능하게 하는 메타데이터(시스템 내부向). "매출 10조 원"만으로 부족한 이유: 어느 회사·몇 년도·분기 vs 연간·연결 vs 별도·원 vs 백만원·**최초 vs 정정 공시**. provenance 필드 묶음: `company / document_type / document_title / published_at / reporting_period / page / table / metric / scope / unit / value / source_url / chunk_id`.
- **provenance가 필요한 주제 판별 6질문**: 잘못된 답의 비용 / 정보 변동성 / 여러 문서 합성 여부 / 수치·기간·버전 중요도 / 출처 충돌 가능성 / 사후 추적 필요성. 해당: 기업·금융, 법률, 의학, 사실검증, KG. 불필요: 창작·번역·정답 고정 FAQ.
- 그래프 엣지에 provenance를 붙이면 3-hop 답의 각 hop을 따로 검증할 수 있다: `A ─HAS_METRIC→ 영업이익 {value, period, source: p.42}`. 지표로는 Provenance completeness / consistency. W3C PROV가 표준 모델.
- Citation 품질의 3단계(Existence / Relevance / Entailment)는 [[RAG-루프와-근거-인용]].

## 5주차 — 엣지 단위 근거와 검토 상태

| 멤버 | 근거 저장 | 시점·버전·검토 |
|---|---|---|
| dldusgh318 | 엣지 `props`에 `chunk_id`·`evidence`·`confidence`, Neo4j 관계마다 `edge_key`(SHA-256) | `extraction_run`(`v0-4predicates` / `v1-5predicates`) — 스키마 버전이 다른 데이터가 섞이면 **조용한 누락**이 생기므로 "정보가 없었던 것"과 "도입 전에 추출한 것"을 구분 |
| Yeongeunn | `assertions`(관계)와 `evidence`(청크 ID·인용·**문자 위치·해시**) 분리 | `review_status`(미검토/승인/반려), `valid_from/valid_to`, `source_version` — Wikidata rank를 쪼갠 번역 → [[Wikidata와-DBpedia]] |
| kdyann | `rdf:Statement` reification에 `sourcePost`·`quote`·`start`·`end`, 코퍼스를 `own`/`reference`로 구분 | `publishedAt`, 검토본 jsonl이 정본 |
| e0ng | `kg_evidence(edge_id, source)` — 엣지가 어느 노션 페이지에서 나왔는지, 필드 단위 evidence | — |
| heebindev | `kg_evidence`(원본 청크·근거 문장), 코드가 근거가 원문에 포함된 관계만 남김 | — |

- kungbi의 `observed_at`(수집기가 관측한 시각)·`completeness`, Yeongeunn의 `valid_from/to`(사실의 유효 기간)·`review_status`(검토 상태), dldusgh318의 `extraction_run`(추출 규칙 버전)은 같은 축의 세 칸이다 — 관측 시점 / 유효 기간 / 추출·검토 버전. 셋을 다 가진 구현은 아직 없다.
- "생성 모델 이름만 저장하는 것은 원문 근거를 대신하지 못한다. 모델은 진술을 만든 도구이고 원문은 그 진술을 검사할 자료다" (Yeongeunn). 출처의 존재 여부와 근거의 적절성은 따로 평가한다.
- 검증 실패의 2분 (e0ng): 필요한 개념·관계가 없음 → 설계 수정 / 개념은 있지만 값이 없음 → **데이터 부족으로 기록**. 기간 정보가 없는 활동을 잘못된 데이터로 판단하지 않는다 → [[온톨로지와-추론]].
- PG·ES 이중 적재에 단일 트랜잭션이 없어 부분 적재가 가능하고, 원본 삭제에 따른 이전 청크 삭제를 지원하지 않는다 (Yeongeunn 자기 한계). 재적재는 멱등해야 한다 — 2회 적재 후 건수 불변 (dldusgh318, e0ng, Yeongeunn) → [[그래프-적재-Postgres와-Neo4j]].
- kungbi 4주차: 1주차의 수집 계약(Slack = channel → thread → message → revision, GitHub = PR → review → commit → diff)이 `Slack 스레드 → PR → 코드 심볼 → 저장소`라는 **질문**을 얻었다. 적재는 여전히 미구현(2026-09-29).
