# W4 지식 그래프의 배경 — 시맨틱 웹에서 업무 온톨로지까지

이 노트는 지식 그래프를 처음 배우는 사람이 아래 여섯 가지를 순서대로 이해하도록 구성했다.

1. 시맨틱 웹에서 오늘날의 지식 그래프까지 어떻게 이어졌는가
2. RDF는 사실을 어떻게 기록하는가
3. RDFS와 OWL은 데이터의 뜻을 어떻게 설명하는가
4. SPARQL로 Wikidata에 어떻게 질문하는가
5. 프로퍼티 그래프와 RDF는 무엇을 다르게 강조하는가
6. 답하지 못한 질문을 그래프로 그리면 무엇이 보이는가

아래의 공지 예시는 개념을 설명하기 위한 가상 문장이다. 마지막 절의 “공결 신청 후 승인까지 며칠 걸려?”는 앞서 답변 근거가 부족한 질문으로 정리한 유형을 사용한다.

## 1. 변천사: 왜 지식 그래프가 필요해졌는가

### 출발점은 문서에 적힌 뜻을 컴퓨터가 구별하기 어렵다는 문제다

예를 들어 “5주차에는 RDF를 공부한다”라는 문장이 있다고 하자.

- **문서 검색:** 이 문장이 들어 있는 문서를 찾는다.
- **남는 문제:** “5주차”가 어느 과정의 주차인지, “RDF”가 주제인지 자료인지, 둘 사이의 관계가 무엇인지 별도로 해석해야 한다.
- **그래프 표현:** 사람이 문장에서 읽은 관계를 다음처럼 구분해 적는다.

~~~text
5주차 ──학습 주제──> RDF
~~~

- 문서는 설명과 맥락을 보존한다.
- 그래프는 **대상**과 **관계**를 구분해 기록하므로 여러 사실을 이어서 물을 수 있다.

### 역사적 흐름

| 단계 | 당시의 질문 | 나온 접근 |
| --- | --- | --- |
| 시맨틱 웹, 2001 | 웹의 글을 컴퓨터도 의미에 따라 연결할 수 없을까? | 대상과 관계에 식별자를 부여하자는 비전 |
| RDF·RDFS·OWL 표준 | 서로 다른 사람이 만든 데이터를 어떤 공통 방식으로 표현할까? | 사실의 표현, 개념의 분류, 논리적 의미를 표준화 |
| 링크드 데이터·DBpedia·Wikidata | 표준으로 표현한 데이터를 실제 웹에서 어떻게 연결할까? | 공개 식별자를 쓰고 다른 데이터의 식별자를 참조 |
| Google Knowledge Graph, 2012 | 검색어의 글자가 아니라 사용자가 가리키는 대상을 알 수 없을까? | 검색 제품에 대상과 관계의 그래프를 활용 |
| 기업 지식 그래프 | 조직의 여러 시스템에 흩어진 정보를 어떻게 연결할까? | 고객·상품·문서 등의 관계를 조직 안에서 통합 |
| GraphRAG | 많은 문서의 관계를 LLM의 검색·요약에 어떻게 활용할까? | 문서에서 그래프를 만들고 질문에 맞춰 탐색·요약 |
| Palantir Foundry Ontology | 연결된 데이터를 업무 화면과 실제 변경 동작에 어떻게 쓸까? | 객체·관계·액션을 조직의 업무 모델로 연결 |

이 표는 공부할 때 따라가기 좋은 순서다. GraphRAG와 Palantir Ontology는 서로 다른 문제에 그래프를 적용한 방향이므로, 한 기술이 다음 기술로 교체되었다는 연대기로 읽지 않는다.

### 2001년 시맨틱 웹: 웹 데이터에도 뜻을 명시하자는 비전

- **문제:** “서울은 대한민국의 수도다”에서 “서울”이라는 글자만 보면 도시인지 사람 이름인지 확정하기 어렵다.
- **제안:** 도시 서울과 국가 대한민국에 각각 식별자를 붙이고, 그 사이를 “수도” 관계로 연결한다.
- **목표:** 문장 표현이 달라도 컴퓨터가 같은 대상을 찾고 관계를 읽게 한다.
- **2001년의 의미:** 팀 버너스리, 제임스 헨들러, 오라 라실라의 글이 비전을 널리 알렸다. W3C도 그해 표준화 활동을 시작했다. 기술이 완성된 시점이라는 뜻은 아니다. ([W3C 발표](https://www.w3.org/news/2001/w3c-launches-semantic-web-activity/), [원문](https://www.scientificamerican.com/article/the-semantic-web/))

웹페이지의 링크와 대상 사이의 관계를 비교하면 차이가 보인다.

~~~text
문서 링크: 서울 소개 페이지 ──링크──> 대한민국 소개 페이지
데이터 관계: 서울이라는 도시 ──수도임──> 대한민국이라는 국가
~~~

- **문서 링크:** 어디를 클릭해 이동하는지 알려준다.
- **데이터 관계:** 현실의 두 대상 사이에 무엇이 성립하는지 기록한다.

### RDF와 OWL: 함께 읽을 수 있는 약속을 만든다

- **RDF:** “대상 A — 관계 R → 대상 B”라는 사실의 기본 모양을 정한다.
- **RDFS:** 대상의 종류와 관계의 기본 뜻을 정한다.
- **OWL:** 개념 사이의 더 복잡한 논리적 의미를 정한다.

세 표준은 서로 다른 사람이 만든 데이터를 같은 방식으로 읽기 위한 약속이다. 각 역할은 2절과 3절에서 예시로 설명한다. ([W3C RDF 입문서](https://www.w3.org/TR/rdf11-primer/), [W3C OWL 입문서](https://www.w3.org/TR/owl2-primer/))

### 링크드 데이터·DBpedia·Wikidata: 약속을 실제 데이터에 사용한다

**링크드 데이터**는 웹 식별자를 통해 서로 다른 데이터가 같은 대상을 가리키고, 관련 데이터로 이동할 수 있게 공개하는 방식이다.

팀 버너스리가 제시한 원칙은 다음 순서로 읽을 수 있다. ([Linked Data 원칙](https://www.w3.org/DesignIssues/LinkedData))

1. 대상에 URI를 붙인다.
2. 웹에서 조회할 수 있는 HTTP URI를 사용한다.
3. 그 URI를 조회하면 대상에 관한 유용한 정보를 제공한다.
4. 관련된 다른 URI를 연결해 다음 데이터로 이동하게 한다.

예를 들어 기관 A가 도시의 인구를, 기관 B가 도시의 대학 목록을 공개한다고 하자.

- 두 기관이 **같은 도시 식별자**를 참조하면 인구와 대학 정보를 연결할 수 있다.
- 도시 이름의 글자가 같기만 해서는 두 기관이 같은 도시를 말하는지 확정할 수 없다.

- **DBpedia**는 위키미디어 프로젝트의 구조화된 내용을 추출해 연결 가능한 데이터로 제공한다.
- **Wikidata**는 사람들이 함께 편집하는 지식 기반이다. 항목마다 ID가 있으며, 항목의 속성·값·출처를 구조화해 기록한다.

두 프로젝트 모두 대상을 식별하고 관계를 기록하지만, 데이터가 만들어지는 방식은 다르다. ([DBpedia 소개](https://www.dbpedia.org/about/), [Wikidata 데이터 접근](https://www.wikidata.org/wiki/Help:Data_access))

| 구분 | DBpedia | Wikidata |
| --- | --- | --- |
| 데이터 형성 | 위키미디어 콘텐츠의 구조화된 부분을 추출한다 | 항목과 진술을 지식 기반에서 직접 편집한다 |
| 기본 사용 모습 | 추출한 데이터를 RDF로 제공해 연결한다 | 항목 ID, 속성 ID, 값, 한정자와 출처를 관리한다 |
| 초보자가 볼 차이 | 기존 콘텐츠에서 정보를 뽑아낸다 | 처음부터 구조화된 진술을 다룬다 |

**시맨틱 웹이 웹 전체의 기본 방식이 되기 어려웠던 이유**

- 식별자와 어휘를 오래 유지할 사람이 필요하다.
- 여러 조직이 같은 개념을 같은 뜻으로 사용하도록 합의해야 한다.
- 모든 웹페이지를 구조화했을 때의 직접적인 이득이 분명하지 않을 수 있다.
- 따라서 RDF와 링크드 데이터는 사라진 것이 아니라, 범위가 정해진 분야와 서비스에서 사용된다.

### 2012년 Google Knowledge Graph: “things, not strings”

- **문제:** “타지마할”이라는 같은 글자가 건물·음악가·다른 장소를 가리킬 수 있다.
- **Google의 접근:** 검색어의 철자뿐 아니라 사용자가 가리키는 대상과 그 관계를 파악한다.
- **의미:** “things, not strings”는 글자열보다 실제 대상을 중심에 둔다는 표현이다.
- **범위:** 2012년 Knowledge Graph 발표는 검색 제품의 사례다. 시맨틱 웹 전체가 완성되었다는 뜻은 아니다. ([Google 공식 발표](https://blog.google/products-and-platforms/products/search/introducing-knowledge-graph-things-not/))

### 기업 KG, GraphRAG, Palantir Ontology

**기업 지식 그래프(KG)**

- **문제:** 고객·계약·문서가 여러 시스템에 나뉘어 저장된다.
- **예:** 같은 회사가 고객 관리 시스템에는 “회사 A”, 계약 시스템에는 “A 주식회사”, 문서 보관함에는 “A사”로 적힐 수 있다.
- **그래프의 역할:** 세 표기가 같은 회사인지 확인한 뒤 연결하면, 그 회사의 계약·담당자·문서를 함께 찾는다.
- **주의:** 이름이 비슷하다는 이유만으로 동일 회사라고 단정하지 않는다.

**GraphRAG**

1. 문서에서 대상과 관계를 추출해 그래프를 만든다.
2. 서로 밀접하게 연결된 대상의 묶음인 **커뮤니티**를 찾는다.
3. 각 커뮤니티의 내용을 미리 요약한다.
4. 질문을 받으면 관련 요약에서 부분 답을 만들고 종합한다.

예를 들어 여러 공지가 “신청”, “승인”, “증빙 서류”를 함께 다룬다면 관련 대상들이 한 묶음으로 나타날 수 있다. Microsoft Research의 2024년 연구는 이런 **커뮤니티 탐지**와 요약을 이용해 자료 전체를 묻는 질문에 답하는 방식을 제안했다. 추출된 관계와 요약이 원문을 정확히 반영했는지는 별도로 확인해야 한다. ([Microsoft Research 논문](https://www.microsoft.com/en-us/research/publication/from-local-to-global-a-graph-rag-approach-to-query-focused-summarization/))

| 질문 | 필요한 정보의 범위 | 적합한 출발점 |
| --- | --- | --- |
| “공결 신청 방법은?” | 특정 사실과 그 근거 | 관련 공지·문장 검색 |
| “전체 공지에서 반복되는 행정 주제는?” | 여러 문서에 퍼진 공통 흐름 | 관련 커뮤니티의 요약 |

Microsoft 논문이 특히 다룬 것은 자료 전체를 이해해야 하는 **전역 질문(global question)**이다. 한 공지에서 답을 찾는 질문에는 전체 커뮤니티 요약이 필요하지 않을 수 있다.

**Palantir Foundry Ontology**는 직원·고객·설비 같은 업무 객체, 객체 사이 관계, 사용자가 실행하는 변경 동작을 함께 정의한다.

| Foundry 용어 | 공지방에 비유한 예 | 뜻 |
| --- | --- | --- |
| Object type | 공지라는 종류 | 어떤 종류의 대상을 다룰지 정한다 |
| Object | 특정 공지 한 건 | 실제 대상 하나다 |
| Link type | 공지가 주차를 알린다 | 두 종류의 대상 사이 관계를 정한다 |
| Link | 공지 A가 5주차를 알린다 | 실제 두 대상 사이 연결이다 |
| Action type | 공지 상태를 변경한다 | 권한과 규칙에 따라 실행하는 업무 동작이다 |

- **RDF·OWL:** 데이터의 관계와 의미를 기술하는 표준이다.
- **Foundry Ontology:** 조직의 데이터를 객체·관계로 나타내고 업무 앱의 변경 동작까지 연결한다.
- **따라서:** Foundry의 “Ontology”는 RDF·OWL 표준의 다른 이름이 아니다. ([Palantir 개념 설명](https://www.palantir.com/docs/foundry/getting-started/introductory-concepts), [Actions 설명](https://www.palantir.com/docs/foundry/object-edits/overview))

Object, Link, Action을 하나의 흐름으로 보면 차이가 분명해진다.

~~~text
Object: 공지 A
Link: 공지 A ──알리는 주차──> 5주차
Action: 권한을 가진 사용자가 공지 A의 상태를 변경한다
~~~

- **Object·Link:** 현재 데이터를 읽고 이해하는 구조다.
- **Action:** 권한을 가진 사용자가 업무상 변경을 실행하는 동작이다.
- **추론과의 차이:** 논리적으로 새 결론을 계산하는 일만으로 공지 상태가 변경되지는 않는다.

## 2. RDF 기본: 사실을 어떻게 적는가

### 트리플: 주어·술어·목적어

- **RDF:** 대상 사이의 관계를 일정한 방식으로 표현하는 데이터 모델이다.
- **트리플:** 관계 하나를 **주어–술어–목적어** 세 자리로 적은 것이다.

~~~text
5주차 ──다루는 주제──> RDF
 주어        술어          목적어
~~~

| 자리 | 묻는 질문 | 예 |
| --- | --- | --- |
| 주어 | 무엇에 관한 사실인가? | 5주차 |
| 술어 | 어떤 관계인가? | 다루는 주제 |
| 목적어 | 관계가 가리키는 대상이나 값은 무엇인가? | RDF |

- **방향:** “5주차의 주제는 RDF다”와 “RDF의 주제는 5주차다”는 다른 사실이다.
- **그래프:** 여러 트리플을 모으면 같은 대상을 중심으로 여러 관계를 따라갈 수 있다.

다음처럼 트리플 세 개를 이어서 생각할 수 있다.

~~~text
5주차 ──다루는 주제──> RDF
5주차 ──사용하는 자료──> RDF 입문 문서
RDF 입문 문서 ──작성 기관──> W3C
~~~

- “5주차 자료를 작성한 기관은?”이라는 질문은 **5주차 → 자료 → 작성 기관**을 차례로 따라가야 한다. 이런 질문을 다중 홉 질문이라고 한다.
- RDF의 주어·술어·목적어는 한국어 문장의 문법 이름과 정확히 같지 않다. RDF에서는 **관계에서 차지하는 세 자리**를 뜻한다.

### URI와 IRI: 같은 대상을 같은 이름으로 가리키기

- **문제:** “5주차”라는 글자만으로는 어느 과정의 주차인지 모호하다.
- **해결:** 대상과 관계에 고유한 웹 식별자를 부여한다.

~~~text
https://example.org/study/week-05
https://example.org/study/hasTopic
https://example.org/study/rdf
~~~

- 첫 번째 식별자는 **주차**, 두 번째는 **관계**, 세 번째는 **주제**를 가리킨다.
- 식별자는 이름표다. 주소처럼 보이더라도 웹페이지가 반드시 열려야 하거나, 적힌 사실이 참이라는 보증은 아니다.
- 표시 이름과 식별자는 다르다. “RDF”와 “알디에프”가 같은 주제를 가리킬 수 있고, “5주차”라는 이름은 여러 과정에서 반복될 수 있다.
- 일반적인 설명에는 **URI**라는 표현이 자주 나온다. RDF 1.1의 정확한 용어는 비영어권 문자까지 허용하는 **IRI**다. ([W3C RDF 입문서: IRI](https://www.w3.org/TR/rdf11-primer/))

### 리터럴: 다른 대상이 아니라 값 자체인 경우

목적어에는 두 종류가 올 수 있다.

- **다른 대상:** 다시 다른 관계로 연결할 수 있는 주제·사람·자료 등이다.
- **리터럴:** 날짜·숫자·문자열처럼 값 자체를 기록한다.

~~~text
5주차 ──다루는 주제──> RDF              RDF라는 대상
5주차 ──마감 날짜────> 2026-10-07       날짜 값
~~~

| 목적어의 종류 | 예 | 언제 쓰는가 |
| --- | --- | --- |
| 식별된 대상 | RDF라는 주제의 IRI | 그 대상에 다른 관계도 연결할 때 |
| 리터럴 | 날짜, 숫자, 이름 문자열 | 값 자체를 기록할 때 |

- **자료형:** “2026-10-07”을 단순한 글자가 아니라 날짜로 다루게 한다.
- **언어 표시:** “RDF 직렬화”라는 이름이 한국어라는 점을 기록한다.

~~~turtle
@prefix ex:  <https://example.org/study/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

ex:week-05 ex:deadline "2026-10-07"^^xsd:date .
ex:rdf ex:label "RDF 직렬화"@ko .
~~~

- 첫 줄의 목적어는 날짜 리터럴이고, 둘째 줄의 목적어는 한국어 문자열 리터럴이다. RDF 트리플에서 리터럴은 목적어 자리에 사용한다.
- “RDF 직렬화”라는 **이름만** 필요하면 문자열로 적을 수 있다.
- 그 주제에 교재·다른 주차·설명을 더 연결하려면 주제 자체에 식별자를 부여한다.

~~~text
이름만 보관: 5주차 ──주제 이름──> "RDF 직렬화"
관계도 연결: 5주차 ──다루는 주제──> [RDF 직렬화]
                                      └─관련 자료──> [W3C 입문서]
~~~

### 네임스페이스와 접두어: 긴 식별자를 짧게 쓰기

- **네임스페이스:** 여러 IRI가 공유하는 긴 앞부분이다.
- **접두어(prefix):** 그 앞부분을 파일 안에서 짧게 적는 별칭이다. 아래 예에서는 ex:가 https://example.org/study/를 대신한다.

~~~turtle
@prefix ex: <https://example.org/study/> .

ex:week-05 ex:hasTopic ex:rdf .
~~~

- **ex:week-05**는 https://example.org/study/week-05를 줄여 쓴 것이다.
- **ex:hasTopic**은 https://example.org/study/hasTopic을 줄여 쓴 것이다.
- 접두어 글자가 달라도 풀어 쓴 IRI가 같으면 같은 대상을 가리킨다.

### RDF와 파일 형식과 저장소

| 용어 | 무엇을 가리키는가 |
| --- | --- |
| RDF | 트리플로 관계를 표현하는 데이터 모델 |
| Turtle | RDF 트리플을 읽기 쉬운 텍스트로 적는 문법 |
| 트리플 스토어 | RDF 그래프를 저장하고 질의하는 시스템 |

이 셋을 구별하면 뒤의 “프로퍼티 그래프 대 RDF 트리플 스토어” 비교가 쉬워진다. RDF는 특정 제품이나 파일 확장자를 뜻하지 않는다.

## 3. RDFS와 OWL: 개념과 관계의 뜻을 정한다

### 먼저 클래스와 속성을 구별한다

- **클래스(class):** 대상의 종류다.
- **개체(instance):** 그 종류에 속하는 구체적인 대상 하나다.
- **속성(property):** 대상이 다른 대상과 맺는 관계 또는 대상이 가진 값이다.

~~~text
클래스: 학습 주차
개체: 5주차
속성: 다루는 주제
~~~

5주차가 학습 주차라는 사실과, 학습 주차가 더 넓은 “학습 단위”에 속한다는 사실을 함께 적을 수 있다.

~~~text
5주차 → 학습 주차 → 학습 단위
~~~

- “학습 주차”는 여러 주차를 묶는 **종류**다.
- “5주차”는 그 종류에 속한 **개체**다.
- “다루는 주제”는 두 대상을 잇는 **관계**다.

속성에는 다른 대상을 가리키는 것과 값 자체를 가리키는 것이 있다.

| 속성 | 목적어 | 예 |
| --- | --- | --- |
| 다루는 주제 | 주제라는 대상 | 5주차 → RDF |
| 마감 날짜 | 날짜 리터럴 | 5주차 → 2026-10-07 |

이 구별은 나중에 질의할 때 중요하다. 다른 대상은 다시 관계를 따라갈 수 있다. 날짜 값은 보통 그 자체로 답에 사용한다.

### RDFS: 기본적인 종류와 계층

**RDFS(RDF Schema)**는 RDF 데이터에서 클래스와 속성의 기본 뜻을 설명하는 표준 어휘다. 아래 표의 이름은 데이터를 쓰는 사람이 임의로 만든 영어 단어가 아니라 표준에서 뜻을 정의한 표현이다.

| RDFS 표현 | 뜻 | 쉬운 예 |
| --- | --- | --- |
| rdf:type | 개체가 어떤 클래스에 속한다 | 5주차는 학습 주차다 |
| rdfs:subClassOf | 한 클래스가 더 넓은 클래스에 속한다 | 학습 주차는 학습 단위의 한 종류다 |
| rdfs:subPropertyOf | 한 관계가 더 넓은 관계의 한 종류다 | “필수 자료로 사용한다”는 “자료로 사용한다”의 세부 관계다 |
| rdfs:domain | 관계의 주어를 어떤 종류로 해석하는가 | “주제를 다룬다”의 주어는 학습 주차다 |
| rdfs:range | 관계의 목적어를 어떤 종류로 해석하는가 | “주제를 다룬다”의 목적어는 주제다 |

예를 들어 다음 두 사실이 있다.

~~~text
① 5주차는 학습 주차다.
② 모든 학습 주차는 학습 단위의 한 종류다.
~~~

- **명시된 사실:** 5주차는 학습 주차다.
- **규칙:** 학습 주차는 학습 단위의 하위 종류다.
- **추론된 결론:** 5주차는 학습 단위이기도 하다.

이처럼 사실과 규칙에서 따라오는 결론을 얻는 일을 **추론(inference)**이라고 한다.

RDFS 문법으로 적으면 다음과 같다.

~~~turtle
@prefix ex:   <https://example.org/study/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ex:week-05 a ex:StudyWeek .
ex:StudyWeek rdfs:subClassOf ex:LearningUnit .
~~~

- 첫 줄은 week-05가 StudyWeek라는 사실이다.
- 둘째 줄은 StudyWeek가 LearningUnit의 하위 클래스라는 규칙이다.
- 두 줄을 함께 쓰면 week-05가 LearningUnit에도 속한다고 추론한다.

관계 계층의 예를 실제 사실까지 이어 쓰면 다음과 같다.

~~~text
규칙: "필수 자료로 사용한다"는 "자료로 사용한다"의 세부 관계다.
사실: 5주차는 자료 A를 필수 자료로 사용한다.
결론: 5주차는 자료 A를 자료로 사용한다.
~~~

- 결론을 별도로 기록하지 않아도 규칙에서 따라온다.
- 저장소가 그 결론을 실제 질의 결과에 보여줄지는 추론 기능과 질의 방식에 달려 있다.

### Domain과 range는 입력 오류 검사와 다르다

- **domain:** 이 관계의 주어를 어떤 종류로 해석할지 정한다.
- **range:** 이 관계의 목적어를 어떤 종류로 해석할지 정한다.

“주제를 다룬다”의 domain을 학습 주차, range를 주제라고 선언한 경우를 보자.

~~~text
선언: hasTopic의 domain = StudyWeek, range = Topic
사실: notice-01 ──hasTopic──> rdf
RDFS 해석: notice-01은 StudyWeek, rdf는 Topic
~~~

- 사람은 notice-01이라는 이름을 보고 “공지에 주차용 관계를 썼다”고 의심할 수 있다.
- RDFS는 그 이름의 영어 뜻을 읽지 않는다. domain 선언에 따라 notice-01을 StudyWeek로 분류한다.
- 따라서 domain과 range를 “틀린 값을 저장하지 못하게 하는 검사”로 사용하면 기대와 다른 결과를 얻는다.
- 입력 데이터의 모양을 검사하려면 SHACL 같은 검증 규칙을 별도로 사용한다. ([W3C RDFS 표준](https://www.w3.org/TR/rdf-schema/), [W3C SHACL 표준](https://www.w3.org/TR/shacl/))

### OWL: 더 자세한 논리적 의미와 제약

**OWL(Web Ontology Language)**은 RDFS보다 자세한 논리적 의미를 표현한다.

- **서로 겹치지 않음:** “공지”와 “사람”은 같은 대상을 동시에 포함하지 않는다고 선언할 수 있다.
- **동등성:** 두 클래스가 같은 대상들의 집합을 가리킨다고 선언할 수 있다.
- **개수에 관한 규칙:** 어떤 관계의 값이 몇 개여야 하는지도 논리적으로 표현할 수 있다.

OWL은 일반적으로 **열린 세계 가정(open-world assumption)**을 사용한다.

- 현재 그래프에 “공지 A의 게시자”가 없으면 “게시자가 없다”라고 결론 내리지 않는다.
- 아직 알려지지 않은 게시자가 있을 수 있다고 해석한다.
- 따라서 필수 게시자 값이 빠졌는지 확인하려면 SHACL에서 “최소 한 개 있어야 한다”는 검증 규칙을 쓰는 편이 알맞다.
- 반대로 공지와 사람을 서로 겹치지 않는다고 선언한 뒤 한 대상을 두 클래스에 모두 넣으면, OWL에서는 논리적 **모순**을 검토할 수 있다.

여기서 **제약**이라는 단어를 주의해서 읽어야 한다.

| 무엇을 원하는가 | 사용하는 개념 | 결과 |
| --- | --- | --- |
| 개념이 논리적으로 어떻게 연결되는지 표현 | RDFS·OWL | 새 분류를 추론하거나 모순을 발견할 수 있다 |
| 입력 데이터가 정해진 형식과 개수를 지켰는지 검사 | SHACL 등 검증 규칙 | 위반한 데이터와 위반 이유를 보고할 수 있다 |

“공지의 제목 칸이 비었다”와 같은 입력 필드 검사와 OWL의 논리적 모순은 다른 문제다. ([W3C OWL 2 Primer](https://www.w3.org/TR/owl2-primer/))

### 스키마와 온톨로지의 차이

두 용어의 쓰임은 분야마다 조금 다르다. 이 노트에서는 질문의 초점을 기준으로 구별한다.

| 스키마 | 온톨로지 |
| --- | --- |
| 어떤 데이터를 어떤 모양으로 기록할지 정한다 | 그 데이터의 개념과 관계가 무슨 뜻인지 설명한다 |
| 예: 공지에 게시일 필드가 있다 | 예: 공지는 학습 주차를 알린다 |
| 형식, 필드, 허용 값에 관심이 많다 | 클래스, 관계, 계층, 논리적 의미에 관심이 많다 |

실제 RDF 프로젝트에서는 온톨로지를 “어휘의 스키마”라고 부르기도 한다. 따라서 이름만으로 판단하기보다 **구조를 정의하는지, 의미를 정의하는지, 입력을 검증하는지**를 구분하는 편이 정확하다.

같은 공지 데이터를 세 관점으로 적으면 차이가 더 분명하다.

| 관점 | 적는 내용 | 확인하려는 것 |
| --- | --- | --- |
| 데이터 구조 | 공지에는 제목과 게시일을 기록한다 | 어떤 필드가 있는가 |
| 온톨로지의 의미 | 공지는 학습 주차를 알릴 수 있다 | 각 개념과 관계가 무엇을 뜻하는가 |
| 검증 규칙 | 모든 공지의 게시일은 날짜 값 한 개여야 한다 | 실제 입력이 요구한 모양을 지켰는가 |

한 파일이나 시스템이 이 세 관점을 모두 담을 수도 있다. 중요한 것은 “스키마”라는 이름만 보고 의미 추론과 데이터 검증을 같은 동작으로 생각하지 않는 것이다.

## 4. SPARQL 맛보기: Wikidata에 질의한다

- **SPARQL:** RDF 그래프에서 원하는 관계의 모양을 찾는 질의 언어다.
- **찾는 단위:** 표의 행이 아니라 주어–술어–목적어 패턴이다.
- **변수:** 아직 모르는 자리에 물음표가 붙은 이름을 넣는다.

앞에서 사용한 작은 공지 그래프가 있다고 하자.

~~~text
5주차 ──주제──> RDF
6주차 ──주제──> SPARQL
~~~

“5주차의 주제는 무엇인가?”에는 주어와 술어가 정해져 있다.

- 아는 값: 주어는 5주차, 술어는 주제다.
- 찾을 값: 목적어에 들어갈 주제다.

~~~text
5주차 ──주제──> ?
~~~

Wikidata는 설치 없이 사용할 수 있는 [공개 질의 화면](https://query.wikidata.org/)을 제공한다. 아래 질의도 같은 원리로 작동한다. ([Wikidata 공식 안내](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service))

~~~sparql
PREFIX wd:  <http://www.wikidata.org/entity/>
PREFIX wdt: <http://www.wikidata.org/prop/direct/>

SELECT ?country
WHERE {
  wd:Q64 wdt:P17 ?country .
}
~~~

질의를 읽고 확인하는 순서는 다음과 같다.

1. 공개 질의 화면에서 새 질의를 열고 코드를 입력한다.
2. 실행 버튼을 누른다. 별도의 RDF 저장소는 필요하지 않다.
3. 결과 표의 country 열에서 나라 항목의 식별자를 확인한다.

한 줄씩 읽어 보면 다음과 같다.

| 질의 부분 | 의미 |
| --- | --- |
| wd:Q64 | 베를린이라는 항목의 ID |
| wdt:P17 | “어느 나라에 속하는가”라는 속성 |
| ?country | 아직 모르는 나라 값 |
| WHERE 안의 한 줄 | 베를린 — 나라 → ?country라는 관계를 찾는다 |
| SELECT ?country | 찾은 나라를 결과에 보여준다 |

- **Q로 시작하는 ID:** 베를린 Q64처럼 대상인 항목을 식별한다.
- **P로 시작하는 ID:** 나라 P17처럼 속성을 식별한다.
- **PREFIX:** 긴 식별자를 짧게 적는 별칭 선언이다.
- **?country:** 아직 모르는 나라가 들어갈 변수다.
- **예상 결과:** 독일을 뜻하는 Q183 같은 ID가 나온다. Wikidata 데이터가 바뀌면 결과도 달라질 수 있다. ([베를린 Q64](https://www.wikidata.org/wiki/Q64), [나라 P17](https://www.wikidata.org/wiki/Property:P17))

여기서 wd와 wdt는 역할이 다르다.

| 접두어 | 가리키는 것 | 이 질의의 예 |
| --- | --- | --- |
| wd: | Wikidata의 대상 항목 | wd:Q64는 베를린 |
| wdt: | 간단히 사용할 수 있는 직접 속성 | wdt:P17은 나라 관계 |

- 처음에는 **wd는 대상, wdt는 직접 관계**라고 읽으면 된다.
- 같은 P17이라도 접두어가 달라지면 Wikidata 데이터 구조에서 가리키는 위치가 달라질 수 있다.

나라의 ID뿐 아니라 표시 이름까지 보고 싶다면, 찾은 나라에 이름을 붙이는 패턴을 하나 더 적을 수 있다.

~~~sparql
PREFIX wd:   <http://www.wikidata.org/entity/>
PREFIX wdt:  <http://www.wikidata.org/prop/direct/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?country ?name
WHERE {
  wd:Q64 wdt:P17 ?country .
  ?country rdfs:label ?name .
  FILTER(LANG(?name) = "ko")
}
~~~

- **첫 번째 패턴:** 나라의 ID를 찾는다.
- **두 번째 패턴:** 바로 그 나라의 이름을 찾는다. 같은 ?country 변수를 쓰므로 두 패턴이 연결된다.
- **FILTER:** 이름 중 한국어 값만 남긴다. 해당 언어의 이름이 없으면 결과가 나오지 않을 수 있다.

Wikidata의 **wdt:P17**은 직접 값을 보는 간단한 질의에 편리하다. 기간이나 출처까지 보려면 주장에 붙은 맥락을 살펴야 한다.

~~~text
주장: 베를린 ──어느 나라에 속함──> 독일
한정자: 이 주장이 적용되는 기간
출처: 이 주장을 뒷받침하는 자료
~~~

- **Statement:** “베를린 — 나라 → 독일”이라는 주장 자체다.
- **Qualifier:** 그 주장이 적용되는 기간처럼 주장을 보충한다.
- **Reference:** 그 주장의 출처를 가리킨다.
- **직접 속성 wdt:** 간단한 값 질의에 사용한다. 질의 결과 한 줄만으로 기간과 출처를 확인했다고 생각해서는 안 된다.
- **상세 구조:** 기간·출처가 답에 필요하면 p:, ps:, pq: 등의 접두어로 statement 구조를 질의한다. 현재 단계에서는 접두어 암기보다 두 질의가 다루는 정보의 깊이를 구별하는 것이 중요하다. ([Wikidata Query Service 설명](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service))

## 5. 프로퍼티 그래프와 RDF 트리플 스토어

- **공통점:** 두 방식 모두 대상과 관계를 연결한다.
- **차이:** 기본 데이터 단위와 관계에 추가 정보를 붙이는 방법이 다르다.

### 같은 사실을 두 방식으로 그리기

공지의 “5주차는 RDF를 다룬다”를 프로퍼티 그래프로 쓰면 다음과 같다.

~~~text
(:StudyWeek {number: 5})
    -[:HAS_TOPIC {source: "공지 A"}]->
(:Topic {name: "RDF"})
~~~

- **노드:** 5주차와 RDF라는 대상이다.
- **레이블:** StudyWeek와 Topic처럼 노드의 종류를 표시한다.
- **관계:** HAS_TOPIC처럼 두 노드를 잇는 방향 있는 연결이다.
- **속성:** number와 name은 노드의 값이고, source는 관계에 붙은 값이다. Neo4j가 이 모델을 사용한다. ([Neo4j 공식 개념 설명](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/))

RDF로 쓰면 관계 하나가 트리플이다.

~~~turtle
@prefix ex: <https://example.org/study/> .

ex:week-05 ex:hasTopic ex:rdf .
ex:rdf ex:label "RDF"@ko .
~~~

- RDF에서는 관계의 이름과 대상에 IRI를 부여한다.
- 기본 트리플에는 주어·술어·목적어 세 자리만 있다. 관계에 “근거: 공지 A”를 붙이려면 그 **주장 자체**를 별도 대상으로 표현하거나 출처별 그래프를 쓰는 등 추가 모델링이 필요하다.

개념적으로는 다음처럼 생각할 수 있다. 아래 그림은 RDF 문법이 아니라 “관계에 근거를 붙이려면 무엇을 더 표현해야 하는가”를 나타낸다.

~~~text
[주장 1]
  ├─ 주어 ──> 5주차
  ├─ 술어 ──> hasTopic
  ├─ 목적어 → RDF
  └─ 근거 ──> 공지 A
~~~

### 두 진영의 철학 차이

| 비교 기준 | 프로퍼티 그래프, Neo4j 계열 | RDF와 트리플 스토어 |
| --- | --- | --- |
| 기본 단위 | 노드, 관계, 각 요소의 속성 | 주어–술어–목적어 트리플 |
| 식별 방식 | 애플리케이션에서 쓰는 노드 ID와 속성을 설계 | IRI를 기본 식별자로 사용 |
| 관계의 추가 정보 | 관계에 속성을 직접 붙이기 쉽다 | 주장·출처를 추가 트리플 등으로 표현한다 |
| 의미의 공유 | 보통 해당 서비스의 모델을 중심으로 사용 | 표준 어휘와 IRI로 다른 데이터와 연결하기 쉽다 |
| 대표 질의 언어 | Cypher | SPARQL |

같은 “5주차의 주제는?”이라는 질문을 두 질의 언어로 적으면 다음과 같다.

~~~cypher
MATCH (:StudyWeek {number: 5})-[:HAS_TOPIC]->(topic:Topic)
RETURN topic.name
~~~

~~~sparql
PREFIX ex: <https://example.org/study/>

SELECT ?topic
WHERE {
  ex:week-05 ex:hasTopic ?topic .
}
~~~

- **Cypher:** StudyWeek 노드에서 HAS_TOPIC 관계를 따라가 Topic 노드의 이름 값을 가져온다.
- **SPARQL:** week-05 IRI와 hasTopic IRI를 고정하고 목적어 자리에 오는 IRI를 찾는다.
- **결과 표현의 차이:** 위 Cypher는 주제의 이름 문자열을 돌려주고, SPARQL은 주제의 식별자를 돌려준다. 같은 형태의 결과를 비교하려면 SPARQL에 이름을 찾는 패턴을 더해야 한다.

선택 기준도 목적에 따라 달라진다.

- 앱 안에서 관계를 따라 탐색하고 관계의 추가 값을 자주 다룬다면 프로퍼티 그래프 모델이 직관적일 수 있다.
- 다른 데이터 제공자와 식별자·어휘를 공유하고 표준 방식으로 교환하려면 RDF가 유리할 수 있다.
- 이 경계는 절대적이지 않다. 프로퍼티 그래프도 외부 ID를 저장할 수 있고 RDF도 조직 내부의 경로 탐색에 사용할 수 있다.
- **트리플 스토어**는 RDF를 저장·질의하는 시스템이다. RDF라는 데이터 모델과 저장 제품을 같은 말로 쓰지 않는다.

## 6. W3에서 답하지 못한 질문을 화이트보드에 그리기

앞서 답변 근거가 부족한 질문 중 하나는 다음과 같다.

> “공결 신청 후 승인까지 며칠 걸려?”

- **찾을 수 있는 정보:** 공결 신청 절차가 담긴 공지다.
- **질문이 요구하는 정보:** 신청 뒤 승인까지 걸리는 기간이다.
- **차이:** 신청 방법을 알아도 처리 기간을 계산할 수는 없다.

화이트보드에는 확인된 관계와 질문에 필요한 관계를 나누어 그린다.

~~~text
[공결 신청] ──hasProcedure──────> [신청 절차]       공지에서 확인 가능
     │
     └────approvalDuration──> [?일]              근거 없음
~~~

| 그림에서 보이는 것 | 질문과의 관계 |
| --- | --- |
| 공결 신청 → 신청 절차 | 신청 방법을 설명한다 |
| 공결 신청 → 승인 소요 기간 | 이 질문에 필요한 관계다 |
| 두 번째 관계가 비어 있음 | 현재 자료만으로 며칠인지 답할 수 없다 |

여기서 **물음표는 실제 그래프에 “?일”이라는 값을 저장한다는 뜻이 아니다.** 답을 얻으려면 이 자리에 기간 값이 필요하지만, 현재는 근거가 없다는 표시다.

- 공지에 “신청 절차”가 있다고 해서 approvalDuration 값을 만들지 않는다.
- 승인 날짜와 신청 날짜가 둘 다 실제로 확인된다면 그 차이를 계산할 수 있다. 한 날짜만 있거나 날짜의 의미가 불분명하면 계산하지 않는다.
- 그래프를 그리는 목적은 없는 답을 채우는 것이 아니라 **비어 있는 근거가 무엇인지** 드러내는 데 있다.

여러 사실을 이어야 하는 질문도 같은 방식으로 그릴 수 있다. 앞서 답을 보류한 다른 질문인 “부산에 같이 간 사람 중 같은 회사에 다니는 사람은 누구야?”를 보자.

이 질문에 답하려면 다음 두 조건을 **같은 두 사람**에게 적용해야 한다.

1. 두 사람이 같은 부산 여행에 참여했다.
2. 두 사람이 같은 회사에 재직한다.

~~~text
[사람 A] ──참여──> [부산 여행] <──참여── [사람 B]
    │                                     │
    └────────재직──> [같은 회사] <──재직──┘
~~~

| 필요한 간선 | 확인할 자료 |
| --- | --- |
| 사람 A → 부산 여행 | 여행 참가 사실을 적은 자료 |
| 사람 B → 부산 여행 | 같은 여행에 참가했다는 자료 |
| 사람 A → 회사 | A의 재직 정보를 뒷받침하는 자료 |
| 사람 B → 같은 회사 | B의 재직 정보를 뒷받침하는 자료 |

이 그림은 **답의 형태**를 보여줄 뿐, 실제 사람이나 회사 관계가 확인되었다는 뜻이 아니다. 네 간선 중 하나라도 근거가 없으면 “같은 회사에 다니는 두 사람”이라는 결론을 낼 수 없다. 특히 “같이 갔다”는 표현만으로 동일 회사에 다닌다고 추측해서는 안 된다.

화이트보드에 질문을 옮길 때는 다음 순서로 생각하면 된다.

1. 질문에 등장하는 대상이 무엇인지 적는다.
2. 답을 얻으려면 대상 사이에 어떤 관계가 있어야 하는지 화살표로 잇는다.
3. 각 화살표를 뒷받침하는 원문이 있는지 확인한다.
4. 빠진 화살표나 서로 충돌하는 근거를 표시한다.

마지막으로 **질문에 필요한 관계 그림**과 **실제 자료에서 확인해 저장한 그래프**를 구별한다.

- 질문 그림에는 아직 찾지 못한 간선도 그릴 수 있다. 이 간선은 “필요한 정보”를 표시한다.
- 저장한 그래프에는 근거를 확인한 간선만 넣는다.
- 저장한 그래프에 간선이 없다는 것은 현재 자료에서 확인하지 못했다는 뜻이다. 현실에 그런 관계가 없다는 증명은 아니다.
