# Advanced RAG 패턴 - Self-RAG부터 GraphRAG까지

## 한 줄 요약

Advanced RAG는 기본 RAG의 “한 번 검색하고, 바로 답한다”는 고정 흐름을 보완하는 설계 묶음이다. 검색이 필요한지 점검하거나, 검색 실패를 보정하거나, 여러 단계로 정보를 찾거나, 관계 그래프를 이용하는 방식이 여기에 속한다.

> 이 문서는 [Wikidocs의 Advanced RAG 패턴](https://wikidocs.net/338696)에서 제시한 학습 범위를 따라 구성했다. 다만 각 패턴의 정의와 세부 동작은 원 논문과 공식 프로젝트 문서를 우선했다.

## 출발점: 기본 RAG

```text
질문 → 검색 → 상위 문서 청크 → LLM 답변
```

기본 RAG는 단순하고 빠르지만 다음을 스스로 처리하지 못한다.

- 이 질문에 정말 검색이 필요한가?
- 가져온 문서가 질문에 충분히 관련 있는가?
- 필요한 사실이 여러 문서에 흩어져 있으면 어떻게 연결할 것인가?
- 문서의 명시적 관계를 따라 찾아야 하면 어떻게 할 것인가?

아래 패턴들은 각각 이 중 한 문제를 해결하려는 것이다. 이름이 비슷해도 같은 방법은 아니며, 모든 패턴을 함께 쓸 필요도 없다.

## 전체 비교

| 패턴 | 핵심 질문 | 핵심 동작 | 적합한 상황 | 주요 비용 |
| --- | --- | --- | --- | --- |
| Self-RAG | 검색·답변을 믿어도 되는가? | 검색 필요성·관련성·근거성을 반성 | 근거성과 사실성이 특히 중요할 때 | 별도 학습 또는 추가 판정 비용 |
| CRAG | 검색 결과가 부실하면? | 검색 품질을 평가하고 보정 경로 선택 | 검색 결과가 자주 불충분할 때 | 평가기·대체 검색 경로 |
| Agentic RAG | 어떤 도구를 어떤 순서로 쓸까? | LLM이 도구와 다음 행동을 결정 | 여러 데이터 소스·복합 작업 | 여러 LLM 호출, 제어 난이도 |
| Multi-hop RAG | 한 번에 찾을 수 없으면? | 중간 결과로 다음 검색을 이어 감 | 연결·비교·교집합 질문 | 홉마다 오류가 누적 |
| GraphRAG | 문서 속 관계를 어떻게 활용할까? | 엔티티·관계를 그래프로 추출·탐색 | 관계 중심·전역적 질문 | 그래프 구축과 품질 검증 비용 |

## 1. Self-RAG: 검색과 답변을 스스로 점검하기

### 핵심 개념

Self-RAG(Self-Reflective Retrieval-Augmented Generation)는 검색을 무조건 실행하지 않고, 검색된 문서의 관련성 및 생성한 답변의 근거성을 점검하도록 학습한 RAG 방법이다.

원 논문의 Self-RAG는 단순히 프롬프트로 “스스로 검토해”라고 지시하는 방식이 아니다. `Retrieve`, `IsRel`, `IsSup`, `IsUse` 같은 **reflection token**을 생성하도록 모델을 학습해, 검색·관련성·근거성·답변 유용성을 제어한다.

```text
질문
  → 검색이 필요한가 판단
  → (필요하면) 문서 검색
  → 문서가 관련 있는가 판단
  → 답변 생성
  → 답변이 문서에 뒷받침되는가 판단
  → 답변 또는 보류
```

### 쉽게 말하면

기본 RAG가 “찾은 문서를 읽고 바로 답하는 사람”이라면, Self-RAG는 “이 자료가 질문과 맞는지, 내가 쓴 문장이 자료에 실제 있는지 한 번 더 확인하는 사람”에 가깝다.

### 주의할 점

일반 LLM 호출 뒤에 평가 프롬프트를 추가하는 워크플로는 Self-RAG의 아이디어를 참고한 설계일 수는 있어도, 논문에서 말하는 학습된 Self-RAG와 동일하다고 부르면 정확하지 않다. 또한 모델 자신의 판정도 틀릴 수 있으므로, 자기 점검은 보증이 아니다.

## 2. CRAG: 검색 결과가 나쁘면 보정하기

### 핵심 개념

CRAG(Corrective Retrieval-Augmented Generation)는 검색 결과의 품질을 평가하고, 그 결과에 따라 검색을 그대로 쓰거나, 일부만 쓰면서 추가 검색을 하거나, 기존 결과를 버리고 다른 정보원을 찾는 방법이다.

원 논문은 경량 retrieval evaluator가 검색 문서의 품질을 평가해 신뢰도에 따른 다른 검색 행동을 촉발하도록 설계한다. 또한 검색 문서에서 핵심 정보에 집중하고 무관한 정보를 걸러내는 분해-재구성 과정을 제안한다.

```text
질문 → 초기 검색 → 검색 품질 평가
                       ├─ 좋음: 결과 사용
                       ├─ 애매함: 관련 부분 사용 + 추가 검색
                       └─ 나쁨: 결과를 대체하거나 다른 정보원 탐색
```

### Self-RAG와 차이

- **Self-RAG**는 검색 필요성, 문서 관련성, 생성 답변의 근거성까지 모델이 반성하도록 한 방법이다.
- **CRAG**는 특히 “이번 검색 결과가 쓸 만한가, 부족하다면 어떻게 고칠까”에 초점을 둔다.

둘 다 품질 점검을 포함하지만, 같은 논문이나 같은 구조가 아니다.

### 주의할 점

대체 검색을 한다고 해서 정답을 찾는 것은 아니다. 검색 범위가 넓어질수록 비용·지연·출처 신뢰성 관리가 함께 필요하다.

## 3. Agentic RAG: 고정 파이프라인 대신 행동을 선택하기

### 핵심 개념

Agentic RAG는 하나의 고정된 RAG 알고리즘 이름이라기보다, LLM 에이전트가 질문을 보고 **어떤 도구를 어떤 순서로 사용할지** 선택하는 RAG 아키텍처 범주다.

```text
질문
  → 에이전트 계획
  → 키워드 검색 / 벡터 검색 / DB 질의 / 웹 검색 등 도구 호출
  → 결과가 부족한지 판단
  → 필요하면 다른 도구 또는 다음 질의 호출
  → 근거를 모아 답변
```

예를 들어 “이번 달 매출 상위 상품의 후기 요약”은 매출 DB 조회와 후기 문서 검색이 모두 필요하다. Agentic RAG는 한 검색기만 항상 호출하는 대신, 필요한 도구를 조합할 수 있다.

### 장점과 한계

- 장점: 데이터 유형과 질문이 다양한 상황에 유연하다.
- 한계: 모델이 잘못된 도구를 고르거나, 불필요한 루프에 빠지거나, 호출 횟수가 늘어나 비용과 시간이 커질 수 있다.

따라서 사용할 수 있는 도구, 최대 호출 횟수, 중단 조건, 출처 기록을 명확히 제한해야 한다.

## 4. Multi-hop RAG: 중간 답을 다음 검색에 쓰기

### 핵심 개념

Multi-hop RAG는 한 번의 검색으로 답할 수 없는 질문을 여러 검색·추론 단계로 나누어 푼다. 각 단계의 결과가 다음 단계의 질의 또는 판단 재료가 된다.

```text
질문: “A 회사 CEO가 졸업한 대학의 설립 연도는?”

Hop 1: “A 회사 CEO” → 사람 P
Hop 2: “사람 P 졸업 대학” → 대학 U
Hop 3: “대학 U 설립 연도” → 연도 Y
답변: Y, 그리고 각 홉의 근거
```

여기서 hop은 단순히 검색을 한 번 했다는 기계적 횟수보다, 답에 필요한 사실 하나를 찾아 다음 연결로 넘어가는 **추론·검색 단계**로 이해하는 편이 정확하다.

### 왜 어려운가

첫 홉에서 사람을 잘못 찾으면 이후 홉도 모두 틀어진다. 또 필요한 문서가 모두 검색되더라도 LLM이 동일 인물·조직·시점을 잘못 연결할 수 있다. HotpotQA는 이런 다중 문서 추론과 supporting facts를 평가하기 위해 만들어진 대표 벤치마크다.

### Agentic RAG와 관계

Multi-hop RAG는 “여러 단계의 검색”이라는 문제 유형 또는 흐름이다. Agentic RAG는 그 단계를 어떤 도구로, 언제 계속할지를 결정하는 제어 방식이다. 따라서 Agentic RAG가 Multi-hop RAG를 구현하는 한 방법이 될 수 있지만 둘은 동의어가 아니다.

## 5. GraphRAG: 엔티티와 관계를 먼저 구조화하기

### 핵심 개념

GraphRAG는 문서에서 엔티티(사람·조직·장소 등)와 관계를 추출해 그래프 형태의 지식 구조를 만들고, 이 구조와 원문을 이용해 질문의 컨텍스트를 구성하는 접근이다.

```text
[사람 P] ── CEO ──> [회사 A]
[사람 P] ── 졸업 ──> [대학 U]
[대학 U] ── 설립연도 ──> [연도 Y]
```

관계가 구조화되어 있으면 “A와 연결된 사람은?”, “두 조건을 모두 만족하는 대상은?” 같은 질문에서 문서 청크 유사도만으로 찾는 것보다 명시적으로 탐색할 수 있다.

### Microsoft GraphRAG는 무엇을 하는가

Microsoft의 GraphRAG 인덱싱 파이프라인은 비정형 텍스트에서 LLM으로 엔티티·관계·주장을 추출하고, 엔티티의 커뮤니티를 찾고, 커뮤니티 요약을 만든다. 텍스트 임베딩도 함께 생성한다. 즉, “그래프만 쓰는 검색”이 아니라 그래프와 텍스트 표현을 함께 다루는 RAG 연구 구현이다.

### 주의할 점

GraphRAG는 관계 중심 질문에 도움이 될 수 있지만, 자동 추출한 엔티티·관계 자체가 틀리면 그 오류가 검색과 답변으로 전파된다. 그래프를 만드는 비용도 작지 않다. Microsoft 공식 문서도 GraphRAG 인덱싱은 비용이 클 수 있으니 작은 데이터로 시작하라고 안내한다.

## 어떤 패턴을 골라야 하는가

```text
정확한 단일 사실을 묻는다
  → 기본 RAG 또는 하이브리드 검색

검색 결과가 자주 엉뚱하거나 부족하다
  → CRAG처럼 검색 품질 평가·보정

답변마다 근거를 더 엄격히 확인해야 한다
  → Self-RAG의 반성 개념, 별도 근거성 평가

여러 도구·데이터 소스를 순서대로 써야 한다
  → Agentic RAG

사실 A → B → C를 연결해야 한다
  → Multi-hop RAG

사람·조직·사건 사이의 관계를 탐색해야 한다
  → GraphRAG 또는 지식 그래프 질의
```

복잡한 패턴이 자동으로 더 좋은 것은 아니다. 먼저 기본 검색의 Recall@k와 근거성을 확인하고, 실제 실패 유형이 반복될 때 그 실패를 해결하는 패턴을 추가하는 것이 타당하다.

## 이 문서를 공부했다는 말의 정확한 표현

“기본 RAG 이후의 고급 RAG 패턴을 비교했다. Self-RAG의 자기 반성, CRAG의 검색 보정, Agentic RAG의 도구 선택, Multi-hop RAG의 단계적 검색, GraphRAG의 관계 기반 컨텍스트 구성을 공부했고, 각 패턴이 해결하려는 실패 유형과 비용을 정리했다.”
