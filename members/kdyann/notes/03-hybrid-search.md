## 한 줄 요약

키워드와 벡터 검색의 순위를 RRF로 합치고 검색한 원문에 근거해 답하되, 여러 문서의 사실과 관계를 연결해야 하는 질문에서 RAG의 한계를 살펴본다.

## 핵심 개념

- 하이브리드 검색: 키워드 일치를 보는 BM25와 의미 유사성을 보는 벡터 검색의 결과를 결합한다.
- RRF (Reciprocal Rank Fusion): 검색기의 원래 점수 대신 문서 순위를 이용해 결과를 융합한다.
- RAG: 질문에 관련된 원문을 검색하고 컨텍스트로 조립해 LLM 답변의 근거로 제공한다.
- 근거 인용: 답변의 주요 주장을 실제로 뒷받침하는 원문 발췌와 출처 URL을 연결한다.
- 다중 홉 질문: 여러 문서에서 사실을 찾고 그 관계를 연결해야 답할 수 있는 질문이다.

## 상세 정리

### RRF: 점수 대신 순위를 합치는 이유

BM25 점수와 벡터 유사도는 척도와 분포가 달라 그대로 더하면 한쪽이 과도하게 영향을 줄 수 있다. 점수를 정규화해 합칠 수도 있지만, 질문마다 달라지는 점수 분포와 정규화 방식·가중치를 고려해야 한다. 같은 범위로 맞춘 점수가 같은 관련도 확신을 뜻하는 것도 아니다.

RRF는 각 검색기의 문서 순위만 이용하므로 서로 다른 점수 척도를 맞추는 과정을 생략한다. 대신 원래 점수에서 1위와 2위가 얼마나 차이 났는지는 잃는다. 각 목록의 순위를 1부터 시작하면 문서 d의 융합 점수는 다음과 같다.

```text
RRF(d) = Σ 1 / (c + rank_i(d))
```

문서가 검색기 i의 반환 목록에 없으면 그 목록의 기여는 0이다. 상위 순위일수록 더 많이 기여하고, 여러 목록에 등장한 문서는 각 기여를 합산한다. c는 순위에 따른 가중치 감소를 조절하는 상수이며 Elasticsearch의 기본값은 60이다. 순위를 합쳤다고 검색 품질이 반드시 좋아지는 것은 아니므로 실제 질문에서 결과를 확인해야 한다.

### RAG: 질문에서 근거 있는 답변까지

RAG는 **질문 → 검색 → 컨텍스트 조립 → LLM 답변 + 근거 인용**의 흐름으로 진행한다. 검색 단계에서 관련 문서를 찾고, 컨텍스트 조립 단계에서 중복을 제거하며 필요한 원문 발췌·문서 ID·출처 URL을 함께 제공한다. LLM은 이 근거에 따라 답하고, 근거가 없거나 충돌하면 추측 대신 모르는 부분을 밝혀야 한다.

[위키독스의 기본 RAG 체인](https://wikidocs.net/376177)은 이 흐름을 리트리버로 문서를 찾고, 검색한 내용을 프롬프트의 컨텍스트에 넣어 답을 생성한 뒤, 문서 메타데이터에서 출처를 반환하는 예제로 설명한다. 검색한 문서를 답과 함께 보여주는 방법을 이해하는 데 참고했다.

[이글루코퍼레이션의 RAG 소개](https://www.igloo.co.kr/security-information/ragretrieval-augmented-generation-llm%EC%9D%98-%ED%95%9C%EA%B3%84%EC%99%80-%EB%B3%B4%EC%99%84-%EB%B0%A9%EB%B2%95/)는 LLM의 환각·최신성 한계에서 출발해 외부 데이터를 검색하고 그 결과로 프롬프트를 보강하는 흐름을 설명한다. 검색을 답변 생성 앞에 붙이는 이유를 이해하는 배경 자료로 참고했다.


### 다중 홉 질문의 한계와 지식 그래프로 이어지는 질문

“내가 쓴 도구 중 참고 작성자도 사용한 도구는?”에 답하려면 내 글에서 도구를 찾고, 다른 글에서 같은 도구와 사용 주체·작업을 확인해야 한다. 이전 임시 실험에서는 전체 질문으로 놓쳤던 Claude Code 참고 글을 도구 이름으로 다시 검색해 활용 팁과 연동 설명을 찾았다. 이때 답변은 격리된 Codex LLM으로 생성했고 검색 범위와 필터도 함께 바꿨으므로, 질문 분해만의 효과로 볼 수는 없다. 무엇보다 활용 권장과 연동 설명은 참고 작성자의 직접 사용을 증명하지 않았다.

현재 통합 v1은 질문마다 독립적으로 검색한 근거를 OpenAI LLM에 전달하며, 앞의 도구 추출·후속 검색을 자동으로 수행하지는 않는다. 초기 실제 API 답변에서는 내 글만 인용해 Claude Code를 ‘참고 게시물에서도 사용한 공통 도구’라고 단정하고, 일반적인 ‘클로드’의 스킬 설명을 Claude Code의 실제 사용 작업으로 연결했다. 인용문이 원문에 있어도 사용 주체와 도구의 관계를 잘못 추론하면 답변은 틀릴 수 있다는 사례!

이후 의미 검토를 붙인 재실행에서는 근거 없는 공통 사용 주장을 제거했다. 다른 재실행에서는 제공된 원문과 일치하지 않는 인용을 차단했는데, 이는 관계 추론 오류와는 별개의 문제다. 직접 작성한 잘못된 공통 사용 문장을 검토에 넣어 차단한 확인도 했지만, 이 결과는 검토 단계만 확인한 것이지 다중 홉 검색의 성공은 아니다.

반대로 내 글의 ‘제가’를 사용자와 연결하지 못하거나, 묻지 않은 다른 플랫폼·추가 도구까지 요구해 보류한 검토 오류도 있었다. 검색 누락, 잘못된 관계 추론, 원문에 없는 사실, 검토의 과도한 보류를 구분해야 실패 원인을 제대로 볼 수 있다. 원문에 맞는 기능·다운로드 답변도 검토 단계에서 지나치게 부분 답변으로 분류된 적도 있었다. 

여기서 **“검색은 문서를 찾는다. 사실과 관계를 찾으려면 무엇이 필요한가?”**라는 질문이 생겼다. 도구가 ‘언급됐다’, 활용을 ‘권장한다’, 다른 도구와 ‘연동된다’, 누군가 ‘직접 사용했다’는 서로 다른 관계다.

## 예시

### 질문 

> 내가 디자인 시스템을 만들 때 쓴 도구 중, 참고 게시물에서도 사용한 도구는 무엇이고 거기서는 어떤 작업에 활용했어?

내가 Pen.dev와 Claude Code를 쓴 것은 확인했지만, **참고 작성자도 직접 사용한 공통 도구와 실제 작업은 확정하지 못했다**. 이전 임시 후속 검색은 [Claude Code 활용 팁](https://www.instagram.com/p/DcpCTaNE2c7/)의 “Start with codebase Q&A”, “Plan before coding”과 [Graphify 설명](https://www.instagram.com/p/DcSAFHgCMhP/)의 “It plugs into tools like Claude Code”를 찾았다. 이는 활용 권장·연동 근거이며 작성자의 직접 사용 근거가 아니다. 수집된 참고 캡션에서는 Pen.dev도 찾지 못했다. 더 관련된 문서를 찾는 것과 질문에 필요한 관계가 실제로 기록되어 있는지는 따로 확인해야 한다.
