# **Hybrid retriever : 벡터로 들어가고 그래프로 넓힌다**

앞에서는 GraphRAG가 그래프를 읽는 방법으로 Local Search, Global Search, Text2Cypher를 살펴봤다. 그중 지금 내 데이터에 가장 잘 맞는 것은 특정 Entity에서 시작해 주변 관계를 따라가는 **Local Search**였다.

그런데 Local Search에는 시작부터 문제가 하나 있다. 그래프를 따라가려면 **어디서 출발해야 하는지 먼저 알아야 한다.** 

예를 들어 사용자가 “졸업 프로젝트에서 작업 큐로 사용한 기술을 다른 프로젝트에서도 썼나?”라고 물었다고 해보자. 사람인 나는 여기서 ‘졸업 프로젝트’가 내가 진행한 **AI 코드 보안 분석 프로젝트 SeCause**를 가리킨다는 것을 알지만, 그래프에는 `secause`라는 이름으로 저장되어 있다. 질문과 노드 이름이 정확히 일치하지 않으면 단순 문자열 비교만으로는 출발점을 찾기 어렵다.

여기서 기존에 만들었던 벡터 검색을 다시 활용할 수 있다. 

**벡터 검색은 어디서 시작할지를 찾고, 그래프는 그 지점에서 어디까지 이동할지를 결정한다.** 이것이 이번에 만들 하이브리드 리트리버의 핵심이다.

## **1. 벡터와 그래프는 서로 다른 문제를 해결한다**

W3에서 사용한 벡터 검색은 표현이 조금 달라도 의미가 비슷한 문서를 찾는 데 강했다. 

반면 질문과 의미적으로 비슷하지 않은 문서까지 넘어가는 데는 한계가 있었다. 
실제로 “SeCause 작업 큐에 사용한 기술을 다른 프로젝트에서도 사용했는가?”라는 질문에서는 SeCause 관련 문서는 찾았지만, 질문에 `Redis`나 다른 프로젝트 이름이 없었기 때문에 프로젝트 **팀 빌딩 서비스 TEAMFICIAL**이나 **기업 연계 프로젝트 직행**의 Redis 사용 기록까지 검색하지 못했다.

그래프는 반대다. 일단 SeCause라는 출발점만 찾으면 저장된 관계를 따라 Redis에 도달하고, 다시 Redis를 사용하는 다른 프로젝트까지 이동할 수 있다.

|  | **벡터 검색** | **그래프 탐색** |
| --- | --- | --- |
| 잘하는 것 | 표현이 달라도 비슷한 정보를 찾음 | 이미 연결된 사실을 따라감 |
| 약한 부분 | 질문에 없는 대상으로 넘어가기 어려움 | 출발 노드를 먼저 찾아야 함 |
| X01에서 | SeCause 문서를 찾음 | Redis를 거쳐 다른 프로젝트까지 이동 |

그래서 둘 중 하나를 고르는 대신 역할을 나눈다.

**벡터 검색 → 출발점 발견 → 그래프 탐색 → 질문에 없던 관련 정보까지 확장**

## **2. 그래프의 출발점은 어떻게 찾을까?**

한 가지 방법은 그래프의 노드 자체를 벡터로 검색하는 것이다. 예를 들어 `SeCause` 노드에 “GitHub 연동 AI 코드 보안 분석 프로젝트” 같은 설명을 붙여 임베딩해두면, 사용자가 “졸업 프로젝트”라고 물어도 의미가 비슷한 SeCause 노드를 찾을 수 있다.

하지만 현재 내 그래프의 노드는 `secause`, `redis`처럼 이름 위주로 되어 있다. 벡터 검색을 위해 노드 설명을 새로 만들고 임베딩까지 관리하는 것은 이번 실험에 비해 일이 커진다.

다행히 W5에서 이미 다른 길을 만들어두었다. 그래프를 만들 때 각 관계가 **어떤 원문 청크에서 추출됐는지 `chunk_id`를 저장**했다. 당시에는 추출한 사실의 근거를 다시 확인하기 위해 넣은 정보였는데, 이번에는 반대로 **검색된 청크에서 그래프로 들어가는 통로**로 사용할 수 있다.

흐름은 다음과 같다.

```
자연어 질문
→ 기존 BM25 + Vector + RRF 검색
→ 관련 청크 발견
→ chunk_id로 해당 청크에서 추출된 관계 조회
→ 연결된 Entity를 그래프 진입점으로 사용
→ 주변 관계 확장
```

예를 들어 기존 검색이 SeCause 관련 청크를 찾아냈다면, 그 청크의 `chunk_id`로 그래프를 조회한다. 그러면 해당 청크에서 추출된 SeCause, Redis, TechnologyUse 등의 노드를 찾을 수 있고, 여기서부터 그래프 탐색을 시작하면 된다.

즉 새로운 노드 검색기를 만드는 대신 **W3에서 만든 검색기와 W5에서 만든 provenance 정보를 연결한다.** 처음에는 인용과 근거 검증을 위해 저장했던 `chunk_id`가 이번에는 검색 결과와 그래프를 연결하는 진입로가 된 셈이다.

## **3. 기존 개인 데이터 에이전트 v1에 그래프를 붙이면?**

W3에서 만든 개인 데이터 에이전트 v1의 검색 과정은 다음과 같았다.

```
질문
→ BM25 + Vector
→ RRF
→ 관련 청크 top-k
→ LLM
→ 답변
```

v2에서는 이 구조를 버리지 않는다. 기존 검색 결과를 그대로 사용하면서, 그 청크에서 그래프로 진입해 **추가로 필요한 정보를 가져오는 단계만 붙인다.**

예를 들어 다시 다음 질문을 해보자.

“AI 코드 보안 분석 프로젝트 SeCause에서 작업 큐에 사용한 기술을 다른 프로젝트에서도 사용했나?”

v1에서는 먼저 BM25와 Vector Search 결과를 RRF로 합쳐 관련 청크를 찾는다. 이 과정에서 SeCause의 분석 흐름을 설명하는 청크는 찾지만, TEAMFICIAL이나 직행의 Redis 사용 기록은 찾지 못했다.

v2에서는 여기서 한 단계 더 진행한다.

```
질문
↓
BM25 + Vector + RRF
↓
SeCause 관련 청크
↓
chunk_id로 그래프 진입
↓
SeCause → TechnologyUse → Redis
↓
Redis → 다른 TechnologyUse → TEAMFICIAL / 직행
↓
새롭게 발견한 관계의 chunk_id 확인
↓
TEAMFICIAL / 직행의 원문 청크 회수
↓
기존 검색 청크 + 그래프 사실 + 추가 원문
↓
LLM 답변
```

여기서 가장 중요한 부분은 **그래프에서 관계만 찾고 끝내지 않는다는 것**이다.

그래프를 통해 “TEAMFICIAL도 Redis를 사용했다”는 사실을 찾았다면, 해당 관계에 저장된 `chunk_id`를 이용해 원문 청크까지 다시 가져온다. 즉 W3에서 검색으로는 찾지 못했던 문서를 **그래프를 우회해서 다시 검색 결과에 넣는 것**이다.

이렇게 보면 GraphRAG가 기존 RAG와 완전히 다른 시스템이라기보다, **기존 검색으로 찾은 정보를 출발점 삼아 검색 범위를 관계 기반으로 확장하는 구조**라는 것이 더 명확해진다.

## **4. 그래프는 넓게 탐색한다고 좋은 게 아니다**

여기까지 보면 그래프를 최대한 멀리 탐색하면 더 많은 정보를 얻을 수 있을 것 같지만 실제로는 반대다. 관계를 계속 따라가면 질문과 상관없는 정보까지 빠르게 늘어난다.

예를 들어 SeCause에서 Redis까지 이동한 뒤 다른 프로젝트의 Redis 사용 사례까지 찾았다면 X01에는 이미 충분하다.

```
SeCause
  ↓
Redis
  ↓
TEAMFICIAL / 직행
```

그런데 여기서 한 단계 더 이동하면 TEAMFICIAL과 직행에서 사용한 다른 기술들까지 나오기 시작한다. 다시 그 기술을 사용하는 프로젝트를 따라가면 그래프의 상당 부분이 컨텍스트에 들어올 수 있다.

따라서 이번 실험에서는 **홉 수, 허브 노드, 컨텍스트 크기**에 제한을 둔다.

### **홉 수는 필요한 만큼만**

X01과 X03은 필요한 연결 관계만 따라가면 해결할 수 있기 때문에 짧은 확장으로 충분하다. 필요 이상으로 멀리 이동하면 정보가 늘어나는 것이 아니라 노이즈가 늘어난다.

### **연결이 너무 많은 노드는 조심한다**

Redis, Spring Boot, Docker처럼 여러 프로젝트에서 반복해서 사용하는 기술은 앞으로 데이터가 늘어날수록 많은 노드와 연결될 가능성이 높다. 이런 노드를 **허브 노드**라고 볼 수 있다.

현재 개인 그래프는 작아서 큰 문제가 없지만, 여러 사람의 데이터를 합치면 Docker 하나에서 주변을 확장했을 때 수많은 프로젝트가 한꺼번에 따라올 수 있다. 따라서 연결 수가 일정 기준을 넘으면 확장을 멈추거나 질문과 관련도가 높은 일부만 선택하는 제한이 필요하다.

### **그래프가 기존 검색 결과를 밀어내면 안 된다**

v2에서는 기존 검색 청크와 그래프를 통해 새로 가져온 청크가 하나의 컨텍스트를 나눠 쓴다. 그래프 결과를 너무 많이 넣으면 원래 검색기가 잘 찾았던 문서가 컨텍스트에서 밀려날 수 있다.

이렇게 되면 GraphRAG가 다중 홉 질문은 잘 풀면서, 기존 v1이 이미 잘 풀던 단순 질문은 오히려 못 풀 수도 있다. 따라서 **그래프 검색은 기존 검색을 대체하는 것이 아니라 부족한 부분을 보완하는 정도로 제한해야 한다.**

## **5. 그래프에서 찾은 사실도 원문과 함께 전달한다**

그래프에서 찾은 트리플을 그대로 LLM에게 던지는 것도 좋은 방법은 아니다.

```
kg:use-secause-redis-1
USES_TECHNOLOGY
kg:tech-redis
```

이런 형태는 DB에는 좋지만 사람이 읽거나 LLM이 문맥을 이해하기에는 불편하다. 그래서 실제 컨텍스트를 만들 때는 그래프의 사실을 자연어에 가까운 형태로 바꾼다.

```
[그래프에서 찾은 사실]

- AI 코드 보안 분석 프로젝트 SeCause에서는 Redis를
  큐 기반 비동기 처리 용도로 실제 사용했다. [근거 3]

- 동아리 팀 빌딩 서비스 TEAMFICIAL에서는 Redis를
  지원자 수 조회 캐시 용도로 실제 사용했다. [근거 6]

- 기업 연계 프로젝트 직행에서는 Redis를
  통근 시간 저장에 사용하는 방안을 제안했지만 실제 구현하지는 않았다. [근거 7]
```

그리고 `[근거 3]`, `[근거 6]`에 해당하는 실제 원문 청크도 함께 전달한다. 이렇게 하면 그래프가 관계를 찾고, 원문이 그 관계의 근거와 상세 설명을 제공하는 식으로 역할을 나눌 수 있다.

특히 `implemented`, `proposed` 같은 상태값도 그대로 전달하기보다 **“실제 구현함”, “제안만 함”**처럼 의미가 분명한 표현으로 바꾼다. X03처럼 구현 여부 자체가 질문의 핵심인 경우에는 작은 표현 차이가 답을 바꿀 수 있기 때문이다.

## **6. 모든 질문에 그래프가 필요한 것은 아니다**

v2를 만들었다고 해서 모든 질문을 그래프로 풀 필요는 없다. 예를 들어 `@Transactional` 내부 호출 문제나 RDS 장애의 원인·수정·검증 과정처럼 현재 그래프 스키마에 표현되지 않은 서술 정보는 기존 문서 검색이 더 중요하다.

반대로 SeCause에서 사용한 기술을 다른 프로젝트에서도 사용했는지 찾는 X01처럼 **질문에 없는 중간 관계를 따라가야 하는 경우**에는 그래프가 강점을 가진다.

이번 비교 실험에서는 복잡한 LLM 라우터까지 만들지 않고, 기존 검색으로 찾은 청크에 그래프 관계가 존재하면 확장하고 없으면 그대로 넘어가는 단순한 방식을 사용한다. 그래프를 붙인 효과 자체를 확인해야 하는 실험에서 별도의 라우터를 추가하면 실패 원인이 하나 더 늘어나기 때문이다.

## **7. 이번 실험에서 예상하는 결과**

아직 아래 내용은 결과가 아니라 **실험 전 가설**이다.

| **질문** | **v1 예상** | **v2 예상** | **이유** |
| --- | --- | --- | --- |
| S01 `@Transactional` 내부 호출 | ✅ | ✅ | 현재 그래프에 없는 서술 정보라 기존 검색이 담당 |
| M01 SeCause 분석 파이프라인 | ✅ | ✅ | 기존 검색만으로 필요한 문서를 찾을 수 있었음 |
| X01 다른 프로젝트에서도 같은 기술을 사용했나 | ❌ | **✅** | 그래프를 통해 Redis를 거쳐 다른 프로젝트의 원문을 회수 |
| X03 제안만 한 기술을 다른 곳에서는 구현했나 | ❌ | **✅** | 관계와 구현 상태를 함께 탐색 |
| 가장 많은 프로젝트에서 사용한 기술 | ❌ | ⚠️ | 일부 서브그래프만 가져오므로 정확한 전체 집계는 어려움 |
| H01 RDS 장애 원인·수정·검증 | ⚠️ | ⚠️ | 현재 그래프 스키마에 장애 과정이 표현되어 있지 않음 |

특히 **집계 질문이 중요하다.** 그래프를 붙인 v2도 결국 관련된 일부 서브그래프를 가져오는 검색기이기 때문에 “가장 많이 사용한 기술”처럼 전체 데이터를 세어야 하는 질문에는 적합하지 않다. 이런 질문은 앞에서 본 Text2Cypher처럼 DB가 직접 `count()`를 수행하는 방식이 더 적합하다.

결국 Local Search와 Text2Cypher가 따로 존재하는 이유도 여기서 드러난다. **그래프를 쓴다는 공통점은 있지만, 해결하려는 질문의 모양이 다르다.**

## **8. 이번 주에 실제로 확인할 것**

W3에서는 BM25와 Vector Search를 RRF로 결합해 **질문과 관련 있는 문서를 더 잘 찾는 방법**을 만들었다. W5에서는 문서에서 Entity와 Relationship을 추출해 **질문에 직접 등장하지 않는 관계를 따라갈 수 있는 그래프**를 만들었다.

W6에서는 이 둘을 처음으로 하나의 검색 과정에 연결한다.

```
질문
↓
BM25 + Vector + RRF
↓
관련 청크
↓
chunk_id를 이용해 그래프로 진입
↓
관계 확장
↓
기존 검색이 놓친 원문 추가 회수
↓
통합 Context
↓
LLM 답변
```

그래서 이번 실험에서 확인하려는 것은 **“벡터 검색과 그래프 중 무엇이 더 좋은가?”가 아니다.**

벡터 검색은 질문과 비슷한 정보를 찾아 **출발점을 만드는 데 강하고**, 그래프는 그 출발점에서 질문에 직접 등장하지 않은 관계까지 **검색 범위를 넓히는 데 강하다.**

따라서 실제로 확인하고 싶은 것은 다음과 같다.

**기존 Hybrid RAG가 찾은 문서를 그래프의 진입점으로 사용하면, 기존 검색이 놓쳤던 다중 홉 정보를 실제로 추가 회수할 수 있을까?**

이 가설이 맞는지는 이제 같은 질문을 **개인 데이터 에이전트 v1과 GraphRAG를 결합한 v2에 각각 입력해 비교**하면 확인할 수 있다.
