> 카카오톡 "대화 내보내기" txt는 기기(안드로이드·iOS/Mac·PC)마다 형식이 다르고, 초 단위가 없고, 첨부·시스템 메시지가 본문 줄과 섞인다. 스터디 멤버 여섯이 같은 종류의 파일을 파싱했고, 규칙을 가장 상세히 문서화한 sese2204의 목록을 뼈대로 do-dop·lys0611의 발견을 합친다.

## 형식

| 항목 | 규칙 |
|---|---|
| 헤더 | 1행 방 이름(`우리동네 카카오톡 대화`), 2행 `저장한 날짜 : 2024년 8월 2일 오후 4:03` (sese2204) |
| 날짜 형식 | 모바일(안드로이드): `2023년 8월 9일 오전 12:34, 홍길동 : 안녕` (sese2204, lys0611). PC·iOS/Mac: `YYYY. M. D. 오전/오후 H:MM, 작성자 : 메시지`와 24시간제 `YYYY. M. D. HH:MM` 두 종류 (do-dop). lys0611의 파서는 윈도우/안드로이드/iOS·맥을 자동 감지 |
| 날짜 구분선 | 그날 첫 메시지와 똑같은 시각 문자열이라 "`, ` 뒤가 없는 타임스탬프 줄"로만 구분된다. 303줄 건너뜀 (sese2204) |
| 여러 줄 메시지 | 이어지는 줄은 앞 메시지에 `\n`으로 붙인다. 290건, 최대 29줄/500자 (sese2204) |
| 시스템 줄 | `님이 나갔습니다.` 등은 ` : ` 구분자가 없다 → sender NULL, `system_leave / system_invite / system_join / system` (sese2204) |
| 본문 속 ` : ` | 첫 구분자로만 자른다. 해당 22건 (sese2204) |
| 비텍스트 | `kind` 13종: text, photo, video, voice, emoticon, file, deleted, shop, link, system… (sese2204). lys0611은 `msg_type` text/link/media/deleted/system 5종, 청킹·임베딩은 text+link만 |
| 첨부 파일명 줄 | 안드로이드는 첨부를 `sha256해시.jpg` 같은 파일명 줄로도 남긴다(1,099건, 여러 장이면 여러 줄). 벡터 검색 결과에 섞여 나와서 알았고 확장자로 photo/video/voice 판정 (sese2204) |
| `<사진 읽지 않음>` | 다음 줄에 한 번 더 찍히는 경우가 있어 첫 줄로 종류를 판정 (sese2204) |
| 오전/오후 12시 | 12시 처리를 목표에 명시 (sese2204) |
| 인코딩 | Windows 내보내기는 UTF-8(BOM), 구형은 cp949. 파서가 둘 다 시도 (lys0611) |
| 초 단위 | **없다.** 같은 분에 수십 개가 몰리니 순서 컬럼 `seq`가 필수. 원본 줄 번호 `line_no`로 검증 (sese2204) |
| CSV 변형 | e0ng의 원본은 `Date`·`User`·`Message` 열 CSV(카카오톡 여부 불명). 큰따옴표 안 줄바꿈은 한 메시지, `Date`·`User`가 빈 행은 직전 메시지에 이어 붙임 |

## 내보내기 자체의 함정 (lys0611)

- PC 카톡에는 **PC에 동기화된 범위의 대화만** 있어 옛 대화가 비어 있을 수 있다. 오래된 기록은 폰에서 내보내는 게 확실하다. "텍스트만 보내기"(txt, 메일 전송) vs "모든 메시지 내부저장소에 저장"이 다르다.
- 대화가 많은 방은 파일이 여러 개로 분할될 수 있다. 전부 `data/raw/`에 넣고 glob으로 읽는다. 파일명에 `ㅇ`·한글이 있으면 glob이 안 되니 항상 큰따옴표.
- 원본은 절대 커밋하지 않는다. 방 멤버들에게 스터디용으로 가명 처리해 쓴다고 알리고 동의를 받는다 → [[개인-데이터-가명화와-공개-범위]].

## 저장과 재적재

- 정본·파생물 분리, 멱등 재적재는 [[데이터-수집과-출처-추적]]. sese2204는 `source_file` 기준 방 upsert + 기존 메시지 삭제 후 COPY, lys0611은 `(room_id, seq)`·`content_hash` 유니크, do-dop은 `--recreate`, e0ng은 ES 인덱스 재생성.
- 익명화 ID는 안정적이지 않다: do-dop의 `user-001`은 이름 기반이 아니라 **첫 등장 순서** 번호라 원본이나 순서가 바뀌면 같은 사람이 다른 ID를 받는다. 여러 파일을 잇거나 사람 노드를 합치려면 고정 매핑(lys0611의 `name_map.json`, 두 방이 공유)이 필요하다.
- grep은 파싱된 JSONL이 아니라 **원본 txt**를 검색한다(do-dop, yujeong430). 여러 줄 결합과 익명화로 줄 구조가 달라지기 때문인데, 그러면 BM25·벡터와 검색 단위가 달라진다 → [[검색의-세-세대]].
