# 6. GraphRAG - 검색과 그래프의 결합

지난주에는 운영체제 노트에서 엔티티와 관계를 추출해 Neo4j에 저장했다.
이번 주에는 검색 결과와 그래프를 함께 사용해 질문에 답하는 GraphRAG를 공부한다.

기존 RAG는 질문과 비슷한 문서 청크를 찾는다.
GraphRAG는 여기에 엔티티와 관계 탐색을 추가한다.

```text
기존 RAG
질문 → 관련 청크 검색 → LLM 답변

GraphRAG
질문 → 관련 엔티티 탐색 → 그래프 관계 확장 → 관련 청크 조립 → LLM 답변
```

*GraphRAG라고 해서 하나의 정해진 구현만 있는 것은 아니다.*
그래프를 만드는 방법, 검색하는 방법과 LLM에 전달하는 방법에 따라 여러 형태가 있다.

## 1. 로컬 서치

로컬 서치는 질문과 관련된 특정 엔티티를 찾은 뒤 그 주변 관계를 탐색하는 방식이다.

```text
질문: SRTN은 SJF와 어떤 관계가 있는가?
→ 질문에서 SRTN과 SJF를 찾음
→ Neo4j에서 두 엔티티 주변 관계 탐색
→ SRTN - IS_A → SJF 관계와 원문 근거 수집
→ LLM에 전달해 답변 생성
```

대략적인 과정은 다음과 같다.

1. 질문과 관련된 엔티티를 찾는다.
2. 엔티티를 그래프 탐색의 시작점으로 사용한다.
3. 시작점에서 1~몇 개의 관계를 따라가며 주변 서브그래프를 가져온다.
4. 연결된 원문 청크와 관계를 컨텍스트로 조립한다.
5. LLM이 컨텍스트를 참고해 답변한다.

Microsoft GraphRAG의 로컬 서치도 질문과 의미적으로 관련된 엔티티를 진입점으로 찾고, 연결된 엔티티·관계·커뮤니티 보고서와 원문 청크를 함께 사용한다.

로컬 서치는 특정 인물, 개념이나 대상의 관계를 묻는 질문에 잘 맞는다.

```text
SJF와 관련된 알고리즘은 무엇인가?
Running 상태 다음에 이동할 수 있는 상태는 무엇인가?
교착상태가 성립하기 위해 필요한 조건은 무엇인가?
```

## 2. 글로벌 서치

글로벌 서치는 특정 엔티티 하나보다 데이터 전체의 주제나 경향을 묻는 질문에 사용한다.

```text
운영체제 노트에서 가장 많이 다루는 주제는 무엇인가?
전체 문서에서 자주 등장하는 개념 집단은 무엇인가?
```

그래프의 노드를 연결이 촘촘한 집단으로 나누는 것을 *커뮤니티 탐지*라고 한다.
Louvain과 Leiden은 대표적인 커뮤니티 탐지 알고리즘이다.

여기서 커뮤니티는 사람들의 온라인 모임이 아니라, 그래프 안에서 서로 유난히 많이 연결된 노드의 묶음이다.
노드끼리 연결된 모양을 보고 알고리즘이 비슷한 주제의 집단을 자동으로 찾는다.

예를 들어 운영체제 개념 그래프가 다음과 같이 연결되어 있다고 가정할 수 있다.

```text
SJF ─ CPU burst ─ 대기 시간
 │
Round Robin ─ quantum ─ 선점

가상 메모리 ─ 페이지 ─ 페이지 폴트 ─ 디스크
```

이 그래프에서는 대략 다음과 같은 커뮤니티가 만들어질 수 있다.

- 프로세스 스케줄링 커뮤니티: SJF, Round Robin, CPU burst, quantum, 대기 시간
- 메모리 관리 커뮤니티: 가상 메모리, 페이지, 페이지 폴트, 디스크

사람이 각 노드에 `스케줄링`, `메모리 관리`라는 주제 이름을 미리 붙이지 않아도, 연결 구조를 통해 비슷한 노드끼리 묶을 수 있다는 것이 핵심이다.
커뮤니티가 만들어진 뒤에는 각 묶음이 어떤 내용을 다루는지 LLM으로 미리 요약할 수 있다.

```text
전체 그래프
→ 커뮤니티 탐지
→ 커뮤니티별 요약 생성
→ 질문과 관련된 요약 선택
→ 여러 요약을 종합해 답변
```

Microsoft GraphRAG의 글로벌 서치는 미리 생성된 커뮤니티 보고서를 검색하고, 각 결과를 요약한 뒤 다시 종합하는 방식으로 답을 만든다.
특정 사실을 찾는 것보다 데이터 전체를 요약하는 질문에 적합하지만, 로컬 서치보다 많은 전처리와 비용이 필요할 수 있다.

정리하면 로컬 서치는 `SJF와 직접 연결된 개념은 무엇인가?`처럼 특정 노드 주변을 보고, 글로벌 서치는 `운영체제 노트에서 주로 다룬 주제는 무엇인가?`처럼 여러 커뮤니티의 요약을 모아서 본다.

Neo4j에서는 GDS(Graph Data Science) 라이브러리로 Leiden이나 Louvain을 실행할 수 있다.
GDS는 Neo4j 데이터베이스와 별도로 설치해야 하는 플러그인이므로 이번 필수 실습에는 포함하지 않고 선택 과제로 둔다.
현재 내 그래프는 엔티티와 관계가 적어서 의미 있는 커뮤니티가 만들어지기 어렵다. 따라서 이번 실습에서는 커뮤니티 탐지를 직접 실행하지 않고 로컬 서치와 Text2Cypher를 먼저 확인한다.

## 3. Text2Cypher

Text2Cypher는 자연어 질문을 LLM이 Cypher 질의로 바꾸는 방식이다.

```text
질문: SJF와 직접 연결된 엔티티를 보여줘.

생성된 Cypher:
MATCH (s:Entity {name: "SJF"})-[r]-(other:Entity)
RETURN s.name, type(r), other.name
```

생성한 Cypher를 Neo4j에서 실행하고 그 결과를 LLM의 답변 근거로 사용할 수 있다.
질문의 조건이 명확하고 그래프 스키마가 단순하면 편리하지만 다음과 같은 문제가 있다.

- LLM이 실제로 없는 노드 라벨이나 관계 이름을 만들 수 있다.
- 관계 방향을 반대로 이해할 수 있다.
- 너무 넓거나 비효율적인 질의를 만들 수 있다.
- 쓰기 질의를 허용하면 데이터를 변경할 위험이 있다.

따라서 LLM에 현재 그래프의 노드 속성과 관계 종류를 알려주고, `MATCH`와 `RETURN` 같은 읽기 질의만 허용해야 한다.
질의 실행 전에 `CREATE`, `DELETE`, `SET`, `MERGE` 같은 쓰기 구문이 없는지도 검사하는 것이 좋다.

## 4. 하이브리드 리트리버

그래프에 엔티티가 많으면 어디서 탐색을 시작할지 먼저 정해야 한다.
엔티티 이름이 질문에 정확히 들어 있다면 문자열로 찾을 수 있지만, 표현이 다르면 찾기 어렵다.

하이브리드 리트리버는 벡터 검색으로 질문과 의미가 가까운 청크나 엔티티를 찾고, 그 결과를 그래프 탐색의 진입점으로 사용한다.

```text
자연어 질문
→ BM25·벡터 검색으로 관련 청크 검색
→ 청크에 연결된 엔티티를 진입점으로 선택
→ Neo4j에서 주변 관계를 1~2 hop 확장
→ 문서 청크와 그래프 관계를 함께 LLM에 전달
```

벡터 검색은 표현이 조금 달라도 관련된 시작점을 찾는 데 유리하다.
그래프 탐색은 시작점에서 명시적으로 연결된 관계를 따라가는 데 유리하다.
두 방식의 역할이 다르기 때문에 함께 사용할 수 있다.

## 5. 그래프 인덱싱은 빌드 시점 선지불

일반적인 벡터 RAG도 문서를 청킹하고 임베딩을 만드는 전처리가 필요하다.
GraphRAG는 여기에 더 많은 작업이 추가된다.

```text
문서 청킹
→ 엔티티와 관계 추출
→ 엔티티 중복 정리
→ 그래프 생성
→ 커뮤니티 탐지
→ 커뮤니티별 요약 생성
→ 검색용 임베딩 생성
```

이 작업을 질문이 들어올 때마다 수행하면 너무 느리고 비싸다.
그래서 데이터가 추가되거나 변경될 때 배치 작업으로 미리 그래프와 요약을 만든다.
질의 시점의 속도를 위해 빌드 시점에 시간과 비용을 먼저 지불하는 셈이다.

DDIA의 일괄 처리 관점으로 보면 원본 문서는 입력이고, 그래프·커뮤니티·요약·임베딩은 다시 만들 수 있는 파생물이다.
스키마나 추출 방식이 바뀌면 원본 문서에서 파생물을 다시 생성할 수 있어야 한다.

## 6. 언제 그래프가 유리한가

그래프는 관계가 명시적으로 저장되어 있고 여러 관계를 따라가야 하는 질문에 유리하다.

```text
SRTN은 어떤 알고리즘의 변형인가?
프로세스가 Running에서 Blocked로 바뀌는 원인은 무엇인가?
특정 개념과 2단계 안에서 연결된 알고리즘은 무엇인가?
가장 많은 관계를 가진 엔티티는 무엇인가?
```

특히 다중 홉, 경로 탐색, 개수 계산과 집계는 Cypher로 정확하게 표현할 수 있다.

## 7. 언제 벡터 검색이 유리한가

그래프에 저장되지 않은 설명이나 원문의 자세한 내용을 찾을 때는 벡터 검색이 더 유리할 수 있다.

```text
SJF의 장단점을 설명해줘.
문맥 교환 과정을 쉽게 설명해줘.
메모리 관리 내용을 전체적으로 요약해줘.
```

그래프는 추출된 엔티티와 관계만 알 수 있다.
추출 과정에서 빠진 사실이나 잘못 저장된 관계는 그래프 검색으로 찾을 수 없다.
지난주 실습처럼 미니 온톨로지가 부족하거나 LLM 추출이 부정확하면 GraphRAG의 답변도 함께 나빠진다.

따라서 그래프가 항상 벡터 검색보다 좋은 것은 아니다.

| 질문 유형 | 더 적합한 방식 |
| --- | --- |
| 원문 설명과 비슷한 내용 찾기 | BM25·벡터 검색 |
| 특정 엔티티 주변 관계 찾기 | 로컬 GraphRAG |
| 여러 관계를 연속해서 따라가기 | 그래프 탐색 |
| 개수·최댓값 같은 집계 | Cypher |
| 데이터 전체의 큰 주제 파악 | 글로벌 GraphRAG |
| 그래프에 추출되지 않은 세부 내용 | 문서 검색 |

## 8. 개인 데이터 에이전트 v1과 v2

3주차의 개인 데이터 에이전트 v1은 BM25와 벡터 검색 결과를 RRF로 합친 뒤 상위 청크를 LLM에 전달했다.

이번에 만들 v2는 같은 검색 결과에서 관련 엔티티를 찾고 Neo4j의 주변 관계를 추가한다.

```text
v1
질문 → BM25 + 벡터 → RRF → 청크 → LLM

v2
질문 → BM25 + 벡터 → RRF → 진입 엔티티 → 그래프 확장
                                └→ 청크 + 관계 → LLM
```

같은 질문을 v1과 v2에 넣고 다음 내용을 비교한다.

- 필요한 근거를 찾았는가?
- 답변이 원문과 그래프에 있는 사실과 일치하는가?
- 여러 관계를 연결하는 질문에 답했는가?
- 관계가 필요 없는 질문에서 불필요한 그래프 정보가 섞이지 않았는가?
- API 호출과 검색 시간이 얼마나 늘어났는가?
