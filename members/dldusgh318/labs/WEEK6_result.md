# **W6 실습 - 검색과 그래프를 실제로 결합해보면**

W5에서는 개인 문서에서 Entity와 Relationship을 추출해 지식 그래프를 만들고, 기존 Hybrid RAG가 놓쳤던 관계를 그래프에서는 찾을 수 있다는 것을 확인했다. 하지만 당시에는 사람이 직접 Cypher를 작성해 그래프를 조회했다.

W6에서는 이 그래프를 실제 개인 데이터 에이전트에 넣었다. W3에서 만든 **BM25 + Vector Search + RRF 기반 에이전트를 v1**, 여기에 검색 결과를 시작점으로 그래프를 확장하는 기능을 추가한 것을 **v2**로 두고 같은 질문으로 비교했다. 추가로 자연어 질문을 LLM이 직접 Cypher로 변환하는 **Text2Cypher**도 함께 실험했다.

이번 실험에서 확인하고 싶었던 것은 단순히 “GraphRAG가 기존 RAG보다 좋은가?”가 아니었다.

**어떤 질문에서 기존 검색이 유리하고, 어떤 질문에서 그래프가 실제로 도움이 되는가?**

결과부터 말하면 **한 방식이 모든 질문에서 이기지는 않았다.** 문서 내용을 설명해야 하는 질문은 기존 검색이 잘했고, 질문에 없는 중간 관계를 건너가야 하는 질문에서는 그래프가 도움이 됐으며, 정확한 개수나 상태 조건을 묻는 질문은 Text2Cypher가 가장 잘 풀었다.

## **1. 같은 질문을 v1, v2, Text2Cypher에 물어봤다**

비교 기준이 되는 v1은 W3에서 만든 개인 데이터 에이전트를 그대로 사용했다.

```
질문
→ BM25 top-50 + Vector top-50
→ RRF
→ top-5 청크
→ LLM 답변
→ 인용 검증
```

v2에서는 이 검색 과정을 그대로 유지하면서, 검색된 청크를 그래프의 진입점으로 사용하는 단계를 추가했다.

```
질문
→ 기존 Hybrid Search
→ top-5 청크
→ chunk_id를 이용해 그래프로 진입
→ 주변 관계를 2홉까지 확장
→ 새롭게 발견한 관계의 원문 청크 회수
→ 기존 검색 결과 + 그래프 결과
→ LLM 답변
```

v1과 v2의 모델, 시스템 프롬프트, top-k와 총 컨텍스트 크기 8,000자는 동일하게 유지했다. 그래프를 추가했다는 차이만 최대한 남겨두기 위해서다.

또 같은 질문이라도 LLM 답변이 달라질 수 있었기 때문에 각 질문을 한 번만 실행하지 않고 **v1과 v2에서 각각 3회 실행해 다수결로 판정**했다. 실제로 X03은 v1 첫 실행에서는 정답이었지만 세 번을 종합하면 부분 정답이었다. 한 번의 실행만 봤다면 결론 자체가 달라질 수 있었던 셈이다.

평가 질문도 v2 결과를 보기 전에 미리 고정했다. 단일 문서 검색으로 풀 수 있는 질문, 관계를 따라가야 하는 질문, 현재 그래프의 술어로 표현하기 어려운 서술형 질문, 전체 데이터를 세어야 하는 집계 질문을 섞었다.

## **2. 결과 : GraphRAG가 항상 맞지는 않았다..**

실험 결과는 다음과 같았다.

| **질문** | **v1** | **v2** | **Text2Cypher** |
| --- | --- | --- | --- |
| S01 `@Transactional` 내부 호출 | ✅ | ✅ | - |
| M01 AI 코드 보안 분석 프로젝트 SeCause의 분석 흐름 | ✅ | ✅ | - |
| X01 SeCause에서 사용한 기술을 다른 프로젝트에서도 사용했는가 | ❌ | 🔺 | ❌ |
| X03 제안만 했던 기술을 다른 프로젝트에서는 실제 구현했는가 | 🔺 | 🔺 | ✅ |
| H01 RDS 장애의 원인·수정·검증 | 🔺 | 🔺 | - |
| A1 가장 많은 프로젝트에서 사용한 기술 | ❌ | ❌ | ✅ |
| A2 제안만 하고 구현하지 않은 기술 | ❌ | ❌ | ✅* |

`A2`의 Text2Cypher는 세 번 중 두 번 정답이었다.

가장 먼저 확인된 것은 **그래프가 필요 없는 질문에서는 v2라고 특별히 좋아지지 않았다는 것**이다. `@Transactional` 내부 호출이나 SeCause의 분석 파이프라인처럼 기존 검색으로 필요한 문서를 이미 찾을 수 있는 질문은 v1과 v2가 모두 해결했다.

반대로 정확한 집계가 필요한 A1과 A2는 v1과 v2가 모두 실패했다. v2도 결국 관련된 일부 서브그래프를 가져오는 검색 방식이기 때문에 전체 그래프를 정확하게 세는 데에는 적합하지 않았다. 이 경우에는 Neo4j가 직접 `count()`와 조건식을 실행하는 Text2Cypher가 훨씬 잘 맞았다.

즉 이번 결과만 보더라도 **GraphRAG라는 하나의 방식이 기존 RAG를 대체하는 구조는 아니었다.**

## **3. 그래프는 v1이 끝내 찾지 못했던 다리를 찾았다**

그래프의 효과가 가장 명확하게 나타난 것은 X01이었다.

질문은 **내가 진행한 AI 코드 보안 분석 프로젝트 SeCause에서 작업 큐에 사용한 기술을 다른 프로젝트에서도 사용했는가**였다.

이 질문의 답을 만들려면 실제로는 다음 관계를 찾아야 한다.

```
SeCause
   ↓
Redis
   ↓
동아리 팀 빌딩 서비스 TEAMFICIAL
```

문제는 질문에 `Redis`라는 단어도, `TEAMFICIAL`이라는 단어도 없다는 점이다. 기존 v1은 세 번 모두 SeCause 관련 문서까지만 검색했고, 결국 다른 프로젝트에서 같은 기술을 사용한 기록을 찾지 못했다고 답했다.

v2는 달랐다.

```
v1 검색
→ SeCause 관련 청크 발견
→ 그래프로 진입
→ SeCause의 TechnologyUse
→ Redis
→ Redis를 사용한 다른 TechnologyUse
→ TEAMFICIAL
```

v1에서는 한 번도 찾지 못했던 TEAMFICIAL까지 세 번 모두 도달했다.

이 결과로 W3부터 세웠던 가설 하나는 실제로 확인할 수 있었다.

**질문에 중간 단서가 없어서 검색할 수 없었던 정보도, 그래프에 관계가 만들어져 있다면 그 관계를 따라 도달할 수 있다.**

하지만 X01의 최종 평가는 완전한 정답이 아니라 `partial`이었다. 여기서 이번 주의 더 중요한 문제가 발견됐다.

## **4. 그래프에서 목적지를 찾는 것과 좋은 근거를 가져오는 것은 다른 문제였다**

v2는 TEAMFICIAL까지 제대로 도달했다. 그런데 그래프를 통해 추가로 가져온 원문을 확인해보니 **평가에서 정답으로 지정했던 청크는 한 건도 들어오지 않았다.**

첫 번째 원인은 회수 순서였다. 처음 구현한 v2는 그래프를 통해 찾은 청크를 `chunk_id` 순으로 컨텍스트에 넣었다. 그래프용으로 배정한 2,200자 예산이 앞쪽에 있던 기업 연계 프로젝트 **직행**의 청크들로 먼저 차면서, 질문에 더 중요한 TEAMFICIAL의 Redis 캐시 청크가 밀려났다.

그래서 실험 결과를 확인한 뒤 별도의 `v2.1`을 만들어 회수 청크를 질문과의 관련도 순으로 정렬했다. 그러자 TEAMFICIAL에서 Redis를 이용해 지원자 수를 캐싱하고 `INCR`, `MGET`을 이용해 조회 성능을 개선했다는 원문이 들어왔고, 답변도 훨씬 구체적으로 변했다.

```
v2
그래프로 TEAMFICIAL 발견
→ 관련 없는 청크가 먼저 컨텍스트를 차지
→ "Redis를 캐싱 인프라로 사용했다"

v2.1
그래프로 TEAMFICIAL 발견
→ 질문 관련도가 높은 원문을 우선 회수
→ "지원자 수를 Redis에 캐싱하고 INCR·MGET으로 조회 성능을 개선했다"
```

그래프 사실을 자연어로 만들어 넣는 영역에서도 같은 문제가 있었다. 진입점인 SeCause에 연결된 Docker, GitHub API 같은 기술이 먼저 들어오면서 정작 필요한 **“TEAMFICIAL에서도 Redis를 지원자 수 집계에 사용했다”**는 경로가 컨텍스트 예산 밖으로 밀려났다.

결국 **그래프 확장에 성공했다고 검색까지 성공한 것은 아니었다.**

**그래프가 어디로 가야 하는지를 알려주더라도, 그곳에서 무엇을 가져올지는 다시 질문과의 관련도를 기준으로 선택해야 한다.**

W3에서는 검색 결과를 랭킹하는 것이 중요했다면, W6에서는 **그래프를 통해 확장한 결과도 다시 랭킹해야 한다**는 문제가 새로 생겼다.

## **5. 그래프는 자신이 만들어진 데이터 밖으로 나갈 수 없다**

X01에서는 더 근본적인 문제도 있었다.

원래 정답으로 지정했던 `경력기술서#325` 청크는 v2.1에서도 회수되지 않았다. 이번 그래프는 전체 1,562개 청크가 아니라 W5에서 선별한 **20개 청크만 LLM으로 추출해 만든 그래프**였고, 해당 청크가 그 20개에 포함되어 있지 않았기 때문이다.

그래프 리트리버는 엣지에 저장된 `chunk_id`를 따라 원문을 가져온다. 애초에 추출하지 않은 청크는 그래프와 연결되어 있지 않으므로 아무리 그래프를 잘 탐색해도 도달할 방법이 없다.

집계 질문 A2에서도 비슷한 현상이 나타났다. 기존 v1은 전체 문서를 검색하기 때문에 Grafana Alloy와 OpenTelemetry Collector를 검토만 했다는 실제 문서를 찾았다. 하지만 이번 평가의 집계 기준은 20개 청크로 만든 그래프였기 때문에 그 정보는 그래프상 존재하지 않았다.

여기서 W5에서 전체 추출을 미뤘던 결정의 다음 단계가 명확해졌다.

**그래프가 답할 수 있는 범위는 그래프를 만들 때 추출한 데이터의 범위를 넘을 수 없다.**

그래프는 원본 데이터 전체의 진실을 자동으로 알고 있는 것이 아니다. **현재 그래프에 들어간 범위의 사실만 알고 있다.** 따라서 GraphRAG의 검색 성능을 제대로 평가하려면 검색 방식뿐 아니라 그래프 자체의 커버리지도 함께 봐야 한다.

## **6. Text2Cypher는 정확한 값에는 강했지만 문장에는 약했다**

Text2Cypher에서는 같은 다중 홉 질문인 X01과 X03의 결과가 완전히 달랐다.

X03은 세 번 모두 성공했다. 이 질문에서는 `status`를 이용해 “제안만 한 사용례”와 “실제 구현한 사용례”를 구분하면 됐다.

```
proposed
implemented
```

둘 다 그래프에 정해진 값으로 저장되어 있기 때문에 LLM이 다음과 같은 조건을 만들기 쉬웠다.

```
WHERE u1.status = 'proposed'
  AND u2.status = 'implemented'
```

반면 X01은 세 번 모두 실패했다. 작업 큐라는 목적을 찾기 위해 LLM이 질문의 표현을 그대로 가져와 다음과 비슷한 조건을 만들었기 때문이다.

```
WHERE u1.purpose CONTAINS '분석 작업 큐'
```

하지만 실제 그래프에는 같은 의미가 다음처럼 저장되어 있었다.

```
"큐 기반 비동기 처리"
"분석 작업을 백그라운드로 분리"
```

사람이 보면 같은 맥락이라는 것을 알 수 있지만 문자열 조건으로는 일치하지 않는다.

이 차이를 통해 Text2Cypher가 잘 맞는 조건도 조금 더 명확해졌다.

```
표현이 달라질 수 있는 목적·설명
→ 의미 유사도를 이용할 수 있는 검색 / 벡터 진입

implemented / proposed 같은 정해진 상태값
프로젝트명
정확한 개수와 정렬
→ Text2Cypher
```

W5에서 `purpose`를 별도의 노드나 정해진 값으로 만들지 않고 자유로운 문자열 속성으로 저장했던 설계의 장단점도 여기서 드러났다. 그래프 구조가 단순해지는 대신 **문장 표현을 정확한 조건으로 질의하기 어려워졌다.**

## **7. Text2Cypher의 더 위험한 문제는 ‘에러 없이 틀리는 것’이었다**

Text2Cypher는 총 21번 실행했고 **실행 자체가 실패한 경우는 한 번도 없었다.** 그런데 그중 네 번은 답이 틀렸다.

세 번은 X01에서 잘못된 문자열 조건 때문에 결과가 0건이 된 경우였고, 한 번은 A2에서 질문의 의미를 다르게 해석한 경우였다.

오히려 Cypher 문법 오류가 발생했다면 문제를 쉽게 발견할 수 있었을 것이다. 더 위험한 것은 다음과 같은 경우다.

```
질문
↓
문법적으로 정상인 Cypher
↓
잘못된 조건
↓
0 rows
↓
"해당하는 사용례가 없습니다."
```

실제로는 데이터가 있는데도 쿼리가 잘못되어 0건이 나온 것인지, 정말 데이터가 없는 것인지 결과만 보고는 구분하기 어렵다.

그래서 이번 구현에서는 0건 결과가 나오더라도 바로 “없다”고 답하지 않고 **어떤 Cypher와 조건으로 검색했는지 함께 보여주도록 했다.**

Text2Cypher에서 중요한 것은 단순히 **“실행 가능한 Cypher를 생성했는가”**가 아니라 **“사용자의 의도를 정확하게 표현한 Cypher를 생성했는가”**였다.

## **8. TechnologyUse를 만든 만큼 질문도 더 정확해야 했다**

A2에서는 또 다른 문제가 나타났다.

질문은 다음과 같았다.

“제안만 하고 구현하지 않은 기술은?”

한 번의 실행에서 LLM은 이를 **기술 자체가 어느 곳에서도 구현되지 않은 경우**로 해석했다. 그래서 직행 프로젝트에서는 제안만 했지만 다른 프로젝트에서는 실제로 사용했던 Redis를 결과에서 제외했다.

하지만 평가에서 의도했던 것은 **특정 프로젝트에서 제안만 하고 구현하지 않은 사용 사례**였다.

W5에서 단순히

```
Project → Redis
```

라고 표현하지 않고,

```
Project
   ↓
TechnologyUse
   ↓
Redis
```

처럼 중간 노드를 만든 이유는 같은 기술이라도 프로젝트마다 목적과 구현 상태가 다르기 때문이었다.

이 구조 덕분에 더 많은 정보를 표현할 수 있게 됐지만, 동시에 **“기술 자체를 묻는 것인지, 특정 기술 사용 사례를 묻는 것인지”**도 구분해야 하게 됐다.

즉 **그래프의 표현력이 높아질수록 자연어 질문을 그래프의 어느 단위에 대응시킬 것인지도 더 중요해졌다.**

## **9. 자동으로 만든 그래프의 품질 문제도 다시 나타났다**

W5에서 발견했던 TechnologyUse 중복 문제도 이번에 실제 병합을 시도했다.

처음에는 같은 프로젝트와 기술을 사용하는 후보들만 좁힌 뒤, LLM에게 두 사용 사례가 같은 사실인지 쌍별로 판단하게 했다. 자동으로 확실하게 병합할 수 있었던 것은 GitHub API 사용례 한 건뿐이었고, TechnologyUse는 45개에서 44개가 됐다.

특히 TEAMFICIAL의 Redis 사용례는 애매했다. 같은 PR에서 나온 Redis 캐시 구현인데도 하나는 `INCR`을 이용한 쓰기 경로, 다른 하나는 `MGET`을 이용한 읽기 경로를 설명하고 있어 LLM이 서로 다른 사용 사례라고 판단했다.

하지만 프로젝트의 기능 단위로 보면 둘 다 **지원자 수 캐시라는 하나의 기능**이었다. 결국 사람이 원문을 확인한 뒤 관련 노드들을 하나로 병합했고 최종 TechnologyUse는 41개가 됐다.

여기서 문제는 LLM의 성능만이 아니었다. **“같은 사용례”가 무엇인지 프롬프트에서 충분히 정의하지 않았던 것**도 원인이었다.

또 하나의 Redis 노드는 실제 기술 사용 사례라기보다 캐시 기능을 구현하면서 겪은 트러블슈팅 기록에 가까웠다. 현재 닫힌 스키마에는 장애나 트러블슈팅을 표현할 클래스와 술어가 없었기 때문에, 추출기가 가장 가까운 `TechnologyUse`에 해당 내용을 넣어버린 것이다.

이 결과는 W5에서 세웠던 생각을 조금 더 확장시켰다.

**스키마 밖의 정보는 항상 사라지는 것이 아니다. 때로는 가장 비슷한 기존 구조에 잘못 들어가기도 한다.**

따라서 스키마가 좁으면 정보를 놓칠 뿐 아니라 **잘못 분류된 그래프를 만들 수도 있다.**

## **10. 이번 실험에서 확인한 역할 분담**

이번 결과를 종합하면 처음에 봤던 세 가지 검색 방식의 역할이 실제 데이터에서도 어느 정도 나뉘었다.

| **질문의 형태** | **잘 맞았던 방식** | **이유** |
| --- | --- | --- |
| 문서의 내용·과정 설명 | **기존 Hybrid RAG** | 원문의 상세한 서술이 중요 |
| 질문에 없는 중간 관계 탐색 | **검색 + Graph Local Search** | 기존 검색 결과에서 출발해 관계를 따라갈 수 있음 |
| 정해진 상태값 조건 | **Text2Cypher** | `implemented`, `proposed`처럼 정확한 조건 사용 가능 |
| 정확한 개수·정렬 | **Text2Cypher** | DB가 전체 그래프를 직접 계산 |
| 자유로운 문장으로 저장된 조건 | **검색 / 벡터 기반 진입** | 문자열이 달라도 의미 유사도로 접근 가능 |
| 현재 스키마에 없는 정보 | **기존 검색** | 그래프에는 애초에 표현되지 않음 |

따라서 W6의 결론은 **“그래프가 벡터 검색보다 좋았다”**가 아니었다.

오히려 각각이 잘하는 문제가 달랐다.

```
서술을 찾는다
→ Hybrid Search

질문에 없는 관계를 따라간다
→ Graph Local Search

정확하게 세고 조건을 건다
→ Text2Cypher
```

그리고 실제 에이전트에서는 이 세 가지를 어떻게 적절하게 조합할지가 다음 문제다.

## **11. 실험 결과를 해석할 때 주의할 점**

이번 결과를 일반적인 GraphRAG의 성능으로 해석할 수는 없다. 가장 큰 이유는 **그래프가 전체 1,562개 청크가 아니라 선별한 20개 청크로 만들어졌고, 평가 질문도 7개뿐이기 때문**이다.

X01에서는 같은 사실을 담고 있는 다른 청크가 들어왔는데도 기존 `equivalent_groups`에 등록되어 있지 않아 recall이 낮게 계산되는 문제도 있었다. 결과를 본 뒤 동등 청크로 추가하면 점수는 올라가지만, 평가 결과를 보고 기준을 바꾸는 셈이기 때문에 기존 점수와 수정했을 때의 점수를 함께 남겼다.

일부 질문은 정답 기준 자체도 실제 질문보다 엄격했다. X01은 사용 용도를 묻는 질문이었지만 expected에는 DB fallback 같은 구현 세부사항까지 포함되어 있어 엄격하게 평가하면 `partial`, 실제 질문에 필요한 정보만 기준으로 보면 `correct`에 가까웠다.

또 현재 evidence 검증은 **원문에 해당 문자열이 존재하는가**만 확인한다. 문자열이 존재한다고 해서 그 문장이 실제로 해당 관계를 뒷받침한다는 뜻은 아니다. 실제로 섹션 제목이나 경로 정보가 evidence 검증을 통과하는 경우도 있었다.

따라서 이번 수치는 최종 성능 지표라기보다 **현재 구조에서 어디가 실패하는지 찾기 위한 실험 결과**로 보는 것이 맞다.

## **12. 다음 단계 — 이제 검색기보다 그래프 자체를 보완해야 한다**

W5에서는 그래프를 만들 수 있는지를 확인했고, W6에서는 그 그래프를 검색에 실제로 연결했다. 그 과정에서 이제 다음 병목도 비교적 명확해졌다.

가장 먼저 필요한 것은 **전체 청크 추출**이다. 현재처럼 20개 표본만 그래프에 들어가 있으면 그래프 검색과 집계 결과 모두 데이터 범위의 영향을 크게 받는다.

스키마도 한 번 확장할 필요가 있다. 현재 기술 사용 중심 스키마로는 H01과 같은 장애·트러블슈팅 정보를 표현할 수 없다. 앞으로 `Issue`를 추가하고 발생 프로젝트, 원인, 수정 방법, 검증 결과를 관계로 표현한다면 지금 `TechnologyUse`에 잘못 들어간 트러블슈팅 기록도 제자리로 보낼 수 있다. 반대로 W5 표본에서 한 번도 사용되지 않았던 `replaces`는 전체 데이터에서도 필요성이 확인되지 않는다면 제거할 수 있다.

그래프 검색 쪽에서는 단순히 2홉을 확장하는 것보다 **질문과 관련된 브릿지 경로와 원문을 우선하는 랭킹**이 필요하다. X01에서 그래프는 TEAMFICIAL까지 제대로 도달했지만 컨텍스트 예산을 잘못 사용해 중요한 근거가 밀려났던 것이 이를 보여준다.

결국 W6를 시작할 때의 질문은 이랬다.

**그래프를 RAG에 넣으면 기존 검색이 못 풀던 질문을 풀 수 있을까?**

실험 후에는 질문이 조금 달라졌다.

**그래프를 따라 목적지까지 가는 것만으로 충분한가?**

결과는 아니었다. **어디로 확장할지뿐 아니라, 확장한 결과 중 무엇을 다시 가져올지, 그래프 자체가 원본을 얼마나 담고 있는지, 자연어 질문을 그래프의 어떤 단위로 해석할지까지 모두 검색 품질의 일부였다.**

그래서 이번 주 결과를 한 문장으로 정리하면 다음과 같다.

**그래프는 기존 검색이 넘지 못했던 관계를 건너게 해줬지만, 좋은 답을 만들려면 그 관계 위에서도 다시 검색하고 검증해야 했다.**

W3에서 시작한 “어떻게 잘 찾을 것인가?”라는 문제는 그래프를 붙였다고 사라진 것이 아니라, **문서 검색에서 그래프 검색으로 한 단계 확장된 셈이다.**
