# 02. 청킹부터 BM25, pgvector, HNSW까지

## 한 줄 요약

회사 기술 문서를 청크로 나누고, 문자열·BM25·벡터 검색을 직접 비교했다. 같은 코사인 검색에서도 HNSW 인덱스로 탐색을 줄일 수 있지만, 좋은 답변 근거를 찾았는지는 별도로 확인해야 한다.

## 핵심 개념

| 역할 | 이번에 사용한 것 |
|---|---|
| 검색할 단위 만들기 | Python 청킹 → 청크 JSONL |
| 문자열 그대로 찾기 | Python 부분 문자열 검색(grep과 비교) |
| 한국어를 검색 단위로 나누기 | Nori |
| 단어로 후보를 찾고 순위 매기기 | Elasticsearch 역색인 + BM25 |
| 텍스트를 숫자 배열로 변환하기 | Ollama / qwen3-embedding:0.6b |
| 벡터를 저장하고 거리 계산하기 | PostgreSQL / pgvector / 코사인 |
| 전체 비교보다 빠르게 근처 탐색하기 | ANN의 한 방법인 HNSW 인덱스 |

## 상세 정리

### 1. 원본 문서와 청크는 뭐가 다른가

`normalized_documents_with_path.jsonl`은 한 줄에 문서 하나를 담은 정규화 파일이다. 문서 ID, 부모 ID, 제목, 경로와 `sections → blocks` 안의 문단·목록·표·코드를 모아둔 상태다. 문서 364개를 읽었을 때 출력했던 ‘청크 수 364’는 잘못된 표현이었다.

청킹 결과는 한 줄에 **검색할 글 조각 하나**가 들어간다. 서로 다른 문서·섹션을 합치지 않고 약 1,400자를 목표로, 본문 최대 2,000자로 나눴다. 원문 ID·문서 경로·섹션·블록 위치를 함께 보존해 검색 결과의 출처를 찾을 수 있게 했다. 원본 파일은 바꾸지 않았다.

이번 `01_chunk_documents.py` 결과는 문서 364개 중 본문이 있는 302개에서 **2,685개 청크**를 만든 것이다. 본문이 없는 62개 문서는 텍스트 청크가 없고, 본문 길이 중앙값은 234자, 최대는 2,000자였다. 예전에 만든 2,739개 결과와는 분할 규칙·스크립트가 다르다. 현재 코드는 이미지 제외, 표 헤더 반복 없음, 글자 수 기준이다. 토큰 길이나 검색 품질 검증을 끝낸 것은 아니다.

처음 스크립트 실행 후 출력도 디렉토리도 없었던 이유는 파일이 비어 있었기 때문이다. 빈 Python 파일은 오류 없이 종료 코드 0으로 끝날 수 있다. 출력·stderr·파일 내용·`__main__` 실행 진입점을 확인하고 코드를 복구했다.

### 2. raw_text와 embedding_text

`raw_text`는 청크 본문이고, `embedding_text`는 **문서 경로 + 섹션 경로 + 본문**을 붙인 문자열이다. raw_text의 일부가 아니라 본문에 맥락을 더한 입력이다. 이름에 embedding이 들어가도 아직 숫자 벡터가 아니다. 경로를 붙이는 것은 선택한 검색 설계이며 모든 RAG에서 반드시 필요한 규칙은 아니다.

임베딩 모델에는 embedding_text를 넣고, 검색에 쓰는 숫자 배열을 돌려받는다. 이번 모델은 청크마다 1,024개 숫자를 반환했다. 각 숫자가 단어 하나와 대응하는 것은 아니다. 검색용 벡터에서 원문을 복원하는 대신, 벡터에 연결해 보관한 본문을 가져온다. 이후 답변용 LLM에는 질문과 검색한 **텍스트**를 전달한다. LLM 내부 토큰화와 검색용 임베딩은 구분해야 한다.

Ollama로 3개 샘플의 개수·차원·유효한 숫자를 확인했다. 이 샘플 테스트는 파일 저장이나 DB 적재를 하지 않았다. 이후 50개로 코사인 검색을 시험하고, 전체 2,685개를 임베딩해 로컬 JSON 캐시에 저장했다. 앞 50개만 검색하면 뒤에 있는 정답은 찾을 수 없으므로 전체 검색 품질을 판단하기에는 부족하다.

### 3. 문자열 검색에서 BM25로

실습의 grep 모드는 Python으로 `검색문자열 in embedding_text`를 검사한다. 대소문자를 구분하는 부분 문자열 검색이고 정규식이나 관련도 순위는 없다. ‘로그인 실패’가 그대로 없으면 ‘로그인에 실패했습니다’를 놓칠 수 있다.

Nori는 한국어 형태소 분석기다. 조사·어미 등을 처리해 검색할 토큰을 만들지만 점수를 매기지는 않는다. 실제 출력은 `Codebeamer에서 로그인에 실패했습니다 → codebeamer | 로그인 | 실패`였다. 형태소를 나눠도 ‘로그인’과 ‘접속’처럼 단어 자체가 다른 문제까지 자동으로 해결되지는 않는다. n-gram은 글자를 일정 길이로 잘라 쓰는 다른 방식이며 이번에는 비교 실험을 하지 않았다.

Elasticsearch는 청크를 저장하고 검색하는 프로그램이다. 청크를 **적재·색인할 때** 토큰을 분석해 ‘단어 → 그 단어가 있는 청크’라는 역색인을 미리 만든다. 질문도 분석한 뒤 역색인으로 후보를 찾고 BM25 점수로 정렬한다. ‘Nori + Elasticsearch’의 이름이 BM25인 것은 아니다. 각각 분석기, 저장·검색 엔진, 점수 계산 알고리즘이다. BM25는 임베딩 벡터 없이 실행할 수 있다.

BM25는 TF(청크 안의 단어 빈도)와 IDF(전체 청크에서 단어의 희소성)를 함께 고려한다. DF는 그 단어가 있는 청크 수이며, 반복 횟수와 다르다. ‘codebeamer’처럼 드문 단어는 흔한 단어보다 구별에 도움이 될 수 있다. 다만 희소성만으로 순위를 정하지 않고 반복 효과를 완만하게 만들며 문서 길이도 보정한다. 긴 청크나 반복이 많은 청크가 무조건 좋은 것은 아니다.

일반 DB에 원본을 두고 Elasticsearch에 검색용 사본을 둘 수도 있다. 이 경우 원본의 수정·삭제가 검색 인덱스에 반영되지 않으면 오래된 내용을 보여줄 수 있다. 동기화는 별도 설계가 필요하다.

### 4. OR와 AND는 후보 선정 조건

‘URM 서버 등록하는 방법’의 Nori 토큰은 `urm | 서버 | 등록 | 방법`이었다. OR는 하나 이상, AND는 분석된 토큰이 모두 있어야 후보가 된다. 입력한 문장 순서 그대로 있을 필요는 없고, 검색 필드에 경로도 있으므로 모든 단어가 본문에만 있어야 하는 것도 아니다.

| 같은 질문 | 일치 청크 수 | 1위 |
|---|---:|---|
| BM25 OR | 709 | URM 초기 설정 / 19.422447 |
| BM25 AND | 1 | URM 초기 설정 / 19.422447 |

AND로 바꾸자 후보는 크게 줄었지만 같은 1위 청크의 점수는 같았다. `top-k`는 보여줄 상위 결과 개수이고 점수 계산 방식이 아니다. 검색어에 ‘시스템’을 추가했는데 그 토큰이 청크에 없다면 AND 후보에서 빠진다. **AND가 사소한 내용까지 덜 놓치는 것은 아니다.** 조건이 엄격해져 관련 문서도 놓칠 수 있다. OR는 더 넓게 찾는 대신 잡음이 늘 수 있다.

### 5. JSON에서 pgvector로 옮기기

PostgreSQL은 여전히 테이블에 행을 저장한다. 이번에는 `chunk_id`, 청크 정보 `jsonb`, `embedding vector(1024)` 컬럼을 사용했다. pgvector는 PostgreSQL에 벡터 타입·거리 연산·인덱스를 추가하는 확장 기능이다. 별도의 DB 프로그램으로 분리해서 쓰는 것은 아니다.

이미 JSON에 저장한 벡터를 DB 컬럼으로 옮겼으므로 문서를 다시 임베딩할 필요가 없었다. 문자열 표현 그대로 일반 텍스트 컬럼에 넣는 대신 벡터 타입으로 변환해 저장한다. 저장 장소가 바뀌어도 같은 벡터와 질문을 사용하면 정확 검색 순위가 같아야 한다. 실제 Python/DB Top-k가 일치했고 최대 점수 차이는 약 `1.3e-7`이었다.

코사인은 벡터의 방향이 얼마나 비슷한지 비교하는 기준이다. 벡터 검색은 더 큰 개념이며 코사인 외에 다른 거리 기준도 있다. pgvector의 `<=>`는 코사인 **거리**이고 작을수록 가깝다. 출력한 유사도는 `1 - 거리`였다.

같은 URM 질문의 전체 벡터 검색 결과는 다음과 같았다.

| 순위 | 문서 | 유사도 |
|---|---|---:|
| 1 | URM 초기 설정 | 0.6678 |
| 2 | URM 고객사 배포 전 체크리스트 | 0.6642 |
| 3 | Admin 사용자 가이드 / Add Server | 0.6583 |

2위는 본문이 ‘현재 기능을 사용중인 고객사 없음’뿐이었다. 경로·제목을 포함한 임베딩 입력이 관련 맥락을 줄 수 있어서, 유사도가 높아도 질문에 답할 본문이 충분한 것은 아니다. 맥락 제거 실험은 생략했으므로 정확한 기여도를 측정한 결과로 해석하지 않는다.

### 6. 정확 검색과 HNSW

정확 검색은 대상 벡터 전체를 비교한다. ANN은 가까운 결과를 빠르게 찾기 위한 근사 탐색이고, HNSW는 그 구현 방법 중 하나인 여러 층의 그래프 인덱스다. 코사인을 대체하는 알고리즘이 아니라 **코사인 거리를 이용해 어디를 탐색할지 줄이는 구조**다.

미리 벡터를 노드로, 가까운 이웃을 연결로 구성한다. 위층은 희소하고 위층에 있는 노드는 아래층에도 존재하며 맨 아래층에는 모든 벡터가 있다. 벡터를 주제별 층에 배정하거나 질문의 층을 분류하는 구조는 아니다. 아래층에서도 벡터 숫자는 같지만 이웃 연결은 층별로 달라진다. 위층에서 B와 D를 거쳐 L에 도착해 내려와도 B·D가 사라지는 것은 아니다.

```text
위층:     B → D → L  (질문에 가까운 지점으로 이동)
                  ↓  같은 L에서 아래층 탐색 시작
아래층:   L → F, G, H … (여러 후보와 이웃을 탐색)
```

트리의 자식으로 내려가는 것이 아니라 같은 노드의 다음 층으로 이동한다. 위층에서 접근 지점을 찾고 아래층에서 주변 후보를 탐색하므로 모든 노드를 방문하지 않을 수 있다. ‘상관없는 벡터를 정확히 제거한 뒤 1,000개만 비교’하는 방식이 아니며 실제 최근접 Top-5를 놓칠 수 있다. `ef_search`는 탐색 후보 폭을 조절하는 설정으로 정확한 방문 개수나 ‘상위층에서 충분한 개수를 채우면 종료’라는 규칙은 아니다.

인덱스를 만들었다고 모든 SQL이 항상 사용하는 것은 아니다. `EXPLAIN ANALYZE`에서 `Index Scan using chunks_embedding_hnsw`를 확인했다. 실습 스크립트는 exact/hnsw 모드를 구분하고 실행 계획으로 실제 사용 여부를 출력한다. 처음 ‘HNSW 없음’이라는 고정 안내만 믿으면 잘못 판단할 수 있다.

제공한 실행 기록에서 exact는 65.023ms, HNSW는 6.371ms로 약 10.2배 차이였다. 두 번의 DB 실행 시간 비교이며 질문 임베딩 시간은 제외했다. 이번 질문의 Top-3는 3/3 겹쳤지만 항상 같은 정확도나 10배 성능을 보장하지 않는다. 캐시 상태·질문·데이터 크기·반복 측정 조건을 맞춰야 일반적인 성능을 판단할 수 있다.

## 예시 / 코드

코사인 검색용 인덱스를 생성했다.

```sql
CREATE INDEX chunks_embedding_hnsw
ON chunks USING hnsw (embedding vector_cosine_ops);
```

검색은 작은 코사인 거리부터 정렬하고 필요한 개수만 가져온다. `:query_embedding`은 클라이언트에서 질문 벡터를 바인딩할 자리다.

```sql
SELECT chunk_id, 1 - (embedding <=> :query_embedding) AS similarity
FROM chunks
ORDER BY embedding <=> :query_embedding
LIMIT 3;
```

실제 코드와 재현 명령은 [검색 실습 README](../labs/01-search-generations/README.md)에 정리했다. 원문 데이터와 벡터 캐시는 Git에 포함하지 않았다.
