> 2001년 시맨틱 웹 비전에서 RDF·OWL, Linked Data, DBpedia·Wikidata, Google Knowledge Graph, 기업 KG, GraphRAG, Palantir Ontology까지. 4주차에 열 멤버가 같은 연표를 각자 썼고, 결론도 같다 — **시맨틱 웹은 실패한 게 아니라 범위를 좁혀 계승됐고, 앞 기술이 뒤 기술로 교체된 순서도 아니다**(Yeongeunn, yujeong430). 이 페이지는 단계마다 "무엇을 포기하고 무엇을 얻었나"를 한 표에 놓고, 멤버마다 다른 설명 각도를 나란히 둔다. RAG 쪽 연표는 [[RAG-변천사]].

## 갈리는 지점

### 시맨틱 웹은 왜 안 됐나 — 조정 문제

- dldusgh318(04.1 분담 노트)의 명제: **"시맨틱 웹은 모두의 협력이 필요한 구조에서 생기는 조정 문제를 해결하지 못했고, KG는 그 문제를 해결했다기보다 협력이 덜 필요한 범위로 좁혀 우회했다."** HTML은 쓰면 내 페이지가 바로 보이지만(내가 이득), 시맨틱 메타데이터는 외부 프로그램이 이해해야 생태계가 이득이다. "좋은 건 알겠는데 내가 왜 먼저 해야 하지?" → 구조화 데이터 부족 → 유용한 서비스 부족 → 만들 이유 부족의 루프.
- 합의 문제는 참여만으로 안 풀린다. Doctorow의 Metacrap을 근거로 "같은 현실을 표현하는 방법은 하나가 아니다". dldusgh318은 자기 실습에서 "사용한다/도입했다/활용했다"를 하나의 `USES_TECHNOLOGY`로 접은 것이 "유일한 정답이라서가 아니다"라고 적었다.
- do-dop은 실패 이유를 4개로 나눴다: 데이터 제공 비용, 공통 의미 합의(Company / LegalEntity / Brand / Subsidiary / BusinessUnit), 품질·신뢰, 현실의 모호성. yujeong430도 넷: 식별자·어휘를 오래 유지할 사람, 여러 조직의 의미 합의, 전면 구조화의 직접 이득 불분명 — "따라서 RDF와 링크드 데이터는 사라진 것이 아니라 범위가 정해진 분야와 서비스에서 사용된다". 이것이 스터디가 **작은 닫힌 스키마**로 시작하는 이유이고, Yeongeunn·kdyann·yujeong430의 스키마가 독립적으로 클래스 5·술어 7 규모에 수렴한 것을 설명한다 → [[폐쇄-스키마-설계]].
- **"실패"를 쪼개면** 정착 못 한 것은 웹 전체의 공통 의미 체계·공용 온톨로지·웹 규모 추론이고, 살아남은 것은 schema.org·JSON-LD 같은 가벼운 구조화와 Wikidata 같은 개체·관계 그래프다. schema.org가 살아남은 이유는 만드는 쪽에도 이득(검색 노출)이 생겼기 때문 — 구조화 아이디어 자체가 불가능했던 게 아니라는 반증 (dldusgh318). do-dop도 "시맨틱 웹은 실패하고 KG가 성공했다는 요약은 틀렸다"로 같은 결론.
- dldusgh318의 자기 교정: 처음엔 "보편성과 논리를 포기할수록 성공했다"로 읽었지만, 정확히는 **"문제의 범위를 좁히고, 외부 참여자와의 합의를 덜 요구하며, 실제 사용 목적에 맞는 모델을 선택할수록 적용하기 쉬워졌다"**. 그 대가는 사일로의 재등장 — "시맨틱 웹은 사일로를 연결하려 했고, 기업 KG는 사일로의 존재를 인정한 채 그 안에서 잘 동작하는 방식을 택했다."

### 온톨로지라는 말의 계보 (kdyann)

- 아리스토텔레스 범주론 → 프레게 논리학(1879) → Gruber(1993)의 "개념화의 명시적 명세" — 배경은 지식기반 시스템 **사이의 공유·재사용**. 1차 논리의 '1차'는 양화 대상이 개별 대상이라는 뜻이고, 괴델 완전성(1930)과 처치 결정불가능성(1936)은 다른 이야기라 1차 논리를 "표현력과 계산가능성의 균형점"으로 적으면 오해다. 링크드 데이터는 "공개 데이터인지"와 별개의 개념(웹 식별자·표준으로 연결하는 방법). 연표 날짜의 1차 출처 URL은 kdyann 노트에 없다.
- kungbi: 시맨틱 웹 계층도(layer cake)는 "현재 모든 시스템이 그대로 구현해야 하는 설계도가 아니다". LOD Cloud의 각 원은 개별 사람이 아니라 데이터셋이다. 외부 그림 5장에 라이선스·출처·처리 내역 표를 붙였다 — 스터디에서 유일한 관행.
- sunghyun의 절제: GraphRAG 논문의 "약 100만 토큰 규모 데이터의 글로벌 질문에서 포괄성·다양성 개선"은 그 평가의 결론이며 정확도·지연·비용 우월을 증명하지 않는다. yujeong430: "한 공지에서 답을 찾는 질문에는 전체 커뮤니티 요약이 필요하지 않을 수 있다" — GraphRAG는 그래프만이 아니라 claims 추출과 텍스트 임베딩을 함께 쓰는 구현이다 (Yeongeunn).

### 멀티홉 실패의 원인을 어느 층위에서 보나

같은 "RAG가 관계를 못 따라간다"를 네 층위로 설명한다. 틀린 말은 없지만 합성할 때 섞으면 진단이 흐려진다.

| 층위 | 설명 | 누가 |
|---|---|---|
| 분포 | 필요한 정보가 서로 다른 청크에 흩어져 있다 | heebindev |
| 스코어링 | 벡터 검색은 질문과 청크를 **개별적으로** 비교하므로 필요한 청크를 다 못 가져온다 | e0ng |
| 융합 | RRF는 없는 두 번째 검색을 만들어주지 않는다 | dldusgh318 (3주차) |
| 표현 | 흩어진 사실을 전부 가져오는 대신 **조인·경로 탐색 문제로** 바꿔야 한다 | lys0611 |

### 스터디로의 환류

- 지금은 "내 문서 → 내가 정한 관계 → 내 그래프"라 합의 대상이 1명이다. 여러 멤버의 그래프를 합치는 순간 `USES` vs `USES_TECHNOLOGY`, `Spring`/`Spring Boot`/`SpringBoot`, 같은 사람의 동일성 문제가 돌아온다 — 관계 합의 ↔ 공통 Vocabulary, 대상 통합 ↔ Entity Resolution, 구조 통합 ↔ Schema·Ontology Alignment, 빠진 정보 ↔ 불완전한 데이터 (dldusgh318). "웹 전체에서는 어려웠던 조정 문제를 작은 스터디라는 제한된 범위에서 직접 경험하게 되는 셈." → [[10기-KG-스터디]] 남은 일.
