# GraphRAG — 검색과 그래프의 결합

## 1. 그래프를 답변의 근거로 사용하기

문서 검색 기반 RAG는 질문과 관련된 문서 조각을 찾아 생성 모델에 전달한다. 생성 모델은 전달받은 내용을 바탕으로 답변한다. 3주차에는 BM25·벡터·RRF 검색을 비교했고, 5주차에는 문서에서 대상과 관계를 추출해 그래프로 저장하고 조회했다.

6주차의 질문은 **“만들어 둔 그래프를 답변에 어떻게 활용할 것인가?”**다.

```text
문서 검색 RAG
질문 → 관련 문서 조각 검색 → 컨텍스트 조립 → LLM 답변

그래프를 결합한 RAG
질문 → 관련 대상·관계 조회 + 문서 검색 → 컨텍스트 조립 → LLM 답변
```

컨텍스트는 모델이 답변할 때 참고하도록 전달하는 정보다. 검색한 문서, 그래프에서 찾은 관계, 그 관계의 원문 근거 등이 들어간다. 리트리버는 이 정보를 찾아오는 부분을 가리킨다.

**GraphRAG는 특정 생성 모델의 이름이 아니라, 그래프에서 얻은 정보를 답변의 근거로 활용하는 방식**이다. 생성 모델을 바꾸지 않고도 근거를 검색하는 경로를 확장할 수 있다. Microsoft의 GraphRAG는 이 접근을 구현한 프로젝트 중 하나이며, 모든 GraphRAG가 동일한 구조를 사용하지는 않는다.

## 2. 문서 검색에 관계 조회를 더하는 이유

이룸페이 문서에 다음 질문을 던진다고 가정한다.

> 회원탈퇴를 막는 정책은 어떤 거래 유형과 관련되는가?

문서 검색에서는 질문과 관련 있는 청크를 가져온다. 필요한 정책과 거래 유형이 모두 검색되면 답할 수 있지만, 일부 정책만 검색되면 답변에서도 정보가 빠질 수 있다.

그래프에는 다음과 같이 연결할 수 있다. 아래는 관계 구조를 설명하기 위한 단순화된 예시다.

```text
[진행 중인 더치페이가 있으면 탈퇴를 차단하는 정책]
    ├─ blocksOperation → [회원탈퇴]
    └─ concernsTransactionType → [더치페이]
```

이 구조에서는 회원탈퇴를 차단하는 정책을 찾고, 각 정책이 대상으로 하는 거래 유형을 조회할 수 있다. 질문과 비슷한 문장을 찾는 데 더해, **저장된 관계를 따라 필요한 정보를 모으는 것**이다.

그래프가 항상 더 정확한 것은 아니다. 추출 과정에서 정책을 누락하거나 잘못 연결했다면 조회 결과에도 문제가 생긴다. 문서 검색과 그래프 조회는 서로 다른 방식으로 근거를 찾으며, 어느 쪽이 유리한지는 질문과 데이터에 따라 달라진다.

### 관계 방향과 조회 방향

`정책 → blocksOperation → 회원탈퇴`는 “정책이 특정 조건에서 회원탈퇴를 차단한다”는 의미다. 회원탈퇴에서 출발해 들어오는 관계를 조회하면 “어떤 정책이 회원탈퇴를 차단하는가?”를 찾을 수 있다.

```text
저장된 관계: 정책 ── blocksOperation ──→ 회원탈퇴
조회할 질문: 회원탈퇴 ←── 어떤 정책이 차단하는가?
```

화살표의 의미는 유지하면서 반대쪽에서 관계를 찾는 것이다. 또한 그래프의 화살표는 실행 순서가 아니다. `서비스 → exposesAPI → API`는 제공 관계이고, `API → callsService → 서비스`는 호출 관계다. 제공 관계만으로 실제 호출 엔드포인트나 호출 순서를 확정할 수는 없다.

## 3. 로컬 서치 — 특정 대상 주변의 근거 찾기

로컬 서치의 ‘로컬’은 컴퓨터의 실행 위치가 아니라 **그래프의 특정 대상 주변**을 뜻한다.

> 계정을 없애지 못하는 경우는 무엇인가?

이 질문을 처리하려면 먼저 “계정을 없애기”가 그래프의 ‘회원탈퇴’와 관련된 표현임을 찾아야 한다. 이렇게 질문 속 표현을 그래프의 대상에 연결하는 작업을 **엔티티 링킹**이라고 한다. 이름·별칭 일치, 임베딩 유사도, 모델의 판단 등을 사용할 수 있다.

```text
질문: 계정을 없애지 못하는 경우는?
    ↓ 엔티티 링킹
회원탈퇴 노드
    ↓ 관련 관계 조회
회원탈퇴를 차단하는 정책들
    ↓ 원문 근거와 조건 수집
컨텍스트 조립
    ↓
LLM 답변 + 출처
```

연결된 노드와 관계 중 필요한 부분을 모은 것을 서브그래프라고 한다. 모든 주변 관계를 무조건 가져오기보다 질문에 필요한 관계 종류와 탐색 범위를 정해야 한다. 범위를 너무 좁히면 근거를 놓치고, 너무 넓히면 무관한 정보와 토큰 사용량이 늘어난다.

Microsoft GraphRAG의 로컬 서치도 질문과 관련된 엔티티를 찾고, 그래프 정보와 원문 정보를 함께 모아 컨텍스트를 구성한다. 그래프 관계만 전달하기보다 원문 근거를 함께 전달하면 조건과 맥락을 확인하는 데 도움이 된다. [로컬 서치 설명](https://github.com/microsoft/graphrag/blob/main/docs/query/local_search.md)

## 4. 하이브리드 리트리버 — 벡터로 찾고 그래프로 확장하기

벡터 검색은 표현이 다른 질문에서 관련 대상을 찾는 데 사용할 수 있다. 그래프 탐색은 그 대상과 연결된 정보를 모으는 데 사용할 수 있다.

```text
“계정을 없애기”
    ↓ 벡터 검색으로 관련 대상 찾기
회원탈퇴
    ↓ 그래프 관계로 확장
차단 정책 → 관련 거래 유형
```

이때 ‘하이브리드’가 무엇을 결합하는지 구분해야 한다.

| 맥락 | 결합 대상 | 역할 |
|---|---|---|
| 3주차 하이브리드 검색 | BM25 + 벡터 검색 | 두 검색 결과를 RRF 등으로 융합 |
| 6주차 하이브리드 리트리버 | 벡터 검색 + 그래프 탐색 | 관련 시작점을 찾은 뒤 관계로 확장 |

두 구성을 함께 사용할 수도 있다. 기존 BM25·벡터 검색 결과에 그래프에서 찾은 근거를 추가하는 식이다. 그래프 결과를 결합한다고 반드시 RRF를 사용해야 하는 것은 아니다.

문서 청크의 벡터와 그래프 노드의 벡터는 구분해야 한다. 기존 청크 벡터를 만들었다고 모든 노드에도 벡터가 생기는 것은 아니다. 연결 방법으로는 다음 두 가지를 생각할 수 있다.

- 노드의 이름과 설명을 임베딩해 관련 노드를 직접 찾는다.
- 문서 청크를 검색하고, 해당 청크를 근거로 추출된 노드와 관계에 연결한다.

어떤 방법이든 검색된 문서와 그래프 대상 사이의 식별자 연결을 유지해야 한다. 이름이 비슷하다는 이유만으로 서로 다른 대상을 합치면 잘못된 관계로 확장될 수 있다.

## 5. 글로벌 서치 — 전체 자료의 경향 파악하기

로컬 서치가 특정 대상에 관한 질문이라면, 글로벌 서치는 자료 전체를 아우르는 질문을 다룬다.

> 프로젝트 전반에서 반복적으로 강조한 설계 원칙은 무엇인가?

회원탈퇴 주변만 조회해서는 인증·결제·카드 등 여러 영역에 걸친 경향을 충분히 설명하기 어렵다. Microsoft GraphRAG는 서로 밀접하게 연결된 대상들을 커뮤니티로 묶고, 각 커뮤니티에 대한 보고서·요약을 만들어 전체적인 질문에 활용한다.

```text
전체 그래프
    ↓ 커뮤니티 탐지
연결이 밀접한 대상들의 묶음
    ↓ 묶음별 보고서·요약 생성
질문과 관련된 정보를 종합
    ↓
전체 관점의 답변
```

여기서 커뮤니티는 사람들의 모임이 아니라 그래프상의 묶음이다. 예를 들어 인증이나 결제와 관련된 묶음이 나올 수 있지만, 실제 분류는 그래프 구조와 알고리즘에 따라 달라진다. Leiden·Louvain은 이런 커뮤니티 탐지에 사용되는 알고리즘이다.

글로벌 서치에서는 미리 만든 요약을 활용할 수 있는 대신, 요약 과정에서 세부 조건이 빠질 수 있다. 특정 API의 정확한 경로나 상태값을 찾는 질문에는 원문이나 상세 관계 조회가 더 적합할 수 있다. [Microsoft 검색 방식 개요](https://microsoft.github.io/graphrag/query/overview/)

회원탈퇴 관련 문서로 만든 작은 그래프는 그 범위의 질문을 다룬다. 이 그래프만으로 프로젝트 전체의 경향을 대표할 수는 없다.

## 6. Text2Cypher — 자연어를 그래프 질의로 바꾸기

5주차에는 작성한 Cypher를 실행해 관계를 조회했다. Text2Cypher는 사용자의 자연어 질문을 LLM이 Cypher로 변환하는 단계를 추가한다.

```text
“회원탈퇴 API가 호출하는 서비스는?”
    ↓ 질문 + 그래프 스키마 전달
LLM이 Cypher 생성
    ↓ 질의 검사 후 실행
Neo4j 조회 결과
    ↓
결과에 근거한 답변
```

LLM이 질의문을 작성하고, 실제 데이터 조회는 Neo4j가 수행한다. 모델이 올바른 질의를 만들려면 사용 가능한 노드 종류, 관계 이름, 방향, 속성 이름을 알아야 한다. 미니 온톨로지에서 정한 의미와 실제 Neo4j의 라벨·관계 타입을 연결해 설명하는 것이 중요하다.

자주 발생할 수 있는 오류는 다음과 같다.

- 존재하지 않는 관계 이름이나 속성을 사용한다.
- 관계 방향을 반대로 작성한다.
- API와 업무 기능을 혼동한다.
- 문법은 맞지만 질문과 다른 대상을 조회한다.
- 빈 결과를 보고 실제로 그런 사실이 없다고 단정한다.

그래프에 없다는 것이 원문이나 실제 시스템에도 없다는 뜻은 아니다. 읽기 전용 권한과 결과 수 제한을 적용하고, 실행 성공 여부와 별개로 질의의 의미를 확인해야 한다. [Neo4j RAG 문서](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)

### 세 방식의 구분

| 방식 | 중심 질문 | 예시 |
|---|---|---|
| 로컬 서치 | 이 대상과 연결된 정보는? | 회원탈퇴 차단 정책과 거래 유형 |
| 글로벌 서치 | 전체 자료에서 드러나는 경향은? | 프로젝트 전반의 설계 원칙 |
| Text2Cypher | 질문을 어떤 그래프 질의로 바꿀 것인가? | 호출 서비스 조회문 자동 생성 |

세 방식은 순서대로 거치는 단계가 아니며, 완전히 배타적인 분류도 아니다. Text2Cypher로 특정 대상의 주변 관계를 조회할 수도 있다.

## 7. 그래프 인덱싱과 배치 처리

질문이 들어올 때마다 모든 문서에서 관계를 추출하고 요약하면 처리 시간과 비용이 반복해서 발생한다. 그래서 검색에 필요한 구조를 미리 만들어 둔다.

| 시점 | 처리 |
|---|---|
| 인덱싱 시점 | 문서 처리, 관계 추출, 대상 식별·병합, 그래프 저장, 필요하면 커뮤니티 요약 |
| 질의 시점 | 질문에 필요한 근거 검색, 컨텍스트 조립, 답변 생성 |

**‘빌드 시점 선지불’은 이후 검색에 쓸 구조를 만들기 위해 계산과 비용을 미리 지불한다는 의미**다. 모든 GraphRAG가 커뮤니티 요약을 요구하는 것은 아니다. 로컬 관계 조회만 사용하는 구성과 글로벌 서치 구성의 준비 비용은 다르다. [Microsoft 인덱싱 개요](https://microsoft.github.io/graphrag/index/overview/)

DDIA의 배치 처리 관점에서는 원문 스냅샷을 입력으로 보고, 그래프·임베딩·요약을 다시 생성할 수 있는 파생물로 볼 수 있다. 원문이 바뀌면 어떤 관계와 요약을 갱신해야 하는지도 관리해야 한다. 이를 위해 문서 버전, 청크 ID, 추출 설정, 근거를 함께 남기는 것이 필요하다.

## 8. 비교 실험에서 확인할 것

GraphRAG의 효과는 그래프 화면의 복잡함이 아니라, 같은 질문에서 필요한 근거와 답변이 개선되는지로 확인한다.

| 질문 유형 | 확인할 점 |
|---|---|
| 단일 사실 | 문서 검색으로 충분한데 추가 비용만 발생하지 않는가? |
| 다중 홉 | 여러 관계를 연결해 필요한 근거를 빠짐없이 찾는가? |
| 집계 | 집계 대상과 중복 기준이 명확하며 그래프 범위가 충분한가? |
| 설명·설계 배경 | 관계로 추출하지 않은 원문 맥락도 확보하는가? |
| 근거 없는 질문 | 없는 관계를 만들어 답하지 않는가? |

v1은 하이브리드 문서 검색, v2는 그래프 근거를 추가한 구성으로 비교할 수 있다. 질문 셋과 생성 모델을 고정하고, 검색 범위·컨텍스트 예산·프롬프트 차이를 기록한다. 필요한 근거를 찾았는지와 그 근거로 올바르게 답했는지는 별도로 평가한다. 응답 시간과 모델 호출 비용도 함께 확인한다.

회원탈퇴 중심의 작은 그래프와 전체 문서 검색을 비교할 때는 그래프가 포함하는 범위를 명시해야 한다. 특정 질문에 맞춰 보완한 그래프의 결과를 전체 데이터에 대한 성능으로 일반화하지 않는다.
