# **3. 검색 결과를 LLM에 연결하기 — RAG Agent**

검색 성능을 개선한 다음에는 Hybrid Search 결과를 LLM에 연결했다.

목표는 단순하다.

**내 Notion 데이터를 기반으로 질문에 답하는 개인 데이터 Agent를 만들어보자.**

하지만 LLM에게 내 데이터 전체를 넘기는 것은 아니다.

질문이 들어오면 먼저 검색한다.

```
사용자 질문
    ↓
BM25 top-50
+
Vector top-50
    ↓
RRF
    ↓
Hybrid top-5
```

그리고 이 **top-5 청크만 LLM의 Context로 전달한다.**

---

# **4. Context 조립**

검색된 청크에는 `[1]`부터 `[5]`까지 번호를 붙였다.

```
[1]
title: Write-Behind
source: ...
text: ...

[2]
title: Cache Strategy
source: ...
text: ...

...

[5]
...
```

LLM에게는 짧은 번호만 보여주지만 프로그램 내부에서는

```
[1] → 실제 chunk_id
[2] → 실제 chunk_id
...
```

매핑을 유지한다.

그래서 나중에 LLM이

```
이 내용은 [2]에 근거합니다.
```

라고 답하면 실제 어떤 청크를 가리키는지 확인할 수 있다.

실제 `Write-Behind` 질문에서는 Hybrid top-5 청크가 모두 Context에 포함되었고, 전체 Context는 **2,929자**였다.

---

# **5. LLM에게 답변과 근거를 함께 요청하기**

이제 조립한 Context와 질문을 LLM에게 전달한다.

구조는 대략 다음과 같다.

```
[질문]
Write-Behind의 동작 방식과 데이터 유실 위험은?

[Context]
[1] ...
[2] ...
[3] ...
[4] ...
[5] ...

→ 이 Context를 근거로 답변
→ 사용한 근거 번호와 원문 snippet도 함께 반환
```

응답은 자유 텍스트가 아니라 구조화된 형태로 받는다.

```json
{
  "answer": "...",
  "citations": [
    {
      "source": 1,
      "snippet": "..."
    }
  ],
  "grounded": true
}
```

여기까지가 일반적인 RAG 흐름이다.

하지만 한 가지 문제가 남는다.

**LLM이 말한 인용을 정말 믿어도 될까?**

---

# **6. 인용 검증**

LLM이 `[1]`을 근거라고 말한다고 해서 실제로 `[1]`에 그 내용이 있다는 보장은 없다.

그래서 이번 실습에서는 **LLM의 인용을 프로그램에서 다시 검증했다.**

LLM이 다음과 같이 답했다고 해보자.

```
source  = [1]

snippet =
"캐시에 먼저 저장한 뒤 DB에 비동기로 반영한다."
```

프로그램에서는 실제 `[1]` 청크의 원문에 이 문장이 존재하는지 검사한다.

```python
snippet in chunk.text
```

즉,

```
LLM
"이 문장이 [1]에 있습니다."
        ↓
프로그램
"진짜 있나?"
        ↓
실제 Context 원문 확인
        ↓
있음 → citation_verified = true
없음 → citation_verified = false
```

실제 `Write-Behind` 질문에서는 두 개의 Citation이 모두 원문에서 확인되어

```
citation_verified = true
```

가 되었다.

다만 이 값의 의미를 구분해야 한다.

```
citation_verified = true

→ 인용한 문자열이 실제 Context에 존재한다.  O
→ 답변 전체의 의미가 무조건 정확하다.         X
```

따라서 답변의 의미 정확성은 별도로

```
semantic_correctness = not_evaluated
```

로 관리했다.

# **7. 여기까지 만들었는데 — RAG는 어디에서 실패할까?**

이제 시스템은 다음 구조가 되었다.

```
질문
 ↓
Hybrid Search
 ↓
관련 청크
 ↓
Context
 ↓
LLM
 ↓
답변 + Citation
 ↓
Citation 검증
```

그런데 여기서 새로운 질문이 생겼다.

**검색이 좋아지고 LLM까지 연결하면 모든 질문에 답할 수 있을까?**

이를 확인하기 위해 일부러 여러 정보를 연결해야 하는 질문을 만들었다.

이번 실험에서는 네 가지 유형을 사용했다.

| **사례** | **유형** |
| --- | --- |
| S01 | Single-hop |
| M01 | 2-hop |
| A01 | Aggregation |
| H01 | 3-hop |

결과는 다음과 같았다.

| **사례** | **Normal RAG** | **Oracle** | **최종 판정** |
| --- | --- | --- | --- |
| S01 Single-hop | 정답 | 정답 | 성공 |
| M01 2-hop | 정답 | 정답 | 성공 |
| A01 Aggregation | 정답 | 정답 | Citation 실패 |
| H01 3-hop | 불완전 | 정답 | Retrieval 실패 |

여기서 예상과 조금 다른 결과가 나왔다.

## **8. Multi-hop이라고 무조건 실패하는 것은 아니었다**

M01에서는 **프로젝트의 Spring `AFTER_COMMIT` 처리부터 FastAPI의 Redis/RQ Worker까지 이어지는 분석 요청 흐름**을 질문했다.

이 질문에 답하려면 서로 다른 두 청크가 필요했다.

```
[청크 A]
Spring
→ Transaction Commit
→ AFTER_COMMIT
→ FastAPI 요청

              ↓ 연결

[청크 B]
FastAPI
→ Redis/RQ
→ Worker
→ 분석 수행
```

즉 하나의 청크만으로는 전체 흐름을 설명할 수 없는 **2-hop 질문**이었다.

그런데 Hybrid Search의 top-5를 확인해보니 필요한 Gold Chunk가 **2/2 모두 검색되어 있었다.**

- **의문) 대체 어떻게 검색된걸까..?**
    
    M01은 두 청크의 정보를 연결해야 답할 수 있었지만, 질문 자체에 `AFTER_COMMIT`, `FastAPI`, `Redis/RQ Worker` 등 양쪽 청크를 검색할 수 있는 단서가 포함되어 있었다. 따라서 Hybrid Search 한 번으로 Gold Chunk 2개가 모두 top-5에 포함되었다. 이는 여러 청크를 조합해야 한다는 것과, 중간 결과를 이용해 재검색해야 하는 엄밀한 multi-hop retrieval은 구분할 필요가 있음을 보여준다.

```
Hybrid top-5
   ├─ Gold Chunk A ⭕
   ├─ Gold Chunk B ⭕
   └─ ...
          ↓
두 근거가 모두 Context에 포함
          ↓
         LLM
          ↓
전체 흐름을 연결해 정답 생성 ⭕
```

따라서 M01은 Normal Context와 Oracle Context 모두에서 성공했다.

이 결과를 통해 **Multi-hop 질문이라고 해서 Chunk 기반 RAG가 반드시 실패하는 것은 아니라는 것**을 확인했다. 필요한 여러 청크가 한 번의 검색 결과에 모두 포함된다면 LLM이 이들을 연결해 답할 수 있었다.

반대로 이후 H01에서는 필요한 세 청크 중 두 개가 검색되지 않았다. 즉 이번 실험에서 중요한 것은 단순한 hop 수보다 **“질문에 필요한 청크를 한 번의 검색으로 충분히 확보할 수 있는가”**였다.

# **9. 실제로 실패한 H01 — 3-hop 질문**

H01은 운영 RDS 인증 장애에 관한 질문이었다.

답을 만들려면 다음 정보를 연결해야 했다.

```
RDS 인증 실패
      ↓
왜 발생했는가?
      ↓
오래된 운영 비밀번호
      ↓
어떻게 수정했는가?
      ↓
환경변수 참조
      ↓
어떻게 검증했는가?
      ↓
내·외부 Health Check
```

즉, 세 종류의 근거 청크가 필요했다.

하지만 실제 Hybrid top-5에서는

```
필요한 Gold Chunk: 3개

검색 성공: 1개
검색 실패: 2개
```

였다.

결국 LLM에게 전달된 Context 자체가 불완전했다.

```
원인 청크  ❌
수정 청크  ❌
검증 청크  ⭕

        ↓
      LLM
        ↓

불완전한 답변
```

그렇다면 여기서 하나의 의문이 생긴다.

**이 질문을 못 푼 이유가 LLM의 추론 능력 때문일까, 아니면 검색 때문일까?**

이를 확인하기 위해 **Oracle Context 실험**을 진행했다.

---

# **10. Oracle Context — 검색 실패와 생성 실패를 구분하기**
 Oracle Context 실험 ❓ : 검색 단계를 건너뛰고, 사람이 정답을 푸는 데 필요한 청크를 직접 LLM에게 넣어주는 실험

Normal RAG에서는 검색기가 Context를 결정한다.

```
질문
 ↓
Hybrid Search
 ↓
검색된 청크
 ↓
LLM
```

Oracle 실험에서는 이 검색 결과를 **사람이 알고 있는 정답 청크로 교체한다.**

```
질문
 ↓
정답 청크를 직접 지정
 ↓
LLM
```

중요한 점은 나머지 조건은 동일하다는 것이다.
- Context 조립 방식
- LLM
- Prompt
- Citation 검증


달라진 것은 오직 검색기가 고른 Context가 아닌 **사람이 지정한 정답 Context** 라는 것!


H01의 결과는 명확했다.

```
Normal Context
→ 불완전한 답변 ❌

Oracle Context
→ 정확한 답변   ⭕
```

즉, 필요한 청크를 직접 넣어주자 같은 LLM이 문제를 해결했다.

따라서 이 사례에서는

LLM이 정보를 조합하지 못한 것이 아니라, **검색 단계에서 필요한 정보를 Context에 넣지 못한 것이 직접적인 실패 원인**이었다.

---
# **11. 또 하나의 발견 — Gold Chunk를 놓쳤다고 무조건 검색 실패는 아니다**

Aggregation 사례인 **A01**에서는 조금 다른 현상이 나타났다.

질문은 다음과 같았다.

**“지원자 수 집계 성능을 개선하면서 DB 조회, Redis 캐시, 장애 폴백을 각각 어떻게 설계했나?”**

이 질문에 답하기 위해 총 3개의 Gold Chunk를 지정했다.

| **Gold Chunk** | **담고 있는 정보** | **검색 여부** |
| --- | --- | --- |
| `팀피셜#1062` | DB 조회 개선 — 여러 모집글의 지원자 수를 한 번에 조회하는 그룹핑 쿼리 | ❌ |
| `팀피셜#1063` | Redis 캐시 — 지원 시 값 증분, Cache Miss 시 DB 값 적재 | ❌ |
| `팀피셜#1064` | Redis 장애 시 예외 처리 및 DB 값으로 폴백 | ✅ |

Hybrid Search의 실제 Top-5는 다음과 같았다.

```
1. 팀피셜#1064
2. A기업_지원자_테스트_엔지니어_이연호_포트폴리오#231
3. B기업_지원자_이연호_포트폴리오#669
4. C기업_지원자_이연호_포트폴리오#740
5. 경력기술서#325
```

Gold Chunk만 기준으로 보면 **3개 중 1개만 검색**했기 때문에 Retrieval Coverage는 `1/3 = 0.333`이었다.

```
Gold Chunk 기준

팀피셜#1062  ❌
팀피셜#1063  ❌
팀피셜#1064  ⭕

→ Retrieval Coverage = 0.333
```

처음에는 당연히 **Retrieval Failure**처럼 보였다.

그런데 실제 LLM의 답변은 정확했다.

### **왜 Gold Chunk를 놓쳤는데도 답할 수 있었을까?**

내 데이터에는 같은 프로젝트 경험이 여러 문서에 반복해서 기록되어 있었다.

팀피셜 원본뿐만 아니라 **A기업 포트폴리오, B기업 포트폴리오, C기업 포트폴리오, 경력기술서** 등에도 지원자 수 조회 성능 개선과 Redis 캐싱 경험이 다시 정리되어 있었다.

따라서 원래 Gold로 지정했던 `팀피셜#1062`, `팀피셜#1063` 자체는 검색하지 못했지만, Hybrid Search가 가져온 **다른 청크에 답변에 필요한 동일하거나 유사한 정보가 존재했다.**

```
Gold ID 기준
팀피셜#1062 ❌
팀피셜#1063 ❌
팀피셜#1064 ⭕

        ↓ 하지만

다른 포트폴리오/경력기술서 청크에서
동일한 프로젝트 정보를 검색 ⭕

        ↓

답변에 필요한 정보는 Context에 존재

        ↓

LLM 정답 ⭕
```

여기서 중요한 점을 하나 발견했다.

**Gold Chunk를 찾았는가와 질문에 답할 수 있는 정보를 찾았는가는 완전히 같은 문제가 아니다.**

```
Gold Chunk ID 누락
        ≠
의미상의 Retrieval 실패
```

특히 내 데이터처럼 **같은 프로젝트 경험이 포트폴리오·경력기술서 등 여러 문서에 중복되어 있는 데이터셋**에서는 특정 Gold ID를 놓쳤더라도 다른 청크가 같은 정보를 제공할 수 있다.

따라서 Retrieval 실패 여부를 단순히 **Gold Chunk ID의 포함 여부만으로 판단하면 안 된다는 것**을 확인했다. Recall은 검색 성능을 비교하는 유용한 지표지만, 실제 RAG에서는 **최종 Context에 질문에 필요한 정보가 존재하는지와 LLM이 그 정보를 이용해 올바르게 답했는지까지 함께 확인해야 한다.**

### **A01의 최종 판정**

A01은 Gold Chunk 2개를 놓쳤지만 다른 청크에서 필요한 정보를 확보해 **답변 자체는 정확했다.**

따라서 Retrieval Failure로 판정하지 않았다.

다만 답변에 포함된 Citation 하나가 실제 Context의 원문 부분 문자열과 일치하지 않아 최종 실패 유형은 **Citation Failure**로 기록했다.

```
Gold Recall       → 1/3
Answer            → 성공
Retrieval Failure → X
Citation          → 1건 검증 실패

최종 판정 → Citation Failure
```

이 사례를 통해 **검색 평가의 Recall과 실제 RAG의 Answerability는 구분해서 봐야 한다**는 점을 확인할 수 있었다.

# **13. 이번 실습에서 확인한 것**

### **① BM25와 Vector는 서로 다른 실패 패턴을 가진다**

W2에서 직접 확인했다.

```
BM25   → 정확한 표현에 강함
Vector → 의미적 표현에 강함
```

### **② RRF로 결합하면 평균 Recall을 높일 수 있었다**

이번 10개 질문에서는

```
Recall@10

BM25      0.610
Vector    0.682
Hybrid    0.734
```

로 Hybrid가 가장 높은 값을 기록했다.

다만 **모든 질문에서 Hybrid가 최고였던 것은 아니다.**

### **③ 검색 결과를 LLM에 연결해 개인 데이터 RAG를 만들 수 있었다**

```
Hybrid top-5
→ Context
→ LLM
→ 답변
```

구조로 내 데이터에 자연어로 질문할 수 있게 되었다.

### **④ Citation을 프로그램으로 검증할 수 있었다**

LLM이 제시한 근거 문장이 실제 Context에 존재하는지 확인해

```
citation_verified
```

를 별도로 기록했다.

### **⑤ Multi-hop 자체가 실패 원인은 아니었다**

2-hop 질문은 필요한 청크가 모두 검색되어 정상적으로 해결됐다.

### **⑥ 실제 병목 중 하나는 Retrieval이었다**

H01에서는 필요한 세 청크 중 두 개를 놓쳤고,

```
Normal ❌
Oracle ⭕
```

결과가 나타났다.

같은 LLM에 정답 청크를 직접 제공하자 해결됐으므로, 이 사례에서는 **Generation보다 Retrieval이 직접적인 병목**이었다.

# **14. 그래서 다음은? — 검색에서 관계로**

여기까지 오면 다음 질문이 자연스럽게 생긴다.

H01의 정보를 다시 보면 사실 각각의 정보는 이미 내 데이터에 존재했다.

```
RDS 인증 실패

오래된 운영 비밀번호

환경변수 참조

Health Check
```

문제는 현재 시스템에서는 이 정보들이 단순히

```
chunk_31
chunk_928
chunk_1201
```

이라는 **서로 독립된 텍스트 조각**이라는 것이다.

검색기가 이들을 모두 찾아줘야만 LLM이 관계를 연결할 수 있다.

하지만 실제 정보에는 관계가 존재한다.

```
RDS 인증 실패
   ── caused_by ──→ 오래된 운영 비밀번호

오래된 설정
   ── resolved_by ──→ 환경변수 참조

배포 정상화
   ── verified_by ──→ Health Check
```

현재 Chunk 기반 검색에는 이 관계가 명시적으로 저장되어 있지 않다.

그래서 W4에서는 새로운 가설을 검증한다.

**텍스트를 잘 검색하는 것을 넘어, 데이터 사이의 관계를 명시적으로 저장하면 여러 청크에 흩어진 정보를 더 안정적으로 찾을 수 있을까?**

이를 위해 다음 주에는 텍스트에서 **Triple**을 추출한다.

```
(subject, predicate, object)

(RDS 인증 실패, caused_by, 오래된 운영 비밀번호)
(오래된 설정, resolved_by, 환경변수 참조)
(배포 정상화, verified_by, Health Check)
```

그리고 W3에서 실패했던 **동일한 H01 질문과 Gold Chunk를 그대로 사용해**

```
Chunk Hybrid Search
        VS
Relation / Graph Search
```

를 비교한다.

즉 W4의 목적은

**“그래프가 더 좋다”를 가정하는 것이 아니라, W3에서 실제로 관찰한 Retrieval 실패를 관계 기반 탐색이 해결할 수 있는지 직접 검증하는 것**

이다.

## **한 줄 정리**

```
W2
BM25와 Vector는 서로 다른 방식으로 검색한다
        ↓
W3
RRF로 둘을 결합하면 어떨까?
        ↓
실험
Hybrid의 평균 Recall이 가장 높았다
        ↓
그럼 LLM까지 연결해보자
        ↓
Hybrid Search → Context → LLM → Citation
        ↓
그런데 여러 청크의 관계가 필요한 질문에서 Retrieval 실패가 발생했다
        ↓
Oracle Context를 넣으니 해결됐다
        ↓
"검색보다 관계를 직접 저장하면 어떨까?"
        ↓
W4 — Triple / Knowledge Graph
```

**검색을 더 잘하는 것만으로 충분하지 않았다.**

W3에서는 BM25와 Vector를 RRF로 결합해 검색 범위를 넓혔지만, 필요한 정보가 여러 청크에 흩어진 H01에서는 여전히 일부 근거를 찾지 못했다. 반면 동일한 LLM에 정답 청크를 직접 제공하자 문제를 해결했다. 이 결과를 바탕으로 W4에서는 **텍스트 조각 사이의 관계를 명시적으로 저장하는 것이 실제 Retrieval 실패를 개선할 수 있는지** 검증한다.
