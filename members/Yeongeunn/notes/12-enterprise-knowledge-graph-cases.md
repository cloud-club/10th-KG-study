# 기업의 지식 그래프 활용 사례

## 1. 기업에서 관계를 관리하는 이유

기업 데이터는 상품, 사람, 기술, 설비처럼 같은 대상을 여러 시스템에서 서로 다르게 표현한다. 문서를 검색하는 것만으로는 동일 대상을 연결하거나 변경의 영향을 따라가기 어려울 수 있다.

지식 그래프는 대상과 관계를 명시해 검색·추천·분석·업무 실행에 활용한다. 아래는 기업이 공개한 자료를 바탕으로 정리한 사례다. 도식은 각 접근을 설명하기 위해 단순화한 예시이며 실제 내부 스키마를 재현한 것은 아니다.

## 2. 구글 — 문자열에서 대상 중심 검색으로

같은 이름이 여러 대상을 가리키고, 같은 대상도 여러 이름으로 불린다. 검색어의 글자만 비교하면 사용자가 어떤 대상을 의미하는지 구분하기 어렵다.

구글은 2012년 Knowledge Graph를 소개하며 검색 대상을 구별하고 관련 사실과 연결된 대상을 제공하는 방향을 설명했다. 단어가 나온 문서를 찾는 데서 나아가 대상 단위로 정보를 묶는 접근이다.

```text
인물 ─출생지→ 도시
인물 ─참여 작품→ 영화
영화 ─감독→ 다른 인물
```

대상을 정확히 연결하면 관련 정보를 모아 보여줄 수 있다. 반대로 동명이인을 합치면 잘못된 사실도 함께 붙는다. 이름의 유사성과 대상의 동일성을 구분하는 작업이 중요하다.

출처: [Google — Introducing the Knowledge Graph](https://blog.google/products/search/introducing-knowledge-graph-things-not/)

## 3. 애플 — 구조화된 지식과 웹 콘텐츠의 연결

구조화된 지식베이스는 대상의 속성을 조회하기 좋지만, 웹 문서의 모든 정보를 미리 담기는 어렵다. 웹 검색은 범위가 넓지만 문서가 어느 대상을 설명하는지 연결해야 한다.

애플의 공개 연구 소개인 *Growing and Serving Large Open-domain Knowledge Graphs*는 웹 콘텐츠에 의미 주석을 붙여 지식 그래프와 연결하고 검색·랭킹에 활용하는 접근을 설명한다.

```text
지식 그래프의 대상 ←설명하는 콘텐츠─ 웹 문서
```

그래프의 구조화된 정보와 웹의 넓은 정보를 연결하는 방식이다. 문서가 대상을 실제로 설명하는지, 정보가 최신인지 판단하는 문제는 남는다. 이 공개 자료만으로 애플 제품 전체의 저장 구조나 모든 질의 처리 경로를 확정할 수는 없다.

출처: [Apple Machine Learning Research](https://machinelearning.apple.com/research/open-domain-knowledgegraphs)

## 4. 아마존 — 상품 속성에서 사용 목적까지

### AutoKnow: 제각각인 상품 정보를 정리

상품군마다 필요한 속성이 다르고, 중요한 값이 상품 설명이나 리뷰에만 들어 있을 수 있다. 모든 상품을 사람이 읽고 구조화하기에는 작업량이 크다.

아마존의 AutoKnow는 상품 분류·카탈로그·사용자 로그 등을 활용해 상품 그래프를 보강하는 접근이다. 유형과 속성을 발견하고, 비정형 텍스트에서 정보를 보충하며, 오류와 동의어를 처리하는 단계로 구성된다.

```text
상품 ─종류→ 텀블러
상품 ─소재→ 스테인리스
상품 ─용량→ 500mL
```

표현이 달라도 공통 속성으로 비교할 기반을 만들 수 있다. 속성 추출·단위 정규화가 틀리면 구조화된 결과도 틀리므로 검증이 필요하다.

출처: [Amazon Science — AutoKnow](https://www.amazon.science/blog/building-product-graphs-automatically)

### COSMO: 상품과 사용하는 이유를 연결

‘비 오는 날 사용할 신발’ 같은 요청에는 상품명뿐 아니라 사용 상황과 기능의 연결이 필요하다.

아마존의 COSMO는 검색–구매 및 함께 구매된 상품 데이터에서 사용 목적 등의 관계 후보를 LLM으로 생성한다. 사람의 라벨링과 기계학습 기반 필터링, 검토 결과의 재반영을 통해 품질을 다루는 절차를 설명한다.

```text
상품의 기능 ─도움이 되는 상황→ 사용 목적
```

속성 검색을 넘어 의도와 관련된 정보를 활용하는 접근이다. 함께 구매됐다는 사실이 특정 구매 이유를 증명하지는 않으므로, 모델이 생성한 관계를 곧바로 사실로 취급해서는 안 된다.

출처: [Amazon Science — COSMO](https://www.amazon.science/blog/building-commonsense-knowledge-graphs-to-aid-product-recommendation)

## 5. LinkedIn — 사람·직무·스킬의 표준화

사용자는 같은 직무나 기술을 서로 다른 표현으로 입력한다. 프로필과 채용공고를 문자열로만 비교하면 관련성이 있는 후보를 놓치거나 다른 의미의 표현을 섞을 수 있다.

LinkedIn은 회원·채용공고·직함·스킬·회사 등의 개체를 지식 그래프로 구성해 검색과 추천 등에 활용한다고 설명한다. 사용자 생성 데이터를 표준화하며 개체 후보 생성, 의미 구분, 중복 제거와 사람의 검증을 결합한다.

```text
회원 ─보유 스킬→ 기술
채용공고 ─요구 스킬→ 기술
회원 ─재직→ 회사
```

공통 스킬과 회사 ID를 중심으로 다른 표현의 정보를 연결할 수 있다. 공개 자료는 사용자가 입력한 관계와 모델이 추정한 관계를 구분하고 피드백을 수집하는 과정도 다룬다. 직접 입력한 정보 역시 오류가 있을 수 있다는 점이 중요하다.

출처: [LinkedIn Engineering — Building the LinkedIn Knowledge Graph](https://www.linkedin.com/blog/engineering/knowledge/building-the-linkedin-knowledge-graph)

## 6. Siemens — 설계 변경의 영향을 시스템 너머로 추적

제조에서는 설계·생산·정비 정보가 서로 다른 시스템에 저장된다. 부품 하나의 변경이 어떤 제품이나 작업에 영향을 주는지 보려면 여러 시스템의 식별자와 관계를 연결해야 한다.

Siemens의 공개 기술 글은 산업 데이터를 지식 그래프의 의미 모델로 연결하고, 설계 변경의 영향을 제조·서비스 영역까지 파악하는 활용을 설명한다. 기업 전체에서 이미 같은 성과가 검증됐다는 의미가 아니라 공개된 접근과 활용 시나리오다.

```text
설계 변경 ─대상→ 부품
부품 ─사용됨→ 제품
제품 ─연결→ 제조·서비스 기록
```

변경 대상과 연결된 데이터를 따라갈 기반을 제공한다. 실무에서는 같은 부품의 버전, 시스템별 코드, 갱신 시점이 맞아야 의미 있는 결과를 얻을 수 있다.

출처: [Siemens — The AI context layer](https://blogs.sw.siemens.com/rapidminer/ai-context-layer-knowledge-graph/)

## 7. AstraZeneca·Elsevier — 연구 근거를 연결한 표적 탐색

신약 연구에서는 여러 자료에 흩어진 생물학적 관계를 함께 검토해야 한다. 논문을 각각 검색하는 것만으로는 어떤 연결이 연구 가설을 지지하는지 살펴보기 어려울 수 있다.

Elsevier가 공개한 AstraZeneca 사례는 암 연구의 후성유전학 표적 탐색을 위해 맞춤형 지식 그래프를 구축한 내용을 다룬다. 알려진 결과를 확인하고 새로운 연구 질문을 탐색하는 데 활용했다고 설명한다.

```text
연구 대상 ─관련 관계→ 생물학적 현상
관계 ─근거→ 연구 문헌
```

연결된 근거를 검토하며 후보를 좁히는 데 활용할 수 있다. 문헌에 등장하는 연관성이 인과관계나 약물의 임상적 효과를 보장하는 것은 아니므로 후속 연구와 검증이 필요하다.

출처: [Elsevier — Knowledge graphs for target discovery with AstraZeneca](https://www-prod.elsevier.com/resources/astrazeneca-epimap-case-study)

## 8. 팔란티어 — 대상과 관계를 업무 동작에 연결

데이터를 연결해 영향을 파악하더라도 실제 업무에는 담당자 지정, 주문 상태 변경 등 후속 동작이 필요하다.

팔란티어의 Ontology 시스템은 객체·링크·속성과 함께 Action·자동화·업무 로직을 다룬다. 데이터의 의미 구조와 업무에서 수행할 변경을 연결하는 접근이다.

| 요소 | 역할 | 예시 |
|---|---|---|
| Object | 개별 업무 대상 | 주문123 |
| Link | 대상 사이의 관계 | 주문123이 제품A를 포함함 |
| Action | 실행할 업무 변경 | 주문123의 담당자 변경 |

RDF로 관계를 표현하는 것과 권한을 확인해 업무 변경을 실행하는 기능은 다르다. 조회에서 실행으로 확장할수록 권한, 변경 이력, 원래 업무 시스템과의 상태 동기화가 중요해진다.

출처: [Palantir — The Ontology system](https://www.palantir.com/docs/foundry/architecture-center/ontology-system)

## 9. 사례 비교

| 기업·사례 | 주된 연결 대상 | 활용 목적 |
|---|---|---|
| 구글 | 대상·별칭·사실 | 대상 구분과 관련 정보 검색 |
| 애플 | 지식 그래프의 대상·웹 콘텐츠 | 검색·랭킹에 필요한 정보 연결 |
| 아마존 AutoKnow | 상품·유형·속성 | 상품 지식 보강 |
| 아마존 COSMO | 상품·기능·사용 목적 | 의도와 관련된 검색·추천 |
| LinkedIn | 사람·직무·회사·스킬 | 표준화된 검색·추천 |
| Siemens | 설계·부품·제조·서비스 정보 | 시스템 간 영향 파악 |
| AstraZeneca·Elsevier | 연구 대상·생물학적 관계·문헌 | 연구 가설과 표적 탐색 |
| 팔란티어 | 업무 객체·관계·동작 | 분석과 업무 실행 연결 |

공통 과제는 식별자 정리, 관계의 의미 합의, 근거·품질 관리, 변경 반영이다. KG를 사용한다는 사실만으로 모든 기업이 같은 DB나 RDF/OWL을 사용한다고 볼 수는 없다. 지식 그래프라는 접근 안에서도 목적과 구현은 다르다.
