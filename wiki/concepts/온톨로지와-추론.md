> RDF가 사실을 적는다면 RDFS·OWL은 그 사실의 **의미와 규칙**을 적고, 추론은 적지 않은 사실을 유도한다. 4주차에 열 멤버가 독립적으로 같은 결론에 닿은 지점이 셋이다 — `domain`/`range`는 검증이 아니라 추론 선언이다, 추론과 탐색은 다르다, 적혀 있지 않은 것은 거짓이 아니라 모르는 것이다(열린 세계 가정). 그리고 dldusgh318의 자기 규정: 스터디 실습이 만드는 것은 온톨로지가 아니라 **범위를 닫은 작은 관계 스키마**다.

## 세 층

| 층 | 역할 | 어휘 |
|---|---|---|
| RDF | 개별 사실 | `rdf:type`, `rdf:Property` → [[RDF와-트리플]] |
| RDFS | 클래스·속성의 기본 의미와 계층 | `rdfs:Class`, `rdfs:subClassOf`, `rdfs:subPropertyOf`, `rdfs:domain`, `rdfs:range` |
| OWL | 더 풍부한 의미와 논리 관계 | `owl:sameAs`, `owl:differentFrom`, `owl:equivalentClass`, `owl:inverseOf`, `owl:SymmetricProperty`, `owl:TransitiveProperty`, `owl:disjointWith`, Restriction |
| 추론 | 사실 + 규칙 → 적지 않은 사실 | 추론기(reasoner). SPARQL 자체는 추론기가 아니다 (do-dop) |

- "완전히 별개의 데이터 모델이 아니라 RDF 위에서 표현력을 점점 늘려간다" (dldusgh318). **OWL ≠ Ontology**: 온톨로지는 무엇을 정의할 것인가, OWL은 그것을 어떻게 표현할 것인가 (e0ng). "RDFS = 스키마, OWL = 온톨로지로 딱 잘라 나뉘지 않는다. RDFS로도 온톨로지를 표현할 수 있다" (dldusgh318).
- **TBox / ABox**: 개념과 규칙(Terminological) vs 실제 사실(Assertional). 개념적 구분일 뿐 다른 DB에 둘 필요는 없다 — 같은 트리플스토어에 함께 둔다 (do-dop). 도식 `ABox + TBox → 추론 → 새 사실`.
- `rdf:type` vs `rdfs:subClassOf` (e0ng): 전자는 인스턴스→클래스, 후자는 클래스→클래스. `ex:p rdf:type BackendDeveloper` + `BackendDeveloper ⊂ Developer ⊂ Person` ⇒ `ex:p rdf:type Developer`, `ex:p rdf:type Person`. heebindev의 예: 대학생 ⊂ 학생 ⊂ 사람. dldusgh318: `Student ⊂ Person ⊂ Agent`.
- `rdfs:subPropertyOf` 추론: "필수 자료로 사용한다" ⊑ "자료로 사용한다"면 세부 관계만 적어도 상위 관계가 따라온다 (yujeong430, kdyann `지도교수다 ⊑ 가르친다`).
- OWL 성질 예: `inverseOf` — `wrote` + `writtenBy inverseOf wrote` ⇒ 역방향 사실 (do-dop); `근무함 inverseOf 고용함` (e0ng). 기존 사실을 "거꾸로 검색"하는 것은 역관계 추론이 아니다 — `inverseOf`는 다른 술어의 **새 사실**을 도출한다 (sunghyun). OWL 표현력 4종: 동치 클래스, 서로소 클래스, 존재 제한, 전칭 제한. 서로소 위반을 추론기가 **모순**으로 찾을 수 있다 (kdyann, Yeongeunn). "실제로 어떤 추론을 지원하는지는 OWL 프로파일과 추론기에 따라 달라진다" (kdyann). "모든 지식 그래프가 OWL을 쓰는 것은 아니다" (Yeongeunn). `TransitiveProperty` — `partOf`가 이행적이면 `Redis 사용 경험 → 프로젝트 → 포트폴리오`가 직접 따라온다 (dldusgh318). 조건으로 클래스 정의 — `:Parent owl:equivalentClass [ owl:intersectionOf ( :Person [ owl:Restriction ; owl:onProperty :hasChild ; owl:minCardinality 1 ] ) ]` (e0ng, 유일하게 Turtle로 끝까지 씀).
- 1차 논리와의 관계: `∀x (Author(x) → Person(x))`. OWL은 이 논리 의미를 웹에서 계산 가능한 범위로 표현하도록 설계된 언어 (do-dop).

## 추론 ≠ 탐색

- 탐색(SPARQL 패턴·Property Path)은 "어떤 노드가 어떤 경로로 연결돼 있나"를 질의 시점에 따라가는 것이고, 추론은 "주어진 사실과 의미 규칙에서 어떤 사실이 논리적으로 따라오나"를 다룬다 (dldusgh318, do-dop). 실제 KG는 둘을 함께 쓴다 → [[SPARQL]].
- 추론 결과가 질의에 반영되는지는 저장소의 추론 지원·설정에 달려 있다. "SPARQL 자체를 추론기라고 부르면 안 된다" (do-dop). "저장소가 그 결론을 실제 질의 결과에 보여줄지는 추론 기능과 질의 방식에 달려 있다" (yujeong430), "의미 규칙을 처리하는 시스템이 필요하다" (Yeongeunn). RDF를 저장하는 것만으로 자동 추론이 실행되지는 않는다 (sunghyun).
- 추론 ≠ LLM의 그럴듯한 추측. 다만 공리·원본 사실이 틀리면 추론 결과도 현실과 어긋난다 (kdyann). "OWL이 현실의 의미를 알아서 결정하는 것은 아니다" (Yeongeunn).

## `domain`/`range`는 검증이 아니다 — 일곱 멤버의 수렴

- `attends rdfs:range School` + `ex:p attends Redis`는 오류가 아니라 **`Redis rdf:type School`을 추론한다** (dldusgh318, "가장 헷갈렸던 부분"). `A ex:wrote B`만 있어도 A를 Person, B를 Book으로 추론한다 (do-dop). "DB 제약처럼 잘못된 값을 거부하는 기능보다 새 타입을 추론하는 의미론에 가깝다" (lys0611). yujeong430의 반례가 가장 선명하다: `hasTopic`의 domain을 StudyWeek로 선언한 뒤 공지에 `notice-01 hasTopic rdf`를 넣으면 사람은 "공지에 주차용 관계를 썼다"고 의심하지만 **RDFS는 그 이름의 영어 뜻을 읽지 않는다 — notice-01을 StudyWeek로 분류한다.** kdyann: `ex:dayoung a ex:Student` 줄이 없어도 `takes`의 domain에서 학생임이 도출된다. Yeongeunn: "잘못된 입력을 거부하는 SQL 제약과 같은 역할은 아니다", 그래서 추출 결과를 거부하는 검증은 코드에서 따로 한다. kungbi, sunghyun도 같은 결론.
- 잘못된 데이터 검사는 **SHACL**의 일이다. dldusgh318의 3열 대조:

| | OWL | SHACL | 스터디 실습 |
|---|---|---|---|
| 목적 | 의미·추론 | 그래프 검증 | 추출 범위 통제 |
| 관점 | 열린 세계 | 대상 그래프 기준 검사 | 실험용으로 범위를 닫음 |

## OWL로 안 되는 것

- "같은 부모를 가진 두 사람은 형제자매"는 `hasSibling`을 대칭 속성으로 선언해도 **생성되지 않는다** — 대칭성은 이미 있는 관계의 역방향만 도출한다. 조건–결론 규칙은 SWRL이나 별도 규칙 엔진. "최단 경로·복잡한 집계·산술까지 OWL 추론으로 해결하려 해서는 안 된다" (do-dop).
- 추론의 위험: 잘못된 `sameAs` 같은 규칙은 오류를 그래프 전체에 전파한다 (lys0611). 서로 다른 IRI ≠ 서로 다른 대상(비유일 이름 가정)이라 `owl:sameAs`는 표현 방법을 줄 뿐 동일성 판단은 Entity Resolution의 몫 (dldusgh318) → [[RDF와-트리플]].

## 열린 세계 가정과 부정 질문

- **OWA**: 적혀 있지 않은 것은 거짓이 아니라 모르는 것. RDF가 웹의 불완전한 데이터를 전제로 만들어졌기 때문 (dldusgh318, do-dop, lys0611, kdyann, Yeongeunn, kungbi, yujeong430). "수강 기록이 없다 ≠ 아무 강의도 안 듣는다. OWL 조건을 DB 필수 필드 검사처럼 해석하면 안 된다" (kdyann). 필수값 검사는 SHACL의 "최소 한 개" 규칙으로 (yujeong430).
- **닫힌 스키마 ≠ 닫힌 세계 가정** (yujeong430, Yeongeunn): 닫힌 스키마는 쓸 클래스·관계 목록을 제한한다는 뜻이고, 닫힌 세계는 기록되지 않은 사실을 거짓으로 취급한다는 별도의 가정이다. "여기서 닫혀 있는 것은 추출에 사용하는 어휘의 범위다" → [[폐쇄-스키마-설계]]. UI·질의 결과도 "저자 없음"이 아니라 "저자 정보 미등록 / 확인 필요"로 써야 한다 (do-dop). "그래프에 경로가 없다는 것은 현재 데이터로 답을 찾지 못했다는 뜻이지 현실에 그 관계가 없다는 증명은 아니다" (do-dop).
- **왜 부정 질문이 근본적으로 어려운가** (dldusgh318): "아직 구현하지 않은 기능은?"에 답하려면 `구현 기록 없음 ≠ 구현하지 않음`의 간극을 메워야 하고, 그러려면 "내가 가진 목록이 전체다"라는 **닫힌 세계 가정**이 필요하다. 3주차에 답 없음 문항을 별도 실패 유형으로 다룬 이유 → [[RAG-실패-유형]], [[RAG-평가-지표]].
- 관계형 스키마는 보통 닫힌 세계를 가정한다 (lys0611). 단, "RDF = OWA, 프로퍼티 그래프 = CWA"로 외우면 안 된다. OWA는 RDF의 형식 의미론과 RDFS/OWL 추론 생태계에서 중요하게 나타나는 관점이고, 프로퍼티 그래프도 설계에 따라 불완전한 데이터를 다룰 수 있다 (dldusgh318) → [[RDF와-프로퍼티-그래프]].

## 스키마 vs 온톨로지 — 세 입장

| 입장 | 누가 |
|---|---|
| 범위(특정 시스템 ↔ 여러 시스템 공유)와 목적(저장·검증 ↔ 의미·추론)으로 **깔끔히 이분** | lys0611 4축표, dldusgh318 4축표("스키마는 구조, 온톨로지는 의미") |
| "필드와 자료형만 정하면 스키마, 클래스 계층·관계 의미·추론 규칙까지 정하면 온톨로지. **경계가 언제나 명확하지는 않다**" | do-dop, heebindev("겹쳐 쓰이기도 한다"고 유보) |
| 제3의 축: 정의 대상(온톨로지)과 표현 언어(OWL)를 분리 | e0ng; sunghyun("OWL 파일이 없어도 의미를 설계했다면 온톨로지 설계") |
| 절대 경계가 아니라 **무게추**(저장·검증 vs 공유 의미·추론) | kdyann; kungbi("경계가 늘 칼같이 나뉘는 것은 아니다") |

## 멤버들이 확인한 것

- 실측은 없다. OWL 온톨로지를 작성하거나 추론기를 돌린 멤버는 4주차에 없다(dldusgh318은 "OWL 문법을 깊게 보진 못했다"고 명시, Description Logic·OWL Profile·추론 알고리즘·SHACL Shape 문법은 범위 밖으로 선언).
- dldusgh318의 자기 규정(2026-09-23): 관계를 `PART_OF`·`USES_TECHNOLOGY`·`HAS_PURPOSE`·`HAS_STATUS` 넷으로 제한하고 그 외는 추출하지 않는다. "풍부한 의미 규칙과 추론을 가진 온톨로지가 아니라 실험 범위를 제한한 작은 스키마"이며 성격은 SHACL에 가깝다. 범위를 닫았기 때문에 몇 주 안에 구현·평가가 가능하다는 논리 → [[지식그래프와-온톨로지]].

## 열린 질문

- 추론을 실제로 켜 본 멤버가 없다. 공용 인프라에는 추론 엔진이 없고(Neo4j·Postgres), Jena·GraphDB를 띄울지는 미정 → [[로컬-인프라]].
- 멤버 그래프를 합칠 때 `sameAs`를 누가 어떤 근거로 선언할 것인가.
