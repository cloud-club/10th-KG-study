listener → target → deployment → code → data

LSP/SCIP reference + multi-tsconfig provenance

이 장애와 관련된 Slack 논의·Notion 결정·배포 변경은?

incident topic → documents → PR → resource observation

이 서비스를 가장 자주 수정·리뷰·문서화한 사람은 누구인가?

person alias → authored/reviewed/edited edges

resource → relation history → logs/metrics evidence → decision

production snapshot ↔ document revision freshness

7 / Pipeline

수집 방식은 세 가지 선택지가 있다.

PIPELINE
OPTIONS
OPTION A

Batch Snapshot

정해진 주기로 전체 또는 범위를 다시 읽는다.

  • 구현·재현이 단순
  • 누락 복구가 쉬움
  • 신선도와 API 비용 한계
초기 backfill에 적합
OPTION B

Event / Webhook

Slack event, GitHub webhook처럼 변경 즉시 반영한다.

  • 낮은 지연
  • 변경량만 처리
  • event 유실·순서 문제
실시간 증분에 적합
OPTION C · RECOMMENDED

Hybrid

event로 빠르게, 주기 reconciliation으로 정확하게.

  • backfill + incremental
  • checkpoint + idempotency
  • full scope로 삭제 검증
운영 구조로 권장
EVENT FOR SPEED, SNAPSHOT FOR TRUTH14 / 17
7 / Recommended

처음부터 실시간보다
정확한 backfill에서 시작한다.

BUILD
ORDER
PHASE 1

계약 고정

schema, ID, redaction, completeness, source scope.

PHASE 2

Backfill

원천별 snapshot을 읽어 payload와 native row 적재.

PHASE 3

Enrichment

chunk, embedding, code analysis, relation candidate 생성.

PHASE 4

Incremental

cursor, webhook, commit diff로 변경분 반영.

PHASE 5

Reconcile

주기 full scan으로 누락·삭제·drift 검증.

각 단계의 출력payload → current/history → chunks → graph → answer evidence
각 단계의 실패partial/denied/unsupported/error를 숨기지 않고 저장
BACKFILL → ENRICH → INCREMENTAL → RECONCILE15 / 17
