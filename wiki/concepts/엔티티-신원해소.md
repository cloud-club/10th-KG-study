> `운영체제`/`OS`/`Operating System`, `Spring`/`Spring Boot`/`SpringBoot`, `Redis`/`redis`/`레디스`가 같은 대상인지 정하는 문제. 4주차 노트 다섯 군데에서 같은 결론이 반복된다 — IRI·Q ID·`owl:sameAs`는 **표현 방법**을 줄 뿐 동일성 **판단**을 대신하지 않는다. 5주차에 실측으로 두 방향의 실패가 나왔다: dldusgh318은 같은 사실이 6개 노드로 **과잉 분리**됐고, e0ng은 이름만으로 ID를 만들어 다른 활동이 **과잉 병합**됐다.

## 정의

- 신원해소(Entity Resolution) = 서로 다른 표기·IRI로 등장한 것이 같은 대상이면 하나의 대표 엔티티로 합치는 과정 (heebindev). 1차 규칙은 이름 정규화 + 같은 `type`·정규화된 이름이면 같은 대상. "이 규칙이 완벽하지 않으므로 **원래 이름도 함께 보관**한다."
- 왜 표준이 해결해 주지 않나 (4주차): IRI는 식별자를 주는 방법일 뿐이고 다른 데이터셋이 같은 사람을 다른 IRI로 부르면 문제는 그대로다 (dldusgh318, do-dop). Wikidata Q ID도 "Wikidata 내부에서 이미 같은 대상으로 정리된 항목"을 식별할 뿐이다. OWL은 비유일 이름 가정이라 서로 다른 IRI ≠ 서로 다른 대상이고, `sameAs`는 선언일 뿐이며 잘못된 `sameAs`는 오류를 그래프 전체에 전파한다 (lys0611) → [[RDF와-트리플]], [[온톨로지와-추론]].
- LLM 추출에서는 **ID를 LLM에 맡기지 않는다.** LLM은 읽을 수 있는 개체명만 내고 코드가 규칙으로 ID를 만든다 (dldusgh318) → [[LLM-트리플-추출]].

## 멤버들이 확인한 것 — 두 방향의 실패

**과잉 분리 (dldusgh318, 20청크 표본)**
- 같은 사실("한 프로젝트에서 Redis로 지원자 수를 캐싱했다")이 여러 청크에서 "캐싱했다 / 조회에 캐시를 적용했다 / 반복 조회 비용을 줄이기 위해 썼다"로 등장하는데 LLM은 청크를 독립 처리하므로 각각 다른 `TechnologyUse`가 된다. 정규화 ID가 `(project, technology, purpose, status)`에 가까워 목적 표현이 조금만 달라도 별개 사용례.
- 결과: `TechnologyUse` **45개가 32개 `(project, technology)` 쌍**에 매핑, 초과 13개. 한 쌍이 6개. 단 13개 전부가 잘못된 중복은 아니다 — 같은 프로젝트의 Redis 2개는 "테스트 결과 저장/implemented"와 "통근 시간 저장/proposed"로 목적·상태가 실제로 다른 별개 사실이라 `(Project, Technology)`만으로 합치면 X03에 필요한 정보가 사라진다.
- 영향: `COUNT(*)`로 "몇 개 프로젝트가 Redis를 쓰나"를 세면 사용례 행 수가 나와 부풀려진다. 반드시 `COUNT(DISTINCT project)`.
- 처방 — 병합 키 5규칙 (전체 추출 전 필수): ① `project_id + technology_id`로 1차 그룹화 ② **`status`가 다르면 절대 자동 병합하지 않는다** ③ purpose는 문자열 일치가 아니라 동의 표현을 같은 클러스터로 ④ **purpose가 NULL이라고 다른 NULL과 자동 병합하지 않는다 — "모름"은 "같음"이 아니다** ⑤ canonical 사용례에 원래 ID와 모든 `chunk_id`/`evidence`를 보존.

**과잉 병합 (e0ng, PR #36 미머지)**
- 엔티티 ID가 활동 이름에서만 나오면 기간이 다른 같은 이름의 활동이 같은 ID로 합쳐진다. 처음 이를 놓쳐 한 활동이 `:Activity, :Document, :Document`처럼 타입이 중복 저장됐다. `add_entity()`를 항상 거치게 고치고 **회귀 테스트**로 막았다.
- 의도된 병합도 있다: 한 활동이 두 기간에 걸치면 같은 엔티티로 합쳐지고 두 기간 모두 `OCCURS_IN_PERIOD`로 연결된다. 한 문서가 활동 전체를 대표하면 `{Activity, Document}` 이중 타입이라 `types[]`를 배열로 둔다.

**넓은 단어로 동일시하지 않는다** (kdyann): 별칭은 합치되 `AI` 같은 넓은 단어를 공유한다고 서로 다른 Project·Concept를 동일시하면 안 된다. 다국어·약어·해시태그는 표현과 뜻을 각각 확인. `MERGE`는 "같은 실체에 같은 ID" 규칙이 먼저 있어야 작동하고 **"`MERGE`만으로 엔티티 해소가 되지는 않는다"** → [[그래프-적재-Postgres와-Neo4j]]. Yeongeunn: `식별자 service:shipping` / `표시 이름 배송서비스` / `확인한 별칭 shipping-service`를 분리하고 "유사한 이름이나 벡터만으로 동일성을 확정하지 않는다". 상태값은 거래 유형별로 의미가 달라 "코드 문자열만 같다고 하나로 합치지 않는다".

**아직 겪지 않은 멤버**: heebindev는 "같은 대상이 여러 이름으로 만들어지지 않았는가"를 점검 항목으로만 남겼다. do-dop은 RAG 단계에서 **엔티티 귀속 오류**(다른 회사의 사실을 질문의 회사 것으로 답함)를 겪었고 그래프에서 노드·엣지로 강제하겠다고 했다 → [[RAG-vs-그래프-질의]].

## IRI·ID 생성 규칙 비교

| 멤버 | 규칙 | 예 |
|---|---|---|
| dldusgh318 | 한글은 국어의 로마자 표기법으로 **음차** 후 소문자, `a-z`와 하이픈만, `kg:use-{프로젝트}-{기술}-{번호}` | `kg:tech-redis`, `kg:use-secause-redis-1` |
| e0ng | 영어로 **번역**한 슬러그, 네임스페이스를 종류별로 분할(`activity:`, `period:`, `organization:`) | `period:2026-summer` |
| heebindev | 이름 정규화 + type, 단일 `os:` 네임스페이스 | 미기재 |
| kdyann | 안정 ID + 유일성 제약, `own`/`reference` 코퍼스 구분 | `cg:` 단일 네임스페이스 |
| Yeongeunn | Service=프로젝트 범위 포함 표준 ID / API=제공 서비스+메서드+경로 템플릿(**실제 사용자 ID가 든 URL 금지**) / Policy=조건·대상·결과 동일성 검토 후, 다른 버전 덮어쓰지 않음 | 활동이 두 기간에 걸치면 같은 엔티티 |

- 같은 문제의 두 해법(음차 vs 번역)이고 어느 쪽도 다른 멤버의 그래프와 바로 맞물리지 않는다. 멤버 그래프를 합칠 때 공통 Vocabulary·Entity Resolution·Schema Alignment가 돌아온다 → [[시맨틱-웹에서-지식그래프까지]].
