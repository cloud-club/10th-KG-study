# **SPARQL 맛보기 — 트리플로 저장한 지식에 어떻게 질문할까?**

앞에서는 RDF를 통해 사실을 `주어 - 술어 - 목적어` 형태의 Triple로 표현하는 방법을 봤다. 그리고 단순히 `프로젝트 → 기술`처럼 두 대상을 연결하는 것만으로 부족할 때는, 관계 자체를 중간 노드로 만들어 목적이나 상태 같은 추가 정보를 붙일 수 있다는 것도 확인했다.

그럼 이제 다음 질문은 자연스럽다. **이렇게 그래프 형태로 저장한 데이터에서 원하는 사실은 어떻게 찾을까?**

관계형 DB에 SQL이 있다면 RDF에는 **SPARQL**이 있다. 이번에는 직접 Wikidata의 공개 데이터를 조회하면서 SPARQL이 그래프를 어떻게 탐색하는지 살펴봤다.

사이트 : https://query.wikidata.org/

## **1. SPARQL은 빈칸이 있는 Triple을 찾는다**

SPARQL의 기본적인 질의 방식은 생각보다 단순하다. RDF가 데이터를 Triple로 저장했으니, 질의할 때도 **찾고 싶은 자리를 변수로 비워둔 Triple**을 만든다.

예를 들어 더글러스 애덤스의 교육기관을 알고 싶다면 `더글러스 애덤스 → 교육기관 → ?` 형태로 질문하면 된다.

```
SELECT ?education ?educationLabel WHERE {
  wd:Q42 wdt:P69 ?education .

  SERVICE wikibase:label {
    bd:serviceParam wikibase:language "ko,en".
  }
}
LIMIT 20
```

결과

여기서 `Q42`는 더글러스 애덤스, `P69`는 교육기관이라는 관계다. `?education` 부분만 비어 있으므로 **Q42의 교육기관(P69)에 해당하는 값을 찾아달라**는 의미가 된다.

결국 기본 구조는 `주어 - 술어 - 목적어` 중 알고 싶은 자리에 `?변수`를 넣는 것이다.

| **패턴** | **의미** |
| --- | --- |
| `A 관계 ?x` | A와 관계된 대상은 무엇인가? |
| `?x 관계 B` | B와 관계된 대상은 무엇인가? |
| `A ?x B` | A와 B는 어떤 관계인가? |

RDF가 사실을 Triple이라는 하나의 형태로 통일했기 때문에 질의 역시 같은 구조를 그대로 사용할 수 있다.

## **2. Wikidata에서는 Q와 P로 대상을 표현한다**

Wikidata를 처음 열면 사람 이름 대신 `Q42`, 관계 대신 `P69` 같은 값이 계속 나온다.

Wikidata에서는 **사람·장소·개념 같은 항목(Item)은 Q**, **항목 사이의 관계나 속성(Property)은 P**로 식별한다.

| **식별자** | **의미** | **예시** |
| --- | --- | --- |
| Q | 항목 | `Q42` = 더글러스 애덤스 |
| P | 속성 | `P69` = 교육기관 |
| P31 | instance of | 어떤 클래스의 인스턴스인지 |
| P279 | subclass of | 어떤 클래스의 하위 클래스인지 |

앞에서 RDF의 IRI를 공부하면서 **이름 자체보다 식별자를 이용해 대상을 구분한다**고 했는데, Wikidata에서 그걸 실제로 볼 수 있었다.

예를 들어 서울은 한국어로 `서울`, 영어로 `Seoul`, 일본어로 `ソウル`이라고 부르지만 Wikidata에서는 같은 Item ID를 중심으로 여러 언어의 이름을 연결할 수 있다.

다만 여기서도 ID가 Entity Resolution 자체를 해결해주는 것은 아니다. **Wikidata 내부에서 이미 같은 대상으로 정리된 항목을 하나의 Q ID로 식별할 수 있는 것**이고, 서로 다른 데이터의 두 대상이 같은지 판단하는 과정 자체가 사라지는 것은 아니다.

## **3. Q 번호만 나오면 읽기 힘들다**

실제로 Wikidata에 질의를 해보면 결과가 `Q1234567` 같은 식별자만 나와서 사람이 알아보기 어렵다.

그래서 실습할 때는 아래 부분을 거의 항상 같이 넣었다.

```
SERVICE wikibase:label {
  bd:serviceParam wikibase:language "ko,en".
}
```

그리고 `?education`이라는 변수가 있다면 `?educationLabel`을 함께 조회하면 사람이 읽을 수 있는 이름도 받을 수 있다.

실습에서는 두 가지를 습관처럼 붙여두면 편했다.

- `SERVICE wikibase:label` → Q ID를 사람이 읽을 수 있는 이름으로 표시
- `LIMIT` → Wikidata 전체를 대상으로 너무 많은 결과를 조회하지 않도록 제한

문법 자체를 외우기보다는 **“Wikidata에서 실습할 때 거의 항상 같이 쓰는 부분”** 정도로 기억하면 될 것 같다.

## **4. SPARQL에서 Join은 같은 변수로 표현한다**

여기서 SQL과 꽤 다르게 느껴졌던 부분이 있었다.

SQL에서는 여러 테이블을 연결하려면 `JOIN ... ON ...`을 명시하지만, SPARQL에서는 **두 Triple Pattern에 같은 변수를 사용하면 자연스럽게 연결된다.**

예를 들어 어떤 학교를 다닌 사람과 그 사람의 고용주를 알고 싶다고 해보자.

```
SELECT ?person ?personLabel ?org ?orgLabel WHERE {
  ?person wdt:P69 wd:Q691283 .
  ?person wdt:P108 ?org .

  SERVICE wikibase:label {
    bd:serviceParam wikibase:language "ko,en".
  }
}
LIMIT 30
```

!image.png

두 Triple에 `?person`이라는 같은 변수가 들어간다.

**학교 ← ?person → 고용주**

첫 번째 조건을 만족하는 사람 중 두 번째 조건까지 만족하는 사람을 찾는 것이다. 별도의 `JOIN` 키워드가 없어도 같은 변수가 두 패턴을 연결한다.

이 부분이 지난주 RAG 실험과 비교했을 때 특히 재밌었다.

지난주에는 여러 문서에 흩어진 정보를 한꺼번에 찾아야 하는 질문에서 Retrieval이 실패하는 경우가 있었다. 예를 들어 **“여행을 함께 간 사람들 중 같은 회사에 다니는 사람이 있는가?”** 같은 질문이라면, 문서 검색에서는 여행 기록과 회사 정보를 담은 청크를 각각 찾아 LLM에게 전달해야 한다.

반면 관계가 이미 그래프로 저장되어 있다면 질문의 형태가 달라진다.

**여행 → 함께 간 사람(?person) → 소속 회사**

즉 여러 문서에서 관련 내용을 다시 찾아내는 문제의 일부를 **이미 구조화된 관계를 연결해서 조회하는 문제**로 바꿀 수 있다.

다만 SPARQL 문법이 간단하다고 해서 다중 홉 문제가 자동으로 해결된다는 뜻은 아니다. **필요한 관계가 그래프에 제대로 추출·저장되어 있다는 전제**가 먼저 필요하다.

## **5. 자주 사용하는 문법은 몇 개만 알아두기**

이번 주는 SPARQL 자체를 깊게 배우는 게 목적은 아니라서, 실제 질의를 읽는 데 필요한 정도만 봤다.

| **문법** | **역할** |
| --- | --- |
| `SELECT` | 어떤 값을 반환할지 선택 |
| `WHERE` | 찾을 Triple Pattern |
| `OPTIONAL` | 관계가 없어도 결과는 유지 |
| `FILTER` | 조건을 걸어 결과 제한 |
| `ORDER BY` | 결과 정렬 |
| `LIMIT` | 반환 개수 제한 |

`OPTIONAL`은 특히 그래프 데이터에서 유용하다. 모든 대상이 동일한 속성을 가지고 있다는 보장이 없기 때문이다. 시작일이 기록된 사람도 있고 없는 사람도 있다면, 시작일을 일반 Triple Pattern으로 요구했을 때는 값이 없는 대상 자체가 결과에서 제외된다. `OPTIONAL`로 두면 대상은 남겨두고 값만 비워둘 수 있다.

## **6. Property Path로 관계를 여러 번 따라갈 수도 있다**

SPARQL에는 관계를 여러 단계 따라가는 **Property Path**도 있다.

예를 들어 `/`를 사용하면 관계를 연속해서 따라갈 수 있고, `*`를 사용하면 특정 관계를 0번 이상 반복해서 따라갈 수 있다.

`?item wdt:P31/wdt:P279* ?class`

정도로 작성하면 어떤 대상의 타입에서 시작해 상위 클래스 관계를 계속 따라가는 식의 질의를 만들 수 있다.

관계형 DB에서도 Recursive CTE 등을 이용하면 비슷한 작업을 할 수 있지만, 그래프 질의 언어에서는 **관계를 따라간다는 개념 자체가 문법에 직접 들어가 있다는 점**이 차이였다.

이번에는 Property Path를 직접 복잡하게 작성하기보다는, **“그래프에서는 관계를 여러 단계 따라가는 질의를 이렇게 표현할 수 있다”** 정도만 알고 넘어간다.

## **7. 그런데 `wdt:`로 조회하면 관계의 추가 정보가 안 보인다**

여기서 앞에서 공부한 **2항 관계의 한계와 reification**이 다시 등장한다.

예를 들어 다음과 같이 조회할 수 있다.

```
wd:Q42 wdt:P69 ?education .
```

의미는 간단하다.

**더글러스 애덤스 → 교육기관 → ?education**

그런데 학교 이름은 알 수 있어도 **언제부터 언제까지 다녔는지** 같은 정보는 이 관계 하나에 들어갈 수 없다.

앞에서 RDF를 공부할 때도 똑같은 문제가 있었다.

`프로젝트 → 기술 사용 → Redis`

만으로는 **왜 사용했는지, 실제 구현한 상태인지**를 표현할 수 없었다.

Wikidata 역시 같은 문제를 가지고 있고, 이를 위해 **statement(진술) 노드**를 중간에 둔다.

**사람 → 진술 노드 → 학교**, 그리고 진술 노드에 **시작일 / 종료일 / 출처 등의 추가 정보**를 연결하는 방식이다.

## **8. `wdt:`와 `p:/ps:/pq:`의 차이**

Wikidata에서 이 차이를 실제 SPARQL 문법으로 보면 이해하기 쉽다.

먼저 `wdt:`는 **값으로 바로 가는 간단한 경로**다.

```
wd:Q42 wdt:P69 ?education .
```

학교가 무엇인지 빠르게 알고 싶을 때는 이것만으로 충분하다.

하지만 해당 교육 이력의 시작일이나 종료일처럼 **그 관계 자체에 붙어 있는 정보**가 필요하면 statement를 거쳐야 한다.

```
wd:Q42 p:P69 ?statement .
?statement ps:P69 ?education .

OPTIONAL { ?statement pq:P580 ?start . }
OPTIONAL { ?statement pq:P582 ?end . }
```

각 접두어의 역할을 정리하면 다음과 같다.

| **접두어** | **역할** |
| --- | --- |
| `wdt:` | 값으로 바로 이동하는 간단한 경로 |
| `p:` | 해당 Property의 statement 노드로 이동 |
| `ps:` | statement가 가지고 있는 주된 값 |
| `pq:` | statement에 붙어 있는 qualifier |

실제로 같은 교육기관 데이터를 `wdt:`로 조회했을 때는 학교만 확인할 수 있지만, `p: → ps:/pq:` 경로로 조회하면 해당 statement에 기록된 시작일이나 종료일 같은 qualifier도 함께 가져올 수 있다.

앞에서 배운 reification이 실제 대규모 Knowledge Graph에서 어떻게 사용되는지 확인할 수 있는 부분이었다.

## **9. 우리가 만든 중간 노드와도 비슷하다**

이번 주 실습에서는 내 프로젝트 경험을 그래프로 만들면서 **“특정 프로젝트에서 특정 기술을 사용한 경험”** 자체를 중간 노드로 만들었다. 이를 편의상 `TechnologyUse`라고 이름 붙였다.

예를 들어 내가 진행한 AI 코드 보안 분석 프로젝트에서 Redis를 사용했다면 단순히 `프로젝트 → Redis`라고 연결하는 대신,

**TechnologyUse → 프로젝트 / Redis / 사용 목적 / 구현 상태**

처럼 저장한다.

Wikidata 역시 교육기관이라는 관계에 추가 정보를 붙여야 할 때,

**사람 → statement → 학교**, 그리고 **statement → 시작일 / 종료일**

처럼 표현한다.

| **Wikidata** | **이번 실습** |
| --- | --- |
| statement | 특정 기술 사용 경험을 나타내는 `TechnologyUse` |
| statement의 주된 값 | 사용한 기술 |
| qualifier | 사용 목적, 상태 등의 추가 정보 |

둘이 완전히 동일한 데이터 모델은 아니지만 **단순한 두 개체 사이의 관계만으로 부족한 정보를 중간 구조를 만들어 표현한다는 발상**은 비슷하다.

재밌는 건 이번에도 이론을 먼저 보고 그대로 따라 만든 게 아니라는 점이다. 내 프로젝트 경험을 표현하기 위해 **프로젝트, 기술, 목적, 상태라는 네 가지 질문에서 역으로 스키마를 만들었는데**, Wikidata에서도 비슷한 모델링 문제를 statement와 qualifier를 통해 해결하고 있었다.

결국 데이터 규모가 개인 프로젝트 수준이든 Wikidata처럼 거대한 Knowledge Graph든 **관계 자체에 추가 정보가 필요해지는 문제는 똑같이 발생한다.**

## **10. 지난주 RAG와 비교하면 무엇이 달라질까?**

SPARQL을 직접 사용해보면서 이번 주 Knowledge Graph를 왜 공부하는지가 조금 더 명확해졌다.

지난주 RAG에서는 질문을 받으면 관련 청크를 검색하고, 그 안에 필요한 정보가 모두 들어오기를 기대했다.

**질문 → BM25/Vector 검색 → 관련 청크 → LLM이 관계를 찾아 종합**

Knowledge Graph에서는 필요한 사실을 미리 관계로 구조화해두고 그 관계 자체를 조회할 수 있다.

**질문 → Graph Query → 관계를 따라 필요한 사실 조회 → LLM**

예를 들어 “같은 학교를 나온 사람들의 고용주는 어디인가?”라는 질문에서 SPARQL은 `학교 → 사람 → 고용주`라는 관계를 직접 연결해서 조회할 수 있었다.

이게 지난주 Retrieval Failure에서 확인했던 문제와 연결된다. 문서 검색에서는 필요한 여러 청크가 모두 검색되어야 하지만, 그래프에서는 **관계가 이미 올바르게 저장되어 있다면 관계를 따라 필요한 사실을 조회할 수 있다.**

물론 공짜는 아니다. 그래프에서 이렇게 조회하려면 그 전에 문서에서 **어떤 것이 Entity인지, 어떤 관계가 있는지 정확하게 추출해서 저장해야 한다.** 잘못된 관계를 저장하면 SPARQL은 그 잘못된 관계를 아주 정확하게 조회할 뿐이다.

그래서 아직 **“Knowledge Graph가 RAG의 Retrieval 문제를 해결한다”**고 결론 내릴 수는 없다. 이번 주와 다음 실습에서 실제로 확인해야 할 가설에 가깝다.

## **그래서 다음은?**

지금까지 RDF로 **사실과 관계를 어떻게 표현하는지** 보고, SPARQL로 **그 관계를 어떻게 조회하는지**까지 확인했다.

그런데 아직 그래프에는 한 가지가 빠져 있다.

`연호 → type → BackendEngineer`와 `BackendEngineer → subclass → Engineer`가 저장되어 있다고 해도, **“그렇다면 연호도 Engineer인가?”**라는 새로운 사실을 어떤 규칙으로 판단해야 하는지는 정하지 않았다.

또 `USES_TECHNOLOGY`라는 관계가 **Project와 Technology 사이에서 사용되는 관계**라는 의미도 아직 정의하지 않았다.

즉 지금까지가 **“그래프를 만들고 조회하는 방법”**이었다면, 다음은 **“그래프 안의 개념과 관계에 어떤 의미와 규칙을 부여할 것인가?”**의 문제다.

그래서 다음에는 **RDFS와 OWL**을 보면서 `Class`, `Property`, `subClassOf` 같은 개념이 무엇인지, **스키마와 온톨로지는 무엇이 다른지**, 그리고 저장하지 않은 사실까지 규칙을 통해 알아내는 **Inference(추론)**가 무엇인지 이어서 살펴본다.
