# 01. 0세대 — grep은 왜 문서 검색에 실패하는가?

## grep은 왜 문서 검색에 부족할까?

grep은 파일을 훑으며 특정 문자열이 존재하는지 찾는 도구다. 정확한 문자열이나 코드, ID를 찾는 데는 강하지만, 문서 검색에서 필요한 관련도 판단과 의미 이해는 하지 못한다.

```
문서: SeCause의 API 응답 시간을 750ms → 150ms로 개선했다.
검색: "성능을 개선한 경험"
→ 의미는 관련 있지만 문자열이 다르므로 grep은 찾지 못한다...
```

### 1. 표현이 다르면 놓친다

grep은 의미가 아니라 문자열을 비교한다.

```
트러블 슈팅 ≠ 트러블슈팅
Elasticsearch ≠ 엘라스틱서치
지식그래프 ≠ 지식 그래프
```


한국어에서는 조사·어미까지 붙기 때문에 이 문제가 더 자주 발생한다. 

grep -w 역시 한국어 형태소를 분석하는 것은 아니므로 근본적인 해결책은 아니다.

### 2. 검색 결과에 순위가 없다

캐시가 포함된 문서가 400개라면 grep은 400개를 모두 찾아줄 뿐, 어떤 문서가 내 검색 의도와 가장 관련 있는지 알려주지 않는다..

```
Redis Look-Aside 캐시 전략 → MATCH
Gradle 빌드 캐시          → MATCH
캐시 파일 삭제            → MATCH
```

즉 grep에게는 모두 같은 MATCH다.

검색 결과를 관련도순으로 보여주려면 단어의 등장 빈도 등의 정보를 이용해 점수를 계산하고 순위를 매기는 과정이 필요하다. 여기서 **역색인**과 **BM25**가 등장한다.

⸻

### 내 데이터로 직접 확인해보기

개인 Notion 문서 131개, 약 0.95MB를 대상으로 검색해봤다.

| **Query** | **grep 결과** | **확인한 문제** |
| --- | --- | --- |
| `캐시` | 407건 | Gradle 빌드 캐시 등이 대량 검색되어 원하는 캐시 전략을 찾기 어려움 |
| `학교` | 51건 | `홍익대학교` 등 부분 문자열까지 함께 검색 |
| `트러블 슈팅` | 1건 | `트러블슈팅`으로 작성된 관련 문서 14건을 놓침 |
| `성능을 개선한 경험` | 0건 | 관련 내용은 있지만 자연어 표현이 달라 검색 실패 |
| `검색이 왜 어려운가` | 0건 | 질문과 동일한 문자열이 없어 검색 실패 |

특히 두 결과가 grep의 한계를 잘 보여줬다.

```
"캐시" → 407건     # 너무 많이 찾음 (Feast)
"성능을 개선한 경험" → 0건  # 아무것도 못 찾음 (Famine)
```

결국 많이 찾는 것과 잘 찾는 것은 다르다!

⸻

### 그래도 grep은 여전히 유용하다!

grep이 나쁜 검색 방법인 것은 아니다. 정확한 문자열 자체가 중요한 경우에는 오히려 적합하다.

```
{학번}
HTTP 404
@Transactional
NullPointerException
SeCause
```

ripgrep(rg) 역시 코드베이스에서 이런 문자열을 빠르게 찾는 데 매우 유용하다. 다만 검색 속도를 크게 개선한 것이지, 문자열 매칭 → 의미 기반 검색으로 검색 방식 자체가 바뀐 것은 아니다.

따라서 핵심 질문은 **“grep은 나쁜가?“가 아니라 “grep은 무엇을 잡고 무엇을 놓치는가?”** 다.

⸻

### 그래서 다음은?

이번 실습에서 두 가지 한계를 확인했다.

```
grep
├─ 정확한 문자열 찾기       → 잘함
├─ 같은 의미, 다른 표현     → 놓침
├─ 관련도 판단              → 못함
└─ 자연어 질문              → 약함
```

먼저 **“찾기는 했는데 어떤 문서가 더 중요한가?”** 라는 문제를 해결하기 위해 다음 단계에서는 역색인(Inverted Index) + BM25를 사용한다.

이후에는 BM25도 해결하지 못하는 **“표현은 다르지만 의미가 같은 문서”**를 찾기 위해 Vector Search까지 비교해볼 예정이다.
