# 04-3. 팔란티어 온톨로지의 Object·Link·Action과 RDF 비교

## 팔란티어 온톨로지란?

팔란티어 온톨로지는 원천 데이터를 업무에서 사용하는 대상과 관계로 매핑하고, 그 대상을 애플리케이션에서 조회하거나 변경할 수 있게 연결하는 계층이다. 사용자는 데이터셋의 열 이름만 보는 대신 고객, 장비, 주문 같은 업무 개념을 중심으로 정보를 다룰 수 있다.

## 구성 요소

| 개념 | 의미 | 간단한 예 |
| --- | --- | --- |
| Object Type / Object | 대상의 종류 / 그 종류에 속하는 개별 대상 | 장비 / 장비 001 |
| Property | 대상의 특성 정의. 개별 Object는 그 값을 가짐 | 장비의 이름, 상태, 설치일 |
| Link Type / Link | 관계의 종류 / 개별 대상 사이의 연결 | 장비와 담당자의 관계 / 장비 001과 담당자 김OO의 연결 |
| Action Type / Action | 허용된 변경 동작의 정의 / 그 정의에 따른 실행 | 장비 상태 변경 / 장비 001의 상태 변경 실행 |

Object Type·Property·Link Type은 대상과 그 관계를 표현하는 기본 요소다. Action은 이렇게 표현한 대상에 어떤 변경을 허용할지 정의한다.

Action에는 입력값, 변경 규칙, 검증 조건과 권한을 구성한다. 온톨로지의 데이터 변경이 외부 시스템이나 물리적 장비의 동작으로 이어지려면 그에 맞는 연동과 실행 구성이 필요하다.

Link Type 생성 화면에는 외래키를 이용하는 방식, 조인 테이블을 이용하는 방식, 관계의 속성을 중간 Object Type으로 표현하는 방식이 보인다. 이 화면은 관계를 어떻게 데이터와 연결할 수 있는지 보여준다.

## Writeback: 사용자의 변경을 데이터에 반영하기

Action 버튼은 정의된 변경 동작을 실행하는 진입점이 될 수 있다. 사용자가 동작을 선택하면 필요한 입력과 실행 조건·권한을 확인하고, 규칙에 따라 온톨로지의 객체·속성·링크를 변경한다.

이를 통해 변경 사항을 다시 기록하는 흐름을 이해할 수 있다. 다만 온톨로지 데이터를 변경하는 것과 외부 시스템에 반영하는 것은 구분해야 한다. 외부 API 호출은 웹훅 등으로 별도 구성하며, 화면의 버튼만 보고 실제 비행편이나 장비가 어떻게 움직이는지 알 수는 없다.

## 대상·관계와 동작·로직을 함께 다룬다

[팔란티어 공식 개요](https://www.palantir.com/docs/foundry/ontology/overview)는 Objects·Properties·Links를 의미를 표현하는 요소(Semantic), Actions·Functions·Dynamic security를 변화와 동작을 다루는 요소(Kinetic)로 설명한다.

Functions는 계산이나 변경에 필요한 업무 로직을 코드로 구현하는 데 사용할 수 있다. 모델을 연결해 예측이나 분석 결과를 업무에서 활용할 수도 있다. 이런 계산이나 모델의 예측은 OWL 공리에서 따라오는 결론을 도출하는 논리적 추론과 구분해야 한다.

## 왜 온톨로지라고 부르는가?

온톨로지는 어떤 분야에서 다루는 대상과 관계를 명시하는 개념과 연결된다. 팔란티어에서도 조직이 사용하는 고객, 주문, 장비 등의 종류와 그 관계를 정의하고, 여러 애플리케이션이 같은 모델을 참조하게 만들 수 있다.

예를 들어 여러 앱이 같은 장비의 식별자, 상태, 담당자 관계를 사용하면 앱마다 그 의미를 따로 정의하는 일을 줄일 수 있다.

## 공통점

- 대상과 관계를 명시한다. 사람, 장비, 주문처럼 식별할 대상과 그 사이의 관계를 구조화할 수 있다. 
- 개념 중심으로 정보를 표현할 수 있다. 저장된 파일이나 테이블을 그대로 보여주는 데서 나아가, 업무에서 사용하는 개념으로 정보를 연결한다. 

## 차이점

| 구분 | 팔란티어 온톨로지 | RDF 및 관련 표준 |
| --- | --- | --- |
| 범위와 목적 | 업무 대상과 데이터, 애플리케이션의 조회·변경 동작을 연결하는 플랫폼 계층 | 사실을 트리플로 표현하고 공유하는 표준 데이터 모델. RDFS/OWL로 의미와 추론을 위한 정의를 확장 |
| 상태 표현과 변경 | Object·Property·Link로 대상을 표현하고, Action으로 변경 동작 구성 | 트리플로 사실을 표현. 시간이나 변화도 모델링할 수 있고 SPARQL Update로 데이터 변경 가능 |
| 실행 기능 | Action Type과 Functions 등으로 업무 동작과 로직 구성 | RDF 자체는 실행 절차를 규정하지 않음. 사용하는 저장소와 애플리케이션에서 구현 |
| 표준과 생태계 | 팔란티어 플랫폼의 기능·도구와 통합 | W3C 표준이며 여러 구현체와 도구에서 사용 가능 |

비교의 핵심은 수정 가능 여부가 아니라 표준 데이터 표현과 업무 플랫폼이 제공하는 범위의 차이

## 장점과 고려할 점

| | RDF와 관련 표준 | 팔란티어 온톨로지 |
| --- | --- | --- |
| 장점 | 표준 어휘와 식별자로 의미를 공유하고 외부 데이터와 연결하기 좋음. 트리플과 속성을 추가하며 모델을 확장 가능 | 업무 모델, 탐색·운영 앱, Action, 권한을 플랫폼 안에서 함께 구성 가능 |
| 고려할 점 | 어휘·온톨로지 설계와 SPARQL 학습이 필요. 성능은 사용하는 저장소, 데이터 규모, 질의와 인덱스 설계에 따라 달라짐 | 플랫폼 의존과 학습 부담. 업무 모델, 권한, 변경 규칙과 외부 연동을 설계·관리해야 함 |
