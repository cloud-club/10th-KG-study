> 정보를 "대상과 관계"로 저장하는 방식. 트리플(주어–술어–목적어)이 단위이고, 온톨로지가 그 위에 개념·관계의 의미와 규칙을 정의한다. 이 스터디의 최종 목표(개인 데이터로 지식그래프 만들기)의 개념 층이자 KG 페이지들의 허브다. **2026-10-02 기준 다섯 멤버(dldusgh318, e0ng, heebindev, kdyann, Yeongeunn)가 실제로 그래프를 추출·적재·질의했다** — 전원 PostgreSQL + Turtle + Neo4j, Triplestore는 없음, 전체 코퍼스 추출을 완주한 멤버도 없음. 4주차 이론은 열 멤버가 같은 연표·같은 함정에 독립적으로 도달했다.

## 용어

| 용어 | 정의 | 자세히 |
|---|---|---|
| 엔티티 | 구분할 수 있는 현실의 대상이나 개념. 이름 ≠ 식별자 — 유사한 이름이나 벡터만으로 동일성을 확정하지 않는다 | [[엔티티-신원해소]] |
| 트리플 | 하나의 사실을 주어–술어–목적어로. 주어 = IRI·Blank Node, 술어 = IRI, 목적어 = IRI·Blank Node·Literal. **Literal은 목적어 자리에만** | [[RDF와-트리플]] |
| 지식 그래프 | 실제 엔티티와 관계를 저장한 **데이터**. "KG가 원문이나 검색을 대체하는 것은 아니다 — 관계가 올바르게 추출됐는지 원문과 근거를 확인할 수 있어야 한다" (kungbi) | [[RAG-vs-그래프-질의]] |
| 온톨로지 | 어떤 개념과 관계를 쓸지 정하는 **의미 체계**. 그루버(1993)의 "개념화의 명시적 명세" — 배경은 지식기반 시스템 사이의 공유·재사용 (kdyann). **OWL 파일이 없어도 의미를 설계했다면 온톨로지 설계** (sunghyun). 모델을 세 개 설치하는 것만으로 만들어지지 않는다 (Yeongeunn) | [[온톨로지와-추론]], [[폐쇄-스키마-설계]] |
| RDF | 트리플을 표현하는 데이터 모델. **RDF 자체는 저장소가 아니고** DB 제품도 자동 추출 모델도 아니다. RDF 1.1의 정확한 용어는 URI가 아니라 **IRI** | [[RDF와-트리플]] |
| Turtle · JSON-LD | 같은 RDF 그래프를 적는 **문법**. RDF = 모델 / Turtle = 문법 / 트리플 스토어 = 저장·질의 시스템 | [[RDF와-트리플]] §직렬화 |
| RDFS · OWL | 클래스·속성의 기본 의미(RDFS)와 더 풍부한 논리(OWL). `domain`/`range`는 검증이 아니라 **추론 선언** — 일곱 멤버가 독립 확인. 검증은 SHACL | [[온톨로지와-추론]] |
| 추론 (Reasoning) | 규칙으로 직접 저장하지 않은 사실을 도출. **탐색(질의)과 다르고** LLM의 추측과도 다르다. RDF를 저장하는 것만으로 추론이 실행되지는 않는다 | [[온톨로지와-추론]] |
| 열린 세계 가정 | 적혀 있지 않은 것은 거짓이 아니라 모르는 것. "그래프에 간선이 없다 ≠ 현실에 관계가 없다". **닫힌 스키마 ≠ 닫힌 세계** | [[온톨로지와-추론]], [[RAG-실패-유형]] |
| SPARQL · Cypher | RDF 그래프 / 프로퍼티 그래프의 질의 언어. 같은 변수를 두 패턴에 쓰면 조인이고 추론이 아니다. 둘 중 하나가 더 좋은 게 아니라 데이터를 어떤 모델로 저장했는지에 달렸다 | [[SPARQL]], [[그래프-적재-Postgres와-Neo4j]] |
| 다중 홉 질문 | 두 개 이상의 관계를 연속해서 따라가야 답이 나오는 질문. 다중 홉이라고 그래프가 필요한 건 아니다 | [[멀티홉-질문과-Bridge-Entity]] |
| 링크드 데이터 | URI로 이름 짓고 HTTP로 조회하고 다른 URI로 연결. "공개 데이터인지"와 별개의 개념 (kdyann) | [[시맨틱-웹에서-지식그래프까지]] |

## 어디서 왔고 어디로 가나

- **역사**: 2001 시맨틱 웹 → RDF·OWL 표준 → Linked Data → DBpedia·Wikidata → Google KG(2012) → 기업 KG → GraphRAG(2024) → Palantir Ontology. 열 멤버의 결론 — 시맨틱 웹은 실패한 게 아니라 **범위를 좁혀 계승**됐고(조정 문제를 한 조직의 설계 문제로), 앞 기술이 뒤 기술로 교체된 순서도 아니다 → [[시맨틱-웹에서-지식그래프까지]], [[Wikidata와-DBpedia]], [[기업-지식그래프-사례]], [[Palantir-Foundry-Ontology]].
- **왜 검색 다음이 그래프인가**: dldusgh318이 3주차 RAG에서 "청크는 문서 조각이고 Triple은 관계다"라고 정리했고, 4주차에 브릿지가 숨은 질문 X01(질문에 `Redis`가 없어 다른 프로젝트로 넘어가지 못함)로 재현했으며, 5주차에 그래프에서 Redis가 3개 프로젝트를 잇는 브릿지로 작동함을 확인했다 — "검색 문제가 조인 문제로 바뀌었다". e0ng도 3주차 RAG가 못 이은 질문을 Cypher 한 경로로 풀었다. 그러나 **공정한 비교는 아직 없고**(Yeongeunn), 다중 홉 질문이 RAG로 풀리는 반례도 셋이며, do-dop은 "그래프가 왜 필요한지는 RAG를 실패해 봐야 알 수 있다"고 방법론으로 뒤집었다 → [[RAG-vs-그래프-질의]], [[멀티홉-질문과-Bridge-Entity]].
- **그래프는 새 비용을 만든다**: "LLM은 구축 비용을 낮췄지만 정규화와 신원해소 문제까지 없애주지는 않았다. 대량 생성이 가능하기 때문에 잘못된 기준을 두면 문제도 대량 생성된다" (dldusgh318). 다음 질문은 "그래프를 만들 수 있는가"가 아니라 **"자동으로 만든 그래프를 어떻게 믿을 수 있는 그래프로 만들 것인가"**. 그래서 "청크는 조각이고 Triple은 관계다" 뒤에 "그러나 Triple이 같은 사실을 가리키는지는 별도로 보장해야 한다"가 붙는다 → [[LLM-트리플-추출]], [[엔티티-신원해소]].
- **GraphRAG**: 엔티티·관계·claims 추출 → 커뮤니티 탐지 → 요약, local/global search. 문서에서 자동 생성·재생성되는 검색 인덱스이지 지속 관리하는 도메인 KG가 아니다 (do-dop). 자동화되는 것은 구축 비용뿐 (dldusgh318). "한 문서에서 답을 찾는 질문에는 커뮤니티 요약이 필요 없을 수 있다" (yujeong430). 스터디에서 그래프를 리트리버로 연결한 멤버는 아직 없다 → [[RAG-변천사]].
- kungbi의 경계: [[OpenViking-컨텍스트-데이터베이스|OpenViking]]은 자료·기억·절차를 찾고 상세 수준을 고르는 것, KG는 엔티티와 관계를 명시하고 관계 경로를 질의하는 것. Palantir의 Action은 조회에서 실행으로 — 추론이 아니다.

## 모델과 저장소

| 질문 | 답 | 자세히 |
|---|---|---|
| RDF 트리플스토어 vs 프로퍼티 그래프? | 배타적 기능 차이가 아니라 설계 관점의 차이. 관계의 부가 정보(RDF는 중간 노드·statement·reification, PG는 엣지 속성), 식별(IRI vs 내부 ID), 의미 정의, 추론 생태계가 갈린다. "RDF = 열린 세계, PG = 닫힌 세계"로 외우지 않는다 | [[RDF와-프로퍼티-그래프]] |
| 어디서 시작하나? | sunghyun(1주차) "Neo4j부터", dldusgh318(4주차) "Postgres 유지 — 벡터 검색과 한 저장소", 5주차 결과는 **전원 Postgres 1차 + Turtle 산출 + Neo4j 탐색** | [[RDF와-프로퍼티-그래프]] §어느 쪽부터, [[그래프-적재-Postgres와-Neo4j]] |
| 정본은 어디? | kungbi "PG canonical + projection" vs sunghyun "병렬 경로"였던 모순은 5주차 실습이 kungbi 쪽으로 수렴 — 단 kdyann·Yeongeunn은 git 밖의 검토 파일이 정본이고 PG도 파생물. 원문 → 검토 파일 → 모든 저장소 | [[데이터-수집과-출처-추적]] |
| 관계에 날짜·근거·상태를 어떻게 붙이나? | 관계를 1급 객체로 올린다 — 중간 노드(dldusgh318 `TechnologyUse`), `rdf:Statement`(kdyann), Wikidata statement + qualifier + reference, `assertions`/`evidence` 테이블(Yeongeunn). 시간은 `valid_from/valid_to`, 검토는 `review_status` | [[RDF와-트리플]], [[Wikidata와-DBpedia]] |
| 관계형 DB는 관계를 못 다루나? | 아니다 — 자기 참조 FK·관계 테이블·재귀 CTE. "관계 종류와 탐색 경로가 늘수록 JOIN과 스키마 변경이 복잡해진다"가 정확한 설명 (do-dop). 집계는 RDB `GROUP BY`가 그래프보다 정확 (lys0611) | [[RDF와-프로퍼티-그래프]], [[PostgreSQL과-pgvector-함정]] |

## 열린 질문

- 여러 멤버의 그래프를 합칠 때 공통 Vocabulary·Entity Resolution·Schema Alignment를 누가 어떻게 하나. 멤버마다 클래스 3·5·5·5·5종이 전혀 다르고 IRI 규칙(음차 vs 번역)도 다르다 → [[시맨틱-웹에서-지식그래프까지]] 환류, [[폐쇄-스키마-설계]].
- 자동 추출 그래프의 **의미 정확도**를 체계적으로 재는 방법. 지금은 heebindev의 눈 검수 8건이 전부다.
- 그래프를 RAG의 리트리버로 연결(GraphRAG)하고 같은 질문·같은 Gold로 청크 검색과 공정 비교하기. Yeongeunn은 "W6 범위"로 남겼다.
- 추론을 실제로 켜 본 멤버가 없다. 공용 인프라에 추론 엔진이 없다 → [[온톨로지와-추론]], [[로컬-인프라]].
