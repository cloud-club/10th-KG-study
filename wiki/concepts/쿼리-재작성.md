> 사용자의 질문을 그대로 검색하지 않고 LLM으로 다시 쓰거나 늘리거나 쪼개서 검색하는 기법 모음. 전부 LLM 호출을 추가하므로 회수율이 이미 충분하면 붙일수록 순손해다.

## 기법 카탈로그 (sese2204 정리)

| 기법 | 무엇을 하나 | 메모 |
|---|---|---|
| 대화형 쿼리 재작성 | 멀티턴에서 지시대명사·생략을 풀어 독립된 질문으로 | 멀티턴이면 **필수** |
| Multi-query / RAG-Fusion | 변형 쿼리 3~5개 생성 → 각각 검색 → [[하이브리드-검색과-RRF|RRF]] 융합 | 구현이 쉽고 가성비 좋음 |
| HyDE | 질문에 대한 *가상의 답변 문서*를 LLM으로 생성 → 그걸 임베딩해 검색 | 질문-문서 임베딩 공간의 비대칭을 우회. 개념적으로 배울 게 많음 |
| Step-back prompting | 구체 질문에서 상위 개념 질문을 뽑아 함께 검색 | |
| 쿼리 분해 | [[멀티홉-질문과-Bridge-Entity|멀티홉 질문]]을 서브 질문으로 | |
| 라우팅 / Adaptive RAG | 애초에 검색이 필요한 질문인지 분류 | [[RAG-변천사]]의 4기 |

- 비용 경고: 이 기법들은 전부 LLM 호출을 추가해 지연과 비용이 곱으로 늘어난다. 회수율이 이미 충분한데 붙이면 순손해다.
- DSPy 접점: 쿼리 재작성 프롬프트 + 리랭킹 판정 프롬프트 + 생성 프롬프트가 겹겹이 쌓인 다단계 파이프라인은 손으로 튜닝하면 금방 한계에 닿는다. DSPy는 그 전체를 하나의 최적화 대상으로 다룬다.

## 재검색(Agentic Search)과의 관계

dldusgh318은 멀티홉 문제의 처방으로 "검색 → 생각 → 재검색 → 답변" 루프(Agentic Search, Iterative Retrieval)를 다뤘다. 사전 분해(쿼리 분해)와 달리 **첫 번째 검색 결과가 두 번째 검색어를 결정**하는 순차 의존을 전제한다. 그가 짚은 한계 세 가지:

1. 첫 검색이 틀리면 잘못된 이름으로 2번째 검색을 해 오류가 누적된다.
2. "언제 검색을 멈출까"의 판단도 LLM에 맡겨야 한다.
3. 홉이 늘수록 검색과 LLM 호출이 함께 늘어 비용이 커진다.

이 결론은 sese2204의 "순손해" 경고와 같은 방향이다. 재검색은 일부 멀티홉을 풀 수 있지만 관계를 매번 텍스트 검색으로 다시 찾아야 한다는 점은 그대로라서, dldusgh318은 관계 자체를 저장하는 [[지식그래프와-온톨로지|그래프]]로 넘어갔다.

## 멤버들이 확인한 것

- 실측한 멤버는 아직 없다 (2026-09-16 기준). sese2204의 실습 로드맵 ④ 단계(multi-query 또는 HyDE)와 스터디 질문 "둘 중 먼저 붙여볼 것"이 열려 있다.
- ur2e의 실험은 쿼리를 사람이 패러프레이즈했을 때 벡터 검색이 어떻게 무너지는지를 보여준다([[임베딩과-벡터-검색]] 참조). 재작성 기법이 이 케이스를 구하는지는 미확인.
