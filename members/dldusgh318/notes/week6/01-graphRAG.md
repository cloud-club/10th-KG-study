# **GraphRAG : 만든 그래프를 RAG에서 어떻게 사용할까?**

W5에서는 내 문서에서 Entity와 Relationship을 추출해 실제 지식 그래프를 만들었다.

그리고 W3의 Hybrid RAG가 답하지 못했던 질문도 그래프에서는 해결할 수 있었다.

대표적으로 이런 질문이었다.

**`SeCause에서 작업 큐에 사용한 기술을 다른 프로젝트에서도 사용했는가?`**

기존 RAG는 질문에 `Redis`라는 단어가 없어서 TEAMFICIAL이나 직행의 Redis 사용 기록까지 찾지 못했다. 반면 그래프에서는 SeCause에서 출발해 관계를 따라가면서 Redis를 찾고, 다시 Redis와 연결된 다른 프로젝트까지 이동할 수 있었다.

```
SeCause
   ↓
Redis
 ↙   ↘
직행  TEAMFICIAL
```

여기까지는 잘 됐다.

그런데 W5에서는 **내가 직접 Cypher를 작성해서** 이 그래프를 조회했다.

실제 개인 데이터 에이전트에서는 사용자가 이렇게 질문하지 않는다.

```
MATCH ...
```

그냥 자연어로 묻는다.

“SeCause에서 쓴 기술을 다른 프로젝트에서도 썼어?”

그러면 이제 새로운 문제가 생긴다.

**자연어 질문을 받았을 때 그래프의 어디서 시작해서, 어떤 관계를 따라가고, 무엇을 LLM에게 전달해야 할까?**

GraphRAG는 이 과정에서 **그래프를 검색에 활용하는 방법**이라고 볼 수 있다.

---

## **1. 그래프를 읽는 방법은 질문에 따라 달라진다**

GraphRAG라고 해서 항상 같은 방식으로 그래프를 검색하는 것은 아니다.

이번에는 크게 세 가지 패턴을 본다.

| **방식** | **쉽게 말하면** | **잘 맞는 질문** |
| --- | --- | --- |
| **Local Search** | 특정 노드에서 주변을 따라간다 | “SeCause는 Redis를 왜 썼어?” |
| **Global Search** | 그래프 전체를 미리 요약해두고 본다 | “내 프로젝트들의 공통적인 특징은?” |
| **Text2Cypher** | LLM이 질문을 Cypher로 바꾼다 | “가장 많은 프로젝트에서 쓴 기술은?” |

결국 차이는 **그래프에서 필요한 정보를 어떻게 꺼낼 것인가**에 있다.

---

# **2. Local Search : 한 지점에서 시작해 주변을 따라간다**

가장 직관적인 방식이고, 사실 W5에서 이미 비슷한 일을 했다. 다시 X01을 질문을 보자!

“SeCause 작업 큐에 쓴 기술을 다른 프로젝트에서도 썼나?”

Local Search라면 다음과 같이 움직인다.

```
자연어 질문
   ↓
① 질문에서 Entity 찾기
   ↓
SeCause (프로젝트)
   ↓
② 주변 관계 따라가기
   ↓
TechnologyUse → Redis
                  ↓
        다른 TechnologyUse
                  ↓
          TEAMFICIAL / 직행 (프로젝트)
   ↓
③ 관련 원문까지 가져오기
   ↓
④ LLM이 답변
```

여기서 각 단계가 하는 일이 조금씩 다르다.

### **① 질문과 그래프의 노드를 연결한다**

먼저 질문에 나온 `SeCause`가 그래프의 어떤 노드인지 알아야 한다.

이 과정을 **Entity Linking**이라고 한다.

가장 단순한 방법은 이름을 비교하는 것이다.

```
질문의 "SeCause"
       ↓
그래프 label = "secause"
```

하지만 사용자가 “졸업 프로젝트에서 작업 큐에 쓴 기술…” 처럼 표현하면 이름만 비교해서는 찾기 어렵다.

그래서 노드의 이름이나 설명을 임베딩해두고 **벡터 검색으로 가장 비슷한 진입 노드를 찾는 방법**도 사용할 수 있다.

이게 뒤에서 볼 **Hybrid Retriever**와 연결된다.

### **② 찾은 노드에서 주변 관계를 따라간다**

진입 노드를 찾았으면 이제 그래프의 엣지를 따라간다.

```
SeCause
  ↓
TechnologyUse
  ↓
Redis
  ↓
TechnologyUse
  ↓
TEAMFICIAL
```

이게 기존 RAG와 가장 크게 다른 부분이다.

RAG에서는 TEAMFICIAL 문서를 찾으려면 질문과 그 문서가 어느 정도 의미적으로 비슷해야 했다.

그래프에서는 그렇지 않고, **이미 저장된 관계를 따라가면 된다.**

그래서 질문에 `Redis`라는 단어가 없어도 Redis에 도달할 수 있다.

W5에서 확인했던 **“검색 문제가 조인 문제로 바뀐다.”** 는 이야기가 실제 RAG 파이프라인 안으로 들어오는 것이다.

### **③ 그래프만 주지 않고 원문도 같이 가져온다**

그렇다고 그래프 정보만 LLM에게 주는 것은 아니다. 그래프는 보통 이런 정보를 잘 표현한다.

```
SeCause → Redis
Redis → TEAMFICIAL
```

하지만 실제 질문에 답하다 보면 이런 정보도 필요하다.

- Redis를 정확히 왜 사용했지?
- 어떤 방식으로 구현했지?
- 원문에서는 어떻게 설명했지?

그래서 그래프가 찾아낸 관계에 연결된 `chunk_id`와 `evidence`를 이용해 **원문까지 다시 가져온다.**

```
그래프
"SeCause → Redis"
      ↓
chunk_id / evidence
      ↓
원문
"큐 기반 비동기 처리를 위해 ..."
      ↓
LLM
```

W5에서 엣지마다 `evidence`와 `chunk_id`를 저장했던 이유가 여기서 다시 나온다.

---

## **Local Search가 잘하는 것과 못하는 것?**

Local Search는 **출발점이 명확한 다중 홉 질문**에 강하다. ex) X01 질문..

반대로 “내가 요즘 어떤 기술에 관심이 많은 것 같아?” 같은 질문에는 잘 맞지 않는다.

특정 프로젝트나 기술처럼 명확한 출발점이 없다.

또 Redis처럼 연결이 많은 노드에서 너무 멀리 확장하면 관련 없는 정보까지 빠르게 늘어난다.

그리고 더 근본적인 한계도 있다.

**그래프에 표현하지 않은 관계는 따라갈 수 없다.**

예를 들어 H01의 “RDS 장애 원인·수정·검증 과정” 은 현재 내 그래프의 기술 사용 중심 스키마에 들어있지 않다.

이런 질문은 기존 Hybrid RAG가 더 적합하다.

즉 **GraphRAG가 기존 RAG를 전부 대체하는 것은 아니다!**

# **3. Global Search : 질문하기 전에 전체를 미리 요약해둔다**

Local Search와 정반대에 가까운 질문도 있다.

“내 프로젝트 전체에서 공통적으로 나타나는 특징은 뭐야?” 같은 질문은 어디서 시작해야 할지가 애매하다.

SeCause 하나만 봐도 안 되고 Redis 주변만 봐도 안 된다. **전체 데이터를 어느 정도 봐야 하는 질문**이다.

그런데 문서가 수천, 수만 개라면 질문할 때마다 전부 LLM에게 넣을 수 없다.

그래서 Global Search는 일을 **질문하기 전에 미리 해둔다.**

### **1. 먼저 그래프를 여러 덩어리로 나눈다**

그래프에서 서로 촘촘하게 연결된 노드들을 찾아 그룹으로 묶는다.

→ 이걸 **Community Detection**이라고 한다.

예를 들면 그래프에서 자연스럽게 이런 덩어리가 생길 수 있다.

```
[커뮤니티 A]
Redis
SeCause
TEAMFICIAL
직행
캐시
비동기 처리

[커뮤니티 B]
Docker
GitHub Actions
배포
CI/CD
...
```

Leiden이나 Louvain은 이런 **서로 연결이 강한 노드 집단을 찾아주는 알고리즘**이다.

### **2. 그리고 각 덩어리를 미리 요약한다**

각 커뮤니티에 어떤 Entity와 관계가 있는지 LLM에게 미리 요약시킨다.

```
커뮤니티 A
    ↓
"여러 프로젝트에서 Redis를
캐시 및 비동기 처리 목적으로 사용..."

커뮤니티 B
    ↓
"Docker와 GitHub Actions를 중심으로
배포 자동화 경험이 반복적으로 나타남..."
```

이렇게 만들어놓은 요약을 **Community Report**라고 생각하면 된다.

질문이 들어오면 원문 전체를 다시 읽는 대신 이 요약들을 활용한다.

```
그래프 구축
   ↓
커뮤니티 탐지
   ↓
커뮤니티별 요약
   ↓
        여기까지 미리 해둠
────────────────────────
질문 들어옴
   ↓
관련 요약들을 검토
   ↓
부분 답변
   ↓
최종 답변으로 종합
```

즉 **비싼 일을 질문 전에 미리 해두는 방식**이다.

이게 이번 주의 다른 주제인 **“그래프 인덱싱은 빌드 시점 선지불이다.”** 와 연결된다.

---

## **그런데 내 데이터에는 굳이 필요할까?**

현재는 그럴 가능성이 낮다.. 내 그래프는 아직 노드가 수십 개 규모다.

이 정도 데이터를 다시 여러 커뮤니티로 나누고 각각 LLM 요약을 생성해서 저장하는 것보다 그냥 전체 그래프를 보는 편이 단순할 수 있다.

그래서 Global Search를 공부하면서 중요한 건 **“GraphRAG니까 Global Search도 구현해야 한다.”**

가 아니라, **“전체를 봐야 하는 질문이 있고, 데이터가 충분히 커지면 이런 방법이 필요해지는구나.”**

를 이해하는 것!!

# **4. Text2Cypher : 질문을 아예 그래프 쿼리로 바꾼다**

세 번째 방법은 조금 다르다.

그래프의 일부를 가져와 LLM에게 판단시키는 대신 **LLM이 직접 Cypher를 작성하게 한다.**

예를 들어 사용자가 “내가 가장 많은 프로젝트에서 사용한 기술은?” 라고 묻는다면

LLM에게 현재 그래프의 구조를 알려주면 다음과 같은 Cypher를 만들 수 있다.

```
MATCH (t:Technology)
      <-[:USES_TECHNOLOGY]-(u:TechnologyUse)
      -[:PART_OF]->(p:Project)
RETURN t.label,
       count(DISTINCT p) AS n
ORDER BY n DESC
LIMIT 1
```

Neo4j가 계산한다.

```
redis | 3
```

그 결과를 다시 자연어로 바꾸면 된다.

→ “Redis입니다. SeCause, TEAMFICIAL, 직행 세 프로젝트에서 사용했습니다.”

---

## **왜 집계 질문에 특히 좋을까?**

Local Search라면 관련 노드를 가져온 뒤 LLM에게 사실상 이런 일을 시키게 된다.

“자, 이 프로젝트들 보고 뭐가 제일 많이 등장했는지 세어봐.”

하지만 정확한 개수 계산은 DB가 훨씬 잘한다.

Text2Cypher에서는 `count(DISTINCT p)` 처럼 그래프 DB가 직접 계산한다.

따라서 **집계, 정렬, 특정 조건 필터링처럼 답이 정확해야 하는 질문**에서 특히 유리하다.

W3에서 top-k 검색만으로는 전체 집계 질문을 제대로 풀기 어렵다는 문제를 봤는데, 여기서는 검색 대신 **DB 질의로 문제 자체를 바꾸는 것**이다.

---

# **5. Text2Cypher의 진짜 문제 : 틀려도 티가 안 날 수 있다**

Text2Cypher는 잘 작동하면 굉장히 편하다.

문제는 LLM이 Cypher를 잘못 만들 수도 있다는 것이다.

예를 들어 실제 관계 이름은 `USES_TECHNOLOGY`인데 

LLM이 `[:USES]` 라고 만들어버릴 수 있다.

혹은 실제 label이 `redis`인데, `{label: 'Redis'}` 라고 검색할 수도 있다.

더 위험한 건 이런 경우다.

```
사용자 질문
"Redis를 쓴 프로젝트 있어?"
       ↓
LLM이 잘못된 Cypher 생성 (ex. redis)
       ↓
Neo4j 결과
0 rows
       ↓
"Redis를 사용한 프로젝트는 없습니다."
```

Cypher 문법이 틀렸다면 에러라도 나지만 **문법은 맞고 의미만 틀렸다면 정상적으로 0건이 나온다..**

그래서 Text2Cypher에서는 **0건 = 데이터가 없음** 이라고 바로 판단하면 안 된다!

---

## **그래서 LLM에게 그래프 구조를 알려줘야 한다!**

LLM에게 그냥 “이 질문을 Cypher로 바꿔줘.” 라고 하면 안 된다.

현재 그래프가 어떻게 생겼는지 같이 알려줘야 한다.

예를 들면…

```
Node
- Project(label)
- Technology(label)
- TechnologyUse(purpose, status)

Relationship
- TechnologyUse -[:PART_OF]-> Project
- TechnologyUse -[:USES_TECHNOLOGY]-> Technology

실제 값 예시
- Technology.label = "redis"
```

이런 정보를 **Schema Injection**, 즉 스키마를 프롬프트에 같이 넣어주는 방식이라고 생각하면 된다.

그리고 실제 질문과 올바른 Cypher 예시도 몇 개 보여줄 수 있다.

```
질문:
"Redis를 사용한 프로젝트는?"

Cypher:
MATCH ...
```

이렇게 **입력과 정답 예시를 몇 개 먼저 보여준 뒤 새로운 문제를 풀게 하는 방식**이 앞에서 한 번 봤던 **few-shot**이다. (지난 주차에도 나온 내용)

W5의 LLM 추출에서도

```
이런 문서 → 이런 Triple
이런 문서 → 아무것도 없으므로 []
```

같은 예시를 보여줬던 것과 원리는 같다.

# **6. 결국 어떤 질문에 뭘 써야 할까???**

세 가지 중 하나가 무조건 좋은 것은 아니다.

내가 지금까지 사용했던 질문을 다시 분류해보면 차이가 명확하다.

| **질문** | **적합한 방식** | **이유** |
| --- | --- | --- |
| S01 `@Transactional` 내부 호출 | **기존 검색** | 그래프에 없는 서술 정보 |
| X01 SeCause 기술을 다른 곳에서도 썼나 | **Local Search** | SeCause에서 관계를 따라가면 됨 |
| X03 제안한 기술을 다른 곳에서는 구현했나 | **Local / Text2Cypher** | 다중 홉 + status 조건 |
| 가장 많은 프로젝트에서 사용한 기술 | **Text2Cypher** | 정확한 집계 필요 |
| H01 RDS 장애 원인·수정·검증 | **기존 검색** | 현재 그래프 스키마에 없는 정보 |
| 내 프로젝트들의 공통적인 특징 | **Global Search** | 특정 시작점 없이 전체를 봐야 함 |

이 표가 이번 주 v1과 v2 비교 실험의 **가설**이 된다.

아직 GraphRAG가 무조건 더 좋다고 결론 내린 것은 아니다.

실제 실험에서는 이 예상대로 나오는지 확인하면 된다.

# **7. 이번에 가져갈 핵심**

W5에서는 그래프를 만들면 RAG가 놓친 관계를 찾을 수 있다는 것을 확인했다.

하지만 그때는 사람이 직접 Cypher를 작성했다.

이번에는 한 단계 더 나아가 **사용자의 자연어 질문과 그래프 사이를 어떻게 연결할 것인지**를 본다.

세 가지 방식은 서로 경쟁하는 기술이라기보다 **질문의 종류에 따라 다른 도구**다.

```
특정 Entity에서 시작
        ↓
   Local Search

데이터 전체를 조망
        ↓
   Global Search

정확한 조건 / 집계
        ↓
   Text2Cypher

그래프에 없는 서술 정보
        ↓
   기존 Hybrid RAG
```

그래서 이번 주에 확인하고 싶은 것은 단순히 **GraphRAG가 기존 RAG보다 좋은가?** 가 아니다

오히려 다음 질문에 가깝다.

**어떤 질문에서 그래프를 사용하는 것이 실제로 도움이 되고, 어떤 질문에서는 기존 검색을 그대로 사용하는 편이 나은가?**

이걸 확인하려면 이제 그래프와 벡터 검색을 실제로 한 파이프라인 안에서 연결해야 한다.
