# **RDFS와 OWL — 관계에 의미와 규칙을 더하려면?**

앞에서는 RDF로 사실과 관계를 Triple 형태로 표현하고, SPARQL로 그 관계를 따라 원하는 정보를 조회하는 방법까지 봤다. 그런데 여기까지 하고 나니 한 가지가 빠져 있었다.

예를 들어 `연호 → type → Student`, `Student → subClassOf → Person`이라는 정보가 있다고 해보자. 사람이라면 **“연호는 Student니까 Person이기도 하겠군”**이라고 자연스럽게 생각한다. 하지만 지금까지 본 RDF는 기본적으로 사실을 표현하는 모델이다. `Student`와 `Person`이 어떤 관계인지, 그 관계를 통해 어떤 새로운 사실을 알아낼 수 있는지 같은 의미를 더 표현하려면 추가적인 어휘와 규칙이 필요하다.

여기서 **RDFS와 OWL**이 등장한다.

## **1. RDF 위에 의미를 쌓아 올리기**

RDF가 `A → 관계 → B`라는 사실을 표현하는 기본 틀이라면, RDFS와 OWL은 그 위에 이 관계와 개념은 어떤 의미인가?를 표현할 수 있게 해준다.

큰 흐름만 보면 이렇게 이해할 수 있다.

**RDF: 사실 표현 → RDFS: 클래스와 속성의 기본적인 의미·계층 표현 → OWL: 더 풍부한 의미와 논리적 관계 표현**

예를 들어 RDF로는 `연호 → attends → 홍익대학교`라는 사실을 적을 수 있다. 여기서 RDFS를 사용하면 `Student는 Person의 하위 클래스다`, `attends라는 속성을 사용하면 그 주어와 목적어의 타입을 이렇게 해석한다` 같은 의미를 추가할 수 있다.

OWL까지 가면 `두 클래스는 서로 겹칠 수 없다`, `두 IRI가 같은 대상을 의미한다`, `이 관계는 대칭적이다`처럼 더 복잡한 의미도 표현할 수 있다.

중요한 건 **RDF, RDFS, OWL이 완전히 별개의 데이터 모델이라기보다 RDF 위에서 사용할 수 있는 표현력을 점점 늘려간다고 보는 것**이다.

## **2. RDFS — 클래스와 속성에 기본적인 의미를 붙인다**

RDFS(RDF Schema)에서는 클래스의 계층이나 Property의 의미를 표현할 수 있다. 이번 주에는 아래 정도만 조사해봤다.

| **어휘** | **의미** |
| --- | --- |
| `rdf:type` | 어떤 대상이 특정 클래스에 속한다 |
| `rdfs:subClassOf` | 한 클래스가 다른 클래스의 하위 클래스다 |
| `rdfs:subPropertyOf` | 한 속성이 다른 속성의 하위 속성이다 |
| `rdfs:domain` | 이 Property를 사용한 주어의 타입을 나타낸다 |
| `rdfs:range` | 이 Property를 사용한 목적어의 타입을 나타낸다 |

예를 들어 `Student subClassOf Person`이라고 정의하고 `연호 type Student`라는 사실이 있다면, 여기서 **`연호 type Person`이라는 새로운 사실을 유도할 수 있다.**

이게 이번 내용에서 중요한 **추론(Inference)**이다.

## **3. 추론 : 저장하지 않은 사실이 생긴다**

처음에는 “적지 않은 Triple이 생긴다”는 표현이 조금 이상했는데, 결국 **이미 알고 있는 사실과 규칙을 이용해 새로운 사실을 유도하는 것**이다.

예를 들어 다음 두 사실이 있다고 하자.

- **Student → subClassOf → Person**
- **연호 → type → Student**

그러면 `연호 → type → Person`을 따로 저장하지 않았어도 유도할 수 있다.

조금 더 이어서 `Person → subClassOf → Agent`까지 정의되어 있다면,

**연호 → Student → Person → Agent ⇒ 연호는 Agent다.**

처럼 클래스 계층을 따라 더 많은 사실을 알아낼 수 있다.

즉 그래프에 모든 사실을 직접 중복해서 저장하지 않더라도 **이미 저장된 관계와 규칙을 이용해 새로운 관계를 알아낼 수 있는 것**이다.

앞에서 SPARQL의 Property Path로 관계를 따라가는 것과 비슷해 보이지만 둘은 조금 다르다. SPARQL은 **질의할 때 그래프를 따라가서 결과를 찾는 것**이고, 추론은 **주어진 사실과 의미 규칙에 따라 어떤 사실이 논리적으로 따라오는지를 다루는 것**이다.

## **4. `domain`과 `range`는 타입 검사가 아니다**

RDFS를 보면서 가장 헷갈렸던 부분은 `domain`과 `range`였다.

| `rdfs:domain` | 이 Property를 사용한 주어의 타입을 나타낸다 |
| --- | --- |
| `rdfs:range` | 이 Property를 사용한 목적어의 타입을 나타낸다 |

예를 들어 `attends`의 range를 `School`이라고 정의했다고 하자. 처음 보면 자연스럽게 

“attends 뒤에는 School만 올 수 있다” 는 제약처럼 느껴진다.

그런데 RDFS에서는 그런 의미가 아니다.

만약 실수로 `연호 → attends → Redis`라고 저장해도 **“Redis는 School이 아니니까 잘못된 데이터입니다”라는 에러가 발생하지 않는다.**

오히려 RDFS의 의미에 따르면:

**attends의 range는 School + attends의 목적어가 Redis → 그러므로 Redis는 School**

이라고 추론한다. 이 차이가 중요했다.

| **내가 처음 생각한 의미** | **실제 RDFS 의미** |
| --- | --- |
| `range School` → School만 올 수 있다 | `range School` → 여기에 온 대상은 School이라고 추론한다 |
| 타입이 다르면 오류 | 새로운 타입이 유도될 수 있음 |
| 데이터 검증 | 의미와 추론 |

즉 `domain`과 `range`는 **“이렇게 데이터를 넣어야 한다”는 유효성 검사 규칙이 아니라, 이 Property가 사용됐을 때 주어와 목적어를 어떤 타입으로 해석할지 알려주는 의미 규칙**이다.

실제로 데이터가 내가 정한 형식을 지키고 있는지 검증하고 싶다면 다른 방법이 필요하고, 뒤에서 잠깐 볼 **SHACL**이 이런 목적에 더 가깝다.

## **5. OWL : 더 복잡한 의미까지 표현하기**

RDFS가 클래스 계층과 Property의 기본적인 의미를 표현한다면, **OWL(Web Ontology Language)**은 그보다 더 풍부한 의미와 논리적인 관계를 표현할 수 있다.

이번 주에는 OWL 문법을 깊게 보진 못했고 **“이런 것까지 표현할 수 있다”** 정도만 봤다.

| **종류** | **예시** | **의미** |
| --- | --- | --- |
| 동일성 | `owl:sameAs` | 서로 다른 IRI가 같은 대상을 의미 |
| 차이 | `owl:differentFrom` | 두 대상이 서로 다름 |
| 역관계 | `owl:inverseOf` | 부모 ↔ 자식처럼 반대 방향 관계 |
| 대칭 관계 | `SymmetricProperty` | A→B라면 B→A |
| 이행 관계 | `TransitiveProperty` | A→B, B→C라면 A→C |
| 클래스 관계 | `disjointWith` | 두 클래스가 동시에 성립할 수 없음 |
| 여러 종류의 제한 | Restriction 계열 | 특정 Property가 만족해야 할 논리적 조건 표현 |

예를 들어 `partOf`를 이행적인 관계로 정의했다고 해보자.

**Redis 사용 경험 → partOf → SeCause 프로젝트 → partOf → 포트폴리오**

라면 `Redis 사용 경험 → partOf → 포트폴리오`라는 관계도 논리적으로 따라올 수 있다.

RDFS에서 봤던 단순한 클래스 계층보다 **관계 자체가 어떤 성질을 가지는지까지 정의할 수 있게 된 것**이다.

다만 여기부터는 표현력이 빠르게 커지고 그만큼 추론도 복잡해진다. 이번 주 목표는 OWL을 직접 설계하는 것이 아니라 **RDF에 의미를 추가하고 그 의미를 바탕으로 새로운 사실을 추론할 수 있다는 개념**까지만 이해하는 것으로 잡았다.

## **6. 그래서 스키마와 온톨로지는 뭐가 다를까?**

이번 주 핵심 질문 중 하나가 **“스키마와 온톨로지는 뭐가 다른가?”**였다.

처음에는 RDFS = 스키마, OWL = 온톨로지라고 딱 잘라 생각하기 쉬운데, 실제로는 그렇게 완전히 분리되는 개념은 아니다. RDFS로도 온톨로지를 표현할 수 있고 OWL은 그 표현력을 더 확장한다.

그래도 개념을 이해하기 위해 단순화하면 이렇게 볼 수 있었다.

|  | **스키마** | **온톨로지** |
| --- | --- | --- |
| 관심사 | 데이터가 어떤 구조를 가지는가 | 개념들이 무엇을 의미하고 어떻게 관계되는가 |
| ex) | Project와 Technology가 있다 | Database는 Technology의 일종이다 |
| 관계 | 사용할 필드·타입 등의 구조 | 클래스 계층, 동일성, 관계의 성질 등 |
| 목적 | 데이터를 일정한 형태로 관리 | 도메인의 의미를 명시적으로 모델링 |

한마디로 정리하면 **스키마는 데이터의 구조에 더 초점을 두고, 온톨로지는 그 데이터가 표현하는 개념과 관계의 의미에 더 초점을 둔다.**

그리고 OWL은 그런 온톨로지를 더 풍부하게 표현할 수 있도록 만든 언어라고 이해했다.

## **7. 열린 세계 : “없다”와 “모른다”는 다르다**

여기서 RDF와 OWL의 사고방식을 이해하는 데 중요한 **Open World Assumption(OWA)**이 나온다.

핵심은 한 문장이다.

**데이터에 적혀 있지 않다고 해서 거짓이라고 판단하지 않는다. 그냥 모르는 것이다.**

예를 들어 데이터에 `연호 → 다닌다 → 홍익대학교`만 있다고 해보자.

“연호가 연세대학교에 다니는가?”라고 물었을 때, 일반적인 애플리케이션 DB에서는 해당 데이터가 없으니 `false`라고 처리하고 싶을 수 있다.

하지만 열린 세계에서는 **연세대학교에 다닌다는 정보가 현재 데이터에 없을 뿐, 실제로 다니지 않는다고 단정할 수는 없다.**

왜 이런 사고방식을 사용할까 생각해보면 RDF가 웹의 데이터를 연결하기 위해 만들어졌다는 배경과 연결된다. 웹에 있는 정보는 항상 불완전하다. 지금 가지고 있는 데이터셋에 어떤 사실이 없다고 해서 세상 전체에 그 사실이 없다고 말할 수는 없다.

따라서 열린 세계에서는 **“없음”과 “모름”을 구분한다.**

## **8. 그래서 부정 질문이 어렵다….**

이 부분은 지난주 RAG 실험을 떠올리니 이해가 쉬웠다.

예를 들어 내 프로젝트 기록을 대상으로 “아직 구현하지 않은 기능은 무엇인가?” 라고 질문한다고 해보자.

문서나 그래프에 `A 기능을 구현했다`는 기록이 없다고 해서 곧바로 “A는 구현하지 않았다” 고 판단할 수는 없다. 그냥 기록을 안 했을 수도 있기 때문이다.

즉, **구현 기록 없음 ≠ 구현하지 않음** 이다.

지난주에도 이런 **부정(Negation)이 포함된 질문**을 별도의 실패 유형으로 생각했는데, 이번에 열린 세계 가정을 보면서 왜 이런 질문이 근본적으로 까다로운지 이해할 수 있었다.

부정 질문에 확실하게 답하려면 어느 시점에는 **“내가 가진 목록이 전체다!!”**라는 전제가 필요하다. 그래야 목록에 없는 것을 실제로 없다고 판단할 수 있다.

이건 웹처럼 불완전한 데이터를 전제로 하는 열린 세계와는 반대되는 **Closed World Assumption(닫힌 세계 가정)**에 가깝다.

## **9. 서로 다른 IRI라고 서로 다른 대상인 것도 아니다**

열린 세계와 함께 흥미로웠던 부분이 하나 더 있다.

OWL에서는 **서로 다른 IRI를 가지고 있다고 해서 반드시 서로 다른 대상이라고 가정하지 않는다.**

예를 들어 `ex:yeonho`와 `ex:leeYeonho`가 있다고 해보자. 이름이 다르니 서로 다른 사람이라고 바로 판단하는 게 아니라, 같은 사람일 가능성도 열어둔다.

둘이 같은 대상이라는 걸 알고 있다면 `owl:sameAs` 같은 표현으로 그 사실을 명시할 수 있다.

이 부분은 앞에서 IRI를 공부할 때 나온 Entity Resolution 문제와 다시 연결된다.

IRI는 대상을 식별하는 방법을 제공하고 OWL은 “이 두 식별자는 같은 대상을 의미한다”고 표현할 방법도 제공한다. 하지만 **실제로 두 대상이 같은 사람인지 판단하는 것 자체를 대신해주지는 않는다.**

나중에 여러 사람의 데이터를 하나의 그래프로 합치려면 결국 `연호`, `이연호`, `Lee Yeonho`가 같은 사람인지 판단해야 하는데, 표준은 그것을 **표현할 방법**을 줄 뿐 실제 판단 문제는 여전히 남는다.

## **10. 그러면 우리가 만든 건 온톨로지일까?**

여기서 이번 주 실습을 다시 돌아봤다.

나는 개인 프로젝트 기록에서 관계를 추출하기 위해 사용할 관계를 우선 네 종류로 제한했다.

- 어떤 프로젝트에 포함되는지 `PART_OF`
- 어떤 기술을 사용했는지 `USES_TECHNOLOGY`
- 왜 사용했는지 `HAS_PURPOSE`
- 현재 어떤 상태인지 `HAS_STATUS`

그리고 이 네 종류가 아닌 관계는 일단 추출하지 않는 방식으로 범위를 제한했다.

처음에는 이것도 넓은 의미에서 온톨로지라고 생각할 수 있었는데, RDFS와 OWL을 공부하고 나니 **우리가 지금 만드는 것은 풍부한 의미 규칙과 추론을 가진 온톨로지라기보다, 실험 범위를 제한한 작은 스키마에 가깝다.**

우리는 `PART_OF`가 이행적이라고 선언해서 새로운 관계를 자동으로 추론하지도 않고, 클래스 사이의 논리적인 관계를 정의하지도 않는다.

목적은 훨씬 단순하다.

**개인 문서 → 정해진 Entity와 관계 추출 → PostgreSQL 저장 → 관계 기반 검색 → 기존 RAG와 비교**

즉 우리가 지금 확인하고 싶은 건 **온톨로지 추론의 효과가 아니라, 문서 속 관계를 명시적으로 구조화했을 때 Retrieval Failure를 줄일 수 있는가**다.

## **11. OWL보다 오히려 SHACL에 가까운 부분도 있었다**

여기서 `domain`, `range`를 보면서 했던 착각이 다시 중요해진다.

우리가 술어를 네 종류로 제한하고 **“이 형식에 맞는 관계만 추출하자”**라고 하는 건 새로운 사실을 추론하려는 게 아니다. 오히려 **허용된 형태인지 검사하고 범위를 통제하려는 목적**에 가깝다.

이런 사고방식은 OWL보다는 **SHACL(Shapes Constraint Language)**과 더 비슷하다.

|  | **OWL** | **SHACL** | **현재 실습** |
| --- | --- | --- | --- |
| 주된 목적 | 의미 표현과 추론 | 그래프 검증 | 추출 범위 통제 |
| 규칙을 사용하는 이유 | 새로운 사실을 유도 | 데이터가 조건을 만족하는지 검사 | 정해진 관계만 추출 |
| 기본적인 관점 | 열린 세계 | 검증 대상 그래프를 기준으로 검사 | 실험용으로 범위를 닫음 |

SHACL 자체를 이번 주에 배우려는 건 아니다. 중요한 건 **“관계를 제한하는 것”과 “온톨로지로 의미를 정의하고 추론하는 것”은 다른 문제**라는 점이다.

그래서 현재 우리가 만든 것을 굳이 정확하게 표현한다면?

**→ 작은 폐쇄형 관계 스키마를 정의하고, 그 스키마에 맞춰 개인 문서에서 그래프를 추출하는 실험**

정도가 가장 맞는 표현 같다… 오히려 범위를 이렇게 제한했기 때문에 몇 주 안에 직접 구현하고 평가할 수 있다.

## **12. 이번에는 어디까지 알면 될까?**

RDFS와 OWL은 더 들어가면 범위가 끝없이 넓어진다. 이번 주에는 아래 정도까지만 가져가기로 했다.

| **주제** | **이번에 볼 것** | **지금은 안 볼 것** |
| --- | --- | --- |
| RDFS | 클래스 계층, domain/range, 기본 추론 | 세부 명세 |
| OWL | RDFS보다 풍부한 의미와 추론이 가능하다는 것 | Description Logic, OWL Profile |
| Inference | 저장하지 않은 사실을 규칙으로 유도한다는 개념 | 추론 알고리즘 구현 |
| OWA | 없는 정보는 거짓이 아니라 모른다는 것 | 형식 의미론 |
| `owl:sameAs` | 동일한 대상을 표현할 수 있다는 것 | 동일성 전파 알고리즘 |
| SHACL | 추론이 아니라 검증이라는 차이 | Shape 문법 |

결국 이번 내용에서 가장 기억할 것은 세 가지였다.

**첫째, 추론은 이미 저장된 사실과 규칙을 이용해 적지 않은 사실을 유도하는 것이다.**

**둘째, RDFS의 `domain`과 `range`는 타입 검사가 아니다.** 조건을 어기면 에러를 내는 게 아니라 오히려 해당 타입이라고 추론할 수 있다.

**셋째, RDF/OWL의 열린 세계에서는 데이터에 없는 사실을 거짓이라고 단정하지 않는다. `없다`와 `모른다`는 다르다.**

## **그래서 다음은?**

지금까지 `RDF → SPARQL → RDFS/OWL`을 따라오면서 **사실을 Triple로 표현하고 → 관계를 조회하고 → 그 관계에 의미와 추론 규칙까지 부여하는 과정**을 봤다.

그런데 여기까지 보면 오히려 궁금한 게 생긴다. 이렇게 웹의 모든 데이터를 의미 있는 관계로 연결하고, 기계가 그 의미까지 이해하도록 만들겠다는 생각은 **왜 시작됐을까? 그리고 이렇게 잘 만들어진 기술들이 있는데 왜 지금 웹 전체가 RDF와 OWL로 이루어져 있지는 않을까?**

이 질문을 이해하려면 기술 문법에서 잠깐 벗어나 **Semantic Web → Linked Data와 Wikidata → Google Knowledge Graph → GraphRAG와 기업 Ontology**로 이어진 흐름을 볼 필요가 있다.

다음에는 이 기술들이 **어떤 문제를 해결하려고 등장했고, 무엇이 현실에서 잘 되거나 잘 안 됐는지** 변천사를 따라가며 정리한다.
