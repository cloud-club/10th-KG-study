# **W5 실습 — 문서에서 지식 그래프를 만들어보면**

**핵심 질문:** W4에서 일반 RAG가 답하지 못했던 질문을 실제 지식 그래프로 만들면 해결할 수 있을까?

그리고 LLM으로 그래프를 자동으로 만들었을 때는 어떤 새로운 문제가 생길까?

---

## **1. 이번 실습에서 확인하고 싶었던 것**

W4에서는 일반 RAG가 답하지 못한 질문을 분석하면서 한 가지 가설을 세웠다.

일반적인 RAG는 **질문의 표현을 바탕으로 관련 청크를 검색**한다. 따라서 답에 필요한 연결고리가 질문에 직접 등장하지 않으면 필요한 문서를 찾지 못할 수 있다.

대표적인 질문이 X01이었다.

**X01. SeCause에서 작업 큐에 사용한 기술을 다른 프로젝트에서도 사용했는가?**

이 질문의 답을 찾으려면 사실 다음과 같은 연결이 필요하다.

```
SeCause
  ↓
작업 큐에 사용한 기술은?
  ↓
Redis
  ↓
Redis를 사용한 다른 프로젝트는?
  ↓
TEAMFICIAL / 직행
```

문제는 질문 어디에도 **`Redis`라는 단어가 없다는 것**이다.

W4의 Hybrid RAG는 `SeCause`, `작업 큐`와 관련된 문서는 찾았지만, Redis를 브릿지로 삼아 다른 프로젝트까지 넘어가지 못했다.

그래서 W4에서는 이를 그래프로 표현하면 해결할 수 있을 것이라고 예상했다.

```
SeCause ──> Redis <── TEAMFICIAL
               ↑
              직행
```

이번 W5에서는 이 그림을 실제 데이터로 만들어보기로 했다.

---

# **2. 문서에서 실제 그래프를 만들었다**

전체 1,562개 청크를 바로 처리하지 않고, 먼저 X01과 X03에 필요한 내용을 포함한 **20개 청크를 표본으로 선택했다.**

전체 흐름은 다음과 같다.

```
내 프로젝트 문서
      ↓
    Chunk
      ↓
LLM Triple Extraction
      ↓
엔티티 / 관계 / 근거
      ↓
 ┌───────────────┐
 │  PostgreSQL   │
 └───────────────┘
      ↓
Turtle / JSON-LD
      ↓
 ┌───────────────┐
 │     Neo4j     │
 └───────────────┘
      ↓
 Cypher로 질의
```

LLM에게 아무 관계나 자유롭게 만들게 하지는 않았다.

앞에서 설계한 닫힌 스키마에 맞춰 다음 세 종류의 엔티티를 추출했다.

| **클래스** | **의미** |
| --- | --- |
| `Project` | SeCause, TEAMFICIAL, 직행 같은 프로젝트 |
| `Technology` | Redis, Spring Boot, FastAPI 같은 기술 |
| `TechnologyUse` | 특정 프로젝트에서 특정 기술을 사용한 사례 |

관계도 미리 정의한 범위 안에서만 추출하도록 제한했다.

```
partOf
usesTechnology
hasPurpose
hasStatus
replaces
```

그리고 각 관계에는 가능하면 **원문의 evidence와 chunk_id**도 함께 저장했다.

즉 이번 실습은 단순히 Neo4j에 노드를 몇 개 만들어본 것이 아니라,

**문서 → LLM 추출 → 검증 → PostgreSQL → RDF → Neo4j → 실제 질의**

까지 한 번 완주해보는 것이 목적이었다.

---

# **3. 첫 번째 결과 — 정말 Redis가 브릿지가 됐다**

실제 추출 결과에서 여러 프로젝트가 공통으로 사용한 기술을 찾아봤다.

| **기술** | **연결된 프로젝트 수** | **프로젝트** |
| --- | --- | --- |
| Redis | 3 | 직행, SeCause, TEAMFICIAL |
| Docker | 2 | SeCause, TEAMFICIAL |
| GitHub Actions | 2 | SeCause, TEAMFICIAL |
| Spring Boot | 2 | SeCause, TEAMFICIAL |

W4에서 화이트보드로 예상했던 구조가 실제 데이터에서도 나타났다.

```
                    Redis
                  /   |   \
                 /    |    \
          SeCause   직행   TEAMFICIAL
```

**Redis가 실제로 서로 다른 프로젝트를 연결하는 브릿지 노드가 된 것이다.**

---

## **4. 왜 그래프에서는 X01을 풀 수 있었을까?**

기존 RAG와 비교하면 차이가 명확하다.

### **기존 RAG**

```
질문
"SeCause 작업 큐에 쓴 기술을
다른 프로젝트에서도 사용했나?"

        ↓ 검색

"SeCause", "작업 큐"와
비슷한 청크를 찾음

        ↓

SeCause 문서는 찾음

        ↓

다른 프로젝트의 Redis 문서는?
        ❌
```

질문에 `Redis`라는 단어가 없기 때문에 TEAMFICIAL의 Redis 캐시 문서를 검색하기 어려웠다.

반면 그래프에서는 검색할 필요가 없다.

### **그래프**

```
SeCause
   ↓
TechnologyUse
   ↓
Redis
   ↓
Redis와 연결된 다른 TechnologyUse
   ↓
TEAMFICIAL / 직행
```

이미 관계가 저장되어 있기 때문에 **연결을 따라가기만 하면 된다.**

즉,

**검색 문제가 조인 문제로 바뀌었다.**

W4에서 세웠던 가설을 실제 데이터로 확인한 첫 번째 결과였다.

---

# **5. X03에서는 `TechnologyUse`를 만든 이유도 확인했다**

두 번째로 확인한 것은 X03이었다.

X03에서는 단순히 같은 기술을 사용했는지가 아니라,

**한 프로젝트에서 제안만 했던 방법을 다른 프로젝트에서는 실제로 구현했는가?**

를 구분해야 했다.

실제 Redis 데이터를 보면 다음과 같았다.

| **프로젝트** | **목적** | **상태** |
| --- | --- | --- |
| 직행 | 통근 시간 저장 | `proposed` |
| SeCause | 큐 기반 비동기 처리 | `implemented` |
| TEAMFICIAL | 지원자 수 캐시 | `implemented` |

여기서 단순히 다음과 같이 저장했다면 문제가 생긴다.

```
직행 ──USES──> Redis
```

이 관계만으로는 Redis를 **왜 사용했는지**, 그리고 **실제로 구현했는지 제안만 했는지**를 표현할 수 없다.

그래서 중간에 `TechnologyUse`를 두었다.

```
             partOf
[Redis 사용례] ───────> 직행
      │
      ├── usesTechnology ──> Redis
      │
      ├── purpose = "통근 시간 저장"
      │
      └── status  = "proposed"
```

덕분에 같은 Redis라도 서로 다른 사용 사례를 구분할 수 있었다.

W4에서 RDF의 reification과 Wikidata의 statement 구조를 공부하면서 봤던 **“관계 자체에 추가 정보를 붙이려면 어떻게 해야 하는가?”**라는 문제가 실제 내 데이터에서도 그대로 나타난 것이다.

---

# **6. 그런데 그래프를 만들자 새로운 문제가 생겼다**

여기까지 보면 지식 그래프를 만들면 모든 문제가 해결된 것처럼 보인다.

그런데 실제 데이터를 확인하면서 오히려 이번 실습에서 더 중요한 문제를 발견했다.

**같은 사실이 여러 개의 `TechnologyUse`로 쪼개지고 있었다.**

대표적인 사례가 TEAMFICIAL의 Redis 사용이다.

실제로는 비슷한 하나의 사용 사례인데 여러 문서와 청크에서 조금씩 다른 표현으로 등장한다.

```
"Redis로 지원자 수를 캐싱했다"

"지원자 수 조회에 Redis 캐시를 적용했다"

"반복 조회 비용을 줄이기 위해 Redis를 사용했다"
```

사람이 읽으면 모두 비슷한 맥락이라는 것을 쉽게 알 수 있다.

하지만 LLM은 각각의 청크를 독립적으로 처리한다.

```
청크 A
  ↓
TechnologyUse #1

청크 B
  ↓
TechnologyUse #2

청크 C
  ↓
TechnologyUse #3
```

실제로 20개 표본만 추출했는데도 TEAMFICIAL과 Redis 사이에 **6개의 `TechnologyUse` 노드**가 만들어졌다.

전체 결과에서도 45개의 `TechnologyUse`가 32개의 `(Project, Technology)` 조합에 대응했다.

즉 자동 추출 과정에서 **사용례가 과도하게 분리되는 현상**이 이미 나타났다.

---

# **7. 그렇다고 같은 기술을 전부 합칠 수도 없다**

처음에는 간단하게 생각할 수 있다.

같은 프로젝트에서 같은 기술을 사용했다면 하나로 합치면 되지 않을까?

하지만 직행의 Redis 사례를 보면 그렇게 할 수도 없다.

```
직행 + Redis
   │
   ├── 테스트 결과 저장
   │      └── implemented
   │
   └── 통근 시간 저장
          └── proposed
```

둘은 같은 프로젝트에서 같은 Redis를 사용하지만 **목적과 상태가 다른 별개의 사실**이다.

따라서

```
(Project, Technology)
```

만 같다고 무조건 합치면 X03에 필요한 정보가 사라진다.

반대로 전혀 합치지 않으면 TEAMFICIAL처럼 같은 사실이 여러 노드로 계속 늘어난다.

결국 다음 문제가 생긴다.

**어디까지를 같은 사용 사례라고 볼 것인가?**

이것이 다음 단계에서 해결해야 할 **Entity Resolution / TechnologyUse 병합 문제**다.

# **8. LLM이 그래프 구축 비용을 줄였지만, 공짜는 아니었다**

이 문제는 W4에서 살펴본 Semantic Web의 역사와도 연결된다.

과거에는 사람이 직접 데이터를 구조화해야 했다.

```
사람
 ↓
Entity 정의
 ↓
Relationship 정의
 ↓
Knowledge Graph
```

그래서 그래프 구축 비용이 매우 컸다.

이번에는 LLM을 사용하면서 이 과정을 상당 부분 자동화할 수 있었다.

```
문서
 ↓
LLM
 ↓
Entity + Relationship
 ↓
Knowledge Graph
```

하지만 자동화하면서 새로운 비용이 생겼다.

```
자동 추출
   ↓
중복 Entity
ID 불일치
같은 사실의 중복 표현
잘못된 관계
   ↓
정규화 / 병합 / 검증 필요
```

즉,

**LLM은 지식 그래프의 구축 비용을 낮췄지만, 데이터 정규화와 신원해소 문제까지 없애주지는 않았다.**

오히려 대량으로 자동 생성할 수 있기 때문에 잘못된 기준을 그대로 두면 문제도 함께 대량으로 생성된다.

---

# **9. NULL이 생긴 것도 실패가 아니었다**

추출 결과를 보면 `TechnologyUse` 45개 중 모든 노드에 목적과 상태가 들어있는 것은 아니었다.

| **항목** | **개수** |
| --- | --- |
| TechnologyUse | 45 |
| purpose 있음 | 26 |
| purpose 없음 | **19** |
| status 있음 | 29 |
| status 없음 | **16** |

처음에는 추출이 제대로 되지 않은 것처럼 보일 수 있다.

하지만 이것은 상당 부분 의도한 결과다.

추출 프롬프트에 다음 원칙을 넣었기 때문이다.

**문서에 명시되지 않은 사실은 추측해서 채우지 않는다.**

예를 들어 원문에

```
"Redis를 적용했다."
```

라고만 적혀 있다면,

```
Technology = Redis
Status = implemented
Purpose = ?
```

가 맞다.

LLM이 임의로 목적을 `캐싱`이라고 만들어내는 것보다 **모른다는 상태를 그대로 남기는 것이 낫다.**

W4에서 열린 세계 가정을 공부하며 봤던

**“없는 것과 모르는 것은 다르다.”**

라는 문제가 이번에는 실제 데이터의 NULL로 나타났다.

---

# **10. 만들어둔 술어가 실제로 하나도 안 쓰이기도 했다**

v0 스키마에서는 커리큘럼의 5개 술어 범위에 맞춰 `replaces`를 포함했다.

그런데 20개 표본에서 결과는:

```
replaces = 0
```

이었다.

스키마를 설계할 때는 필요할 것이라고 예상했지만 현재 데이터에서는 실제 사례가 나오지 않은 것이다.

이것도 중요한 결과였다.

**스키마는 처음부터 완성되는 것이 아니라 실제 데이터를 추출하고 질문을 풀어보면서 검증해야 한다.**

따라서 전체 데이터를 추출한 뒤에도 `replaces`가 사용되지 않는다면 v1에서는 제거할 수 있다.

닫힌 스키마의 목적은 많은 술어를 만드는 것이 아니라 **필요한 관계만 안정적으로 추출하는 것**이기 때문이다.

# **11. 구조화 출력을 써도 후처리는 필요했다**

20개 표본 중 18개는 정상 처리됐고 2개에서는 JSON 응답이 중간에 끊겼다.

또 LLM이 생성한 ID 하나에는 예상하지 못한 공백이 들어갔다.

```
정상
kg:use-...-tmap-api-1

실제 출력
kg:use-...- tmap-api-1
             ↑
```

이 작은 차이 때문에 하나의 사용례를 구성하던 관계 일부가 연결되지 않았고, 최종 적재 과정에서 해당 사용례가 제외됐다.

즉 구조화 출력을 사용했다고 해서 **데이터 품질까지 자동으로 보장되는 것은 아니었다.**

그래서 현재 파이프라인은 단순히 LLM 결과를 그대로 저장하지 않고,

```
LLM 출력
   ↓
스키마 검증
   ↓
evidence 검증
   ↓
ID 정규화
   ↓
불완전 사용례 검사
   ↓
DB 적재
```

과정을 거친다.

**LLM 추출과 검증은 별개의 단계가 아니라 하나의 파이프라인으로 봐야 한다.**

---

# **12. 왜 전체 1,562개를 바로 추출하지 않았나**

이번에는 전체 데이터 대신 20개만 먼저 처리했다.

처음부터 전체 데이터를 돌리는 편이 더 빨라 보일 수도 있다.

하지만 20개만 처리했는데도 이미 다음 문제가 발견됐다.

```
TechnologyUse 과잉 생성
ID 불일치
purpose/status 결측
replaces 0건
JSON 응답 절단
```

이 상태로 전체 1,562개를 추출하면 작은 설계 문제가 그대로 확대된다.

```
잘못된 추출 규칙
      ×
1,562개 청크
      ↓
훨씬 큰 정리 비용
```

따라서 현재는 전체 추출을 하지 않고 먼저 `TechnologyUse`의 병합 기준과 추출 규칙을 수정하기로 했다.

**20개 표본은 최종 결과가 아니라 전체 파이프라인을 검증하기 위한 PoC였다.**

---

# **13. 이번 실습에서 확인한 것**

W5를 시작할 때 확인하고 싶었던 것은 단순했다.

**그래프를 만들면 W4에서 RAG가 답하지 못했던 질문을 실제로 풀 수 있을까?**

결과적으로 X01과 X03에서는 가능했다.

```
W4

Hybrid RAG
    ↓
질문에 없는 Redis 브릿지를 찾지 못함
    ↓
X01 / X03 실패

W5

문서
 ↓
LLM Triple Extraction
 ↓
Knowledge Graph
 ↓
Redis 브릿지 탐색
 ↓
X01 / X03 해결
```

특히 W4에서 화이트보드에 그렸던

```
SeCause ──> Redis <── TEAMFICIAL
               ↑
              직행
```

구조가 실제 추출 결과에서도 그대로 나타났다.

하지만 동시에 새로운 문제도 확인했다.

```
RAG의 문제
"관계를 못 찾는다"
        ↓
그래프로 해결
        ↓
새로운 문제
"그 관계가 정말 같은 사실인가?"
```

그래서 이번 실습의 결론은 다음 한 문장으로 정리할 수 있다.

**그래프는 RAG가 못 풀던 질문을 풀어줬지만, 그래프 자체의 품질 문제를 새로 만들었다.**

---

## **14. 다음 단계**

현재 바로 전체 1,562개 청크를 추출하지 않는다.

먼저 해야 할 일은 **같은 `TechnologyUse`를 어떻게 식별하고 병합할 것인지 결정하는 것**이다.

기본 방향은 다음과 같다.

```
Project + Technology
        ↓
1차 후보 그룹

Status가 다르다
        ↓
병합하지 않음

Purpose가 비슷하다
        ↓
동일 사용례인지 판단

Purpose가 NULL이다
        ↓
자동 병합하지 않음
"모름" ≠ "같음"
```

그 뒤에야 전체 파이프라인을 실행한다.

```
TechnologyUse 병합 기준 확정
        ↓
전체 1,562개 추출
        ↓
PostgreSQL 재적재
        ↓
Neo4j 재적재
        ↓
X01 / X03 재평가
        ↓
최종 그래프 시각화
```

즉 다음 단계의 질문은 더 이상

**“그래프를 만들 수 있는가?”**

가 아니다.

이제는

**“자동으로 만든 그래프를 어떻게 믿을 수 있는 그래프로 만들 것인가?”**

가 된다.

## **기억할 세 가지**

**1. Redis가 실제 브릿지가 됐다.**

W4에서 RAG가 놓쳤던 연결을 실제 그래프에서는 관계 탐색으로 찾을 수 있었다.

**2. `TechnologyUse` 중간 노드는 실제로 필요했다.**
같은 Redis라도 `proposed`와 `implemented`, 그리고 서로 다른 목적을 구분할 수 있었다.

**3. 자동 구축은 새로운 품질 문제를 만들었다.**

같은 사실이 여러 `TechnologyUse`로 분리되면서 중복·정규화·신원해소 문제가 등장했다.

따라서 이번 W5의 가장 중요한 발견은 **“그래프를 만들었다”가 아니라 “그래프를 만들어보니 다음 문제가 무엇인지 보였다”**는 것이다.
